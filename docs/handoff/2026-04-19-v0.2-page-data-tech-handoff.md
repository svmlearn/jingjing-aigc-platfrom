## 2. 当前最关键的收敛结论

### 2.1 页面结构已收敛

`V0.1` 先按 6 个一级页面收：

1. `导入页`
2. `内容中心`
3. `商家画像`
4. `改写工作台`
5. `账号管理`
6. `发布任务`

其中一个关键决定是：

- `草稿中心` 先并入 `内容中心` 的标签页

另一个关键决定是：

- `审核与发布准备` 先用详情面板 / 抽屉承载，不单独做一级页面

### 2.2 数据主链路已收敛

当前最重要的数据主链路已经明确为：

`SourceItem -> ContentDraft -> ContentVariant -> PublishJob`

而“商家画像”输入层由下面 3 个对象支撑：

- `MerchantProfile`
- `AudienceProfile`

最新收敛补充：

- `V0.1-A` 先不引入 `StoreProfile`
- 当前先按“一个商户工作区 = 一个商户主体”建模
- 商户资料先收口到：名称、地址、联系人、联系电话、服务项目
- `V0.1-A` 先按“一个商户 = 一个 owner 账号”实现
- 后续若要扩成员，只追加成员关系与角色层，不改业务主链路

### 2.3 技术方案已经不是单纯 `Supabase + Vercel`

当前更准确的结论是：

- **`V0.1` 推荐方案 = `Vercel + Supabase + 独立 Worker`**

也就是说：

- `Vercel` 承接管理后台和轻 API
- `Supabase` 承接 Postgres 与 Storage
- `Worker` 第一阶段至少承接导入任务
- 发布任务可以放到后一阶段再接

补充边界：

- 这里的“内部登录”指这个管理后台自己的内部登录
- 不是面向第三方用户的正式 SaaS 用户系统

新确认的方向：

- 长期用户体系明确按**多租户 SaaS** 设计
- `V0.1` 注册先采用**邀请码机制**
- 这样既能控流，也能避免过早开放注册带来的噪音和风险
- 当前不做多成员协作界面
- 当前不做复杂角色权限体系

部署层补充共识：

- `V0.1-A` 首选先试**托管式抓取 API**，不默认先租 VPS
- 如果托管 API 覆盖或稳定性不够，再补 **1 台 VPS** 跑 `Worker`
- VPS 首月起步配置可按 `2 vCPU / 4 GB RAM / 50 GB SSD / Ubuntu 22.04`
- 如果很快要接浏览器自动化抓取或后续发布自动化，再升到 `4 vCPU / 8 GB RAM`

### 2.4 `Supabase Postgres` 已经可以开始设计 migration

本轮已经补了一版 SQL 级别的 schema 草案，意味着接下来如果要进入实现，不需要再停留在“表怎么拆”的讨论层。

## 5. 当前不需要重新争论的点

下面这些本轮已经足够收敛，下一窗口不需要再来回打转：

- 当前版本是内部自用版
- `MediaCrawler` 只保留内部导入参考能力，不当正式商用底座
- `AIWriteX` 只借工作流思路，不直接当产品壳
- `social-auto-upload` 是后续发布阶段最值得接入的执行层
- `草稿中心` 当前先并入 `内容中心`
- `Supabase + Vercel` 本身不够，必须加 `Worker`
- 长期用户体系按多租户 SaaS 设计
- `V0.1` 注册先用邀请码机制
- `V0.1-A` 先按“一个商户一个 owner”实现
- 后续多成员扩展通过新增 membership / role 层解决
- `V0.1-A` 若做真实抓取，优先尝试托管 Scraper API，VPS 作为第二方案
