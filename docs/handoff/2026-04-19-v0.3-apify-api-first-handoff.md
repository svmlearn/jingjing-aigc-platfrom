## 4. 实测里最重要的变化

### 4.1 小红书 detail 不是不能用

首轮用裸链接时字段很空。

第二轮改用小红书页面自然生成的完整链接后，成功拿到：

- 标题
- 正文
- 作者
- 点赞/评论/收藏/分享
- 标签
- 图片/视频
- 发布时间

所以现在判断改为：

- 小红书 `detail` 可用
- 但输入链接质量非常关键

### 4.2 小红书 comments 也不是不能用

首轮有 actor 返回空 dataset。

第二轮改用：

- `easyapi/all-in-one-rednote-xiaohongshu-scraper`
- `mode = comment`
- 完整自然链接

后，成功拿到：

- 主评论
- 用户信息
- 点赞数
- IP 属地
- 创建时间
- 子评论

所以现在判断改为：

- 小红书 `comments` 可用
- 但要选对 actor，并继续压测

### 4.3 成本有波动

第二轮里，小红书评论成本差异明显：

- 有的样本约 `0.0169 USD`
- 有的样本约 `0.1074 USD`

说明评论任务必须做：

- 条数限制
- 并发限制
- 成本监控

## 7. 当前还没有完全拍死的风险

### 7.1 Apify 不是官方数据接口

这些 actor 多数仍然是社区或第三方维护。

所以：

- 能跑通
- 能作为 PoC 主线
- 但还不能叫“长期稳定官方接口”

### 7.2 小红书完整链接问题

如果用户直接粘贴裸链接，可能会影响抓取质量。

产品上要考虑：

- 接受完整链接为最佳实践
- 裸链接允许尝试
- 如果字段为空，提示用户重新复制完整链接

### 7.3 评论成本问题

评论比详情更贵，也更不稳定。

第一版建议：

- 默认最多 `30` 条评论
- 评论失败不阻断正文导入
- 评论导入状态可以单独标为 `partial`

## 9. 当前是否需要用户拍板

暂时不需要。

我建议默认继续按：

> `V0.1-A = Vercel + Supabase + Apify API-first`

往下推。

真正需要后续拍板的是：

1. 是否接受 `Apify` 作为第一版付费 API 服务商
2. 小红书评论默认抓多少条
3. 如果 Apify 成本超过预期，要不要切 Bright Data 对照
4. 真实代码工程放在当前目录，还是新建 `app` 子目录
5. 前端是否默认采用 `Next.js + Tailwind + shadcn/ui`

当前可以先按默认值：

- `Apify` 先做 PoC 主服务商
- 小红书评论默认 `30` 条
- 结果质量不足时不阻断主流程
