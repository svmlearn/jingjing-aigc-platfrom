# 2026-04-20 V0.4 架构与 A/B 分支交接

## 1. 当前一句话结论

`V0.1-A` 的主线方案已经收敛为：

```text
Next.js / Vercel
-> Supabase Auth + Postgres + Storage
-> Apify 托管抓取 API
-> OpenAI 改写
```

当前目标不是先做完整 SaaS，也不是先做发布矩阵，而是先跑通：

```text
邀请码注册
-> 商户资料
-> 小红书/抖音内容导入
-> 内容中心查看
-> AI 改写
-> 保存草稿
```

---

## 2. 为什么现在要 Git 初始化

建议现在就在当前项目目录初始化 Git。

原因：

1. 接下来要拆 `A/B` 两条并行分支
2. 没有 Git 基线，分支无法可靠隔离
3. 后续合并需要一个干净的共同起点
4. 现在目录仍然干净，主要是文档和 references，适合建立初始基线

建议流程：

```text
main
  -> commit: planning baseline
  -> commit: app scaffold baseline
  -> branch: feature/a-core-import
  -> branch: feature/b-admin-ui-rewrite
```

注意：

- 不要把 `.env`、`.env.local`、`node_modules`、`.next`、`.DS_Store` 提交
- `Apify token`、`Supabase service role`、`OpenAI key` 只能放本地环境变量

## 3. 当前架构原则

## 3.1 Vercel 不是纯前端

这次必须把 `Vercel / Next.js` 当成服务端来写。

浏览器可以看到我们自己的接口地址，例如：

```text
POST /api/import-jobs
POST /api/source-items/:id/rewrite
```

但浏览器不能看到：

- `APIFY_TOKEN`
- `OPENAI_API_KEY`
- `SUPABASE_SERVICE_ROLE_KEY`
- Apify actor 真实调用细节
- 数据库高权限写入逻辑

正确链路：

```text
浏览器
-> Next.js server route
-> 服务端校验用户和 merchant 权限
-> 服务端调用 Apify / OpenAI / Supabase
-> 返回业务结果
```

错误链路：

```text
浏览器
-> 直接调用 Apify / OpenAI / Supabase service role
```

---

## 3.2 后续迁移服务器要靠 adapter 隔离

为了后续从 `Vercel + Supabase` 迁移到自有服务器，当前实现必须遵守：

1. 数据访问走 repository，不让 Supabase 调用散落在页面里
2. 抓取走 `ImportProviderAdapter`，不让 Apify 调用散落在页面里
3. AI 改写走服务端 adapter，不让前端直连 OpenAI
4. migration 尽量保持标准 Postgres SQL
5. 不依赖 Supabase Edge Functions
6. 不优先依赖 Vercel Cron / Vercel KV

这样未来迁移路径是：

```text
现在：浏览器 -> Vercel Next.js server -> Supabase / Apify
以后：浏览器 -> 自有服务器 Node/Next.js server -> Postgres / Apify 或 Worker
```

## 6. A/B 分支拆法

## 6.1 分支前置条件

在拆 A/B 之前，需要先在 `main` 做一个共同脚手架基线：

```text
app/
  package.json
  next.config.ts
  tsconfig.json
  src/
  supabase/
```

这个脚手架基线只做：

- Next.js 初始化
- Tailwind / shadcn/ui 基础配置
- Supabase client/server 基础封装
- 基础目录结构
- `.env.example`

不要在脚手架基线里塞复杂业务。

---

## 6.2 A 分支：Core Import / Backend

建议分支名：

```text
feature/a-core-import
```

目标：

> 把注册、商户、数据库、Apify 导入和服务端 API 做通。

主要负责：

- Supabase migration
- 邀请码注册 API
- 商户资料 API
- `ApifyProviderAdapter`
- `ImportJob` 状态机
- 小红书/抖音导入 API
- `source_items` / `imported_comments` 落库
- 导入限流和错误处理
- 结果质量校验

A 分支建议拥有的文件范围：

```text
app/supabase/**
app/src/server/**
app/src/lib/db/**
app/src/lib/auth/**
app/src/app/api/**
app/.env.example
```

A 分支验收标准：

- 能创建邀请码
- 能用邀请码创建商户 owner
- 能创建/更新商户资料
- 能调用 Apify 导入小红书 detail
- 能调用 Apify 导入小红书 comments
- 能把结果写入 `source_items`
- 能把评论写入 `imported_comments`
- 不暴露任何服务端密钥到前端

---

## 6.3 B 分支：Admin UI / Rewrite UX

建议分支名：

```text
feature/b-admin-ui-rewrite
```

目标：

> 把用户能操作的后台界面、内容中心、改写工作台和草稿体验做出来。

主要负责：

- 后台全局壳
- 注册页
- 商户资料页
- 导入页 UI
- 内容中心 UI
- 内容详情抽屉
- 评论列表 UI
- 改写工作台 UI
- 草稿列表和草稿详情
- AI 改写交互体验

B 分支建议拥有的文件范围：

```text
app/src/app/(auth)/**
app/src/app/dashboard/**
app/src/components/**
app/src/styles/**
app/src/lib/ui/**
```

B 分支可以先使用：

- mock API
- mock data
- A 分支约定的 API contract

B 分支验收标准：

- 用户能看到完整后台壳
- 能走注册/商户资料页面流程
- 能粘贴链接发起导入请求
- 能查看内容列表和详情
- 能查看评论列表
- 能进入改写工作台
- 能生成/保存草稿的前端流程跑通

## 7. A/B 对齐契约

为了减少冲突，A/B 必须共享这些 contract。

建议放在共同基线或 A 分支先产出，B 分支按它对接：

```text
app/src/contracts/import.ts
app/src/contracts/content.ts
app/src/contracts/draft.ts
```

最小 API contract：

```text
POST /api/import-jobs
GET  /api/import-jobs/:id
GET  /api/source-items
GET  /api/source-items/:id
GET  /api/source-items/:id/comments
POST /api/source-items/:id/rewrite
GET  /api/content-drafts
PATCH /api/content-drafts/:id
```

如果 A/B 并行时接口没准备好：

- B 分支用 mock adapter
- 不直接绕过 contract
- 不在 UI 里写 Apify/OpenAI/Supabase service role 调用

---

## 8. 合并策略

推荐顺序：

1. `main` 完成脚手架基线 commit
2. 从 `main` 同时开：
   - `feature/a-core-import`
   - `feature/b-admin-ui-rewrite`
3. A 分支先合入 `main`
4. B 分支 rebase/merge 最新 `main`
5. B 分支接真实 API
6. 合并 B 分支
7. 做一次端到端验收

原因：

- A 分支产出真实 API 和数据结构
- B 分支接入时冲突更少
- 最终闭环以真实 API 为准
