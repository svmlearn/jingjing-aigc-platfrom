## 2. 已确认共识

1. 后台目标是完整还原 `docs/designs/AIGC平台后台` 这套暗色 AIGC 控制台原型，不只是补几个页面。

8. `draft / enabled / disabled` 是 Agent 生命周期，是否线上由 `agent_route_bindings.consultation_default` 决定。

## 5. 管理员账号体系计划

### 5.1 账号模型

推荐采用 Supabase Auth 管理邮箱和密码，不自建明文或自定义密码哈希表。

新增业务表：

```text
platform_admin_users
- id
- auth_user_id
- email
- display_name
- role: super_admin | admin
- status: active | disabled
- created_by_admin_id
- last_login_at
- created_at
- updated_at
```

说明：

1. 密码由 Supabase Auth 负责。
2. `platform_admin_users` 只负责后台权限身份。
3. 商家用户和后台管理员可以同属 `auth.users`，但后台进入必须存在 active 的 `platform_admin_users` 记录。
4. 当前 `ADMIN_SETUP_SECRET` 不再作为日常登录方式，只建议保留为首次初始化 super_admin 的 bootstrap 保护。

### 5.2 首个超级管理员初始化

待实现时建议采用其中一种路径：

1. 推荐路径：当系统没有任何 `platform_admin_users` 时，允许通过 `ADMIN_SETUP_SECRET` 进入一次性初始化页，创建首个 `super_admin`。
2. 备选路径：通过 Supabase SQL / 管理脚本预置首个 auth user 和 `platform_admin_users` 记录。

日常登录流程：

```text
输入邮箱和密码
  -> Supabase Auth signInWithPassword
  -> 查询 platform_admin_users
  -> status 必须为 active
  -> 建立后台 session
  -> 按 role 控制页面和操作权限
```

### 5.3 角色权限初稿

| 能力 | super_admin | admin |
| --- | --- | --- |
| 登录后台 | 是 | 是 |
| 查看总览 | 是 | 是 |
| 邀请码创建 / 停用 | 是 | 是 |
| 查看商户 | 是 | 是 |
| 修改商户状态 / 会员档位 | 是 | 否，默认只读 |
| 上传知识 / 重试索引 | 是 | 是 |
| 创建 / 编辑 Skill 草稿 | 是 | 是 |
| 启用 / 禁用 Skill | 是 | 待确认，建议初期仅 super_admin |
| 编辑 Agent 草稿 | 是 | 是 |
| 发布 Prompt / 回滚 Prompt | 是 | 待确认，建议初期仅 super_admin |
| 复制 Agent | 是 | 是 |
| 设为线上 Agent | 是 | 否 |
| 运行 Agent 调试 | 是 | 是 |
| 修改 LLM Runtime / 全局开关 | 是 | 否 |
| 管理后台管理员账号 | 是 | 否 |

需要用户最终确认的权限点：

1. 普通 `admin` 是否可以发布 Prompt。
2. 普通 `admin` 是否可以启用 / 禁用 Skill。
3. 普通 `admin` 是否可以创建邀请码。


第一版不做：

### 7.4 Knowledge Set API

现有 `knowledge_documents` 和上传能力要保留，但需要补知识集层。

```text
GET    /api/platform-admin/knowledge/sets
POST   /api/platform-admin/knowledge/sets
PATCH  /api/platform-admin/knowledge/sets/:setId
POST   /api/platform-admin/knowledge/documents

```

规则：

1. 上传知识必须选择至少一个知识集。
2. indexed 文档才参与检索。
3. disabled 知识集即使被 Agent 挂载，也不参与检索并给出风险提示。

### 7.5 Agent 调试 API

```text
POST /api/platform-admin/agent-test-runs
GET  /api/platform-admin/agent-test-runs?agentId=...
```

规则：

1. 不写入 `consultation_sessions`。
2. 不扣商家积分。
3. 保存 `agent_test_runs`。
4. 展示 prompt version、候选 skills、实际加载 skills、knowledge hits、tool summary、最终回复或失败原因。

### 7.6 商家端 runtime 接入

现有商家端咨询要从旧配置迁到新绑定：

1. 读取 `agent_route_bindings.consultation_default`。
2. 校验 Agent 存在且 enabled。
3. 读取 active prompt。
4. 读取 enabled 且已绑定的 Skills 作为候选 Skill。
5. 读取 enabled 且已绑定的 Knowledge Sets。
6. Knowledge 检索只查已挂载知识集内 indexed 文档。
7. 记录 `agent_runtime_snapshots`。
8. 预留 `check_entitlement / record_usage_event / credit ledger` 调用点。

## 10. 并行分支与分工策略

结论：本轮按 5 个开发分支推进，`main` 可以承担最终验收 / 集成分支的角色。

不建议只拆成两个大分支作为默认方案。两个分支虽然合并简单，但会让“后台 API / runtime / auth”全部挤在一个后端分支里，开发和验收都会变重。

更推荐：

```text
1 个基础分支
+ 4 个功能分支并行
最终按顺序合入 main 做验收
```

### 10.1 推荐分支总览

| 分支 | 定位 | 是否阻塞其他分支 | 建议 owner |
| --- | --- | --- | --- |
| `codex/v2.2-admin-foundation` | 数据模型、contract、初始化 seed 基础 | 是，先做短平快 | Schema / backend |
| `codex/v2.2-admin-auth-rbac` | 管理员账号密码登录、角色、权限守卫 | 依赖 foundation | Auth / backend |
| `codex/v2.2-agent-assets-api` | Agent、Prompt、Skill、Knowledge Set 的后台 API | 依赖 foundation | Backend |
| `codex/v2.2-admin-console-ui` | 暗色后台壳子和页面还原 | 依赖 foundation 的 contract，可先接 mock adapter | Frontend |
| `codex/v2.2-agent-runtime-debug` | 商家端 runtime 接入、测试台运行、快照 | 依赖 agent API | Runtime / backend |

原则：

1. `foundation` 分支先做、先验收、先冻结；它不是和后面四个功能分支完全同时起跑。
2. `foundation` 冻结后，`auth-rbac`、`agent-assets-api`、`admin-console-ui` 可以并行。
3. `runtime-debug` 可以提前读代码和做局部准备，但真实接入最好等 `agent-assets-api` 稳定后再合。
4. 每个功能分支结束时必须写 handoff，说明 commit、验证、未完成项、是否需要补 migration。
5. 合入 `main` 前，每个分支要先完成本分支最小验证；`main` 只接收“可验收”的分支结果，不接半成品。

### 10.7 main 作为验收 / 集成分支

本轮可以不额外创建 `codex/v2.2-admin-console-integration`，直接把 `main` 作为最终验收 / 集成分支。

前提：

1. 每个开发分支必须先在自己的 worktree 里完成最小验证。
2. 每个开发分支必须有 handoff 和 commit。
3. 合入 `main` 只能按顺序进行，不要多个分支同时往 `main` 合。
4. `main` 在验收期可以短暂承担集成环境角色；如果用户希望 `main` 始终保持绝对稳定，则仍应改用独立 integration 分支。

推荐合并顺序：

```text
1. codex/v2.2-admin-foundation
2. codex/v2.2-admin-auth-rbac
3. codex/v2.2-agent-assets-api
4. codex/v2.2-admin-console-ui
5. codex/v2.2-agent-runtime-debug
```

`main` 验收清单：

1. `pnpm lint`
2. `pnpm build`
3. 后台登录：
   - super_admin
   - admin
   - disabled admin
4. 后台页面逐页打开。
5. Agent 创建、复制、发布 Prompt、设线上。
6. Skill 创建、启用、挂载。
7. Knowledge 上传、加入知识集、失败重试。
8. Agent 调试运行并保存记录。
9. 商家端咨询使用当前线上 Agent。
10. Supabase migration 状态写入 progress。

`main` 验收交付：

1. 最终 commit。
2. `docs/progress/YYYY-MM-DD-v2.2-admin-console-main-acceptance.md`
3. `docs/handoff/YYYY-MM-DD-v2.2-admin-console-main-acceptance-handoff.md`
4. 明确是否 push；默认待用户验收后再 push。

### 10.8 如果只拆两个分支

如果人手少或想降低管理成本，也可以拆成两个分支：

```text
codex/v2.2-admin-backend-foundation
codex/v2.2-admin-console-ui
```

后端分支负责：

1. Auth / RBAC。
2. Supabase migration。
3. Agent / Skill / Knowledge Set API。
4. 商家端 runtime。
5. Agent 调试 API。

UI 分支负责：

1. 暗色 Shell。
2. 后台所有页面还原。
3. 接后端 API。

两分支方案的风险：

1. 后端分支过大，验收周期长。
2. Runtime 和后台 API 容易互相阻塞。
3. UI 分支等待 API 时可能需要临时 mock adapter。

适用场景：

1. 只有 1-2 位开发者。
2. 用户希望降低并行复杂度。
3. 当前目标是先做一版能跑的整体闭环，而不是多人极速并行。

### 10.9 最推荐执行方式

本项目当前推荐：

```text
先做 foundation 分支，尽快验收并冻结。
随后并行 auth-rbac / agent-assets-api / admin-console-ui。
最后 runtime-debug 接入真实咨询链路。
五个开发分支按顺序合入 main，在 main 上做最终验收。
```

这样拆的原因：

1. migration 和 contract 先定住，后续分支不会互相猜字段。
2. UI 可以先基于 contract 做，不必等待 runtime 完全完成。
3. Runtime 最危险，放在后面接入，避免一开始影响商家端现有咨询。
4. `main` 可以直接成为验收环境，减少一个长期集成分支的管理成本。
5. 但每个分支必须先自验，避免把半成品合入 `main` 后让主线变成排错现场。

## 12. 权限默认值与仍需拍板事项

### 12.1 当前默认权限

本轮已按“超管做高风险动作，管理员做日常配置与测试”的原则收敛。

默认规则：

1. `admin` 可以登录后台、查看总览、查看商户、维护知识、编辑 Agent 草稿、创建 / 编辑 Skill 草稿、复制 Agent、运行 Agent 调试。
2. `admin` 不可以发布 / 回滚 Prompt。
3. `admin` 不可以设为线上 Agent。
4. `admin` 不可以修改系统配置。
5. `admin` 不可以管理后台管理员账号。
6. `admin` 不可以禁用商户或修改商户会员档位。
7. `super_admin` 拥有所有后台能力，并负责线上绑定、Prompt 发布、系统配置、管理员账号管理等高风险动作。

### 12.2 仍可在开工前拍板的细节

这些不是方向性阻塞，但实现前最好有默认值：

1. 普通 `admin` 是否可以创建和停用邀请码；当前建议允许创建，停用由 `super_admin` 负责。
2. 首个 `super_admin` 初始化采用“一次性初始化页”还是“手工 SQL / 脚本预置”；当前建议一次性初始化页。
3. 管理员账号管理是否放在系统配置页里，而不是新增一级导航；当前建议放在系统配置页，仅 `super_admin` 可见。
4. V2.2 是否只预留积分 gate，还是本阶段就强制扣真实积分；当前建议本阶段只预留 gate 和 usage event，不先强制真实扣费。
