# V2.1 商家知识库与咨询上下文补强实现计划

日期：2026-04-29
状态：开工前计划，不包含代码实现
对应 PRD：`docs/产品文档/V2.1-商家知识库与咨询上下文补强-PRD.md`

## 1. 文档定位

本文件用于把 `V2.1-商家知识库与咨询上下文补强-PRD.md` 收敛成可执行实现任务书。

本轮目标不是建设完整的自动长期记忆系统，而是：

1. 明确区分三层上下文：
   - 基础信息
   - 平台方法论知识库
   - 商家知识库（商家私有资料 + 手动录入的商家记忆）
2. 让商家可以上传和维护自己的私有资料，也可以手动录入可编辑的商家记忆。
3. 让咨询链路继续复用现有知识检索底座，把商家知识库作为补充上下文接进来。

本轮默认遵循项目 `AGENTS.md`：

1. 正式实现时优先独立 worktree。
2. 代码 + 最小验证 + handoff。
3. 默认不直接 merge / push。

## 2. 已确认共识

1. `平台方法论知识库` 与 `商家知识库` 必须是两个清晰分层的产品概念。
2. `平台方法论知识库` 是平台级方法论库，不属于某个商家。
3. `商家知识库` 是商家私有长期上下文入口，只能被当前商家看到和使用。
4. 本轮不做自动提炼 `memory`，也不做对话结束后的自动写回。
5. 商家基础信息继续作为咨询初始上下文。
6. 商家知识库先承担“补充长期上下文”的作用。
7. 如果信息不足，由咨询 Agent 在对话中继续追问，商家在对话中补充。
8. 商家知识库在 V1 分成两个产品动作：
   - `知识库上传`：上传 `txt / md` 商家资料。
   - `记忆录入`：手动新建可编辑的短文本商家记忆。
9. 每份商家资料和每条商家记忆都必须命名。
10. 商家一次只上传一份资料，不做批量上传。
11. 状态按代码状态完整展示：
   - `uploaded`：已上传，待处理
   - `queued`：队列中
   - `processing`：处理中
   - `indexed`：可用于咨询
   - `failed`：处理失败
12. 编辑规则：
   - `txt / md` 文件型资料：只能编辑资料名称，不能在线替换文件正文。
   - 商家记忆：可以编辑记忆名称，也可以编辑正文内容。
13. 商家记忆限制 `1000` 个可见字符以内，且按单 `chunk` 处理。
14. `txt / md` 不加额外字数限制，沿用现有文档切分逻辑，但 UI 需要提示单文件最大 `10MB`。
15. 商家侧暂时不需要 `knowledge_sets`，本轮不做商家知识集分组或 Agent 绑定管理。

## 4. V1 实现策略

### 4.1 总体策略

本轮优先复用现有 `knowledge_documents / knowledge_chunks / knowledge_ingestion_jobs` 体系，不新增 `merchant_memories` 表，不做新的 memory runtime。手动录入的商家记忆先作为 `merchant-scoped document + single chunk` 承接。

V1 采用：

```text
商家基础信息
  + 商家知识库（merchant-scoped documents，包括商家资料和商家记忆）
  + 平台方法论知识库（platform-scoped documents）
  -> 共同构成咨询上下文
```

### 4.2 为什么本轮不新建 memory 表

原因：

1. 当前 schema 已能承接商家私有资料。
2. 当前检索层已天然支持 `merchantId` 过滤。
3. 本轮核心需求是“商家能上传和维护自己的资料，并手动录入可编辑记忆”，不是“系统自动提炼稳定事实”。
4. 如果现在同时做 `商家知识库 + 自动 memory 提炼`，实现范围会明显膨胀，且会把产品概念再次混掉。

## 5. 术语与产品边界

### 5.1 平台方法论知识库

定义：

- 平台级方法论库
- 服务于咨询 Agent 的方法论检索
- 内容包括：SOP、平台规则、方法论、案例拆解、通用策略

本轮不改它的底层存储能力，但要在产品文案和页面命名上明确它是“平台方法论知识库”。

### 5.2 商家知识库

定义：

- 当前商家私有的长期上下文入口
- 内部分成 `知识库上传` 和 `记忆录入`
- `知识库上传` 内容包括：项目介绍、FAQ、案例、活动说明、会议纪要、渠道资料等 `txt / md` 文件资料
- `记忆录入` 内容包括：商家主动补充的短文本事实、偏好、经验判断、经营注意事项等
- 当前商家可上传多份资料，也可录入多条商家记忆
- 只对当前商家自己可见和可用

### 5.3 基础信息

定义：

- 商家在注册登录后填写的基础资料
- 继续作为咨询台的初始上下文
- 不并入商家知识库

## 6. 任务拆解

### 6.1 任务 A：商家侧知识库 API

建议新增 API：

```text
GET    /api/merchant-knowledge/documents
POST   /api/merchant-knowledge/documents
PATCH  /api/merchant-knowledge/documents/:documentId
DELETE /api/merchant-knowledge/documents/:documentId
```

原则：

1. 不允许客户端传入任意 `merchantId` 作为目标商家。
2. 所有商家侧操作都必须：
   - 先获取当前登录用户
   - 再反查当前 `merchantId`
   - 再只操作该 `merchantId` 下的数据
3. API 对外只暴露商家自己的文档，不提供跨商家查询入口。

#### GET

返回：

- 当前商家的商家资料和商家记忆列表
- 每条内容至少包含：
  - 名称
  - 类型
  - 状态
  - 更新时间
  - 是否允许编辑正文

#### POST

支持两种模式，对应两个产品动作：

1. `知识库上传`：
   - `txt`
   - `md`
2. `记忆录入`：
   - `title`
   - `textContent`

校验规则：

1. `title` 必填。
2. 文件模式只允许 `txt / md`，单文件最大 `10MB`。
3. 记忆正文不能为空。
4. 记忆正文按 trim 后可见字符计数，`<= 1000`。

#### PATCH

按文档类型分支：

1. 文件型资料：
   - 只允许修改 `title`
   - 不允许替换文件正文
2. 商家记忆：
   - 允许修改 `title`
   - 允许修改 `textContent`
   - 修改正文后需要重新进入处理流程

#### DELETE

删除当前商家自己的商家资料或商家记忆。

### 6.2 任务 B：商家侧 service / repository 复用层

当前 `knowledge-service.ts` 是平台端命名，建议本轮不要复制一整套重复实现，而是抽一层通用逻辑，然后分别暴露：

- `uploadKnowledgeDocumentForPlatformAdmin()`
- `uploadKnowledgeDocumentForMerchant()`
- `createMerchantMemoryForMerchant()`
- `updateKnowledgeDocumentForMerchant()`
- `listKnowledgeDocumentsForMerchant()`
- `deleteKnowledgeDocumentForMerchant()`

需要补的关键点：

1. 校验当前文档是否属于当前商家。
2. 商家记忆编辑后，需要支持正文重新入库。
3. 商家记忆原文和单个 chunk 都建议保存在 Supabase；`txt / md` 文件原始内容可继续放 COS，切片后的 chunks 进入 Supabase。

### 6.3 任务 C：chunk 策略分流

这是本轮最容易被忽略、但必须写死的规则。

#### 文件型资料

对于 `txt / md`：

- 继续沿用当前 `chunkKnowledgeText()` 逻辑
- 不额外加字数限制
- 系统按长度自动切分多个 chunk

#### 商家记忆

对于 `记忆录入`：

- 限制 `1000` 个可见字符以内
- 产品语义上视为一条“商家记忆”
- 技术实现上建议写入：
  - `1 document`
  - `1 chunk`

注意：

- 不要让商家记忆继续走通用长文切分逻辑，否则 `1000` 个可见字符以内的记忆仍可能按 `chunkSize` 被切成多个 chunk，与本轮规则冲突。

建议做法：

1. 在文档 `metadata` 写入：
   - `sourceType = "memory" | "file"`
   - `contentKind = "merchant_memory" | "merchant_document"`
   - `chunkPolicy = "single" | "auto"`
2. 入库时按 `chunkPolicy` 分流：
   - `single`：整段正文生成一个 chunk
   - `auto`：走现有自动切块逻辑

### 6.4 任务 D：商家端页面入口

建议优先放在：

- `app/src/components/merchant/settings-workspace.tsx`

V1 固定实现方式：

- 放在 `商家设置` 下的一个新 Tab，Tab 名为 `商家知识库`

原因：

1. 改动面小
2. 与“基础信息”和“商家自己的长期资料”关系更近
3. 不需要额外扩展商家端主导航

页面最小能力：

1. 列表查看
2. 知识库上传
3. 记忆录入
4. 编辑内容
5. 删除内容
6. 展示状态

### 6.5 任务 E：商家知识库页面规则

#### 列表展示字段

最小列表字段建议：

- 名称
- 内容类型
  - `txt 文件`
  - `md 文件`
  - `商家记忆`
- 处理状态
  - `已上传，待处理`
  - `队列中`
  - `处理中`
  - `可用于咨询`
  - `处理失败`
- 更新时间
- 操作
  - 编辑 / 改名
  - 删除

#### 编辑能力

文件型资料：

- 仅允许改名
- 页面上明确提示：
  - “该类型资料不支持在线修改正文，如需修改内容，请删除后重新上传”

商家记忆：

- 允许改名
- 允许编辑正文
- 保存时继续执行 `1000` 个可见字符限制

#### 失败恢复

商家记忆：

- 允许修改正文后再次保存
- 重新进入处理流程

文件型资料：

- 允许改名
- 允许重新处理
- 不能直接修正文
- 只能删除后重新上传

### 6.6 任务 F：商家隔离与权限防串库

本轮必须硬性保证：

1. 商家列表只返回当前商家自己的数据。
2. 商家编辑/删除时，目标文档必须属于当前商家。
3. 咨询检索时，只能命中：
   - `scope = platform`
   - `scope = merchant && merchant_id = 当前商家`

4. 任意跨商家访问都必须阻断。

建议验证场景：

1. 商家 A、商家 B 分别上传资料。
2. 商家 A 打开商家知识库，只能看到 A 的资料。
3. 商家 A 发起咨询，不能命中 B 的资料或记忆。
4. 用 B 的文档 ID 访问 A 的编辑/删除接口，应返回无权限或不可见。

### 6.7 任务 G：咨询侧轻量文案修正

本轮原则上不改咨询 agent 主逻辑，但建议做一处轻量修正：

- 把当前咨询侧过于单一的“检索平台方法论知识库”文案，调整成更准确的表述

可选方向：

- `检索知识上下文`
- `检索知识库`
- `检索平台方法论与商家上下文`

原因：

1. 商家知识库接入后，咨询侧实际读取的不再只是平台方法论库。
2. 如果仍只叫“平台方法论知识库”，用户会误解自己的商家资料和商家记忆没有被使用。

## 8. 验证清单

### 8.1 功能验证

1. 商家可新增 `txt` 文件资料。
2. 商家可新增 `md` 文件资料。
3. 商家可通过 `记忆录入` 新建商家记忆。
4. 商家记忆超过 `1000` 个可见字符时被阻断。
5. 文件型资料可改名但不可编辑正文。
6. 商家记忆可改名且可编辑正文。
7. 商家记忆编辑正文后会重新进入处理流程。
8. 商家可删除资料或记忆。
9. 列表可正确显示五种处理状态。
10. 商家之间列表和咨询检索严格隔离。
11. 商家侧不出现 `knowledge_sets` 分组或绑定管理。

### 8.2 咨询链路验证

1. 没有商家知识库内容时，咨询仍可继续。
2. 有“可用于咨询”的商家资料或商家记忆时，咨询可命中这些内容。
3. `已上传，待处理`、`队列中`、`处理中` 和 `处理失败` 的内容不应被当作已可用上下文。
4. 信息不足时，Agent 继续在对话中追问，而不是跳出当前流程。

### 8.3 回归验证

1. 平台端知识库上传、入库、删除能力不应被改坏。
2. 现有商家设置基础信息保存能力不应被改坏。
3. 现有咨询会话创建、发送消息和回复能力不应被改坏。

## 9. 风险与注意事项

### 9.1 产品风险

1. 如果前端命名不清，用户仍会把“商家知识库”和“平台方法论知识库”混成一层。
2. 如果把商家记忆也按长文自动切块，产品规则会与实现不一致。
3. 如果编辑规则没写死，后续很容易误做成“文件可在线替换正文”。

### 9.2 技术风险

1. 当前平台端 service 命名偏 `ForPlatformAdmin`，直接复用时容易导致职责混乱，需要抽通用逻辑。
2. 商家记忆编辑后，如果不更新 Supabase 中的原文来源，只更新 chunks，后续 retry source 可能与当前正文不一致。
3. 咨询侧文案如果不修，会误导用户对“资料是否被读取”的认知。

## 10. 推荐实施顺序

1. 先补商家侧 API 与 service 分层。
2. 再实现商家记忆 `1000` 个可见字符和单 chunk 规则。
3. 再做商家设置里的知识库入口与页面。
4. 再补编辑/删除规则。
5. 最后做咨询侧轻量文案修正与整体验证。

## 11. 本轮非目标

- 不做自动 memory 提炼。
- 不做对话结束后的自动写回。
- 不做商家侧 `knowledge_sets` 分组或 Agent 绑定管理。
- 不做批量上传。
- 不做 `pdf/docx` 等新格式。
- 不做搜索、筛选、分页增强。
- 不做商家资料在咨询台中的来源明细展示。
- 不做平台后台对商家知识库的管理界面。
