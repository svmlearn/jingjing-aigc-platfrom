# V2.1 商家知识库与商家记忆开发执行清单

日期：2026-04-29
状态：开工前 checklist
对应 PRD：`docs/产品文档/V2.1-商家知识库与咨询上下文补强-PRD.md`
对应测试文档：`docs/test/2026-04-29-v2.1-merchant-knowledge-memory-test-plan.md`

## 1. 本轮目标

在 `商家设置` 中新增 `商家知识库` Tab，支持两个产品动作：

1. `知识库上传`：商家上传 `txt / md` 商家资料。
2. `记忆录入`：商家手动新建可编辑的短文本商家记忆。

本轮只接入 `咨询上下文组装`，不接图文工作台、不接视频工作台、不做商家侧 `knowledge_sets`。

## 2. Worktree 规划

### 2.1 推荐数量

本轮推荐只开 `1` 个实现 worktree。

原因：

1. API、service、商家设置 UI、咨询上下文文案共享同一套 `knowledge_documents / knowledge_chunks` 约定，拆太散反而容易出现 metadata、状态映射和接口契约不一致。
2. 本轮不新增 migration，不接图文/视频，不碰商家侧 `knowledge_sets`，整体仍属于一个可控的垂直切片。
3. 商家知识库页面和商家侧 API 需要频繁对齐字段名、状态名和错误提示，单 worktree 收口更稳。

### 2.2 推荐 worktree

由用户自行创建 worktree。建议分支名：

```bash
git worktree add ../v2.1-merchant-knowledge-memory -b codex/v2.1-merchant-knowledge-memory
```

开工前建议先确认当前两份需求文档已经被 commit 或明确导出 patch，否则新 worktree 可能拿不到本轮确认后的文档。

### 2.3 不建议拆分的原因

暂不建议拆成 `backend` 和 `frontend` 两个 worktree。

主要风险：

1. 商家记忆的 `sourceType / contentKind / chunkPolicy` 规则需要 API、service、UI 同步理解。
2. 状态展示从三态改为 `uploaded / queued / processing / indexed / failed` 五态，前后端拆开容易漏映射。
3. 商家资料和商家记忆虽然是两个产品动作，但都落在同一个商家知识库列表和同一组商家侧 API 上。

### 2.4 什么时候才考虑第 2 个 worktree

只有出现以下情况之一，才考虑再开第 `2` 个 worktree：

1. 需要另一个开发者并行做完整 UI 视觉重构，而 API/service 已经先稳定。
2. 实现过程中发现必须新增 migration 或大幅调整知识库底层 schema。
3. 商家知识库之外临时追加了图文工作台或视频工作台上下文接入。

如果开第 `2` 个 worktree，建议职责边界如下：

```text
worktree A：商家知识库 API / service / repository / 咨询上下文
worktree B：商家设置 UI / 手动交互验收 / 视觉微调
```

默认仍以 `worktree A` 为主线，`worktree B` 不应改 API contract、repository 或 consultation service。

## 3. 开发执行 Checklist

### A. API 与 service

- [ ] 新增商家侧 API：
  - `GET /api/merchant-knowledge/documents`
  - `POST /api/merchant-knowledge/documents`
  - `PATCH /api/merchant-knowledge/documents/:documentId`
  - `DELETE /api/merchant-knowledge/documents/:documentId`
  - 可选：`POST /api/merchant-knowledge/documents/:documentId/retry`
- [ ] 所有商家侧 API 只从当前登录用户反查 `merchantId`，不允许客户端传入目标 `merchantId`。
- [ ] 抽出或复用知识库通用处理逻辑，保留平台后台现有上传能力不变。
- [ ] 文件型商家资料只允许 `txt / md`，UI 和 API 都提示单文件最大 `10MB`。
- [ ] 商家记忆正文按 trim 后可见字符计数，限制 `<= 1000`。
- [ ] 商家记忆写入 `1 document + 1 chunk`，不得走自动长文切块。
- [ ] 商家资料走现有自动切块逻辑。
- [ ] 商家记忆原文存 Supabase，例如写入 `knowledge_documents.metadata.sourceText`，用于编辑、重试和审计。

### B. 数据与状态

- [ ] 所有商家侧内容写入 `knowledge_documents.scope = merchant`。
- [ ] 所有商家侧内容必须写入当前 `merchant_id`。
- [ ] 建议 metadata 规则：
  - `sourceType = "file" | "memory"`
  - `contentKind = "merchant_document" | "merchant_memory"`
  - `chunkPolicy = "auto" | "single"`
- [ ] 状态展示按代码态映射：
  - `uploaded`：已上传，待处理
  - `queued`：队列中
  - `processing`：处理中
  - `indexed`：可用于咨询
  - `failed`：处理失败
- [ ] 只有 `indexed` 内容进入咨询检索上下文。
- [ ] 删除 V1 可做硬删除 document，级联删除 chunks/jobs；COS 源文件清理后置。

### C. 商家端页面

- [ ] 在 `商家设置` 增加 `商家知识库` Tab。
- [ ] 页面提供两个入口按钮：`知识库上传`、`记忆录入`。
- [ ] 列表展示字段：名称、内容类型、处理状态、更新时间、操作。
- [ ] 内容类型显示：`txt 文件`、`md 文件`、`商家记忆`。
- [ ] 文件型资料只允许改名、删除、重新处理；不允许在线编辑正文。
- [ ] 商家记忆允许改名、编辑正文、删除、重新处理。
- [ ] 空状态和失败状态使用面向商家的中文提示，不暴露技术错误。
- [ ] 商家侧不展示 `knowledge_sets`、知识集分组、Agent 绑定等平台管理概念。

### D. 咨询上下文

- [ ] 继续使用混排 topK：平台方法论知识库 + 当前商家已 indexed 的商家资料/商家记忆。
- [ ] 搜索结果保留 `scope`、`documentTitle`、`content`，插入咨询上下文。
- [ ] 咨询工具卡片或摘要文案避免只写“平台侧知识”，推荐 `检索平台方法论与商家上下文`。
- [ ] `uploaded / queued / processing / failed` 内容不得进入咨询上下文。
- [ ] 不改图文工作台、视频工作台的上下文组装。

## 4. 文件边界

### 高概率新增

```text
app/src/app/api/merchant-knowledge/documents/route.ts
app/src/app/api/merchant-knowledge/documents/[documentId]/route.ts
app/src/components/merchant/merchant-knowledge-library.tsx
```

如果实现“重新处理”独立接口，可新增：

```text
app/src/app/api/merchant-knowledge/documents/[documentId]/retry/route.ts
```

### 高概率修改

```text
app/src/contracts/knowledge.ts
app/src/lib/db/knowledge-repository.ts
app/src/server/api/knowledge-service.ts
app/src/server/api/schemas.ts
app/src/components/merchant/settings-workspace.tsx
app/src/server/api/consultation-service.ts
```

### 尽量不动

```text
app/supabase/migrations/**
app/src/app/platform-admin/**
app/src/components/platform-admin/**
```

说明：本轮优先用现有 schema + metadata 承接差异，不新增 migration；平台后台只做必要兼容，不做顺手重构。
