## 2. 总体迁移策略

不要一口气把所有 Supabase 能力都重写完。按风险从低到高拆：

1. 先把数据库 schema 和核心业务读写迁到普通 PostgreSQL。
2. 再把素材上传、成片下载、worker 改接国内 COS 和国内 PostgreSQL。
3. 再处理登录和账号体系，逐步替换 Supabase Auth。
4. 最后再做域名、HTTPS、PWA 正式安装体验和备案后切换。

第一阶段目标不是“生产上线”，而是证明：

```text
国内手机网络
-> 打开服务器 IP 页面
-> 登录 / 进入中介端或商家端
-> 上传素材到国内 COS
-> 创建 video_edit_jobs
-> worker 领取任务
-> FireRed / OpenStoryline 生成视频
-> final.mp4 上传国内 COS
-> 页面可重新签名并下载成片
```

## 7. Auth 迁移说明

这是最大的代码风险点。Supabase Auth 的密码 hash 不能直接当作普通数据库密码迁出来复用。

推荐做法：

### 验证期

```text
创建最小 app_users 表
使用 bcrypt / argon2 保存新密码 hash
手工创建 1 个管理员、1 个商家账号、1-3 个中介成员账号
使用服务端 session cookie 登录
```

验证期不迁老用户密码，不追求完整账号体系。

### 正式迁移期

```text
导出 Supabase 中业务用户映射关系
为用户生成重置密码 / 邀请链接
用户首次登录时设置新密码
逐步废弃 Supabase Auth
```

需要改造的当前落点：

- `app/src/lib/supabase/server.ts`
- `app/src/lib/supabase/admin.ts`
- `app/src/lib/supabase/browser.ts`

### 9.2 IP 阶段和 PWA 限制

IP 阶段用于验证：

- 页面访问。
- API。
- 上传。
- worker。
- 下载。

IP 阶段不强求完整 PWA 安装体验。原因是手机 PWA / service worker 通常需要 HTTPS 安全上下文，公网 IP 自签证书体验不稳定。

正式 PWA 安装体验放到：

```text
ba-ba-ke.com ICP 备案
-> app.ba-ba-ke.com HTTPS
-> manifest / icons / service worker 验收
```

| 风险 | 表现 | 处理 |
