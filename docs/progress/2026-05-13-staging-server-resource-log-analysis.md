# 2026-05-13 staging 服务器资源日志与国内服务器选型结论

## 1. 背景

本记录用于修正国内化部署采购判断。

此前文档偏向“Web/API 一台服务器、worker 一台服务器”。根据 2026-05-13 的 staging 服务器监控、worker 运行日志和当前代码实现，第一阶段更合理的方案是：

```text
先买 1 台国内 8 核 16G 服务器混跑 Web/API + worker + FireRed。
worker 维持单并发。
数据库使用托管 PostgreSQL。
素材和成片使用同地域国内 COS。
```

## 2. 证据来源

- 用户提供的腾讯云监控截图。
- 本地下载日志目录：`docs/临时-服务器日志/`
- 用户提供的 `2026-05-13 COS 运行时间戳与结果对应` 排查记录。
- 当前仓库 worker 代码和 Docker / OpenStoryline 配置。

本记录不包含任何密钥、密码、provider key。

## 4. worker 并发事实

当前 worker 代码事实：

- `workers/video-worker/worker/app/config.py` 中 `WORKER_MAX_CONCURRENCY` 默认值为 `1`。
- 当前配置还会在 `WORKER_MAX_CONCURRENCY != 1` 时抛错。
- poller 领取任务时按单任务循环处理。

用户提供的成功任务时间线也说明当前是队列串行：

| Job ID | 输入素材数 | worker 领取 | 引擎完成 | DB 成功 |
| --- | ---: | --- | --- | --- |
| `61ae9626-9d19-4ecd-b671-31ec315eab54` | 3 | 2026-05-13 13:18:32 | 2026-05-13 13:39:47 | 2026-05-13 13:39:49 |
| `8591e620-0526-474e-b0cd-1fbc3e8b0335` | 6 | 2026-05-13 13:39:59 | 2026-05-13 14:06:36 | 2026-05-13 14:06:39 |

第二个任务虽然更早创建于 `2026-05-13 13:22:48`，但实际到 `13:39:59` 才被 worker 领取，基本发生在前一个任务完成之后。

结论：

```text
当前系统不是多视频并发生成，而是单 worker 串行处理。
因此不能把 8 核 16G 直接写成“支持 3 并发”。
```

## 5. FireRed / OpenStoryline 资源判断

当前实现不跑本地大模型，也不需要 GPU。大模型、VLM、LLM、TTS 等主要通过外部接口调用。

但它不是纯轻量任务，仍会消耗：

- Docker / Docker Compose 常驻资源。
- FireRed / OpenStoryline Python 运行时。
- FFmpeg 视频渲染和编码。
- CPU torch / torchaudio 相关依赖。
- TransNetV2 切镜、FunASR、HuggingFace embedding / FAISS 等可能的本地 CPU 组件。
- 素材下载、临时文件读写、成片上传。
- COS 网络 IO。

所以判断应是：

```text
不需要 GPU，不需要本地大模型服务器。
但需要足够 CPU、内存、磁盘和网络余量，尤其是 FFmpeg 和临时文件阶段。
```

## 6. 采购结论

### 6.1 第一阶段推荐

```text
服务器：1 台国内 8 核 16G
系统盘：100G 起
数据盘：300G SSD 起，500G 更从容
公网带宽：10Mbps 起
数据库：托管 PostgreSQL，2 核 4G / 100G 起
对象存储：同地域国内 COS，私有桶，按量或 500G 起步资源包
worker 并发：先保持 1
```

这套配置用于：

- Next.js / Node API
- Nginx
- Docker
- video-worker
- FireRed / OpenStoryline
- 单并发视频生成

### 6.2 不推荐现在购买的配置

```text
不建议继续用 2 核 4G 作为国内验证主机。
不建议一开始买 4 台机器区分测试 / 灰度 / 正式。
不建议一开始强制拆 Web/API 和 worker 两台服务器。
不建议把数据库也长期塞进同一台机器。
```

### 6.3 后续扩容触发条件

出现以下情况时，再拆分或升级：

- 单并发时 8 核 16G 的 CPU / 内存 / IO 长时间贴边。
- 视频任务执行导致 Web/API 明显变慢。
- 队列等待时间影响中介端使用体验。
- 需要把 worker 并发提升到 2 或 3。
- 需要 Web/API 和 worker 分别发布、回滚和扩容。

后续拆分建议：

```text
Web/API 服务器：4 核 8G 起
Worker 服务器：8 核 16G 起
2-3 并发 Worker：16 核 32G 起
```

## 7. 待补技术项

资源升级不能替代工程补强。国内化验证同时需要补：

- worker 阶段耗时日志：claim、下载、AI、FFmpeg、上传、DB 回写。
- job heartbeat。
- job timeout 策略。
- failed_retryable / failed_manual 分类。
- 手动重跑入口。
- signed URL 过期后重新生成下载链接。
- 队列长度和等待时间可视化。
- 服务器 CPU、内存、磁盘、网络监控。
