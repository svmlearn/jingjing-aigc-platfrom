## 修复内容

### P0-01 生成团队内容 pending / worker 缺失

已修复：

- 新增 `deploy/domestic/systemd/jingjing-content-generation-worker.service` 模板。
- 部署时会在服务器安装并启用 `jingjing-content-generation-worker.service`。
- worker 继续调用 `/api/content-generation/jobs/run-next`，单次只处理一个 Dify job。
- Dify transient 失败改为 `failed_retryable`，缺少 `DIFY_API_KEY_MISSING` 仍为人工处理。
- queue claim 支持重新领取 `failed_retryable` 且未超过 `max_attempts` 的 job。

### P0-02 生成团队内容未使用当前咨询日历上下文

已修复：

- `/api/content-generation/batches` 支持 `consultationSessionId`。
- 商家咨询台点击“生成团队本周内容”时会把当前 session id 带给后端。
- batch service 会读取当前 consultation session 的 `strategySnapshot.contentCalendarDraft`。
- 若当前 session 有日历草案，则强制刷新团队成员的 `daily_content_tasks`，来源为 `consultation_calendar`。
- daily task 保存：
  - `teamCalendarSource.calendarItems`
  - `teamCalendarSource.calendarGuidance`
  - `teamCalendarSource.consultationSessionId`
  - `knowledgeRefs`
  - `calendarItemIds`
- Dify `calendar_task_json` 和 `fallback_knowledge_text` 会继续通过现有输入字段携带隐藏上下文，不新增 Dify Start 输入。

### P1-01 Agentic RAG 多轮 query 深挖不足

已修复：

- model-json planner 的 ready tools 允许读类工具重复出现，写类工具仍按完成状态收敛。
- deterministic fallback 不会因为读类工具可重复而无限重复读取。
- native tool calling system prompt 增加明确策略：当用户列出“项目优势 / 方法论 / 话术 / 素材边界”等多个维度时，应拆成不同 query 逐轮检索，不要只用一个大 query。

### P1-02 素材和事实支撑不足

已修复：

- `fallback_knowledge_text` 增加视频画面生成原则：画面边界来自日历素材提示、视频素材能力和成员可补拍方式；未命中的客户签约、客户访谈、政策文件、价格收益、老业主反馈等不要写成确定事实或已有素材。
- `calendar_task_json` 继续携带 `videoAssetCapabilities`。
- 该修复是上下文和提示约束，不是代码硬门禁；最终由 Dify/LLM 基于上下文生成。

### P1-03 hidden guidance 污染旧测试信息

已修复：

- guidance 汇总时过滤明显测试占位信息，例如“图文内容”“AI视频”“测试区域”“用于验证成员端登录、邀请码注册和团队加入链路”等。
- `assetCapabilityHints` 不再把泛化卖点硬转换成素材能力，只保留较可信的场景线索。

## Claude Code 工具调用对照结论

对照路径：

- `/Users/wy/Desktop/静境/静境4.0/小红书抖音矩阵获客平台/references/open-source/claude-code项目/claude-code-main`

关键源码证据：

- `src/services/api/claude.ts:1700` 到 `1713`：请求模型时传入 `tools: allTools` 和 `tool_choice`。
- `src/utils/api.ts:119` 到 `178`：把内部 Tool 映射成模型可见的 `name`、`description`、`input_schema`。
- `src/query.ts:551` 到 `558`：把 `tool_use` block 作为 loop 是否继续的关键依据，而不是依赖普通文本。
- `src/query.ts:832` 到 `846`：收集 assistant 消息里的 `tool_use` block。
- `src/query.ts:1383` 到 `1385`：对收集到的 tool_use 调用 `runTools(...)`。
- `src/services/tools/toolExecution.ts:614` 到 `679`：runtime 对模型给出的 tool input 做 schema 校验；校验失败也以 `tool_result` 形式回到上下文。
- `src/services/tools/toolExecution.ts:1207` 到 `1222`：runtime 真正执行工具。
- `src/services/tools/toolExecution.ts:1456` 到 `1466` 和 `1715` 到 `1727`：runtime 把成功或失败结果封装为带 `tool_use_id` 的 `tool_result` user message。
- `src/query.ts:1718` 到 `1720`：下一轮上下文是 `messagesForQuery + assistantMessages + toolResults`。
- `src/utils/messages.ts:5160` 到 `5375`：Claude Code 还会修复或阻断 `tool_use` / `tool_result` 不配对的问题。

结论：

- Claude Code 不是让模型输出任意自然语言 JSON 后由业务代码硬猜，而是使用 Anthropic 原生结构化 `tool_use` block。
- runtime 的职责是暴露工具、校验参数、执行工具、把同 id 的 `tool_result` 放回下一轮上下文。
- 是否检索、检索什么 query、检索几轮，应该由模型基于 system prompt、工具描述和上一轮 tool_result 自己决定。
- 当前项目因为原生 tool calling 在线上会挂起，采用 `model_json_tool_use` 作为传输兼容层是可接受的，但语义必须贴近 Claude Code：模型发起工具调用，runtime 不做“自动先查 RAG”的业务硬编码。
- 本轮已把“必须第一步调用 retrieve_knowledge_base”的提示软化为“应优先考虑先调用”，避免把 agent loop 退化成固定流程。
