# 2026-05-27 咨询 Agent 素材检索工具需求

## 结论

当前咨询 Agent 还缺两个关键业务工具：

1. 从商家视频素材库中检索已上传/已打标视频素材的工具。
2. 从已沉淀的社交媒体爆款内容库中检索内容的工具。

这两个工具是“让 Agent 在用户明确要求参考真实素材和真实爆款内容时，能够真实检索并解释参考来源”的前提。它们不是内容日历生成的硬门禁；即使不检索，Agent 也可以基于用户口头信息和已有策略资产给出可用建议。但一旦 Agent 声称“参考了素材库 / 爆款库”，就必须能说明检索到了什么、没有检索到什么，不能把推断包装成检索事实。

## 需要补的两个工具

### 1. `search_project_video_materials`

建议语义：

- 从当前商家的视频素材库检索 ready 视频素材。
- 主要读取 `merchant_media_clips`，必要时沿用 private media repository 的检索能力。
- 用于回答：
  - “我现有视频素材能拍什么内容？”
  - “哪些素材适合做夜宵、烤串、工业园、工友下班等选题？”
  - “你刚才规划内容日历到底参考了哪些视频？”

建议参数：

```json
{
  "query": "烤串 工业园 工友 下班 夜宵",
  "limit": 8,
  "orientation": "landscape|portrait 可选",
  "minDurationSeconds": "可选",
  "maxDurationSeconds": "可选"
}
```

建议返回给 Agent 的字段：

- `clipId`
- `assetId`
- `title` 或简短描述
- `description`
- `tags / sceneTags / shotTags / peopleTags / qualityTags`
- `width / height / orientation / durationSeconds`
- `matchReason`

不要把 OSS key、bucket、下载 token、签名 URL 直接暴露给模型；模型只需要素材语义和可引用 ID。

### 2. `search_saved_viral_materials`

建议语义：

- 从当前商家已经沉淀的社交媒体爆款内容库里检索。
- 不调用外部 TikHub。
- 不新增 provider 结果。
- 只读当前已有 `source_items` / `imported_comments` / `asset_objects` 中的 ready 爆款内容。

用于回答：

- “你参考了哪些爆款内容？”
- “这个烧烤摊可以借鉴哪些开头、标题、评论痛点？”
- “我已有的爆款内容库里有没有和工业园、夜宵、酱料相关的内容？”

建议参数：

```json
{
  "query": "烧烤 夜宵 工业园 下班 工友 独家酱料",
  "platform": "douyin|xiaohongshu 可选",
  "limit": 8
}
```

建议返回给 Agent 的字段：

- `materialId`
- `platform`
- `title`
- `materialType`
- `description/bodyText/scriptText`
- `engagementLabel`
- `structureSummary`
- `topComments`
- `originalUrl`
- `matchReason`

返回内容要紧凑，避免把 raw TikHub payload 整包塞进上下文。

字段口径补充：

- `description / bodyText / scriptText` 当前来自 `source_items.body_text` 或 `source_items.script_text`，本质是保存下来的图文正文、视频标题/脚本/描述文本，不要擅自称为“正文摘要”，除非代码后续真的新增摘要生成。
- `structureSummary` 当前主要来自 provider normalizer 写入的 `source_items.structure_summary`，常见内容包括 `materialType`、`provider`、`coverUrl`、`imageUrls`、`videoUrls`、`tags`、`rank`、`durationMs` 等归一化元数据。它不是 TikHub 已经帮我们完成的“爆款结构拆解”，也不是系统当前稳定生成的开头/冲突/转折/评论痛点分析。
- 如果后续需要“结构拆解”，应新增明确字段，例如 `analysisSummary` / `creativeStructure`，由我们自己的分析链路生成并标明来源；不要把现有 `structureSummary` 误命名为完整拆解。
- 社媒爆款检索返回给 Agent 的内容应包含：内容文本本体、互动标签、评论痛点、媒体形态摘要（图片数、视频数、封面数、是否有视频），以及可引用 ID；不要暴露 OSS key、bucket、签名 URL。

## 为什么这是 P0/P1 级缺口

这不是“锦上添花”，但也不是内容日历生成的强制前置门禁。

用户已经在真实业务路径里要求：

> 我这里有很多自己上传的视频素材了，还有一些社交媒体的爆款内容库，你参考他们的来帮我规划，帮我建议。

Agent 随后生成了内容日历建议，但在用户追问“你都检索了什么爆款内容，或者什么视频素材”时，只能承认没有工具。

如果用户已经明确要求参考已有素材库 / 爆款库，而 Agent 没有真实工具能力，会造成三个问题：

1. 生成内容日历时没有真实证据链。
2. Agent 不能解释“为什么这个选题适合你现有素材”。
3. 用户无法相信它真的利用了素材库和爆款库。

所以修复时，核心验收不是“工具列表里多两个名字”，而是当用户明确要求参考素材库 / 爆款库或追问“你检索了什么”时，Agent 能在咨询里真实调用、真实返回、真实解释；如果本轮没有调用，也要说清楚“这次建议基于你刚才描述和已有策略资产，不是基于素材库检索”。

## 2026-05-27 补充讨论记录

### 工具调用不做日历生成门禁

这两个检索工具不应阻塞 `update_content_calendar`。Agent 可以不检索也生成营销日历。

推荐行为是：

1. 用户泛泛问“怎么拍 / 给我排个日历”时，Agent 可以直接基于上下文建议。
2. 用户明确说“参考我上传的视频素材 / 参考已有爆款库”时，Agent 应优先考虑调用对应只读工具。
3. 用户追问“你检索了什么”时，如果本轮没有调用工具，Agent 必须承认没有检索，不能补造检索结果。

### Planner 后续处理

当前代码里仍存在 `app/src/server/api/consultation-runtime/planner.ts`，但目标方向是逐步去掉 planner 编排，让咨询 Agent 更接近 Claude Code 式 tool loop：工具作为能力清单交给模型，runtime 负责校验、执行、压缩和展示。

实现这两个检索工具时，不要为了它们新增 planner 硬编码流程；优先走 `native_tool_calling_loop_v1` / runtime tool registry。planner 清理单独作为后续架构任务处理。

### 社媒爆款返回字段命名

不要使用容易误导的 `textSummary` 作为当前实现字段名。当前数据里保存的是文本本体或 provider 描述，不是模型摘要。

建议返回字段：

- `text`: 图文正文或视频脚本/描述文本，来自 `bodyText / scriptText / description`，做长度裁剪即可。
- `structureMetadata`: 当前 `structureSummary` 的安全子集，表示 provider 归一化元数据，不声称是创意结构拆解。
- `mediaSummary`: 根据 `asset_objects` 或 `structureSummary.imageUrls/videoUrls/coverUrl` 得出的媒体形态摘要，例如图片数、视频数、封面数、是否有视频。
- `topComments`: 当前已保存的代表性评论。
- `matchReason`: 为什么命中本次 query。

如果未来要返回“开头方式 / 冲突点 / 转折 / 评论痛点 / 结尾 CTA”这类真正结构拆解，必须另建分析字段或分析工具，不要复用 `structureSummary` 这个名字假装已经有。
