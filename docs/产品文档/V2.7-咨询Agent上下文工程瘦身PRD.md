# V2.7 咨询 Agent 上下文工程瘦身 PRD

> 状态：评审稿  
> 创建时间：2026-05-21  
> 来源：咨询 Agent 上下文工程对照评审、Claude Code reference 对照、当前代码事实核对  
> 关联页面：`docs/架构规范/咨询Agent上下文工程对照评审.html`

## 1. 背景

当前咨询 Agent 的 native tool calling 链路已经基本打通，但真实聊天体验仍有“怪”的感觉：模型能调用工具，也能写入日历或策略资产，但回复容易显得流程化、过度解释内部机制，或者被过多上下文牵引。

本轮评审判断：问题优先不是工具调用本身，而是上下文组装方式过重、重复、边界不清。当前 system prompt 与 user JSON 同时注入了大量规则、状态和调试信息，导致模型需要在多个权威来源之间自行判断。

## 2. 当前代码事实

### 2.1 当前 system prompt 注入内容

native tool calling 路径中，system prompt 依次拼入：

- agent prompt
- soul
- 专家容器
- skill catalog
- active skills
- skill references
- business tools
- ContextInjector 说明
- native tool loop 规则
- 日历规则
- RAG 规则
- guardrail 规则

### 2.2 当前 user JSON 注入内容

user JSON 当前包含：

- merchant
- userMessage
- round
- contextInjection
- strategySnapshot
- knowledgeMatches
- toolResults
- skillDisclosure

其中 `contextInjection` 内部又包含 `targetExpert`、`mentionRouting`、`sessionContext`、`expertTraffic`、`budget` 等字段。`sessionContext` 内部又重复携带 `strategySnapshot`、`strategyMarkdown`、`toolResults` 等信息。

### 2.3 tool result 已经会回给 LLM

native tool calling 路径中，工具执行结果会以 `role: "tool"` 消息回填给模型。工具解析失败、不可用、guardrail 拒写等失败结果，也会作为 tool result 回填。

因此，user JSON 中再放 `toolResults` 属于重复注入。工具结果的权威来源应是 tool result message，而不是 contextInjection 或 user JSON 的重复摘要。

### 2.4 RAG 当前返回数量

当前默认检索配置：

- consultation agent `retrievalTopK = 5`
- knowledge runtime `retrievalTopK = 5`

每次检索会先用 `topK * 2` 做 keyword/vector/direct scan，再 merge 成最多 `topK` 个结果。多轮检索会累积 knowledgeMatches，当前最多保留 24 个 unique chunk。

这意味着 `knowledgeMatches` 如果不区分“本轮命中”和“历史命中”，会让模型把旧依据误当成本轮依据。

## 3. 核心问题

### 3.1 ContextInjector 概念边界不清

从产品语义上看，所有塞给 LLM 的内容都属于上下文工程，包括 system prompt、tools、RAG、skills、tool results、strategySnapshot、user JSON。

但当前有一个名为 `contextInjection` 的 user JSON 大对象，好像它才是“上下文注入器”。这会导致两个问题：

- 概念上误导：它不是整个上下文注入器，只是会话状态包。
- 实现上过重：它把策略资产、工具结果、budget、expertTraffic 等全部打包给 LLM。

### 3.2 策略资产重复

`strategySnapshot` 已经作为 user JSON 顶层字段存在，`contextInjection.sessionContext.strategySnapshot` 再放一次是重复。

策略资产应只有一个主入口，避免模型不清楚哪个才是当前权威状态。

### 3.3 工具结果重复

tool result 已经通过 tool message 回填给模型。user JSON 顶层 `toolResults` 和 `contextInjection.sessionContext.toolResults` 都应移除。

需要保留的是“工具结果诚实性规则”，不是重复的工具结果摘要。

### 3.4 budget 给主模型没有价值

budget 报告对开发和调试有用，但对主 LLM 没有明确业务价值。模型看到 budget 不会更会聊天，反而可能被系统工程信息干扰。

budget 应作为 runtime 内部硬预算和 debug 信息，不进入主模型上下文。

### 3.5 expertTraffic 暂无主链路价值

如果当前不是强多专家并发协作，`expertTraffic` 每轮注入会增加理解成本。专家交接信息可以保留，但应缩小为 `expertRouting` 或必要的 handoff 摘要，而不是整包 `sharedConsultationState / ExpertTurnNote`。

### 3.6 skillDisclosure 更像调试信息

主模型已经看到：

- skill catalog
- active skills
- skill references

`skillDisclosure` 只是候选 skill / active skill 的结构化命中记录，包括 score、triggerReasons、referenceTitles 等。它更适合前端调试面板和 runtimeSnapshot，不应塞给主模型。

### 3.7 日历规则过于流程化

当前 prompt 中对“什么时候写日历、什么时候改标题”的说明过细，容易把模型变成流程执行器。

用户期望是：LLM 自己判断是否足够了解用户；足够时可以提醒用户“现在可以写营销日历”。用户明确要求改标题时就改标题。

必须保留的强规则是：如果营销日历已经生成过团队内容，修改前必须提醒用户后续团队内容可能需要重新生成，并确认是否继续。

## 4. 产品目标

### 4.1 目标

1. 让主 LLM 只看到本轮必要上下文，减少重复和调试信息。
2. 将 `ContextInjector` 从“给 LLM 看的大对象”改成 runtime 内部的上下文选择机制。
3. 保留工具调用能力，但减少业务规则对自然聊天的干扰。
4. 明确 RAG chunks 的来源、轮次和当前相关性。
5. 保留专家切换能力，但不引入无必要的共享事实层。

### 4.2 非目标

1. 本 PRD 不直接更换模型 provider。
2. 本 PRD 不重写所有 skill 内容。
3. 本 PRD 不改变 Dify、video-worker、内容生成链路的数据合同。
4. 本 PRD 不删除 runtimeSnapshot、debug 面板或事件日志中的调试信息。

## 5. 新设计原则

### 5.1 ContextInjector 改为内部 ContextPackSelector

不再把 `contextInjection` 作为 user JSON 对象传给主 LLM。

新增或重命名内部概念：

- `ContextAssembler`：负责拼装所有候选上下文。
- `ContextPackSelector`：按本轮 intent 选择哪些上下文进入 LLM。
- `ContextBudgetEnforcer`：执行硬预算、裁剪和 omit，不只是报告。

LLM 最终只看到选择后的少量上下文，不看到“上下文注入器的工作报告”。

### 5.2 保留 expertRouting，而不是共享事实层

专家切换时，真正需要告诉 LLM 的是：

```json
{
  "expertRouting": {
    "activeAgentKey": "...",
    "activeDisplayName": "...",
    "roleDescription": "...",
    "knowledgeSetIds": ["..."],
    "knowledgeDocumentIds": ["..."],
    "rawMention": "@营销专家"
  }
}
```

换专家时，本质上切换：

- 专家自己的 system prompt
- soul.md
- skill catalog / active skills
- knowledge boundary

不需要额外维护一个“共享事实层”大对象。

### 5.3 user JSON 只保留必要字段

目标 user JSON：

```json
{
  "merchant": {
    "name": "...",
    "industry": "...",
    "serviceItems": [],
    "defaultCta": []
  },
  "userMessage": "...",
  "round": 3,
  "expertRouting": {},
  "strategySnapshot": {},
  "currentKnowledgeMatches": []
}
```

应移除：

- `contextInjection`
- `toolResults`
- `skillDisclosure`
- `budget`
- `expertTraffic`

### 5.4 toolResults 只保留 tool message 权威来源

native tool calling 中，工具结果以 `role: "tool"` 回填。JSON tool loop 中，工具结果以 `tool_result` 内容回填。主模型应依赖这些消息，不再读取 user JSON、`tool_loop_state` 或其他状态对象里的重复摘要。

保留一条稳定协议：

> 工具结果诚实性规则：如果 tool result 是 skipped、failed、guardrail rejected 或未完成，最终回复不能声称已经写入或执行成功。

该规则归入工具循环协议层。

#### 5.4.1 JSON tool loop 状态消息禁止复刻 toolResults

当前 JSON tool loop 里存在一个运行时状态消息：

```json
{
  "type": "tool_loop_state",
  "availableTools": ["retrieve_knowledge_base", "update_content_calendar"],
  "completedTools": ["retrieve_knowledge_base"],
  "observations": [
    {
      "toolName": "retrieve_knowledge_base",
      "status": "completed",
      "summary": "检索平台方法论与用户知识库，命中 5 个受控片段。"
    }
  ],
  "decisionRules": [
    "如果用户要求基于知识库生成营销日历，应优先考虑先调用 retrieve_knowledge_base...",
    "只有当本轮 tool_result 已经提供足够依据后，才选择 update_content_calendar..."
  ]
}
```

这个形态必须继续瘦身，避免把已移除的 `toolResults` 换一个字段名塞回主模型。

明确要求：

1. `tool_loop_state.observations` 不得携带每个工具的 `summary`、`payload`、`knowledgeMatches`、`calendar`、`strategySnapshot` 或任何业务结果摘要。
2. 如果保留 `observations` 字段，只能作为极简状态索引，例如 `{ "toolName": "retrieve_knowledge_base", "status": "completed" }`；更推荐直接删除 `observations`，改用 `completedToolNames` / `failedToolNames` / `skippedToolNames`。
3. `tool_loop_state` 不得重复解释工具结果。模型需要读取的业务事实只能来自前序 `tool_result` 消息。
4. `tool_loop_state` 不得包含 `decisionRules` 这类代码硬编码业务决策规则。是否继续检索、是否写日历、是否追问，应由模型基于用户目标、available tools 和前序 `tool_result` 自行判断。
5. 允许保留的代码级状态只限工具循环控制所需字段，例如：

```json
{
  "type": "tool_loop_state",
  "turn": 2,
  "maxTurns": 8,
  "availableToolNames": ["update_content_calendar"],
  "completedToolNames": ["retrieve_knowledge_base"],
  "failedToolNames": [],
  "skippedToolNames": [],
  "writeToolsAlreadyUsed": [],
  "stateNote": "Read prior tool_result messages as the authority. Do not rely on summaries here."
}
```

6. 如果后续确实需要给模型一条提醒，只能保留协议级提醒，不允许写成业务流程规则。例如可接受：`Read prior tool_result messages as the authority.`；不可接受：`如果用户要求生成营销日历，应先调用 retrieve_knowledge_base。`
7. runtimeSnapshot / debug 面板可以继续保留完整 tool result summaries，但这些 summaries 不得进入主模型消息流。

### 5.5 RAG 只放当前相关 evidence

`knowledgeMatches` 改为 `currentKnowledgeMatches` 或 `selectedKnowledgeMatches`。

每条 chunk 必须带最少元信息：

```json
{
  "documentTitle": "...",
  "chunkId": "...",
  "score": 0.82,
  "content": "...",
  "query": "...",
  "toolCallId": "...",
  "turn": 3,
  "freshness": "current_turn"
}
```

规则：

- 单次 retrieve 默认最多 5 个 chunk。
- 多轮 retrieve 可以存在，但进入主 LLM 的 chunks 必须经过选择。
- 历史 chunks 不默认进入主 LLM，除非被本轮 intent 选中。
- 调试面板可以显示全部历史命中，主模型只看 selected evidence。

### 5.6 日历和工具规则改成少量硬规则

本节的目标不是新增一套更长的工具说明，而是把当前 `consultation-service.ts` 里已经膨胀的 system prompt 做减法。实现时必须先识别“之前 prompt 里混了哪些东西”，再按产品确认的白名单保留。没有进入白名单的旧规则，不得因为“也许有用”继续留在 system prompt。

#### 5.6.1 之前 system prompt 里混入的内容

当前实现里，native tool calling 和 JSON tool loop 的 system prompt 除了 agent / soul / expert / skills / tools / `slim_v2` 之外，还额外拼接了大量流程规则。和本次瘦身直接相关的旧规则大致包括：

1. 工具循环协议：告诉模型当前运行 `native_tool_calling_loop_v1` 或 `model_json_tool_loop_v1`，要求 native 模式用 API tools 字段返回结构化 `tool_calls`，JSON 模式只输出 JSON object。
2. runtime 职责说明：强调 runtime 只负责提供、校验和执行工具，是否检索、是否换 query、是否写日历由模型判断。
3. 知识库读取规则：当用户要求读取、查看、总结、盘点或分析用户知识库/上传资料时，先调用 `retrieve_knowledge_base`。
4. 多轮检索规则：做团队选题、营销日历、图文文案或视频脚本规划时，如果一次检索只覆盖部分信息，可以换 query 继续检索；如果用户列出多个检索维度，也要拆成多个 query。
5. 日历写入前置规则：用户要营销日历、团队选题、图文/视频脚本这类会沉淀为后续任务的内容时，如果本轮还没有知识库或素材依据，先检索；调用 `update_content_calendar` 前判断依据是否足够；不要先写日历再补查依据。
6. 旧链路迁移说明：写明“内容日历 -> 生成团队内容 -> Dify”，并补充“不再通过用户端图文工作台或视频工作台作为前置”。
7. 已下线/未暴露工具说明：继续提到 `generate_article_brief` / `generate_video_brief`，并告诉模型“只在用户明确要求工作台 brief 时使用”。
8. 历史日历说明：`strategySnapshot.contentCalendarDraft` 可能是历史资产，不能把历史日历当成本轮已完成。
9. 重复日历写入规则：一处说“生成内容日历/营销日历/团队选题时调用 `update_content_calendar`”，另一处又说“修改标题、摘要、日期、内容类型或选题角度也必须调用”。
10. 团队内容影响规则：如果当前日历已经生成过团队内容，修改前说明影响并询问用户确认。
11. 视频画面约束：视频选题、脚本方向或日历隐藏上下文的画面描述必须基于素材能力、用户确认场景或可补拍方式。
12. 其它工具路由规则：什么时候调用 `update_strategy_snapshot`、`search_benchmark_materials`、`retrieve_knowledge_base`、`read_history`。
13. 失败诚实规则：工具 skipped、failed、guardrail rejected 或不可用时，最终回复必须承认未写入或未完成。
14. 最终输出边界：最终回复只给用户中文自然语言，不输出内部工具名、JSON、Markdown 表格或 debug payload。

问题不在于每一句都错，而在于这些规则被一起塞进全局 system prompt 后，会重新制造冗余：有些和当前可用工具不一致，有些重复表达同一个日历写入义务，有些属于历史迁移背景，有些应该交给工具 schema、guardrail 或 runtime debug，而不是每轮都让主模型阅读。

#### 5.6.2 产品确认只保留的 system prompt 白名单

以下规则允许继续留在 system prompt。实现时应尽量使用短句，不要扩写成多段说明。

1. 工具调用协议：`native_tool_calling_loop_v1` 必须通过 API tools 字段返回结构化 `tool_calls`，不要在正文里输出工具 JSON。JSON fallback 模式只保留等价的最小 JSON 输出协议。
2. 写入类工具时机：写入类工具仍要在信息足够后再调用。
3. 日历写入前置判断：不要先写日历再补查依据。在调用 `update_content_calendar` 前，应先判断当前知识库和素材能力依据是否足够。
4. 日历写入义务：当用户要求生成、补充或调整内容日历、营销日历、团队选题、本周图文/视频任务时，优先考虑调用 `update_content_calendar`，并传入可执行的 calendar 条目。
5. 团队内容影响提醒：如果当前日历已经生成过团队内容，修改前必须提醒用户后续团队内容可能需要重新生成，并确认是否继续。
6. 工具结果诚实性：工具返回 skipped、failed、guardrail rejected 或未完成时，最终回复必须承认本轮未写入或未完成，不能声称已经更新。
7. 用户可见输出边界：最终可见回复只输出给用户的中文自然语言，不输出内部工具名、JSON、Markdown 表格或 debug payload。

#### 5.6.3 明确删除项

以下内容必须从 system prompt 或 JSON tool loop 状态消息中删除，除非未来 PRD 明确重新引入：

1. 删除所有关于 `generate_article_brief` / `generate_video_brief` 的说明。理由：这两个工具当前没有暴露给 LLM，模型无法调用；告诉模型“只在某场景使用它们”只会增加噪音。
2. 删除“不再通过用户端图文工作台或视频工作台作为前置”这类旧链路迁移解释。理由：这是产品/架构背景，不是模型本轮决策必需信息。
3. 删除重复日历规则。保留“生成、补充或调整日历时优先调用 `update_content_calendar`”这一句即可，不要再单独列“修改标题、摘要、日期、内容类型或选题角度也必须调用”。
4. 删除依赖 `observations.summary` 的规则表述。JSON tool loop 下一轮应该读取前序 `tool_result`，不是读取 runtime 额外生成的 observations 摘要。
5. 删除 `tool_loop_state.decisionRules`。不要把“是否先检索、是否写日历、是否追问”这类业务判断塞到状态 JSON 里。确实必须保留的规则，只能进入 5.6.2 的 system prompt 白名单。
6. 不要新增“当前没有暴露的工具怎么使用”的说明。工具未出现在当前 `availableTools` 或 API tools 字段中，就不应该出现在 prompt 中。

不在 5.6.2 白名单里的旧工具规则，如果仍被认为有价值，应优先下沉到更合适的位置：工具 schema 描述、runtime guardrail、开发调试面板、handoff 或架构文档。不得默认继续塞回每轮 system prompt。

### 5.7 budget 只做内部硬预算

budget 不进入主 LLM。

需要改成内部真实控制：

- 按 bucket 计算字符或 token。
- 超出预算时裁剪、摘要或 omit。
- 输出 debug 信息到 runtimeSnapshot / 开发面板。
- 记录哪些字段被省略，便于排查。

## 8. 验收标准

### 8.1 上下文结构验收

- user JSON 不再包含 `contextInjection`。
- user JSON 不再包含 `toolResults`。
- user JSON 不再包含 `skillDisclosure`。
- user JSON 不再包含 `budget`。
- user JSON 不再包含 `expertTraffic`。
- user JSON 保留 `strategySnapshot` 作为唯一策略资产入口。
- 专家切换信息以 `expertRouting` 形式保留。

### 8.2 工具结果验收

- native tool calling 下，completed/skipped/failed/rejected tool result 都能回到模型消息流。
- JSON tool loop 下，completed/skipped/failed/rejected tool result 都只能通过 `tool_result` 消息承载业务结果。
- 当工具 skipped/failed/rejected 时，最终回复不能声称已经执行成功。
- 不依赖 user JSON 的 `toolResults` 也能完成最终回复。
- `tool_loop_state` 不包含 `observations.summary`、`observations.payload`、`observations.knowledgeMatches` 或任何工具结果业务摘要。
- `tool_loop_state` 不包含 `decisionRules` 数组，也不包含“先检索再写日历”“只有依据足够才写日历”这类代码硬编码业务流程规则。
- 如需给 JSON tool loop 传运行状态，只能传工具名列表和状态列表，例如 `availableToolNames`、`completedToolNames`、`failedToolNames`、`skippedToolNames`、`writeToolsAlreadyUsed`。

### 8.3 RAG 验收

- 单次 retrieve 默认最多进入 5 个 selected chunks。
- 多轮检索后，主模型只看到 current/selected chunks，不默认看到全部历史 chunks。
- 每条 selected chunk 带 query/toolCallId/turn/freshness。
- 调试面板仍能看到完整历史命中。

### 8.4 日历行为验收

- 用户明确要求生成日历时，模型可在信息足够后调用 `update_content_calendar`。
- 用户明确要求改标题时，模型直接修改对应日历项，不需要额外流程解释。
- 如果日历已经生成团队内容，修改前必须提醒影响并询问确认。
- 轻问答不应长期携带完整日历规则。

### 8.5 体验验收

- 简单聊天不再出现明显内部机制说明。
- 模型不再向用户暴露 skillDisclosure、budget、contextInjection 等内部词。
- 回复更像顾问对话，而不是流程日志。

## 9. 实施建议

### 9.1 第一步：移除明显重复 user JSON

优先从 native tool calling payload 中移除：

- `contextInjection`
- `toolResults`
- `skillDisclosure`

保留：

- `merchant`
- `userMessage`
- `round`
- `strategySnapshot`
- `knowledgeMatches` 暂时重命名或包成 `currentKnowledgeMatches`

### 9.2 第二步：重写 ContextInjector

将 `buildConsultationContextInjection` 改为内部选择器，不再返回给主 LLM 的大对象。

新增：

- `buildExpertRoutingContext`
- `buildSelectedTurnContext`
- `buildSelectedKnowledgeMatches`
- `buildContextOmissionDebug`

### 9.3 第三步：RAG current/history 分层

在 retrieve tool result 中记录 query、toolCallId、turn。

state 内部可保留全部 `knowledgeMatches`，但 build LLM payload 时只输出 selected/current。

### 9.4 第四步：system prompt 工具规则瘦身

修改 `app/src/server/api/consultation-service.ts` 中 `buildNativeToolCallingMessages` 和 `buildJsonToolLoopMessages` 的 system prompt 拼接。本步骤的交付不是“重写一个更完整的 prompt”，而是删除旧 prompt 中未进入白名单的流程规则。

#### 9.4.1 旧实现需要识别的规则来源

执行方先按下面清单核对旧实现，避免漏删。当前 native prompt 和 JSON prompt 的文字不完全一样，但冗余来源一致。

1. 协议类：`native_tool_calling_loop_v1`、`model_json_tool_loop_v1`、只输出 JSON object、tool_use / finalResponse JSON 格式。
2. runtime 职责类：runtime 只负责校验和执行工具，模型自行判断是否调用 `retrieve_knowledge_base`、是否换 query、是否写 `update_content_calendar`。
3. 检索类：读取知识库/上传资料先 `retrieve_knowledge_base`；一次检索覆盖不全时换 query；用户列出多个维度时拆 query。
4. 日历前置类：营销日历、团队选题、图文/视频脚本这类任务若没有知识库或素材依据，先检索；调用 `update_content_calendar` 前判断依据足够。
5. 历史资产类：`strategySnapshot.contentCalendarDraft` 只是历史资产，不能当成本轮已完成。
6. 旧工作台链路类：内容日历到 Dify 的链路解释，以及“不再通过用户端图文工作台或视频工作台作为前置”。
7. 未暴露工具类：`generate_article_brief` / `generate_video_brief` 的使用条件。
8. 重复写入类：生成日历要调用 `update_content_calendar`；修改标题、摘要、日期、内容类型、选题角度也要调用 `update_content_calendar`。
9. 团队内容影响类：已生成团队内容后，修改日历要提醒影响并确认。
10. 其它工具类：`update_strategy_snapshot`、`search_benchmark_materials`、`read_history`、再次 `retrieve_knowledge_base` 的路由提示。
11. 失败诚实类：skipped、failed、guardrail rejected、工具不可用时不能声称已完成。
12. 输出边界类：最终回复只输出中文自然语言，不输出工具名、JSON、Markdown 表格或 debug payload。

#### 9.4.2 只保留这些 system prompt 规则

以下是产品确认的保留白名单。执行时可以为了 native / JSON 两种循环做最小措辞差异，但语义不得扩展。

1. `native_tool_calling_loop_v1`：工具必须通过 API tools 字段返回结构化 `tool_calls`，不要在正文里输出工具 JSON。
2. `model_json_tool_loop_v1`：只保留最小 JSON 工具循环协议，即 tool_use / final 两类动作和 finalResponse 输出要求。
3. 写入类工具仍要在信息足够后再调用。
4. 不要先写日历再补查依据。在调用 `update_content_calendar` 前，应先判断当前知识库和素材能力依据是否足够。
5. 当用户要求生成、补充或调整内容日历、营销日历、团队选题、本周图文/视频任务时，优先考虑调用 `update_content_calendar`，并传入可执行的 calendar 条目。
6. 如果当前日历已经生成过团队内容，修改前必须提醒用户后续团队内容可能需要重新生成，并确认是否继续。
7. 工具返回 skipped、failed、guardrail rejected 或未完成时，最终回复必须承认本轮未写入或未完成，不能声称已经更新。
8. 最终可见回复只输出给用户的中文自然语言，不要输出内部工具名、JSON、Markdown 表格或 debug payload。

建议最终形态是 8 条以内的短句。不要把 9.4.1 的旧规则清单重新改写成 prompt。

#### 9.4.3 必须删除的旧 prompt 内容

1. 删除 `generate_article_brief` / `generate_video_brief` 的所有 system prompt 说明。当前 LLM 不接收这两个工具，prompt 中不得出现“只在用户明确要求工作台 brief 时使用”这类句子。
2. 删除“不再通过用户端图文工作台或视频工作台作为前置”。这是旧架构迁移说明，不是当前模型决策规则。
3. 删除重复的“修改某一条日历标题、摘要、日期、内容类型或选题角度时，也必须通过 `update_content_calendar`”句子。这个含义已经被“生成、补充或调整内容日历”覆盖。
4. 删除 JSON prompt 中“observations 里尚未有 `retrieve_knowledge_base` 的 completed 结果”这类表述，改成依赖前序 `tool_result`。后续还要配合 9.5 删除 `observations.summary`。
5. 删除把同一件事拆成多句的检索-写入规则。例如“如果本轮 tool_result 尚未提供依据先检索”和“调用 update_content_calendar 前判断依据是否足够”只能保留后一种更短、更通用的表达。
6. 删除旧 prompt 里对 `contentCalendarDraft` 的长解释。历史日历是否可复用应通过用户意图、strategySnapshot 字段和工具写入逻辑判断，不应作为每轮 system prompt 的长规则。
7. 删除视频画面素材约束的全局长句。如果这条仍需要，应移动到 `update_content_calendar` 的 tool schema 或内容生成专项 prompt，而不是作为所有咨询轮次的全局规则。
8. 删除不属于当前可用工具集的路由说明。只有当工具真实出现在当前 `availableTools` / API tools 中，才允许出现对应的最小使用说明。

#### 9.4.4 不允许转移到 JSON 状态消息

删掉的规则不能换个地方塞进 `tool_loop_state`。尤其禁止：

- 用 `decisionRules` 保存“先检索再写日历”“只有依据足够才写日历”“什么时候 update_content_calendar”。
- 用 `observations[].summary` 总结工具业务结果，再让模型根据 summary 决策。工具业务结果应来自前序 `tool_result`。
- 用 `tool_loop_state` 解释旧工作台链路或未暴露工具。

验收标准：system prompt 中只剩 9.4.2 白名单规则；`tool_loop_state` 中没有 `decisionRules`，也没有 `observations.summary` 或等价的业务结果摘要。

### 9.5 第五步：JSON tool loop 状态消息瘦身

修改 `app/src/server/api/consultation-runtime/runtime.ts` 中构造 `tool_loop_state` 的逻辑。

必须删除：

- `observations[].summary`
- `observations[].payload`，如果未来被加入也禁止保留
- `observations[].knowledgeMatches`，如果未来被加入也禁止保留
- `decisionRules` 整个数组

推荐目标结构：

```json
{
  "type": "tool_loop_state",
  "turn": 2,
  "maxTurns": 8,
  "availableToolNames": ["update_content_calendar"],
  "completedToolNames": ["retrieve_knowledge_base"],
  "failedToolNames": [],
  "skippedToolNames": [],
  "writeToolsAlreadyUsed": []
}
```

状态消息只回答“当前还能调用什么、哪些工具已经完成或失败”，不回答“工具具体返回了什么、模型下一步应该怎么做”。工具具体返回内容只读前序 `tool_result`。

### 9.6 第六步：预算硬执行

将 `buildContextBudgetReport` 从“统计”升级为：

- bucket selector
- clipper
- omit policy
- debug report

不再把 budget report 给主模型。

## 10. 风险与回滚

### 10.1 风险

- 移除 contextInjection 后，某些依赖旧字段的 prompt 测试可能失败。
- RAG selected/current 分层如果过严，可能导致模型引用不到历史依据。
- 日历规则瘦身后，模型可能在少数情况下少调用写入工具。

### 10.2 回滚策略

- 保留旧 payload builder behind feature flag。
- 新增 `contextPackMode = slim_v2 | legacy_v1`。
- 出现明显回退时可切回 legacy_v1。
