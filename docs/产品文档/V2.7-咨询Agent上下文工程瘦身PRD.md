# V2.7 咨询 Agent 上下文工程瘦身 PRD

> 状态：评审稿  
> 创建时间：2026-05-21  
> 来源：咨询 Agent 上下文工程对照评审、Claude Code reference 对照、当前代码事实核对  
> 关联页面：`docs/架构规范/咨询Agent上下文工程对照评审.html`

## 1. 背景

当前咨询 Agent 的 native tool calling 链路已经基本打通，但真实聊天体验仍有“怪”的感觉：模型能调用工具，也能写入日历或策略资产，但回复容易显得流程化、过度解释内部机制，或者被过多上下文牵引。

本轮评审判断：问题优先不是工具调用本身，而是上下文组装方式过重、重复、边界不清。当前 system prompt 与 user JSON 同时注入了大量规则、状态和调试信息，导致模型需要在多个权威来源之间自行判断。

## 2. 当前代码事实

### 2.1 当前 system prompt 注入内容

native tool calling 路径中，system prompt 依次拼入：

- agent prompt
- soul
- 专家容器
- skill catalog
- active skills
- skill references
- business tools
- ContextInjector 说明
- native tool loop 规则
- 日历规则
- RAG 规则
- guardrail 规则

### 2.2 当前 user JSON 注入内容

user JSON 当前包含：

- merchant
- userMessage
- round
- contextInjection
- strategySnapshot
- knowledgeMatches
- toolResults
- skillDisclosure

其中 `contextInjection` 内部又包含 `targetExpert`、`mentionRouting`、`sessionContext`、`expertTraffic`、`budget` 等字段。`sessionContext` 内部又重复携带 `strategySnapshot`、`strategyMarkdown`、`toolResults` 等信息。

### 2.3 tool result 已经会回给 LLM

native tool calling 路径中，工具执行结果会以 `role: "tool"` 消息回填给模型。工具解析失败、不可用、guardrail 拒写等失败结果，也会作为 tool result 回填。

因此，user JSON 中再放 `toolResults` 属于重复注入。工具结果的权威来源应是 tool result message，而不是 contextInjection 或 user JSON 的重复摘要。

### 2.4 RAG 当前返回数量

当前默认检索配置：

- consultation agent `retrievalTopK = 5`
- knowledge runtime `retrievalTopK = 5`

每次检索会先用 `topK * 2` 做 keyword/vector/direct scan，再 merge 成最多 `topK` 个结果。多轮检索会累积 knowledgeMatches，当前最多保留 24 个 unique chunk。

这意味着 `knowledgeMatches` 如果不区分“本轮命中”和“历史命中”，会让模型把旧依据误当成本轮依据。

## 3. 核心问题

### 3.1 ContextInjector 概念边界不清

从产品语义上看，所有塞给 LLM 的内容都属于上下文工程，包括 system prompt、tools、RAG、skills、tool results、strategySnapshot、user JSON。

但当前有一个名为 `contextInjection` 的 user JSON 大对象，好像它才是“上下文注入器”。这会导致两个问题：

- 概念上误导：它不是整个上下文注入器，只是会话状态包。
- 实现上过重：它把策略资产、工具结果、budget、expertTraffic 等全部打包给 LLM。

### 3.2 策略资产重复

`strategySnapshot` 已经作为 user JSON 顶层字段存在，`contextInjection.sessionContext.strategySnapshot` 再放一次是重复。

策略资产应只有一个主入口，避免模型不清楚哪个才是当前权威状态。

### 3.3 工具结果重复

tool result 已经通过 tool message 回填给模型。user JSON 顶层 `toolResults` 和 `contextInjection.sessionContext.toolResults` 都应移除。

需要保留的是“工具结果诚实性规则”，不是重复的工具结果摘要。

### 3.4 budget 给主模型没有价值

budget 报告对开发和调试有用，但对主 LLM 没有明确业务价值。模型看到 budget 不会更会聊天，反而可能被系统工程信息干扰。

budget 应作为 runtime 内部硬预算和 debug 信息，不进入主模型上下文。

### 3.5 expertTraffic 暂无主链路价值

如果当前不是强多专家并发协作，`expertTraffic` 每轮注入会增加理解成本。专家交接信息可以保留，但应缩小为 `expertRouting` 或必要的 handoff 摘要，而不是整包 `sharedConsultationState / ExpertTurnNote`。

### 3.6 skillDisclosure 更像调试信息

主模型已经看到：

- skill catalog
- active skills
- skill references

`skillDisclosure` 只是候选 skill / active skill 的结构化命中记录，包括 score、triggerReasons、referenceTitles 等。它更适合前端调试面板和 runtimeSnapshot，不应塞给主模型。

### 3.7 日历规则过于流程化

当前 prompt 中对“什么时候写日历、什么时候改标题”的说明过细，容易把模型变成流程执行器。

用户期望是：LLM 自己判断是否足够了解用户；足够时可以提醒用户“现在可以写营销日历”。用户明确要求改标题时就改标题。

必须保留的强规则是：如果营销日历已经生成过团队内容，修改前必须提醒用户后续团队内容可能需要重新生成，并确认是否继续。

## 4. 产品目标

### 4.1 目标

1. 让主 LLM 只看到本轮必要上下文，减少重复和调试信息。
2. 将 `ContextInjector` 从“给 LLM 看的大对象”改成 runtime 内部的上下文选择机制。
3. 保留工具调用能力，但减少业务规则对自然聊天的干扰。
4. 明确 RAG chunks 的来源、轮次和当前相关性。
5. 保留专家切换能力，但不引入无必要的共享事实层。

### 4.2 非目标

1. 本 PRD 不直接更换模型 provider。
2. 本 PRD 不重写所有 skill 内容。
3. 本 PRD 不改变 Dify、video-worker、内容生成链路的数据合同。
4. 本 PRD 不删除 runtimeSnapshot、debug 面板或事件日志中的调试信息。

## 5. 新设计原则

### 5.1 ContextInjector 改为内部 ContextPackSelector

不再把 `contextInjection` 作为 user JSON 对象传给主 LLM。

新增或重命名内部概念：

- `ContextAssembler`：负责拼装所有候选上下文。
- `ContextPackSelector`：按本轮 intent 选择哪些上下文进入 LLM。
- `ContextBudgetEnforcer`：执行硬预算、裁剪和 omit，不只是报告。

LLM 最终只看到选择后的少量上下文，不看到“上下文注入器的工作报告”。

### 5.2 保留 expertRouting，而不是共享事实层

专家切换时，真正需要告诉 LLM 的是：

```json
{
  "expertRouting": {
    "activeAgentKey": "...",
    "activeDisplayName": "...",
    "roleDescription": "...",
    "knowledgeSetIds": ["..."],
    "knowledgeDocumentIds": ["..."],
    "rawMention": "@营销专家"
  }
}
```

换专家时，本质上切换：

- 专家自己的 system prompt
- soul.md
- skill catalog / active skills
- knowledge boundary

不需要额外维护一个“共享事实层”大对象。

### 5.3 user JSON 只保留必要字段

目标 user JSON：

```json
{
  "merchant": {
    "name": "...",
    "industry": "...",
    "serviceItems": [],
    "defaultCta": []
  },
  "userMessage": "...",
  "round": 3,
  "expertRouting": {},
  "strategySnapshot": {},
  "currentKnowledgeMatches": []
}
```

应移除：

- `contextInjection`
- `toolResults`
- `skillDisclosure`
- `budget`
- `expertTraffic`

### 5.4 toolResults 只保留 tool message 权威来源

native tool calling 中，工具结果以 `role: "tool"` 回填。JSON tool loop 中，工具结果以 tool_result 内容回填。主模型应依赖这些消息，不再读取 user JSON 的重复摘要。

保留一条稳定协议：

> 工具结果诚实性规则：如果 tool result 是 skipped、failed、guardrail rejected 或未完成，最终回复不能声称已经写入或执行成功。

该规则归入 native tool loop 协议层。

### 5.5 RAG 只放当前相关 evidence

`knowledgeMatches` 改为 `currentKnowledgeMatches` 或 `selectedKnowledgeMatches`。

每条 chunk 必须带最少元信息：

```json
{
  "documentTitle": "...",
  "chunkId": "...",
  "score": 0.82,
  "content": "...",
  "query": "...",
  "toolCallId": "...",
  "turn": 3,
  "freshness": "current_turn"
}
```

规则：

- 单次 retrieve 默认最多 5 个 chunk。
- 多轮 retrieve 可以存在，但进入主 LLM 的 chunks 必须经过选择。
- 历史 chunks 不默认进入主 LLM，除非被本轮 intent 选中。
- 调试面板可以显示全部历史命中，主模型只看 selected evidence。

### 5.6 日历规则改成判断原则

保留为更自然的判断原则：

> 当你判断已经足够理解用户、项目、素材能力和内容目标时，可以告诉用户：现在信息足够，可以开始写营销日历。若用户明确要求生成或修改日历，则按用户意图执行。

强制保留：

> 如果当前日历已经生成过团队内容，修改前必须提醒用户：后续团队内容可能需要重新生成，并确认是否继续。

不再长期携带过细的“什么时候写日历 / 什么时候改标题”流程说明。

### 5.7 budget 只做内部硬预算

budget 不进入主 LLM。

需要改成内部真实控制：

- 按 bucket 计算字符或 token。
- 超出预算时裁剪、摘要或 omit。
- 输出 debug 信息到 runtimeSnapshot / 开发面板。
- 记录哪些字段被省略，便于排查。

## 8. 验收标准

### 8.1 上下文结构验收

- user JSON 不再包含 `contextInjection`。
- user JSON 不再包含 `toolResults`。
- user JSON 不再包含 `skillDisclosure`。
- user JSON 不再包含 `budget`。
- user JSON 不再包含 `expertTraffic`。
- user JSON 保留 `strategySnapshot` 作为唯一策略资产入口。
- 专家切换信息以 `expertRouting` 形式保留。

### 8.2 工具结果验收

- native tool calling 下，completed/skipped/failed/rejected tool result 都能回到模型消息流。
- 当工具 skipped/failed/rejected 时，最终回复不能声称已经执行成功。
- 不依赖 user JSON 的 `toolResults` 也能完成最终回复。

### 8.3 RAG 验收

- 单次 retrieve 默认最多进入 5 个 selected chunks。
- 多轮检索后，主模型只看到 current/selected chunks，不默认看到全部历史 chunks。
- 每条 selected chunk 带 query/toolCallId/turn/freshness。
- 调试面板仍能看到完整历史命中。

### 8.4 日历行为验收

- 用户明确要求生成日历时，模型可在信息足够后调用 `update_content_calendar`。
- 用户明确要求改标题时，模型直接修改对应日历项，不需要额外流程解释。
- 如果日历已经生成团队内容，修改前必须提醒影响并询问确认。
- 轻问答不应长期携带完整日历规则。

### 8.5 体验验收

- 简单聊天不再出现明显内部机制说明。
- 模型不再向用户暴露 skillDisclosure、budget、contextInjection 等内部词。
- 回复更像顾问对话，而不是流程日志。

## 9. 实施建议

### 9.1 第一步：移除明显重复 user JSON

优先从 native tool calling payload 中移除：

- `contextInjection`
- `toolResults`
- `skillDisclosure`

保留：

- `merchant`
- `userMessage`
- `round`
- `strategySnapshot`
- `knowledgeMatches` 暂时重命名或包成 `currentKnowledgeMatches`

### 9.2 第二步：重写 ContextInjector

将 `buildConsultationContextInjection` 改为内部选择器，不再返回给主 LLM 的大对象。

新增：

- `buildExpertRoutingContext`
- `buildSelectedTurnContext`
- `buildSelectedKnowledgeMatches`
- `buildContextOmissionDebug`

### 9.3 第三步：RAG current/history 分层

在 retrieve tool result 中记录 query、toolCallId、turn。

state 内部可保留全部 `knowledgeMatches`，但 build LLM payload 时只输出 selected/current。

### 9.4 第四步：日历规则瘦身

把 system prompt 中多条日历硬规则合并成：

- 信息足够时可以写日历的判断原则。
- 用户明确修改时按意图修改。
- 已生成团队内容时必须提醒并确认。

### 9.5 第五步：预算硬执行

将 `buildContextBudgetReport` 从“统计”升级为：

- bucket selector
- clipper
- omit policy
- debug report

不再把 budget report 给主模型。

## 10. 风险与回滚

### 10.1 风险

- 移除 contextInjection 后，某些依赖旧字段的 prompt 测试可能失败。
- RAG selected/current 分层如果过严，可能导致模型引用不到历史依据。
- 日历规则瘦身后，模型可能在少数情况下少调用写入工具。

### 10.2 回滚策略

- 保留旧 payload builder behind feature flag。
- 新增 `contextPackMode = slim_v2 | legacy_v1`。
- 出现明显回退时可切回 legacy_v1。

## 11. 待确认问题

1. `strategyMarkdown` 是否完全退出主 LLM，还是在用户明确要求改策略文档时按需注入？
2. `expertTraffic / ExpertTurnNote` 是否只在圆桌多 Agent 场景保留？
3. `skill catalog` 是否后续也要做 top candidates，而不是全量候选？
4. `knowledgeMatches` 的 selected 策略是否由规则筛选，还是让轻量模型/LLM 做 evidence selection？
5. 前端调试面板是否需要单独展示 omittedContext 和 prompt budget？
