# 2026-04-28 项目收口建议文档

## 1. 总建议

现在不要继续盲目加功能。

这个项目已经证明方向可行，但还没到“可以大范围承诺生产闭环”的阶段。下一步应该先做收口：

```text
冻结当前成果
-> 跑最小验证
-> 明确 P0/P1/P2/P3 边界
-> 再继续 productionConfig 和真实出片 smoke
```

一句话：

先把“能验收的链路”做硬，再做“更好看的交互”。

## 2. 立刻要做的 6 件事

### 2.1 先冻结当前 dirty master

当前主工作区已有较多未提交改动。建议立即选择一种方式冻结：

1. 建一个 `codex/` 分支并提交当前成果。
2. 或导出 patch。
3. 或明确标记哪些文件属于本轮、哪些文件暂不接收。

推荐：

```text
创建 codex/openstoryline-scenes-runtime-freeze
提交当前 app scenes + worker readiness + dockerignore 相关改动
```

不建议继续在当前 dirty master 上直接叠 P3。

### 2.2 把当前能力分成 P0/P1/P2/P3

建议固定口径：

| 阶段 | 含义 | 当前状态 |
| --- | --- | --- |
| P0 | Docker-first OpenStoryline / FireRed 运行面 | 基本成立，但当前未提交改动需复验 |
| P1 | `productionConfig` 到 worker / FireRed 的合同映射 | 必须继续补齐 |
| P2 | 平台 UI 配置配音、BGM、字幕、原声 | 只能在 P1 稳定后承诺 |
| P3 | 二次修改、复用 session/context、重跑任务 | 已有设计文档，不能先做假按钮 |

对外表达必须保守：

```text
当前具备真实引擎接入骨架和 Docker 运行面。
下一步是补齐生产配置合同和真实出片验证。
```

不要说：

```text
已经完整支持文字配音、BGM 和二次修改。
```

### 2.3 先补 P1 合同，不要先扩 P3 UI

P1 的核心不是界面，而是这条链路：

```text
app productionConfig
-> video_edit_jobs.input_payload.productionConfig
-> worker ProductionDirective
-> openstoryline-engine RunRequest
-> FireRed production_config + service_config
-> result_payload.openstoryline
```

建议 P1 验收条件：

- voiceover 配置能进入 FireRed payload。
- BGM 配置能进入 FireRed payload。
- subtitles/render/originalAudio 有默认值和明确字段。
- 成功结果能记录 `session_id`、`production_config_used`、`selected_bgm`、`voiceover`。
- 失败能明确归类为合同问题、资源问题、provider 问题或执行问题。

### 2.4 做一次真实出片 smoke

真实 smoke 的标准不要太大。

建议只验一条最小任务：

```text
1 个草稿
1 个锁定脚本
1-2 个可下载 COS 素材
voiceover.enabled=true
bgm.enabled=true
final_video 输出
```

验收必须看到：

- worker claim 到任务。
- FireRed 创建 session。
- `final.mp4` 存在。
- `ffprobe` 能看到视频流，若开配音/BGM 还要看到音频流。
- COS 有最终视频对象。
- `video_edit_jobs.result_payload` 有引擎元数据。
- UI 能看到结果或明确失败原因。

### 2.5 清理文档真相源

现在文档数量已经偏多。建议不要再新增大量探索稿。

建议保留三类真相源：

- 产品当前真相：`docs/产品文档/V2.1-*`
- 架构当前真相：`docs/架构规范/2026-04-27-video-job-payload-contract.md`、`2026-04-28-openstoryline-worker-docker-first-result.md`、后续 P1 文档
- 当前任务状态：`docs/current-task.md`

其他 progress/handoff 作为证据，不要默认塞给 M 同学或新 Agent。

### 2.6 给 M 同学的上下文要短

给 M 同学的交接建议只包含：

1. 当前目标。
2. 当前能力边界。
3. 要看哪些文件。
4. 哪些不要碰。
5. 最小验证命令。
6. 未完成风险。

不要把所有历史探索、旧部署记录、长计划文件一次性丢过去。

## 3. 工程策略建议

### 3.1 保留 worker 隔离

坚持这条链路：

```text
app
-> video_edit_jobs
-> video-worker
-> openstoryline-engine
-> firered-openstoryline
```

不要改成：

```text
app
-> firered-openstoryline
```

理由：

- 主应用不适合承担长任务执行。
- 密钥、资源、模型、临时目录应隔离在 worker 侧。
- COS 上传、失败重试、清理和状态回写属于 worker 责任。

### 3.2 保留 skeleton adapter

`skeleton` 不是废代码。

它的价值是：

- 本地开发不依赖真实 FireRed。
- CI 能测合同。
- FireRed 资源或密钥缺失时能验证上游链路。

建议：

- skeleton 永远作为默认测试 adapter。
- fire_red 作为真实生产 adapter。
- 两者共享同一份 `RunRequest` 合同。

### 3.3 不要删除当前 vendored FireRed

现在不要因为“看起来像外部项目”就删 `workers/video-worker/openstoryline/firered`。

已核对：

- GitHub 上游源码约 1.16 MB。
- 当前 vendored 版本约 1.15 MB。
- 主要风险不是源码体积，而是 runtime 缓存和资源进入 Git/Docker context。

正确动作：

- 保留源码。
- 严格 `.dockerignore`。
- 严格 `.gitignore`。
- 不提交 `.venv`、`.downloads`、`resource`、`outputs`、`.storyline` 运行状态。

### 3.4 能力承诺必须过三道门

以后任何“已经支持 X”的说法，必须同时满足：

1. 合同字段已经从 app 到 worker 到 engine。
2. 自动化测试覆盖关键路径。
3. 至少一次真实或接近真实的 smoke 验证。

如果只满足第一项，只能说“字段已接入”。

如果只满足前两项，只能说“合同和测试通过”。

只有三项都满足，才能说“能力可用”。

## 4. 产品策略建议

### 4.1 当前 MVP 不要追求完整剪辑自由度

用户真正要的是：

```text
从咨询和门店素材出一条能获客的视频
```

不是：

```text
做一个完整视频剪辑软件
```

所以近期应优先：

- 脚本结构化。
- 每个镜头可上传素材。
- 自动生成可预览视频。
- 失败原因可理解。
- 能修一句话、换素材、重跑任务。

暂缓：

- 复杂时间线编辑器。
- 多轨道精剪。
- 大量可调参数。
- 未稳定前的高级二次编辑 UI。

### 4.2 镜头表是好方向

当前未提交的 `productionScenes` 方向值得保留。

原因：

- 它把“文案”变成“可拍摄任务”。
- 它让商家知道每段视频要补什么素材。
- 它能把素材上传和 worker input assets 对齐。
- 它为后续 P3 二次修改提供最小上下文单元。

但要注意：

- 镜头上传成功不等于 worker 已能用。
- 还要验 COS 下载、排序、绑定、payload、出片。

### 4.3 修订入口要分两类

不要只做一个“重新生成”按钮。

建议分成：

| 类型 | 用户意图 | 系统动作 |
| --- | --- | --- |
| 文案修订 | 改目标人群、钩子、卖点、CTA | 重新生成脚本候选 |
| 制作修订 | 换音乐、配音、字幕、节奏、素材 | 创建新 video job |

这能避免 Retry 和 Revision 混在一起。

## 5. 协作策略建议

### 5.1 中大型任务继续用 worktree

触发条件：

- 改动超过 1 个文件。
- app 和 worker 都会动。
- 涉及合同、迁移、发布链路。
- 会持续超过一轮会话。

默认流程：

```text
冻结当前基线
-> 创建 worktree
-> 文件边界写清楚
-> 分支内完成验证
-> 写 progress/handoff
-> 待验收，不默认 merge
```

### 5.2 Review findings 要逐项闭环

好的做法已经出现了：

- 先指出 finding。
- 再修复。
- 再写复验记录。
- 最后才进入待合并。

建议保留这个节奏。

不要因为 lint/build 过了就忽略业务合同问题。

### 5.3 文件独占要写进任务说明

app 和 worker 并行时，必须明确：

- 谁改 `app/src/server/api/video-job-payload.ts`
- 谁改 `workers/video-worker/worker/app/directive.py`
- 谁改 `docker-compose.yml`
- 谁改架构文档

不要靠口头记忆。

### 5.4 真实账号和发布链路保持保守

涉及真实发布时必须先确认：

- 目标商家
- 目标门店
- 目标平台
- 目标账号
- 测试环境还是正式环境

当前项目还没到自动发布阶段，不要提前接真实发布动作。

## 6. 建议的下一阶段计划

### 阶段 A：冻结和验收当前 dirty 改动

目标：

- 当前 scenes / upload / readiness 改动可回退、可验证、可交接。

验收：

- app lint/typecheck/build 通过。
- Agent 测试通过。
- worker 测试通过。
- Compose config 通过。
- 文档记录当前仍未真实出片。

### 阶段 B：补齐 P1 productionConfig 合同

目标：

- 配音、BGM、字幕、渲染参数从 app 传到 FireRed。

验收：

- app payload 有 `productionConfig`。
- worker directive 标准化。
- engine adapter 转成 FireRed `production_config/service_config`。
- FireRed prompt 明确不改锁定脚本。

### 阶段 C：真实出片 smoke

目标：

- 证明真实链路产出 `final.mp4`。

验收：

- `final.mp4` 写入 COS。
- job 状态成功。
- result payload 可用于 UI 预览和 P3 修订。

### 阶段 D：再做 P3 修订

目标：

- 在真实产物和元数据存在后，再接二次修改。

验收：

- 文案修订和制作修订分流。
- Revision 创建新 job，不覆盖原结果。
- Retry 只处理临时失败。

## 7. 不建议做的事

近期不建议：

- 继续扩大 UI，而不补 P1 合同。
- 直接让 app 调 FireRed。
- 删除 vendored FireRed。
- 把本地 FireRed 运行目录复制进仓库。
- 把 `docs/superpowers/plans` 长计划当作给 M 同学的默认上下文。
- 在 dirty master 上继续跨 app/worker 大改。
- 未真实 smoke 就承诺“已支持配音和音乐”。

## 8. 最终建议

项目现在不是缺想法，而是缺收口纪律。

最优路径是：

```text
先冻结当前成果
再补 P1 合同
再做真实 smoke
最后做 P3 修订体验
```

只要坚持这个顺序，当前项目可以稳步从“可运行 staging”走到“可验收的视频生产链路”。

如果顺序反过来，先做 UI 和宣传口径，后面很容易再次出现“按钮能点，但后端没有真实闭环”的问题。
