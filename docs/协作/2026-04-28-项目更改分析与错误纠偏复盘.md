# 2026-04-28 项目更改分析与错误纠偏复盘

## 1. 结论

本项目已经从早期探索推进到 `staging 可运行 + V2.1 协作开发 + 视频生产链路接入` 阶段。

当前最重要的变化不是某个页面或接口，而是主链路已经收敛成：

```text
咨询 / 增长策略
-> 脚本候选与素材确认
-> video_edit_jobs 作业合同
-> video-worker 执行
-> OpenStoryline / FireRed 引擎
-> COS 产物回写
-> 预览、审核、修订
```

同时也出现了几类典型错误：

1. 过早把“骨架可跑”说成“完整闭环”。
2. 曾把本地 4GB FireRed 运行目录和 GitHub 上游源码混为一谈。
3. 一度让合同边界不够硬，导致 app 和 worker 都可能接收不可执行输入。
4. 多文件改动在主工作区持续累积，冻结和交接节奏仍不够稳定。
5. 文档数量增长很快，但真相源和验收口径还需要继续压缩。

已经做出的纠偏总体方向是正确的：合同先行、worker 隔离、Docker-first、fail closed、review findings 逐项复验、密钥和运行缓存隔离。

## 5. 错误举动与已做改正

### 5.1 把骨架可跑误说成完整闭环

错误：

- OpenStoryline skeleton、Docker Compose、FireRed API 存在后，容易被表述成“视频生产完整支持”。
- 实际当时只是 P0 运行面成立，`productionConfig -> service_config / TTS / BGM` 仍未完整闭环。

改正：

- 在 `2026-04-28-openstoryline-worker-docker-first-result.md` 明确改口：
  - P0 可以保留。
  - P1 必须继续。
  - P2/P3 不要提前做假闭环。

剩余风险：

- 当前未提交代码已经继续推进 scenes 和上传 UI，但真实出片 smoke 仍依赖 LLM/VLM/TTS/COS/Supabase 密钥和素材。

### 5.2 混淆本地 4GB 目录和 GitHub 上游源码

错误：

- 一度把 `D:\codex work\FireRed-OpenStoryline` 的体积当成 OpenStoryline 源码体积。
- 这会导致两种错误决策：要么误删必要源码，要么把 `.venv/resource/.downloads/outputs` 等运行垃圾带进项目。

改正：

- 对比 GitHub `FireRedTeam/FireRed-OpenStoryline` 后确认上游源码约 1.16 MB。
- 当前 vendored 版本约 1.15 MB，不是大包袱。
- 增加 `.dockerignore`，把 runtime assets/cache 排除在 build context 外。

剩余风险：

- 如果后续有人从本地运行目录复制文件，仍可能把模型、密钥、输出带进仓库。

### 5.3 主应用和 worker 的职责边界差点混掉

错误：

- 讨论中曾出现让主应用直接调用 FireRed / OpenStoryline 的倾向。
- 这会让主应用承担长任务执行、失败重试、COS 上传、资源清理、密钥隔离等不该承担的职责。

改正：

- 收敛为 Docker-first worker 链路：

```text
Next.js API
-> video_edit_jobs
-> video-worker
-> openstoryline-engine
-> firered-openstoryline
-> COS
```

剩余风险：

- 后续如果为了快速演示绕过 worker，会重新制造假闭环。

### 5.4 合同校验起初不够硬

错误：

- app 侧曾允许非 COS 输入资产进入 worker payload。
- app 侧曾允许“确认了素材引用但没有可下载素材”的作业创建。
- worker 侧曾上传未请求输出。
- worker 侧对 malformed directive、locked script、desired outputs、input assets 的校验不够完整。

改正：

- app 前置拒绝不可执行素材。
- worker 前置拒绝 malformed payload。
- worker 上传按 `desired_outputs` 过滤。
- 失败原因区分 `failed_manual` 和 `failed_retryable`。
- 相关 review finding 均有 progress 记录和复验。

剩余风险：

- 真实素材链路还要继续覆盖上传、排序、COS 可下载性、worker 下载和最终产物回写。

### 5.5 缺少依赖和健康检查导致“看起来启动了”

错误：

- 早期容器运行发现缺少 `ffmpeg`。
- FireRed Web/MCP 子进程如果部分退出，容器可能仍被误认为可用。
- `openstoryline-engine /health` 只能说明服务活着，不能说明 FireRed adapter 真正 ready。

改正：

- Dockerfile 补运行依赖。
- FireRed 新增 `/health`。
- `openstoryline-engine` 新增 `/ready`。
- Compose 使用 `/ready`，并让 FireRed 容器监督两个子进程。

剩余风险：

- `/ready` 仍不等于真实出片成功，必须补真实 smoke。

### 5.6 密钥和配置曾有泄露风险

错误：

- 外部 FireRed 本地配置曾发现真实 provider key，不能原样带入仓库。
- vendor 外部项目时，如果不清理配置，容易把密钥提交。

改正：

- FireRed 配置改为 env placeholder。
- 文档多次强调不能复制本地真实配置。
- 密钥扫描没有发现明显 `sk-...` 或长明文 key。

剩余风险：

- `.env`、真实 provider 配置、TTS 配置仍必须保持本地或服务器私密，不进入 Git。

### 5.7 工作区冻结节奏仍不稳定

错误：

- 当前主工作区再次累积 19 个 modified 文件和多个 untracked 文件。
- 这违背了本项目“中大型改动优先 worktree + freeze + handoff”的理想节奏。

改正：

- 之前曾通过 app/worker worktree 拆分和 progress 复验降低冲突。
- 当前也已通过 `docs/current-task.md` 沉淀上下文。

剩余风险：

- 如果继续在 dirty master 上叠功能，会增加回滚、验收、交接成本。

## 8. 本轮复盘判断

项目方向是对的，但节奏要收紧。

最该坚持的是：

- 合同先行，不靠口头约定。
- worker 隔离，不让主应用背长任务。
- 真实 smoke 之前不承诺生产能力。
- dirty worktree 先冻结，再继续下一阶段。

最该避免的是：

- 继续扩 UI 形成假闭环。
- 把本地运行目录当源码。
- 把历史探索稿当当前真相源。
- 把“测试通过了一部分”当成“业务闭环通过”。
