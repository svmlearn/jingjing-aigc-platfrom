## 1. Worktree 优先隔离开发 = Context Firewall 执行层

### 1.1 当前判断

本项目高频使用 `git worktree`，其本质已经接近参考项目“Sub-Agents × Context Firewall”的执行层设计。

区别只是：

- 参考项目把它命名为 sub-agent 架构；
- 本项目目前是由用户和主 Agent 手动完成任务转交；
- 实际效果都是把“实现上下文”和“主线判断上下文”隔离开。

因此后续可以把本项目的 worktree 规则正式升级为：

> 中大型任务默认进入独立 worktree，并推荐由新的实现 Agent 实例承接。

worktree 规则不应被 sub-agent 取代，而应与 sub-agent 结合：

1. worktree 负责物理隔离代码改动；
2. sub-agent 负责上下文隔离和任务执行；
3. Controller 负责把任务书直接发给 sub-agent；
4. 用户不再需要长期扮演“复制提示词到分支 Agent、再复制结果回主 Agent”的信息搬运角色。

这里的“实现 Agent”不要求必须是系统内置 subagent 工具。只要满足以下条件，就算符合本项目的执行层模式：

1. 使用独立 worktree；
2. 使用一份明确的任务指令；
3. 实现 Agent 不直接污染主目录；
4. 完成后交付 commit / diff / 验证结果；
5. 由主 Agent 或 reviewer 再做审查。

### 1.2 对应角色：implementer

`implementer` 是执行层编码 Agent。

职责：

1. 只在指定 worktree / branch 内工作；
2. 只处理任务书中授权的范围；
3. 根据 PRD、架构文档、handoff 和主 Agent 指令完成实现；
4. 自行运行最小必要验证；
5. 输出清晰的完成说明、改动文件、验证结果和剩余风险；
6. 不默认 push；
7. 不默认 merge；
8. 不自行扩大任务边界。

推荐交付物：

1. 最终 commit；
2. `git status` 干净或明确说明未提交文件；
3. 关键验证命令及结论；
4. 如任务需要，补充 `docs/handoff/` 或 `docs/progress/`；
5. 给 reviewer 的简短审查入口说明。

### 1.3 主 Agent 对 implementer 的指令方式

本项目已经多次采用过这种方式：

1. 主 Agent 先理解任务和真相源；
2. 主 Agent 生成一段完整指令；
3. 用户把这段指令粘贴给 worktree 中的新 Agent；
4. implementer 在分支里完成任务；
5. 用户把 implementer 的结果再粘贴回主 Agent；
6. 主 Agent 审查该 worktree / commit。

这个模式应该保留，但应从“人工复制粘贴”升级为“Controller 调度 sub-agent”。

后续可在 AGENTS 或 skill 中补一个“实现 Agent 任务书模板”，至少包含：

1. 任务目标；
2. worktree 路径；
3. branch 名称；
4. 必读文档；
5. 可改文件范围；
6. 禁止触碰范围；
7. 验证命令；
8. 交付格式；
9. 是否允许 push / merge。

Codex 落地后，Controller 可以直接 spawn `implementer`，并把上述任务书作为初始消息传入。`implementer` 的长期职责和约束写在 `.codex/agents/implementer.toml`，单次任务的目标、文件边界和验证命令由 Controller 在本次派发消息中提供。

## 2. Code-reviewer 两阶段审查

### 2.1 当前判断

本项目已经反复出现“一个 Agent 实现，另一个 Agent 审查”的工作方式。

后续应正式把它定义为 `code-reviewer` 角色，而不是只靠临时聊天判断。

`code-reviewer` 不负责继续堆功能，主要负责判断：

1. 任务是否真的按要求完成；
2. 实现是否符合 PRD / 架构 / handoff；
3. 代码质量是否足够进入主线；
4. 验证证据是否可信；
5. 是否可以进入合并决策。

### 2.2 两阶段审查

第一阶段：Spec 合规审查

检查重点：

1. 是否完成任务书里的目标；
2. 是否偏离 PRD 或架构文档；
3. 是否改了不该改的文件；
4. 是否把探索性假设写成已实现事实；
5. 是否遗漏 handoff / progress / 验证记录；
6. 是否存在账号、环境、发布目标等高风险误用。

第二阶段：代码质量审查

检查重点：

1. 是否有明显 bug 或回归；
2. 是否破坏现有数据结构、接口契约或状态机；
3. 是否有不必要的大范围重构；
4. 是否有 mock / fallback / skeleton 假成功；
5. 是否通过必要验证；
6. 是否存在合并前必须修复的问题。

### 2.3 reviewer 输出格式

`code-reviewer` 的输出应优先给结论，不写泛泛总结。

推荐格式：

1. 阻塞问题：必须修复后才能合并；
2. 非阻塞问题：可以后续处理，但需要记录；
3. 验证结果：已跑、未跑、无法跑；
4. 合并建议：可合并 / 修复后再审 / 暂不合并；
5. 如需返工，直接生成给 implementer 的下一轮修复指令。

### 2.4 与主 Agent 的关系

`code-reviewer` 可以由主 Agent 执行，也可以由新的独立 Agent 实例执行。

推荐规则：

1. 小改动：主 Agent 可直接 review；
2. 中大型 worktree：建议由主 Agent 进入 review 模式；
3. 高风险任务：建议再开一个独立 reviewer Agent；
4. 如果 implementer 已经做了大量上下文判断，reviewer 应尽量使用独立上下文，避免被实现过程锚定。

## 3. Sub-Agent 调度规则草案

本节用于后续合并进根目录 `AGENTS.md`。

当前先记录“可以派发哪些 Agent、何时派发、如何隔离”。第一版 `.codex/agents/*.toml` 已落地 `implementer` 和 `code-reviewer`。

### 3.1 可派发的 Sub-Agent

| Agent | 参考项目文件 | Codex 拟定文件 | 参考 Skill / 能力 | 职责 | 当前优先级 |
|-------|--------------|----------------|-------------------|------|------------|
| `implementer` | `agents/implementer.md` | `.codex/agents/implementer.toml` | `dev-builder` / Codex `worker` | 编码实现 + 编译验证 + 自检 | 第一优先级 |
| `code-reviewer` | `agents/code-reviewer.md` | `.codex/agents/code-reviewer.toml` | `code-review` / Codex review 模式 | Spec 合规审查 + 代码质量审查 + 输出报告 | 第一优先级 |
| `feedback-observer` | `agents/feedback-observer.md` | `.codex/agents/feedback-observer.toml` | `feedback-writer` | 记录用户反馈、修正和流程信号 | 二期 |
| `evolution-runner` | `agents/evolution-runner.md` | `.codex/agents/evolution-runner.toml` | `evolution-engine` | 扫描 feedback，生成 AGENTS / skills / 流程优化建议 | 二期 |

### 3.2 派发时机

`implementer`：

1. 中大型代码实现；
2. 已经有明确 PRD、handoff、任务书或文件边界；
3. 需要在独立 worktree 中完成；
4. 主 Agent 不应把实现细节塞进当前主线程导致上下文污染；
5. 可以明确授权它修改哪些文件或模块。

`code-reviewer`：

1. implementer 已完成 worktree 改动；
2. 如本任务启用了 `long-task-gate`，硬校验已经通过或至少已有明确 gate 报告；
3. 准备进入合并前判断；
4. 用户要求 review；
5. 改动涉及主链路、状态机、数据结构、账号/发布/worker 等高风险区域；
6. 主 Agent 需要避免被 implementer 的实现叙事锚定。

`feedback-observer`：

1. 用户明确指出 Agent 行为问题；
2. 用户修正了开发流程、沟通方式、验证方式或任务边界；
3. 同类问题可能再次出现，值得沉淀为流程反馈；
4. 本项目建立 feedback 目录和规则后再启用。

`evolution-runner`：

1. session 初始化时可选触发；
2. 用户要求复盘近期流程；
3. feedback 已积累到足够数量；
4. 需要提出 AGENTS / skills / 模板优化建议。

`evolution-runner` 返回的进化建议必须展示给用户逐条确认、跳过或延后，不能自动执行。

### 3.3 Sub-Agent 隔离原则

适用于所有 sub-agent 派发。

1. 每个 Task 默认使用 fresh 实例，不复用之前的 sub-agent；
2. Controller 必须提供完整任务上下文，包括 Spec 条目、交付清单、涉及文件、项目结构、验证命令和禁止事项；
3. Sub-agent 默认不继承主 session 的隐含历史；
4. 如果 sub-agent 需要历史上下文，Controller 必须显式写进任务书；
5. Codex 支持 fork 当前上下文，但本项目默认不使用 fork，除非用户明确要求“让子 Agent 带着当前完整上下文继续”；
6. 隔离不是可选最佳实践，而是防止 Task A 的错误假设污染 Task B 的基本保证；
7. 多个 implementer 并行时，必须分配互不重叠的文件/模块所有权；
8. sub-agent 不应直接 push / merge，除非任务书明确授权。

### 3.4 Controller 的职责

Controller 是主控 Agent，不等同于 implementer。

职责：

1. 判断任务是否需要 sub-agent；
2. 选择 agent 类型；
3. 准备完整任务书；
4. 分配 worktree / branch / 文件边界；
5. 等待并收敛 sub-agent 结果；
6. 对结果做最终判断；
7. 必要时生成下一轮修复指令；
8. 决定是否进入 commit / push / merge / handoff 流程。

Controller 不应把“开了 sub-agent”当作完成本身。sub-agent 的输出只是证据，是否采纳仍由 Controller 判断。

### 3.5 feedback 和 memory 不能混淆

后续如果引入 `feedback-observer` 和 `evolution-runner`，必须区分 feedback 与 memory。

拟采用规则：

1. feedback 用于记录“用户修正 AI 行为、流程、判断标准”的信号；
2. feedback 的目标是改进 `AGENTS.md`、skills、模板和工作流；
3. memory 用于跨 session 记住用户偏好、项目上下文和长期事实；
4. 用户修正 AI 行为时，应优先走 feedback 流程，而不是只写 memory；
5. evolution-runner 只能基于 feedback 生成进化建议，不能把 memory 当作流程缺陷证据；
6. 任何进化建议在执行前都必须经用户确认。

当前本项目尚未正式建立 `.codex/feedback/` 或等价目录，因此本节先作为合并规划，不立即创建反馈系统。

### 3.6 worktree + sub-agent + gate + review 闭环

本项目后续推荐的开发闭环：

1. Controller 识别任务类型和风险；
2. 需要隔离开发时，创建或指定独立 worktree；
3. Controller 判断任务是短任务还是长任务；
4. Controller 生成任务书；
5. Controller spawn `implementer`，把 worktree 路径、branch、任务目标、文件边界、验证命令、禁止事项，以及“是否长任务”的判断一次性传入；
6. `implementer` 在 worktree 内完成编码、编译验证和自检；
7. 如果任务被定义为长任务，启用 `long-task-gate`，由硬校验和独立验收判断是否达到完成门槛；
8. `implementer` 返回改动说明、验证结果、风险和 commit / diff 状态；
9. Controller spawn 或切换到 `code-reviewer`；
10. `code-reviewer` 对 worktree 改动做两阶段审查；
11. Controller 根据 review 结果决定：返工、补验证、写 handoff、commit、等待用户合并决策。

这个闭环对应当前手动流程的自动化版本：

- 过去：主 Agent 写提示词 -> 用户复制给 worktree Agent -> worktree Agent 做完 -> 用户复制结果回主 Agent -> 主 Agent review；
- 后续：Controller 直接调度 implementer / code-reviewer，并收敛结果。

### 3.7 长任务判定与 long-task-gate 触发

长任务不是 implementer 自己随意声明的状态。

本项目建议采用：

1. Controller 在派发前先判断任务是否属于长任务；
2. 该判断必须写进 sub-agent 任务书；
3. 如果是长任务，任务书中必须明确写出 `long-task-gate`、完成承诺、source docs、硬校验方向和验收口径；
4. 如果不是长任务，任务书中也应明确写出“本任务不启用 long-task-gate”，避免 sub-agent 误判；
5. implementer 收到任务后可以复核长短任务判断；如果认为 Controller 判断有误，应先返回 `NEEDS_CONTEXT` 或提出异议，不应擅自扩大流程；
6. 只要任务书明确要求长任务模式，implementer 应按 `.codex/skills/long-task-gate/SKILL.md` 启动并检查 gate；
7. `long-task-gate` 的完成状态只能由脚本检查和独立 verifier 写入，不能由 implementer 或 Controller 口头宣布完成。

核心原则：

> Controller 负责做长任务判断并显式派发；implementer 负责按该判断执行；gate 负责给出是否真的完成的机器和独立验收结果。

在 Codex 中，含有“长任务”“Completion Gate”“long-task-gate”等明确触发词的任务可能触发对应 skill，但本项目不能依赖隐式关键词碰运气。任务书必须显式写清楚是否启用 gate。

### 3.8 hooks 的边界

hooks 不应被当成所有流程的前提。

当前判断：

1. `long-task-gate` 适合继续使用 Stop hook，因为它要防止长任务在完成门槛前过早停止；
2. `feedback` 第一版不强制依赖 hook，可以先由 Controller 在用户明确修正 AI 行为时手动或半自动触发 `feedback-observer`；
3. 后续如果 feedback 流程稳定，再考虑增加 hook，用于 session 结束、用户显式反馈、或特定事件后的自动记录；
4. 不建议一开始就用 hook 自动写大量 feedback，避免把噪音沉淀成规则；
5. `evolution-runner` 更不应该通过 hook 自动修改规则，只能生成建议并交给用户确认。

## 4. 项目记忆与反馈边界

本项目暂不需要额外引入独立 memory 系统。

当前判断：

1. `docs/handoff/` 是任务交接记忆；
2. `docs/progress/` 是执行事实、验证结果和阶段进展记忆；
3. `docs/产品文档/` 和 `docs/架构规范/` 是稳定真相源；
4. `AGENTS.md` 是 Agent 协作规则和工作方式；
5. `.codex/skills/` 是可复用执行能力；
6. 如无特别需要，不新增独立 `memory/` 目录。

`feedback` 与上述项目记忆不同。

feedback 记录的不是“项目事实”，而是“AI 行为和流程应该如何改进”的信号，例如：

1. 用户指出 Agent 任务边界处理错误；
2. 用户指出某种验证方式不够；
3. 用户修正 sub-agent 派发方式；
4. 用户要求某类任务以后必须走 worktree / review / gate；
5. 用户指出某个 skill 或 AGENTS 规则需要演进。

因此后续如果建立 feedback 机制，建议使用项目级目录，例如 `.codex/feedback/`，并只把可复用的流程改进信号写入其中。

## 5. 参考工作流对照

参考项目的完整工作流大致是：

1. 描述想法；
2. 生成需求文档；
3. 设计规范；
4. 设计图制作；
5. 开发计划；
6. 项目开发；
7. 自动审查；
8. 自动修复；
9. 提交推送；
10. Phase 验证；
11. 迭代修改；
12. 构建发布；
13. 经验沉淀。

本项目不应原样复制这 13 步，而应该按已有能力做映射。

### 5.1 已经基本具备的部分

描述想法 / 梳理问题：

- 本项目已有 `thinking-partner`，适合用于从模糊想法收敛核心问题、拆解卡点、共创行动方案。

生成需求文档：

- 本项目已有 `prd-doc-writer`，适合输出 PRD、用户故事、验收标准、ASCII 线框和 Mermaid 流程图。
- 不是所有任务都需要重新生成 Product-Spec.md；已有 V2.1/V2.5/V2.7 等 PRD 时，应优先复用现有真相源。

需求变更 / 迭代修改：

- 本项目已有 `req-change-workflow`，适合处理“改需求、调整交互、重构流程、影响多模块”的任务。
- 后续可把它视为参考流程第 11 步“迭代修改”的主要承接方式。

提交推送：

- 本项目已有 Git / worktree / handoff 规则。
- 但本项目默认不应照搬“审查双 PASS 后自动 commit + push”。
- 更适合保持当前策略：可以 commit，push / merge 默认需要用户明确授权。

### 5.2 已经有，但更适合保持可选的部分

设计规范：

- 本项目可用 `design-exploration`、`ui-ux-pro-max` 或外部设计流程承接。
- 如果用户已经在别处完成视觉方向或设计稿，本项目不强制重复生成 Design-Brief.md。

设计图制作：

- 本项目不强制把 Pencil / Figma 原型制作纳入主开发流程。
- 设计图可以外置完成，再作为输入交给开发 Agent。
- 后续只有在某一阶段明确要做 UI 原型交付时，再启用对应设计流程。

Phase 验证：

- 本项目已有部分能力，包括常规编译验证、功能测试、handoff/progress 记录，以及 `long-task-gate`。
- 但 Phase 验证目前还不是独立标准流程，后续可以再补。

构建发布：

- 本项目已有部署、worker、服务器验证等经验，但不同链路差异很大。
- 暂不抽象成统一 `/release-builder`，后续按 app、worker、Dify、服务器部署分别沉淀。

### 5.3 当前最值得补齐的缺口

项目开发：

- 参考项目的 `/dev-builder` 对应本项目应新增或明确的 `implementer` 流程。
- 本项目不一定需要一个叫 `/dev-builder` 的命令，但需要一份稳定的实现 Agent 任务书模板。

自动审查：

- 参考项目的 `code-reviewer` 可以直接借鉴。
- 本项目应优先落地“两阶段审查”：先查 Spec 合规，再查代码质量。

自动修复：

- 参考项目的 `bug-fixer` 或“补实现后重新审查”机制值得吸收。
- 本项目建议先采用半自动方式：reviewer 生成明确修复指令，交给 implementer 在同一 worktree 继续修复，然后重新 review。
- 暂不建议一开始就做完全自动循环，避免误改范围扩大。

经验沉淀：

- 参考项目的 `feedback-observer` / `evolution-runner` 值得借鉴。
- 本项目已有 `handoff`、`progress`、session 复盘和 `.codex` 备份，但还缺少定期提炼“流程改进建议”的机制。
- 后续可考虑新增一个轻量复盘流程：从 handoff/progress/session 中提取高频问题，生成 AGENTS / skills 的修改建议。
