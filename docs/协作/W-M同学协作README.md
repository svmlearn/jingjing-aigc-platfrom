# W-M 同学协作 README

## 1. 为什么要有这份文档

这个项目接下来会进入第一次两个人协作开发：

- W 同学：产品负责人，负责业务判断、用户流程、体验验收、需求优先级。
- M 同学：开发负责人，负责具体实现、接口对接、worker、数据库和部署相关工作。

两个人都不是传统意义上“全职工程团队配置”，但都会使用 AI 来帮助自己思考、写代码、读代码和整理文档。因此，项目协作方式要适配一个现实：

很多产品想法可以口头聊，但凡是涉及接口、数据表、状态机、部署、错误处理、保存位置、worker 输入输出这类技术细节，就不能只靠口头记忆，需要落成文档，让双方和各自的 AI 都能读。

这份 README 的目标不是增加流程负担，而是减少误会：

- W 同学不用被技术术语淹没。
- M 同学不用猜产品到底要什么。
- AI 不用每次从聊天记录里考古。
- 出问题时能回到文档，知道当时是怎么约定的。

## 2. 协作原则

### 2.1 口头适合聊什么

口头交流适合：

- 产品感觉。
- 页面好不好用。
- 用户看到这里会不会困惑。
- 某个按钮叫法。
- 某个流程先做简单版还是完整版。
- 需求优先级。
- 临时脑暴和想法发散。

口头聊完以后，如果只是产品体验判断，可以不用立刻写很正式的文档。

### 2.2 必须写文档的内容

只要涉及下面任何一类，就必须写进文档：

- 新增或修改 API。
- 新增或修改 Supabase 表结构。
- 新增或修改 worker 输入输出。
- 视频任务状态、失败原因、重试策略。
- 图文 / 视频草稿保存位置。
- 「我的内容」「素材中心」「咨询历史」之间的数据边界。
- 页面跳转时 URL 要携带哪些参数。
- 某个字段是必填还是可选。
- 某个任务失败后用户看到什么。
- 部署、回滚、环境变量、密钥存放方式。

一句话规则：

如果这件事未来可能让另一个人或 AI 问“这里到底怎么定的”，那就写文档。

## 3. 角色分工

### 3.1 W 同学负责

W 同学主要负责：

- 定义业务目标。
- 判断用户流程是否合理。
- 明确页面上用户看到什么。
- 决定哪些需求先做，哪些后做。
- 验收 staging 效果。
- 给出产品反馈。
- 决定文案、按钮、流程是否符合产品预期。

W 同学不需要把所有技术细节都讲成工程语言，但要尽量把用户动作和预期结果说清楚。

建议表达方式：

```text
当用户从内容日历点击「进入视频工作台」时，我希望视频工作台知道：
1. 用户点的是哪一天的哪条内容；
2. 这条内容是种草还是转化；
3. 后续生成的脚本和视频任务要能回到「我的内容」。
```

### 3.2 M 同学负责

M 同学主要负责：

- 把产品流程拆成可实现的前端、后端、worker 任务。
- 判断需要改哪些接口和表结构。
- 写代码、跑测试、部署 staging。
- 把接口变更、表结构变更、worker 输入输出写成 W 同学能看懂的文档。
- 遇到不确定的产品点，主动用文档列出问题给 W 同学确认。

M 同学不需要写很传统、很重的工程文档，但要避免只写“已修复”“已优化”这种 W 同学和 AI 看不出边界的话。

建议表达方式：

```text
我这次需要新增 calendarItemId 字段。
它的作用是：用户从内容日历进入工作台后，系统能知道用户点的是哪一条内容建议。
如果不加这个字段，只靠 strategyTag，会分不清同一个策略下的多条内容。
```

## 4. 文档怎么分

项目里不同文档有不同用途，尽量不要混写。

### 4.1 产品需求

放在：

```text
docs/产品文档/
```

适合写：

- PRD。
- 页面流程。
- 用户故事。
- 验收标准。
- W 同学对功能的产品判断。

当前重要文档：

```text
docs/产品文档/V2.1-咨询驱动主链路体验补强-PRD.md
docs/产品文档/V2.1-内容日历到图文视频工作台协作PRD.md
```

### 4.2 技术边界和接口约定

放在：

```text
docs/架构规范/
```

适合写：

- API contract。
- 数据表说明。
- worker 输入输出。
- 状态机。
- agent runtime 和工具边界。
- 环境变量规则。

### 4.3 执行记录

放在：

```text
docs/progress/
```

适合写：

- 今天改了什么。
- 哪些 SQL 已经跑过。
- 哪些部署成功。
- 哪些 smoke test 通过。
- 哪些问题还没解决。

### 4.4 交接说明

放在：

```text
docs/handoff/
```

适合写：

- 下一位 AI 或同学从哪里继续。
- 当前 branch / commit / 部署状态。
- 做完但还没验收的东西。
- 有哪些不要碰的文件。

### 4.5 W-M 协作文档

放在：

```text
docs/协作/
```

适合写：

- 两个人之间的协作约定。
- 给对方看的解释文档。
- 技术问题的非工程化说明。
- 需要 W 同学确认的问题清单。
- M 同学写给 W 同学的实现说明。

## 5. 接口或表结构变更怎么沟通

如果 M 同学需要改接口、表结构或 worker 输入输出，建议按下面这个小模板写，不需要很长。

```text
# 变更标题

## 背景
为什么要改，不改会有什么问题。

## 产品影响
用户会看到什么变化，或者 W 同学需要验收什么。

## 技术变更
新增 / 修改了哪些接口、字段、表、状态。

## 示例
给一个请求、响应或数据样例。

## 兼容性
旧数据会不会受影响，旧页面会不会坏。

## 需要 W 同学确认
列出 1-5 个产品问题，不要一口气抛太多。

## 验收标准
怎样才算这次改完。
```

示例：

```text
# 内容日历进入视频工作台需要携带 calendarItemId

## 背景
现在只传 sessionId 和 strategyTag，同一个策略下面可能有多条内容日历，视频工作台无法知道用户点的是哪一条。

## 产品影响
用户从某条日历点击进入视频工作台后，页面能展示这条日历对应的标题、摘要和内容目标。

## 技术变更
URL 新增 calendarItemId。
生成视频脚本时，把 selectedCalendarItem 写入 content_drafts.input_snapshot。

## 示例
/dashboard/video?source=consultation_calendar&sessionId=xxx&calendarItemId=yyy&strategyTag=种草

## 需要 W 同学确认
如果 calendarItemId 找不到，是返回咨询页，还是让用户继续用 strategyTag 兜底生成？
```

## 6. W 同学怎么提需求

W 同学提需求时，不需要一开始就想清楚技术实现。推荐按这个格式说：

```text
我希望用户在【哪个页面】做【哪个动作】后，
系统能【产生什么结果】，
这个结果要保存到【哪里】，
如果失败了，用户应该看到【什么提示】。
```

示例：

```text
我希望用户在视频工作台点击「生成视频」后，
系统先保存视频脚本，再创建视频任务，
视频生成成功后成片要出现在「我的内容」，
如果失败了，用户能看到失败原因，并且可以重试。
```

如果 W 同学只是有想法，还不确定，可以先标注：

```text
这是一个想法，还没定。
```

如果已经决定要做，可以标注：

```text
这个需求已定，按这个做。
```

## 7. M 同学怎么回产品问题

M 同学回复时，建议少用纯技术黑话，多用“产品能感知到的影响”解释。

不推荐：

```text
需要改 schema，加 payload 字段，不然 worker 消费不了。
```

推荐：

```text
这里需要在数据库里多存一个 input_payload。
它的作用是保存用户这次生成视频时带入的脚本、素材和日历上下文。
否则 worker 运行时只能看到任务 ID，看不到用户到底想生成什么视频。
```

如果必须用技术词，后面补一句解释：

```text
RLS：Supabase 的行级权限规则，用来保证一个商家只能读自己的数据。
```

## 8. 状态标记

文档里建议统一使用这些状态词：

- `想法`: 只是脑暴，还没决定。
- `讨论中`: 方向大概对，但还有问题没确认。
- `已定`: 产品已经确认，可以开发。
- `开发中`: M 同学正在实现。
- `待验收`: 已部署或已提交，等 W 同学看效果。
- `已验收`: W 同学确认通过。
- `暂缓`: 先不做，但不删除。

避免使用含糊表达：

- “差不多好了”
- “应该可以”
- “后面再说”
- “优化了一下”

如果确实不确定，就写清楚哪里不确定。

## 9. 每次交付最好包含什么

M 同学每次交付给 W 同学，最好包含：

- 改了什么。
- 为什么改。
- W 同学应该看哪个页面。
- W 同学应该怎么测试。
- 哪些还没做。
- 有没有新增接口、字段、表结构。
- 有没有需要 W 同学决定的问题。

推荐格式：

```text
这次完成：
- 视频任务失败后展示失败原因。
- failed_retryable 状态下可以点击重试。

W 同学可以这样测：
- 进入 /dashboard/video。
- 创建一个视频任务。
- 如果 worker 写入 failed_retryable，页面会出现重试按钮。

还没做：
- failed_manual 的人工处理入口还只是文案，没有客服流转。
```

## 10. AI 协作方式

两个人都可以让自己的 AI 读文档和代码，但要遵守：

- 不要只把聊天记录当真相源。
- 重要结论要写回仓库文档。
- 让 AI 开工前，先读相关 PRD / progress / handoff。
- 如果 AI 发现文档和代码不一致，要先标注“不一致”，不要直接假装都对。
- 不要让 AI 把还没实现的东西写成已经实现。
- 不要把 API key、密钥、token 写进文档或 commit。

给 AI 的推荐开场：

```text
请先读 docs/协作/W-M同学协作README.md，
再读本任务相关的 PRD / progress / handoff，
然后告诉我当前已实现、未实现、需要我确认的点。
```

## 11. 当前和视频开发最相关的文档

M 同学做视频 / worker 前，建议按顺序读：

```text
docs/协作/W-M同学协作README.md
docs/产品文档/V2.1-内容日历到图文视频工作台协作PRD.md
docs/架构规范/2026-04-28-current-architecture.md
docs/progress/2026-04-25-supabase-migration-current-state.md
```

读完后，M 同学最好先输出一份自己的理解：

```text
我理解我负责的是：
1. ...
2. ...

我需要 W 同学确认的是：
1. ...
2. ...

我准备先改这些文件：
1. ...
2. ...
```

## 12. 安全和边界

协作时默认遵守：

- 不把 `references/` 参考项目提交到远端。
- 不把 API key、Supabase service role、COS secret 写进代码或文档。
- 所有真实环境变量放 `.env`、Vercel、服务器环境变量或密钥管理中。
- 先在 staging 验证，再考虑生产。
- 不做真实账号发布，不接小红书 / 抖音真实发布权限。
- 涉及数据库迁移时，要写明是否已经在 Supabase staging 执行。
- 涉及 worker 部署时，要写明部署到哪台服务器、哪个 commit、是否 smoke test 通过。

## 13. 这个 README 怎么维护

这份文档不是一次性写完的规则书。

后续如果 W 同学和 M 同学发现：

- 某种沟通方式不好用。
- 某类变更总是说不清。
- 某个模板太重。
- 某个目录放文档不合适。

可以直接改这份 README。

原则只有一个：

让 W 同学、M 同学，以及双方的 AI，都能更快知道“现在到底怎么协作”。
