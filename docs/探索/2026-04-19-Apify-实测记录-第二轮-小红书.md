# Apify 实测记录（第二轮：小红书专项）

## 1. 为什么要做第二轮

首轮测试里，小红书出现了明显分化：

- `creator` 可用
- `detail` 用裸链接时字段很空
- `comments` 有 actor 返回空 dataset

第二轮的目标是确认：

1. 小红书 `detail` 是不是因为裸链接缺少上下文参数而失败
2. 小红书 `comments` 是不是完全不可用
3. 哪些 actor / 输入方式更适合进入 `V0.1-A` 主线验证

测试日期：

- `2026-04-19`

重要限制：

- 本轮没有向 Apify 传浏览器 cookie
- 只使用小红书页面自然生成的完整链接
- 完整链接保留了 `xsec_token` 等上下文参数

---

## 2. 样本来源

通过本地 Chrome 打开：

- `https://www.xiaohongshu.com/explore`

从页面 DOM 中提取自然生成的完整帖子链接和主页链接。

这一步很重要，因为小红书很多页面链接包含：

- `xsec_token`
- `xsec_source`
- `channel_type`

这些参数可能影响第三方 actor 的抓取结果。

---

## 3. 本轮测试组合

## 3.1 小红书 `detail`

actor：

- `huggable_quote/xiaohongshu-all-in-one-scraper`

输入模式：

```json
{
  "mode": "postDetail",
  "postUrls": ["完整小红书帖子链接"],
  "maxItems": 1
}
```

测试结果：

- 样本 1：成功
- 样本 2：成功

拿到的关键字段：

- `id`
- `type`
- `title`
- `description`
- `user.nickname`
- `likes`
- `comments`
- `collects`
- `shares`
- `tags`
- `images`
- `video`
- `ipLocation`
- `createTime`

这说明：

- 小红书 `detail` 可以跑通
- 但要优先使用页面自然生成的完整链接
- 不能只传裸 `https://www.xiaohongshu.com/explore/{note_id}`

---

## 3.2 小红书 `profile`

actor：

- `huggable_quote/xiaohongshu-all-in-one-scraper`

输入模式：

```json
{
  "mode": "profile",
  "profileUrls": ["完整小红书主页链接"],
  "maxItems": 1

```

测试结果：

- 成功

拿到的关键字段：

- `profileUrl`
- `redId`
- `nickname`
- `description`
- `gender`
- `avatar`
- `ipLocation`
- `follows`
- `fans`
- `interaction`

这说明：

- 小红书主页资料可用

---

## 3.3 小红书 `comments`：huggable actor

actor：

- `huggable_quote/xiaohongshu-all-in-one-scraper`

输入模式：

```json
{
  "mode": "comments",
  "postUrls": ["完整小红书帖子链接"],
  "maxItems": 5
}
```

测试结果：

- run 成功
- dataset item 数量：`0`

判断：

- 这个 actor 的 `comments` 模式，本轮不能判定为可用

---

## 3.4 小红书 `comments`：easyapi all-in-one actor

actor：

- `easyapi/all-in-one-rednote-xiaohongshu-scraper`

输入模式：

```json
{
  "mode": "comment",
  "postUrls": ["完整小红书帖子链接"],
  "maxItems": 30
}
```

测试结果：

- 样本 1：成功，返回 `2` 条 item
- 样本 2：成功，返回 `5` 条 item

拿到的关键字段：

- `postUrl`
- `comment.id`
- `comment.note_id`
- `comment.content`
- `comment.user_info.nickname`
- `comment.like_count`
- `comment.ip_location`
- `comment.create_time`
- `comment.sub_comments`
- `comment.sub_comment_count`

样本 2 还拿到了：

- 主评论
- 子评论
- 子评论数量
- 作者标记 `is_author`

判断：

- 小红书 `comments` 不是完全不可用
- 但要使用正确 actor 和正确模式：
  - `easyapi/all-in-one-rednote-xiaohongshu-scraper`
  - `mode = comment`
- 并且要尽量传页面自然生成的完整链接

## 4. 本轮重要成本信号

本轮不同调用成本差异明显：

- `huggable` 的小红书 `detail` 单条约 `0.0002 USD`
- `huggable` 的小红书 `profile` 单条约 `0.0052 USD`
- `easyapi all-in-one` 的小红书 `comment` 样本 1 约 `0.0169 USD`
- `easyapi all-in-one` 的小红书 `comment` 样本 2 约 `0.1074 USD`

这里最重要的不是绝对价格，而是：

- 评论成本可能明显高于详情
- 不同帖子评论成本差异很大
- `maxItems`、评论回复量、actor 运行时间都会影响成本

---

## 5. 第二轮修正后的判断

首轮结论里“小红书 comments 暂不判可用”需要修正为：

> 小红书 comments 可跑通，但 actor 选择和链接质量非常关键。

更准确的状态是：

| 能力 | 当前判断 | 推荐 actor |
|---|---|---|
| 小红书 `detail` | 可用 | `huggable_quote/xiaohongshu-all-in-one-scraper` |
| 小红书 `profile` | 可用 | `huggable_quote/xiaohongshu-all-in-one-scraper` |
| 小红书 `userPosts` | 可用 | `easyapi/rednote-xiaohongshu-user-posts-scraper` |
| 小红书 `comments` | 可用但需继续压测 | `easyapi/all-in-one-rednote-xiaohongshu-scraper` |

---

## 6. 对产品方案的影响

这轮以后，`Apify` 已经不只是“理论可接”。

更准确的产品判断是：

- `V0.1-A` 可以把 `Apify` 作为 API-first 的主线 PoC 服务商
- 小红书和抖音都已经有可跑通路径
- 但还不能直接宣布“生产稳定”

原因：

1. 中文社媒 actor 质量差异明显
2. 小红书必须保留完整链接上下文
3. 评论成本和稳定性还需要更多样本验证
4. 免费额度/低阶套餐存在 actor 内存并发限制

---

## 7. 当前推荐接入策略

如果 `V0.1-A` 先接 Apify，建议先按能力拆 actor：

### 小红书

- `detail`
  - `huggable_quote/xiaohongshu-all-in-one-scraper`
  - `mode = postDetail`
- `profile`
  - `huggable_quote/xiaohongshu-all-in-one-scraper`
  - `mode = profile`
- `creator/userPosts`
  - `easyapi/rednote-xiaohongshu-user-posts-scraper`
- `comments`
  - `easyapi/all-in-one-rednote-xiaohongshu-scraper`
  - `mode = comment`

### 抖音

- `detail`
  - `easyapi/douyin-video-downloader`
- `comments`
  - `natanielsantos/douyin-comments-scraper`

---

## 8. 当前仍需继续验证

下一步不是再证明“能不能跑通”，而是验证稳定性：

1. 小红书 `detail` 连续 10 条完整链接成功率
2. 小红书 `comments` 连续 10 条完整链接成功率
3. 评论成本在不同评论量帖子上的区间
4. 是否能稳定映射到 `source_items` 和 `imported_comments`
5. 如果不从小红书页面拿完整链接，而是用户直接贴链接，是否需要先做链接规范化/补全

---

## 9. 一句话结论

第二轮以后，Apify 的小红书链路可以从：

- “不确定能不能用”

上调为：

- **“可以作为 V0.1-A 的 API-first PoC 主方案继续推进，但必须保留 actor 选择、完整链接、成本控制和稳定性压测这四个风险项。”**
