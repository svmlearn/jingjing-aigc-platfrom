# Apify 实测记录（首轮）

## 1. 测试目的

这轮不是再看文档介绍，而是直接用真实 `Apify token` 跑一轮最小样本，验证：

1. 能不能真正启动
2. 能不能真正返回结构化数据
3. 返回字段够不够支撑我们当前主链路

测试日期：

- `2026-04-19`

测试方式：

- 使用 `Apify API`
- 以最小样本做异步 run
- 优先验证：
  - `detail`
  - `creator`
  - `comments`

## 4. 实测结果

## 4.1 小红书 `detail`

actor：

- `huggable_quote/xiaohongshu-all-in-one-scraper`

状态：

- **成功启动**
- **run 成功**

返回情况：

- 返回了 `1` 条 item
- 但字段质量偏弱

本次拿到的关键字段：

- `postUrl`
- `id`

本次没有拿稳的关键字段：

- `title`
- `description/content`
- `user.nickname`

这轮实际结果更接近：

- **技术上能跑**
- **业务上还不够好**

## 4.2 小红书 `creator`

## 6. 这轮最重要的几个现实结论

### 6.1 `Apify` 这条路确实能接

至少在这轮里，已经实证了：

- 不是纸上谈兵
- 可以用 token + actor + API 跑真实样本

### 6.2 但 actor 质量差异很大

同样都是“run 成功”：

- 有的返回业务上可用字段
- 有的只是任务成功，但结果很空
- 有的甚至 dataset 是空的

### 6.3 小红书比抖音更不稳定

本轮样本里：

- 小红书 `creator` 最好
- 小红书 `detail` 一般
- 小红书 `comments` 当前不可用

而抖音：

- `detail` 可用
- `comments` 可用

### 6.4 不能只看 README

这轮已经出现了 2 类非常典型的问题：

1. README/直觉里的 input 字段名和真实 schema 不完全一致
2. README 说支持某模式，但当前 actor 实际输入校验并不接受

这也是为什么：

- **Apify 只能先叫“可试、可接、值得继续验证”**
- 还不能直接叫“稳定主方案已确认”

## 7. 当前对项目主线的判断

如果按 `V0.1-A` 的优先级来判断：

- `抓内容 -> 改写内容`

那本轮更适合的结论是：

- `Apify` **可以继续留在主线候选**
- 但需要按平台拆开判断，不要整体打包乐观

更具体一点：

### 小红书

- `creator`：继续保留
- `detail`：继续验证，不能直接定
- `comments`：暂不判可用

### 抖音

- `detail`：可继续推进
- `comments`：可继续推进

---

## 8. 下一轮建议

最值得继续做的不是再盲试更多 actor，而是：

1. 给小红书 `detail` 再换 1 到 2 个 actor 对比
2. 给小红书 `comments` 分别测试：
   - 当前 actor 换样本
   - 是否需要 cookie
3. 如果小红书 comments 仍不稳定，就尽早接受现实：
   - `V0.1-A` 先以 `detail + creator` 为主
   - 评论能力后置或换方案

---

## 9. 当前一句话结论

这轮真实结果说明：

- **Apify 不是不能用**
- **但它不是“一接就稳”**
- **更准确的状态是：抖音链路比小红书成熟，小红书链路里 `creator` 最有希望，`comments` 目前最不稳**

- 第二轮小红书专项测试已修正本轮部分判断
