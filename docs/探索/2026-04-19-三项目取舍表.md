# 三项目取舍表

## 1. 目的

这份文档不是再重复“它们有什么功能”，而是基于前面的现成功能盘点，直接回答：

- 哪些功能要
- 哪些功能不要
- 哪些必须自己补

判断标准只有两个：

1. 能否帮助我们最快拼出一个可用版本
2. 能否进入未来面向第三方商家的产品路线

补充前提：

- 本文原始判断偏“未来面向第三方商家产品化”
- 如果当前阶段是**内部自用 / 自己玩 / 非对外 SaaS**，则部分能力可以先保留为内部版能力，再在未来商业化时替换

---

## 2. 先说结论

### 2.1 直接保留

- `social-auto-upload` 的发布执行层
- `social-auto-upload` 的账号登录 / cookie / check / upload CLI contract

### 2.2 只参考，不直接并入产品代码

- `AIWriteX` 的内容工作流
- `AIWriteX` 的模板系统
- `AIWriteX` 的文章管理思路
- `MediaCrawler` 的 creator / search / detail 采集设计
- `MediaCrawler` 的 API 控制面和数据落盘思路

### 2.3 第一版不要

- `social-auto-upload` 的历史 Web 前后端
- `AIWriteX` 的公众号发布能力
- `AIWriteX` 的小说/配图实验室/手机机器人等扩展功能
- `MediaCrawler` 的评论词云、贴吧、知乎、微博等泛平台能力

### 2.4 必须自己补

- 统一商家工作台
- 商家/门店/品牌知识库
- 统一任务编排层
- 统一素材与内容数据模型
- 审核流
- 把“采集结果 -> 改写输入 -> 发布任务”串起来的中间层

### 2.5 当前内部自用版的特殊放宽

如果当前阶段只是自己内部使用，可以临时放宽：

- `MediaCrawler` 的 `creator`
- `MediaCrawler` 的 `detail`
- `MediaCrawler` 的评论抓取

但这属于：

- 先用于验证链路
- 未来若走正式产品化，再替换或重构

## 3. 授权与可商用风险

这个部分非常重要，因为它直接影响“能不能直接改成产品”。

### 3.1 `social-auto-upload`

当前观察到的事实：

- README 写的是 “暂时采用 MIT License”
- 但当前本地拉下来的仓库根目录里 **没有看到 `LICENSE` 文件**

结论：

- 技术上它最适合直接接入
- 但在正式对外产品化前，**必须再次核对上游许可证文件是否完整存在**

当前决策：

- **可作为第一优先级技术基座候选**
- 但在真正商用前，做一次许可证复核

### 3.2 `AIWriteX`

当前观察到的事实：

- `LICENSE` 是 Apache 2.0
- 但 `NOTICE` 和 README 明确加了附加限制
- 明确写了：
  - 非商业使用
  - 禁止分发衍生作品
  - 禁止向第三方提供 SaaS / API 托管等服务

结论：

- **不能直接并入一个面向第三方商家的 SaaS 产品**

当前决策：

- **只参考思路，不直接合入正式产品代码**
- 如果后面真要复用其代码，必须先单独获得授权

### 3.3 `MediaCrawler`

当前观察到的事实：

- README 和代码头部都明确写了：
  - 仅供学习和研究
  - 禁止商业用途

结论：

- **不能直接作为商用采集底座**

当前决策：

- 面向第三方产品时：**只参考架构与接口设计，不直接并入产品**
- 当前内部自用阶段：**可以把 creator/detail/comment 作为内部工具能力先保留**

|---|---|---|---|---|---|
| 小红书发布执行 | `social-auto-upload` | 登录、check、图文上传、视频上传、定时发布 | 直接保留 | 这是当前最成熟、最贴近目标平台的能力 | 作为内部 `publisher service` 封装 |
| 抖音发布执行 | `social-auto-upload` | 登录、check、图文上传、视频上传、定时发布、商品参数 | 直接保留 | 同上，且对 MVP 价值最高 | 作为内部 `publisher service` 封装 |
| 多账号 cookie 管理 | `social-auto-upload` | `account_name` -> cookie 文件、多账号隔离、状态校验 | 直接保留 | 省掉最麻烦的一层基础设施 | 封成账号中心底层能力 |
| 发布 CLI contract | `social-auto-upload` | `login/check/upload-video/upload-note` | 直接保留 | 非常适合作为内部任务执行协议 | 外层包一层 API/任务表 |
| 定时发布能力 | `social-auto-upload` | `--schedule` 已有 | 直接保留 | 属于现成价值，不需要重造 | 接到统一排期模型里 |

| 快手/B站/视频号/百家号额外发布 | `social-auto-upload` | 部分已接入、成熟度不一 | 第一版不要 | 会分散精力，与你当前目标不一致 | MVP 先只保留小红书/抖音 |
| 内容生成主工作流 | `AIWriteX` | 生成 -> 创意变换 -> 模板/设计 -> 保存 | 参考后自补 | 产品方向很有用，但许可证不适合直接并入 | 按流程思路自己实现或重写 |
| 模板系统 | `AIWriteX` | 模板分类、CRUD、预览、复制、移动 | 参考后自补 | 模板管理成熟，但代码不能直接用于第三方 SaaS | 设计自己的模板中心 |

| 热点获取 | `AIWriteX` | 多平台热榜抓取 | 第一版可选，不做核心 | 可做增强，但不是 MVP 必需 | 后置到 V0.2 |
| 小红书内容格式化 | `AIWriteX` | 已实现文案格式适配 | 保留思路 | 对改写输出有帮助 | 抽象成“输出模版规则” |
| 抖音脚本格式化 | `AIWriteX` | 已实现短视频脚本化输出 | 保留思路 | 对口播脚本生成有帮助 | 抽象成“脚本输出规则” |
| 公众号发布 | `AIWriteX` | 真正已实现 | 第一版不要 | 当前目标不是公众号，且代码许可受限 | 暂不纳入 |

## 5. 第一版建议明确“不要”的东西

这些能力不是说永远不要，而是 **现在不要背**：

### 5.1 不要接 `social-auto-upload` 历史 Web

原因：

- 官方自己都写了不是主线
- 接进去会背历史接口债

### 5.2 不要把 `AIWriteX` 当成整个产品壳

原因：

- 许可证不适合直接面向第三方服务
- 它的产品中心仍然偏公众号/写作工具

### 5.3 不要直接把 `MediaCrawler` 并进正式产品

原因：

- 许可风险明确
- 平台风控和商业风险都高

补充：

- 如果只是当前内部验证版，可以先保留 creator/detail/comment 能力
- 但在文档里应明确标记为“内部工具链能力”，不要当成未来商业版默认基座

### 5.4 不要第一版就做“全网全自动批量抓对标博主全部内容”

原因：

- 工程复杂
- 法务/平台风险大
- 容易把项目拖成纯采集工具

## 6. 必须自己补的能力

这一块是三项目拼接后，真正缺的“产品层”。

### 6.1 商家/门店/品牌知识库

必须自己补。

原因：

- 三个项目都没有面向本地商家的品牌建模
- 但这恰恰是改写成“符合商家自身情况”的基础

建议内容：

- 商家信息
- 门店信息
- 目标客群画像
- 主打项目
- 卖点
- 服务区域
- 语气风格
- 禁用表达
- CTA 模板

### 6.2 统一素材与内容数据模型

必须自己补。

原因：

- 采集结果、AI 草稿、发布素材目前分散在三个项目自己的数据结构里
- 不补这一层，后面串不起来

建议对象：

- `SourceItem`
- `ImportedContent`
- `BrandProfile`
- `ContentDraft`
- `PlatformVariant`
- `PublishJob`

### 6.3 统一任务编排层

必须自己补。

原因：

- 三个项目目前都是各自跑各自的
- 我们需要把“导入 -> 改写 -> 审核 -> 发布”真正串起来

### 6.4 审核流

必须自己补。

原因：

- 你这个产品面向商家，不可能完全黑箱自动发
- 至少第一版一定要有人审一下

### 6.5 统一 Web 工作台

必须自己补。

原因：

- 三个项目都不是为你这个产品形态设计的前台
- 第一版仍然需要一个自己的控制台

建议至少包含：

- 导入区
- 内容草稿区
- 审核区
- 账号区
- 发布任务区

### 6.6 “贴链接导入 -> 可改写输入”的解析层

必须自己补。

原因：

- `MediaCrawler` 擅长抓
- `AIWriteX` 擅长写
- 但中间“怎么把抓回来的结构转成可改写输入”这层没人做

## 7. 第一版最推荐的组合方式

### 7.1 真正直接用的

- `social-auto-upload` 的小红书/抖音发布执行能力

### 7.2 只借结构和思路的

- `AIWriteX` 的内容工作流、模板和文章管理设计
- `MediaCrawler` 的 creator/detail/search 采集设计

### 7.3 自己要补的中台

- 商家品牌层
- 导入解析层
- 内容草稿中心
- 审核流
- 任务编排
- 统一工作台

---

## 8. 一句话版取舍

如果非要压缩成一句话：

- **拿 `social-auto-upload` 做发布引擎**
- **拿 `AIWriteX` 学内容工作流，但不直接并代码**
- **拿 `MediaCrawler` 学 creator 抓取与 API 设计，但不直接并代码**
- **真正产品化的那一层，必须自己补**
