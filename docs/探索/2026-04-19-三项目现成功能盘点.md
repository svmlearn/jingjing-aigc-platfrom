# 三项目现成功能盘点

## 1. 目的

这份文档不从“我们想做什么”出发，而是只回答一个问题：

这三个开源项目 **今天已经提供了哪些具体能力**。

这样后面做取舍时，才是基于现成资产拼装，而不是重新幻想一套产品。

涉及项目：

- `references/open-source/social-auto-upload`
- `references/open-source/AIWriteX`
- `references/open-source/MediaCrawler`

---

## 2. 总览结论

先给一个最短结论：

- `social-auto-upload`：最像“可直接拿来接入”的发布执行层
- `AIWriteX`：最像“内容工作流和模板系统”
- `MediaCrawler`：最像“采集导入工具 + API/WebUI”，但许可明确限制商业用途

也就是说，这三个项目并不是功能重叠的关系，而是天然分成三层：

1. 采集层：`MediaCrawler`
2. 改写层：`AIWriteX`
3. 发布层：`social-auto-upload`

---

## 3. `social-auto-upload` 现成功能

### 3.1 项目形态

它同时具备三种形态：

- CLI 工具
- uploader 模块库
- 旧版 Flask + Vue Web 管理台

本地重点文件：

- `references/open-source/social-auto-upload/sau_cli.py`
- `references/open-source/social-auto-upload/docs/CLI.md`
- `references/open-source/social-auto-upload/uploader/`
- `references/open-source/social-auto-upload/sau_backend.py`
- `references/open-source/social-auto-upload/sau_frontend/src/router/index.js`

### 3.2 已有平台支持

按当前主线 CLI 已接入的平台：

- 抖音
- 快手
- 小红书
- Bilibili

从 uploader / backend 还能看到额外平台：

- 视频号
- 百家号
- TikTok

但它们和主线 CLI 的成熟度不一致。

### 3.3 已有 CLI 能力

CLI 已明确提供的能力：

- `login`
- `check`
- `upload-video`
- `upload-note`

其中：

- 抖音：登录、校验、视频上传、图文上传、定时发布、商品链接参数
- 快手：登录、校验、视频上传、图文上传、定时发布
- 小红书：登录、校验、视频上传、图文上传、定时发布
- Bilibili：登录、校验、视频上传、定时发布

从 `sau_cli.py` 可确认：

- 每个平台通过独立子命令暴露
- `account_name` 映射到独立 cookie 文件
- 支持 `--schedule`
- 支持 `--headless / --headed`

### 3.4 账号与登录管理能力

已经具备：

- 多账号隔离
- cookie 文件持久化
- cookie 有效性校验
- 本地登录流程
- Bilibili 二维码登录

从旧版 backend 还能看到：

- 账号列表管理
- 账号删除
- 上传/下载 cookie 文件
- 批量校验账号状态

### 3.5 发布相关能力

已经具备：

- 视频发布
- 图文发布
- 定时发布
- 批量发布接口
- 基于不同平台 uploader 的执行逻辑

抖音额外支持：

- 商品链接
- 商品标题
- 缩略图

### 3.6 Web 管理台能力

旧版 Web 端已经存在这些页面：

- `Dashboard`
- `AccountManagement`
- `MaterialManagement`
- `PublishCenter`

从 Flask API 可确认已有的后端接口能力：

- 素材上传与管理
- 账号管理
- SSE 登录状态流
- 发布单条任务
- 批量发布任务
- cookie 上传/下载

### 3.7 已有能力的成熟度判断

最成熟：

- CLI
- uploader
- 小红书 / 抖音 / 快手发布链路

次成熟：

- 多账号管理
- 定时发布

较旧或次要：

- Flask + Vue Web 管理台

### 3.8 明确没看到的能力

当前没看到它原生提供：

- 内容采集
- AI 改写
- 选题/热点分析
- 品牌知识库
- 审核流
- 商家多租户模型

### 3.9 对后续拼接的价值

这个项目最像：

- “发布执行引擎”

能最快复用的部分：

- CLI contract
- uploader 分层
- 账号 cookie 管理
- 小红书/抖音图文与视频上传逻辑

## 4. `AIWriteX` 现成功能

### 4.1 项目形态

它同时具备这些形态：

- 内容生成引擎
- FastAPI Web 应用
- 模板与知识库系统
- 文章管理系统
- WebView/桌面化入口

本地重点文件：

- `references/open-source/AIWriteX/src/ai_write_x/core/unified_workflow.py`
- `references/open-source/AIWriteX/src/ai_write_x/core/content_generation.py`
- `references/open-source/AIWriteX/src/ai_write_x/adapters/platform_adapters.py`
- `references/open-source/AIWriteX/src/ai_write_x/web/app.py`
- `references/open-source/AIWriteX/src/ai_write_x/web/api/`
- `references/open-source/AIWriteX/knowledge/templates/`

### 4.2 已有内容工作流能力

从 `unified_workflow.py` 可以明确看到，它的主流程是：

1. 生成基础内容
2. 进行“维度化创意变换”
3. 做模板化或设计化格式转换
4. 保存内容
5. 可选发布

也就是说，它不是一个单纯的“调用模型生成文本”工具，而是已经有：

- 工作流编排
- 平台适配
- 保存与发布钩子

### 4.3 已有生成能力

从 `content_generation.py` 和 `generate.py` 能确认：

- 使用 CrewAI / 多 Agent 工作流
- 支持基于 topic 的生成
- 支持参考 URL 借鉴模式
- 支持 reference ratio
- 支持生成任务状态跟踪
- 支持停止生成
- 支持 WebSocket 日志输出

### 4.4 已有热点与输入能力

从 `tools/hotnews.py` 和 `config.yaml` 可确认：

- 支持多平台热搜获取
- 平台包括微博、抖音、小红书、快手、B站、头条、知乎等
- 可以按平台权重选择热点

### 4.5 已有模板系统

从 `web/api/templates.py` 和 `knowledge/templates/` 可确认：

- 模板分类管理
- 模板 CRUD
- 模板复制、移动、重命名
- 模板内容编辑
- 模板 HTML 预览

模板库本身已经存在多个行业分类：

- 健康养生
- 教育学习
- 新闻时事
- 情感心理
- 美食旅行
- 科技数码
- 时尚生活
- 职场发展
- 财经投资

### 4.6 已有文章管理能力

从 `web/api/articles.py` 可确认：

- 文章列表
- 文章内容读取
- 文章编辑保存
- 文章预览
- 文章删除
- 发布记录
- 发布历史
- 图片上传
- 图片库读取

### 4.7 已有发布能力

这里要特别区分：

#### 真正已实现的发布

- 微信公众号发布

从 `tools/wx_publisher.py` 和 `articles.py` 可确认：

- 微信上传图片
- 草稿/发布流程
- 封面处理
- 发布记录保存
- 多公众号凭据循环发布

#### 仅做了平台适配、未做真实发布

这些平台已经有 `Adapter`，但 `publish_content()` 仍返回 `NOT_IMPLEMENTED`：

- 小红书
- 抖音
- 今日头条
- 百家号
- 知乎
- 豆瓣

也就是说，`AIWriteX` 当前对这些平台的真实能力是：

- 有内容格式化逻辑
- 没有真正的发布执行逻辑

### 4.8 已有 Web 配置与管理能力

从 `web/api/config.py` 可确认：

- 配置读取和内存更新
- 配置落盘
- UI 配置
- 模板分类和模板读取
- 平台列表
- 系统消息
- 页面设计配置
- 更新检查

### 4.9 模型与图像能力

从 `config.yaml` 可确认：

- 支持多模型提供商配置
- 支持图片生成接口配置
- 支持 HTML / Markdown / txt 输出
- 支持 auto_publish 开关
- 支持 format_publish 开关

### 4.10 已有能力的成熟度判断

最成熟：

- 内容生成工作流
- 模板系统
- 文章管理
- 微信发布

次成熟：

- 热点输入
- Web 配置管理

明显未完成：

- 小红书 / 抖音等平台的真实发布

### 4.11 明确没看到的能力

当前没看到它原生提供：

- 多平台账号托管发布
- 小红书/抖音真实发布执行
- 对标账号内容抓取
- 统一素材库与发布任务队列

### 4.12 对后续拼接的价值

这个项目最像：

- “内容中台 + 模板系统”

能最快复用的部分：

- 生成工作流
- 热点/参考输入模式
- 模板分类管理
- 文章编辑/预览/保存
- 平台内容格式适配

## 5. `MediaCrawler` 现成功能

它同时具备这些形态：

- CLI / 命令行采集工具
- 多平台 crawler 模块
- FastAPI WebUI API
- 数据文件浏览接口
- WebSocket 日志与状态接口

本地重点文件：

- `references/open-source/MediaCrawler/main.py`
- `references/open-source/MediaCrawler/config/base_config.py`
- `references/open-source/MediaCrawler/api/main.py`

### 5.2 已有平台支持

从 `main.py` 的 `CrawlerFactory` 可确认支持：

- 小红书 `xhs`
- 抖音 `dy`
- 快手 `ks`
- Bilibili `bili`
- 微博 `wb`

### 5.5 已有抓取增强能力

从配置和 README 可确认：

- 评论抓取
- 二级评论抓取
- 指定 creator 抓取
- 指定帖子 ID 抓取
- 关键词抓取
- 媒体资源抓取开关
- 评论词云生成
- IP 代理池配置

### 5.6 已有存储能力

从 `config/base_config.py` 和 `store/` 可确认：

- excel

从 `store/` 目录还能看出：

- 各平台都有各自 store 实现
- 至少覆盖内容、评论、创作者等结构化数据持久化

### 5.7 已有 API / WebUI 能力

从 `api/main.py` 与 `routers/` 可确认：

- 启停 crawler
- 查看 crawler 状态
- 查看运行日志
- WebSocket 推送日志

- 浏览导出数据文件
- 下载导出数据
- 查看数据统计
- 获取平台配置项

这意味着它已经不只是采集脚本，而是有一个“可控的采集服务壳”。

### 5.8 已有数据查看能力

从 `api/routers/data.py` 可确认：

- 列出数据文件
- 预览 JSON / CSV / Excel
- 下载文件
- 统计文件数量、体积、平台分布、类型分布

### 5.9 已有能力的成熟度判断

最成熟：

- 多平台 crawler 分层
- search/detail/creator 三种采集模式
- 评论抓取
- 数据导出与多存储
- API 启停与日志

次成熟：

- WebUI 壳
- 文件预览

### 5.10 明确限制

这个项目最大的限制不是技术，而是许可和定位：

- README 明确写了仅供学习和参考
- README 明确写了禁止商业用途
- `main.py` 头部也重复写了非商业学习许可

所以它即便技术上能抓，也不能直接拿来当我们的商用核心底座。

### 5.11 对后续拼接的价值

这个项目最像：

- “采集导入工具 + 采集服务参考实现”

能最快复用的部分：

- creator / detail / search 模式设计
- crawler 模块分层
- 数据落盘方式
- API 控制面

## 7. 当前最重要的事实结论

### 7.1 `social-auto-upload` 不是内容系统，是发布系统

它最值得复用的，是：

- 发布执行
- 账号 cookie
- 多账号上传

### 7.2 `AIWriteX` 不是小红书/抖音发布器，是内容工作流

它最值得复用的，是：

- 生成链路
- 模板系统
- 文章管理

它对小红书/抖音目前不是“能发”，而是“能改成适配文案/脚本格式”。

### 7.3 `MediaCrawler` 不是发布系统，是采集系统

它最值得复用的，是：

- 对标账号 creator 模式
- search/detail/creator 的采集抽象
- 数据结构和 API 壳

但许可限制决定了它只能作为研究和接口设计参考。

---

## 8. 基于“现成功能”能拼出来什么

如果完全基于这三个项目当前已经存在的能力，能最快拼出的版本其实是：

1. 用 `MediaCrawler` 的思路做“对标账号内容导入”
2. 用 `AIWriteX` 的工作流做“内容改写和脚本生成”
3. 用 `social-auto-upload` 做“小红书/抖音多账号发布”

注意，这里说的是“能拼出的方向”，不是说三者能直接无缝接起来。

中间仍然缺一层：

- 统一的数据模型
- 统一任务编排
- 商家品牌信息层
- 统一 Web 工作台

---

## 9. 下一步最合适做什么

基于这份盘点，下一步不该再泛泛聊需求，而应该进入：

- “基于现成功能的取舍”

也就是：

1. 这三个项目各自保留哪些能力
2. 哪些能力不用，避免背负历史包袱
3. 哪些缺口必须自己补

这一步做完，才适合进入 V0.1 PRD。
