# 三项目能力拼接清单

## 1. 目的

这份文档用于回答一个非常实际的问题：

我们现在想做的“小红书 / 抖音矩阵获客平台”，在第一阶段到底能从现有开源项目里直接借到哪些能力，哪些只能借思路，哪些暂时不要碰。

当前参考的三个项目：

- `social-auto-upload`
- `AIWriteX`
- `MediaCrawler`

## 2. 当前产品目标再对齐

结合目前讨论，第一阶段的核心不是“做一个全网爬虫平台”，而是做一条能跑通的业务闭环：

1. 导入对标账号内容或公开内容链接
2. 提取标题、正文、口播、结构、选题方向
3. 结合商家自身情况生成改写版本
4. 输出适合小红书 / 抖音的文案或脚本
5. 统一管理授权账号并发布

后续增强方向：

- 数字人口播
- 更多平台扩展
- 更自动化的灵感采集
- 数据看板与获客归因

## 3. 三个项目各自最适合承担什么

### 3.1 `social-auto-upload`

最适合承担：

- 发布执行层
- 多账号登录与账号状态检查
- 小红书 / 抖音图文和视频发布
- 基于 CLI 的发布任务执行

本地重点目录：

- `references/open-source/social-auto-upload/sau_cli.py`
- `references/open-source/social-auto-upload/uploader/`
- `references/open-source/social-auto-upload/skills/xiaohongshu-upload/`
- `references/open-source/social-auto-upload/skills/douyin-upload/`

我们可以直接借的能力：

- `account_name` 维度的账号管理思路
- 小红书 / 抖音上传命令抽象
- 发布链路中的登录、检查、上传三段式流程
- 平台 uploader 分目录拆分方式

我们不建议直接沿用的部分：

- 它自带的前端/历史 Web 形态，不适合作为我们正式产品壳
- 项目整体仍在重构中，不能把业务核心完全绑死在它的现状结构上

结论：

- 这是当前三者里最适合真实接入的一层

### 3.2 `AIWriteX`

最适合承担：

- 内容工作流参考
- 改写与生成链路参考
- 模板管理和知识组织方式参考
- 热点/搜索/借鉴内容进入生成工作流的编排思路

本地重点目录：

- `references/open-source/AIWriteX/src/ai_write_x/core/unified_workflow.py`
- `references/open-source/AIWriteX/src/ai_write_x/core/content_generation.py`
- `references/open-source/AIWriteX/src/ai_write_x/adapters/platform_adapters.py`
- `references/open-source/AIWriteX/src/ai_write_x/tools/hotnews.py`
- `references/open-source/AIWriteX/knowledge/templates/`

我们可以直接借的能力：

- “导入/搜索 -> 生成 -> 模板适配 -> 发布前产物”的工作流拆法
- 平台适配层概念
- 模板库和知识库目录组织方式
- 生成多版本内容的思路

我们不建议直接沿用的部分：

- 产品形态偏公众号与写作助手，不等于本地生活商家矩阵 SaaS
- 不适合直接拿它的界面结构当我们的产品原型

结论：

- 更适合做“内容中台”的方法参考，而不是最终产品外壳

### 3.3 `MediaCrawler`

最适合承担：

- 对标账号内容导入
- 创作者主页内容抓取
- 平台内容采集层设计参考
- 采集结果存储和 API 暴露参考

本地重点目录：

- `references/open-source/MediaCrawler/media_platform/`
- `references/open-source/MediaCrawler/store/`
- `references/open-source/MediaCrawler/api/`
- `references/open-source/MediaCrawler/config/`

我们可以直接借的能力：

- 多平台 crawler 分层方式
- 小红书 / 抖音 / 快手等平台模块拆分
- 创作者主页、关键词、帖子详情等抓取入口设计
- 采集后存储层拆法

我们不建议直接沿用的部分：

- 项目 README 已明确写明“仅供学习和参考，禁止用于商业用途”
- 不适合直接作为我们对外商用的底座
- 作为第一阶段核心卖点的风险太高

结论：

- 更适合做内部参考、灵感导入研究、接口设计参考

## 4. 第一阶段可以拼出来的能力

如果只基于这三个项目的现有能力做拼接，第一阶段最现实的产品闭环是：

### 4.1 可做闭环

1. 导入公开内容链接或对标账号内容
2. 抽取标题、正文、口播文案、内容结构
3. 结合商家品牌信息改写成小红书/抖音版本
4. 人工审核
5. 多账号发布

### 4.2 对应拼接方式

- 内容导入层：参考 `MediaCrawler`
- 内容改写层：参考 `AIWriteX`
- 发布执行层：接入 `social-auto-upload`

### 4.3 当前就能比较稳做的产物

- 小红书图文文案
- 抖音标题 + 口播脚本
- 批量发布任务
- 多账号排期
- 商家品牌模板

## 5. 第一阶段不要高估的能力

以下这些不要在 V0.1 里假设已经成熟：

- 全自动批量稳定抓取所有对标账号全部内容
- 全自动高质量视频脚本拆解与镜头还原
- 直接数字人生成并自动投放
- 无风控地大规模矩阵发布
- 一键商用化 SaaS 交付

## 6. 对 V0.1 最有价值的拼接结论

### 6.1 先做“半自动灵感导入”

做法：

- 支持粘贴小红书 / 抖音链接
- 支持导入对标账号内容结果
- 支持人工选择内容进入改写工作台

不要先做：

- 自动全量扫全网

### 6.2 先做“商家定制改写”

做法：

- 给每个商家建立品牌信息卡
- 基于商家业务、卖点、地域、客群，改写生成内容

这是产品真正差异化的开始。

### 6.3 先做“授权账号发布中台”

做法：

- 小红书 / 抖音账号接入
- 账号状态检查
- 发布日志
- 失败重试

这是当前最有商业价值、也最有工程门槛的一层。

## 7. 下一步最适合做什么

基于这份拼接清单，下一步最适合进入：

- `V0.1 PRD`

因为现在已经不是“能不能做”的问题，而是：

- 第一版到底做哪些页面
- 第一版用户怎么走流程
- 第一版哪些能力必须有，哪些先不做
- 第一版怎么把三项目的能力重新包装成自己的产品
