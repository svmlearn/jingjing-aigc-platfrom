# 分支探索：网页端 Agent + 本地浏览器桥接抓取设想

## 1. 这是什么

这是一条**分支探索**，不是当前主方案。

它用于回答一个设想：

> 我们的产品未来能不能像 Codex 当前调用 `web-access` 一样，不依赖云端抓取集群，而是借用户自己的本地 Chrome 去抓小红书 / 抖音内容？

当前结论：

- **可以探索**
- 但它不是“网页天然可以做到”
- 必须在网页端之外，再补一个**本地浏览器桥接层**

---

## 2. 为什么现在会产生这个想法

本轮已经验证过：

- 在当前本机环境里，`web-access` 可以借助用户本地 Chrome
- 读取小红书首页卡片
- 进入帖子详情页
- 抓到正文与一部分评论

这会自然引出一个问题：

> 那未来产品能不能也复用这种模式，让用户自己的浏览器承担抓取？

---

## 3. 关键判断

### 3.1 不能直接“复用 skill”

当前这套能力之所以成立，是因为：

- `web-access` 是 **Codex 本地环境里的能力**
- 它能连本机 Chrome 的调试端口
- 它能通过本地代理去操控浏览器

这不等于：

- 我们未来的普通网页前端，天然就有这种权限

所以未来产品不能直接说：

- “网页调用一个 skill，就能控制用户浏览器”

更准确的说法应该是：

- **产品自己实现一个类似 `web-access` 的本地浏览器桥接层**

### 3.2 纯网页不能直接控制用户 Chrome

原因很简单：

- 浏览器沙箱限制
- 普通网页拿不到这种级别的浏览器控制权
- 更不可能默认获取用户登录态与页面控制能力

所以如果要走这条路，至少要有下面其中一种：

1. `Chrome 扩展`
2. `Chrome 扩展 + 本地桌面助手`
3. `桌面 App`

---

## 4. 最可能的产品形态

当前最适合想象的不是“纯 SaaS”，也不是“纯本地工具”，而是：

```text
网页端 Agent
    +
Chrome 扩展（本地桥）
```

它们的职责可以这样拆：

### 网页端

负责：

- 登录
- 商户资料
- 内容中心
- 改写工作台
- AI 生成
- 草稿管理
- 发布管理

### Chrome 扩展

负责：

- 打开指定页面
- 读取当前页面 DOM
- 抓取帖子详情
- 抓取博主主页内容列表
- 利用用户已登录的浏览器状态访问平台内容

---

## 5. 这条路的价值

如果这条路成立，它能绕开很多重基础设施问题：

- 不需要我们一上来维护浏览器集群
- 不需要一上来维护代理池
- 不需要集中保管用户的平台登录态
- 用户本地已经登录的平台账号，可以被就地利用

对于“小商户 / 单人运营 / 轻协同”这类场景，它是很有吸引力的。

---

## 6. 这条路的代价

它并不是零成本方案，而是把问题从“云端抓取”换成了“本地桥接”。

新增代价主要有：

- 用户需要安装扩展
- 浏览器权限申请要谨慎设计
- 用户关闭浏览器后，本地抓取能力就停了
- 不适合真正的后台无人值守批量任务
- 浏览器兼容与扩展审核都要考虑

所以它更像：

- 一条适合产品化探索的轻量路线

而不是：

- 当前主链路立刻替代托管 API 的确定方案

---

## 7. 当前对它的定位

当前建议把它放在下面的位置：

- `docs/探索/` 下的分支探索
- 作为未来抓取架构的备选分支

而不是：

- 当前 `V0.1-A` 的主线方案

当前主线仍应优先验证：

- 有没有稳定托管抓取 API 可以直接买

如果有，主线优先走 API。

如果没有，再进一步认真评估这条“本地浏览器桥接”路线。

---

## 8. 什么时候值得重新拉起这条探索

出现下面任一信号，就值得把这条分支重新拉上台面：

1. 托管抓取 API 覆盖不足
2. 托管抓取 API 成本明显偏高
3. 平台登录态内容必须依赖用户本地浏览器
4. 目标用户以单人运营为主，不适合云端重抓取方案

---

## 9. 当前一句话结论

这条路**可行，但不是当前主线**。

更准确的定位是：

- **一个值得保留的分支探索**
- 当前先不取代托管 API 方案
