# 小红书抖音矩阵获客平台-初版方案

## 1. 项目定位

### 1.1 目标用户

- 本地生活类小商家
- 第一阶段重点：健身房、瑜伽馆、普拉提馆、舞蹈工作室、美业门店
- 典型角色：老板、店长、兼职运营、代运营团队

### 1.2 核心痛点

- 不会持续产出小红书/抖音内容
- 有素材但不会整理成平台适配内容
- 想做矩阵号，但多账号管理和发布很麻烦
- 想参考同行内容，但缺少稳定的“灵感导入 -> 改写 -> 发布”闭环

### 1.3 产品一句话

一个面向本地商家的“小红书/抖音内容获客工作台”：把公开灵感、商家自有素材和品牌信息整理成可发布内容，并统一管理授权账号进行矩阵分发。

### 1.4 第一阶段做什么

- 聚焦小红书和抖音
- 聚焦图文笔记、短视频标题文案、发布排期
- 聚焦“内容生产效率”和“多账号分发效率”

### 1.5 第一阶段不做什么

- 不做“全网无限量爬取”作为核心卖点
- 不做评论区自动群发、私信轰炸、外挂式增长
- 不做复杂 CRM
- 不做跨行业通用大平台，先垂直打透本地生活

## 2. 三个开源项目怎么组合

这三个项目适合组合，但在系统里的角色不一样。

### 2.1 `social-auto-upload`

定位：发布执行层的核心参考项目，第一阶段可以真接入。

为什么适合：

- 重点覆盖小红书、抖音等国内平台
- 已经有多账号、CLI、上传、定时发布能力
- 比从零写平台 adapter 快很多

建议用法：

- 作为 `Platform Adapter` / `Publish Worker` 的底层实现
- 上层由我们自己包一层任务中心、账号中心、日志与重试机制
- 不直接把它原样当产品前台，而是作为“发布引擎”

### 2.2 `AIWriteX`

定位：内容工作流的参考项目，适合借思路，不建议重度耦合成产品底座。

为什么值得参考：

- 它已经验证了“采集/话题 -> AI 生成/改写 -> 发布”的工作流
- 适合借鉴 prompt 编排、模板化、配图和内容处理流程

不建议重度耦合的原因：

- 当前产品重心偏公众号与内容创作桌面工具
- 不天然等于“面向本地商家的矩阵 SaaS”
- 我们未来需要更强的商家知识库、门店模板、审批流和多租户能力

建议用法：

- 借它的内容链路设计
- 参考其模板系统、配置组织方式、AI 工作流拆法
- 不把核心业务直接绑死在它的 UI/应用形态上

### 2.3 `MediaCrawler`

定位：灵感导入层/研究工具，可做内部能力参考，不建议在 MVP 就作为商家侧主能力。

为什么它仍然重要：

- 多平台公开内容导入能力强
- 非常适合做“灵感池”“同行案例库”“选题观察”

为什么不该成为第一优先级：

- 商业化和平台合规风险最高
- 商家真正先买单的，往往不是“抓多少”，而是“能不能稳定地产内容并发出去”
- 采集是增强项，不是第一性价值

建议用法：

- 第一阶段只做“有限、可控的灵感导入”
- 优先支持手动粘贴链接、导入文本、导入商家自有素材
- 自动化采集放到后续增强版本，并做好权限、来源记录和内容溯源

## 3. 推荐的系统架构

### 3.1 总体原则

- 先做“可跑通闭环”，再做“大而全平台”
- 先做“授权发布 + AI 改写”，再扩展“灵感采集”
- 把“内容”和“账号发布”分层，避免后面平台策略变化时全盘重写

### 3.2 总体分层

```text
┌─────────────────────────────────────────────┐
│                Web Admin / Ops              │
│ 商家工作台 / 内容日历 / 发布管理 / 审核台        │
└─────────────────────────────────────────────┘
                    │
┌─────────────────────────────────────────────┐
│              Workflow Orchestrator          │
│ 导入任务 / 生成任务 / 审核任务 / 发布任务         │
└─────────────────────────────────────────────┘
        │                    │                 │
        │                    │                 │
┌──────────────┐   ┌────────────────┐   ┌────────────────┐
│ Ingest Layer │   │ Content Layer  │   │ Publish Layer  │
│ 灵感导入/素材库 │   │ 改写/模板/知识库 │   │ 账号/任务/平台适配 │
└──────────────┘   └────────────────┘   └────────────────┘
        │                    │                 │
        └────────────┬───────┴──────────────┘
                     │
          ┌──────────────────────────┐
          │ Shared Data & Infra      │
          │ Postgres / Redis / OSS   │
          │ Audit / Logs / Secrets   │
          └──────────────────────────┘
```

### 3.3 推荐技术栈

为了更顺手复用现有开源项目，我建议第一阶段偏 Python。

- 前端：Next.js 管理后台
- 后端 API：FastAPI
- 异步任务：Celery / RQ
- 数据库：PostgreSQL
- 缓存与队列：Redis
- 文件存储：S3 / MinIO
- 模型层：OpenAI-compatible API + 可切换模型配置
- 平台发布层：接 `social-auto-upload`

这样做的原因：

- `social-auto-upload`、`AIWriteX` 都更容易从 Python 生态吸收
- 平台自动化和 Worker 更适合放在异步任务体系里
- 后续如果前端要多租户 SaaS 化，Next.js 管理台会更舒服

## 4. 模块边界

下面这几个模块建议从一开始就切清楚。

### 4.1 商家与门店中心

职责：

- 商家、门店、品牌、操作员、角色权限
- 一个商家可对应多个门店和多个发布账号

不要承担：

- 不直接处理内容生成
- 不直接执行发布

核心对象：

- `Merchant`
- `Location`
- `User`
- `Role`

### 4.2 品牌知识库

职责：

- 存储门店介绍、课程类型、价格带、主打卖点、适用人群
- 存储禁用词、品牌语气、常用 CTA、优惠规则
- 存储“什么能说、什么不能说”

不要承担：

- 不负责具体发布
- 不直接绑定平台账号逻辑

核心对象：

- `BrandProfile`
- `Offer`
- `ContentPolicy`
- `AudienceSegment`

### 4.3 灵感导入层

职责：

- 导入公开内容链接
- 导入商家自己的图文、视频脚本、客户案例、课程海报
- 将导入内容标准化为统一素材结构

不要承担：

- 不直接输出最终发布文案
- 不直接耦合平台发布逻辑

核心对象：

- `SourceItem`
- `ImportedAsset`
- `SourceChannel`
- `SourceTrace`

建议第一阶段支持的导入方式：

- 粘贴小红书/抖音链接
- 粘贴文本
- 上传图片/视频
- 批量导入门店已有素材

### 4.4 内容工作台

职责：

- 根据品牌知识库 + 灵感素材生成内容草稿
- 区分小红书和抖音两种平台风格
- 支持“仿写风格但保留商家自身信息”
- 支持多版本文案生成

不要承担：

- 不直接做账号登录
- 不负责底层平台上传细节

核心对象：

- `ContentDraft`
- `PromptTemplate`
- `RewriteTask`
- `PlatformVariant`

建议这里重点做的能力：

- 一键改写成“小红书笔记”
- 一键改写成“抖音标题 + 口播/字幕稿”
- 按行业模板生成
- 按门店活动自动替换 CTA

### 4.5 审核与发布准备台

职责：

- 人工预览和修改
- 审核是否能发
- 选择门店、账号、时间
- 补充封面、标签、话题、定位信息

不要承担：

- 不直接执行底层自动化脚本

核心对象：

- `ReviewTask`
- `ApprovalRecord`
- `PublishPlan`

### 4.6 发布执行层

职责：

- 管理授权账号
- 调用平台 adapter 执行发布
- 处理排队、失败重试、状态同步

不要承担：

- 不做内容创作决策
- 不做品牌知识管理

核心对象：

- `PublishingAccount`
- `PlatformCredential`
- `PublishJob`
- `PublishResult`

建议实现方式：

- 平台适配器统一接口
- `social-auto-upload` 作为多个平台 adapter 的底层实现
- 由我们自己定义统一任务状态：
  - `pending`
  - `running`
  - `waiting_login`
  - `failed_retryable`
  - `failed_manual`
  - `published`

### 4.7 数据分析与获客归因

职责：

- 统计发布情况、内容产量、账号活跃度
- 后续接入播放、互动、线索转化

第一阶段先不做重：

- 暂不做复杂归因模型
- 暂不做 CRM 闭环

核心对象：

- `PostMetric`
- `LeadEvent`
- `Campaign`

### 4.8 运维与合规层

职责：

- 来源留痕
- 发布日志
- 敏感内容检测
- 账号异常预警

必须从第一阶段就有：

- 每条内容保留来源记录
- 每次发布保留任务日志
- 账号状态可视化

## 5. 我建议先做哪一层

### 5.1 结论

系统建设上，先打 `发布层`；
产品验证上，先跑一条“薄闭环”。

这两个说法不冲突。

### 5.2 为什么先打发布层

因为真正有门槛、也最决定产品成败的，是：

- 小红书/抖音账号授权是否稳定
- 多账号管理是否顺手
- 图文/视频内容是否真的能发出去
- 失败重试和日志是否可控

AI 改写这件事，短期内不是最大壁垒；发布链路才是。

### 5.3 但产品验证不能只做发布

如果只做发布层，用户会觉得它只是“一个上传工具”。

所以 MVP 最好做一条极薄的完整链路：

```text
导入一条灵感链接/一段原文
-> 选择门店品牌档案
-> 生成小红书版本 / 抖音版本
-> 人工修改
-> 选择账号和发布时间
-> 发布
```

也就是说：

- 工程上优先攻克发布执行能力
- 体验上先给用户一个完整闭环

## 6. MVP 版本路线

### V0.1 内部验证版

目标：

- 先在自己团队或代运营场景里跑通

必须有：

- 商家/门店基础信息
- 授权账号管理
- 粘贴链接或文本导入
- 小红书/抖音双平台改写
- 内容审核与发布
- 发布任务日志

不做：

- 自动批量采集
- 多租户计费
- 复杂数据看板
- 评论/私信 CRM

验证点：

- 1 个商家，2-5 个账号，能稳定跑完 20 条内容的生成与发布

### V0.2 试点商家版

目标：

- 给 3-10 个试点商家使用

新增：

- 内容日历
- 门店模板库
- 多账号批量排期
- 素材库
- 常用提示词模板
- 发布失败补偿机制

验证点：

- 商家能自己完成每周排期，不依赖技术人员陪跑

### V0.3 增强增长版

目标：

- 把“生成与发布工具”升级为“灵感驱动增长工具”

新增：

- 热点/同行灵感池
- 行业选题库
- 爆文结构拆解
- 内容复用建议
- 门店活动自动套版

验证点：

- 商家对系统的价值感知从“省事”变成“能持续产内容”

### V1.0 商业化版

目标：

- 面向更多商家稳定售卖

新增：

- 多租户 SaaS
- 套餐与计费
- 团队协作与审批
- 审计日志
- 基础经营看板
- 更完整的账号健康检测

## 7. 推荐的实施顺序

### 第 1 阶段：先做一条最薄闭环

顺序：

1. 商家/门店模型
2. 品牌知识库最小版
3. 内容改写最小版
4. 小红书/抖音发布适配
5. 发布任务状态页

目标：

- 尽快把第一条内容发出去

### 第 2 阶段：补运营效率

顺序：

1. 内容日历
2. 批量排期
3. 素材库
4. 模板库
5. 发布失败补偿

目标：

- 让 1 个运营能管多个账号

### 第 3 阶段：再补灵感导入

顺序：

1. 链接导入增强
2. 灵感池
3. 行业选题库
4. 同行内容拆解

目标：

- 让系统开始具备“帮你找内容方向”的能力

## 8. 这版方案的关键判断

### 8.1 不是先做“采集平台”，而是先做“内容工作台 + 发布中台”

因为小商家真正付费，是为了省时间、稳定产出、统一发号，不是为了研究爬虫。

### 8.2 `social-auto-upload` 是当前最值得真正接入的一个

它最接近我们第一阶段的硬需求。

### 8.3 `AIWriteX` 更适合借方法，不适合直接当产品外壳

可借其工作流思路，但 SaaS 产品形态要自己掌控。

### 8.4 `MediaCrawler` 更适合后置

它重要，但不应该成为第一个里程碑。

## 9. 下一步建议

我建议我们下一轮直接进入更具体的设计，优先做下面两份内容：

1. `V0.1 MVP 功能清单`
2. `系统信息架构图 + 页面清单`

到这一步时，我们就能开始决定：

- 首页工作台长什么样
- 内容改写流程怎么走
- 账号授权和发布任务界面怎么设计
- 第一批数据库表怎么建
