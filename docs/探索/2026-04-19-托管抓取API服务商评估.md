# 托管抓取 API 服务商评估

## 1. 评估目的

当前主问题不是“能不能自己搭抓取”，而是：

> 有没有足够稳定的托管抓取 API 服务商，能直接承担我们的小红书 / 抖音导入工作？

如果有，`V0.1-A` 主线优先走 API 方案。

如果没有，再回头补：

- 自建 `Worker`
- 自建 VPS
- 本地浏览器桥接等替代路线

评估日期：

- `2026-04-19`

---

## 2. 当前需要覆盖的抓取能力

本轮只看最接近业务闭环的 3 类能力：

1. `detail`
   输入单条帖子链接，返回详情
2. `creator`
   输入博主主页，返回帖子列表
3. `comments`
   返回评论与部分回复

当前不把下面这些作为第一轮硬门槛：

- 全网关键词海量搜索
- 超大规模并发抓取
- 全平台扩展
- 强实时监控

---

## 3. 评估标准

### 3.1 必看

- 是否有官方公开产品页面或文档
- 是否明确支持小红书 / 抖音
- 是否可通过 API / webhook 取回结构化结果
- 是否不需要我们自己维护代理池和浏览器集群

### 3.2 加分项

- 官方自己托管计算与反爬基础设施
- 有 SLA / uptime / 企业支持
- 字段结构稳定
- 支持 webhook

### 3.3 扣分项

- 只是社区脚本
- 核心能力靠第三方个人维护
- 官方页面没法确认覆盖范围
- 评论 / 主页列表只能间接拼出来

---

## 4. 候选服务商

## 4.1 `Bright Data`

### 当前看到的官方信号

官方有明确产品页：

- [Xiaohongshu Scraper](https://brightdata.com/products/web-scraper/xiaohongshu)
- [Douyin Scraper](https://brightdata.com/products/web-scraper/douyin)

我从官方页面确认到的点：

- `Xiaohongshu` 页面明确写了：抓取任务运行在 `Bright Data` 自己的基础设施上，不需要自己维护服务器或代理池
- `Douyin` 页面明确写了：可以采集 `video titles`、`descriptions`、`creator names`、`likes`、`comments`、`hashtags`
- 两页都强调：
  - managed cloud
  - built-in proxies & unblocking
  - API / webhook delivery
  - `99.99% uptime`

### 优点

- 这是当前最像“正式托管抓取 API 服务商”的一档
- 官方自己覆盖了 `Xiaohongshu` 和 `Douyin`
- 不要求我们先租 VPS
- 更适合直接做 `V0.1-A` 试点

### 风险

- `Xiaohongshu` 官方产品页虽然明确有站点级 scraper，但没有像 `Douyin` 页面那样把 `creator / comments / detail` 模式逐项写死
- 这意味着：
  - 它大概率能做
  - 但仍需要试跑确认字段完整度

### 当前判断

- **第一优先级候选**
- 最适合拿来做 `V0.1-A` 的正式试用验证

---

## 4.2 `Apify`

### 当前看到的官方信号

官方平台与 API 文档都很成熟：

- [Run Actor API](https://docs.apify.com/api/v2/act-runs-post)
- [Security Whitepaper](https://apify.com/security-whitepaper.pdf)

针对小红书 / 抖音，平台上确实有现成 Actor：

- [RedNote User Posts Scraper](https://apify.com/easyapi/rednote-xiaohongshu-user-posts-scraper)
- [RedNote Comments Scraper](https://apify.com/easyapi/rednote-xiaohongshu-comments-scraper)
- [All-in-One RedNote Scraper](https://apify.com/huggable_quote/xiaohongshu-all-in-one-scraper)
- [Douyin Comments Scraper](https://apify.com/natanielsantos/douyin-comments-scraper)

### 优点

- API 和 webhook 集成成熟
- 试错成本低
- 很适合快速 PoC
- 覆盖 `detail / creator / comments` 的拼装可能性比较高
- `Run Actor` 接口本身是通用执行接口，能否直接“传链接抓取”取决于所选 actor 的输入 schema，这一点已经另整理为：
  - `2026-04-19-Apify-最小可验证调用清单.md`

### 风险

最关键的问题不是平台本身，而是：

- 这些小红书 / 抖音 Actor 大多标注为 **Maintained by Community**

这意味着：

- `Apify` 平台是稳定的
- 但具体到某个中文社媒 Actor，并不等于企业级稳定

比如我查到的页面里，多个 Actor 都明确显示：

- `Maintained by Community`

### 当前判断

- **第二优先级候选**
- 更适合做快速验证与成本测试
- 但不适合在没试跑前就直接认定为“稳定主方案”
- `2026-04-19` 已完成首轮真实 token 样本测试，详见：
  - `2026-04-19-Apify-实测记录-首轮.md`
- 首轮结果说明：
  - 抖音 `detail / comments` 比较可用
  - 小红书 `creator` 有希望
  - 小红书 `detail / comments` 需要继续专项验证
- `2026-04-19` 第二轮小红书专项测试后，结论上调为：
  - 小红书 `detail` 在传完整自然链接时可用
  - 小红书 `profile / userPosts` 可用
  - 小红书 `comments` 使用 `easyapi/all-in-one-rednote-xiaohongshu-scraper` 的 `comment` 模式可跑通
  - 详见：
    - `2026-04-19-Apify-实测记录-第二轮-小红书.md`

## 4.3 `Scrapeless`

### 当前看到的官方信号

我查到的是：

- [Scraping API Quickstart](https://docs.scrapeless.com/zh/scraping-api/quickstart/getting-started/)
- [Webhook](https://docs.scrapeless.com/zh/scraping-api/features/webhook/)
- [Scraping Browser Quickstart](https://docs.scrapeless.com/zh/scraping-browser/quickstart/getting-started/)

这些文档说明：

- 它有通用抓取 API
- 有异步任务 + webhook
- 也有托管浏览器能力

### 优点

- 基础设施形态是对的
- 也支持异步任务和 webhook
- 可以作为后备方案观察

### 风险

当前我没有在官方页面上直接确认到：

- 小红书 ready-made scraper
- 抖音 ready-made scraper
- `detail / creator / comments` 的明确站点级覆盖声明

所以它更像：

- 一个通用抓取平台

而不是当前就能确认的：

- 现成小红书 / 抖音稳定方案

### 当前判断

- **观察名单**
- 当前不作为第一轮主选型

## 5. 当前推荐排序

基于 `2026-04-19` 查到的官方资料，我当前建议排序是：

1. `Bright Data`
2. `Apify`
3. `Scrapeless`

补充说明：

- 第二轮实测后，`Apify` 已经可以作为 `V0.1-A API-first PoC` 的直接候选
- 但是否替代 `Bright Data` 成为正式主方案，仍需看更大样本的稳定性和成本

---

## 6. 推荐结论

### 6.1 当前主线建议

当前最值得直接推进的主线是：

- **先用 `Bright Data` 做正式试跑**

原因：

- 它是这轮里最像“正式 API 服务商”的
- 官方明确覆盖 `Xiaohongshu` 与 `Douyin`
- 明确强调不需要自己维护服务器和代理池
- 明确有 managed cloud、API、webhook、uptime、企业支持

### 6.2 `Apify` 怎么用更合理

`Apify` 不要直接替代 `Bright Data` 做正式结论。

更合理的定位是：

- 并行做低成本 PoC
- 重点验证：
  - `creator`
  - `comments`
  - 结构字段完整度

如果 `Bright Data` 价格或覆盖不理想，`Apify` 可以成为备选。

### 6.3 当前不建议的做法

当前不建议直接默认：

- 先租 VPS
- 先自建抓取集群
- 先自己养浏览器自动化基础设施

因为在确认托管方案是否可用前，这些都太早。

---

## 7. 当前还缺的最后一脚

虽然已经能做推荐，但还差一轮真实验证：

### 必测用例

1. 小红书 `detail`
2. 小红书 `creator`
3. 小红书 `comments`
4. 抖音 `detail`
5. 抖音 `creator`
6. 抖音 `comments`

### 每个用例只看 4 件事

1. 能不能成功返回
2. 字段是否够用
3. 评论是否完整
4. 成本是否能接受

---

## 8. 当前一句话结论

如果现在就要选一个主方向：

- **主线先走托管 API**

如果现在就要选一个最值得优先试的服务商：

- **先试 `Bright Data`**

如果要留一个低成本备选：

- **并行看 `Apify`**
