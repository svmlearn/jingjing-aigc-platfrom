# 托管抓取 API 验收清单

## 1. 这份清单的用途

这份文档不关心供应商讲得多漂亮，只关心一件事：

> 它返回的数据，够不够支撑我们当前的主链路  
> `导入内容 -> 看评论/结构 -> 改写内容`

适用对象：

- `Bright Data`
- `Apify`
- 未来任何其他托管抓取 API

评估日期：

- `2026-04-19`

---

## 2. 当前主链路真正需要的能力

`V0.1-A` 不是做全网情报平台，所以第一轮只验这 3 类：

1. `detail`
   输入单条帖子链接，拿到帖子详情
2. `creator`
   输入博主主页链接，拿到主页资料或帖子列表
3. `comments`
   输入帖子链接，拿到评论和部分回复

这轮不把以下能力当硬门槛：

- 海量关键词搜索
- 大规模并发采集
- 7x24 小时监控
- 全平台扩展

---

## 3. 验收样本应该怎么准备

每个平台至少准备 3 组固定样本：

1. `detail` 样本
   一条正常可访问的帖子链接
2. `creator` 样本
   一个正常可访问的博主主页链接
3. `comments` 样本
   一条评论数足够多的帖子链接

建议：

- 小红书、抖音各准备一套
- 同一套样本连续测试 3 次
- 再换一套不同样本交叉测试

这样我们才能看出：

- 是平台本身不稳
- 还是个别链接不稳

---

## 4. 三类能力的最低验收标准

## 4.1 `detail`

### 必须成功拿到

- 平台
- 原始帖子链接
- 帖子唯一标识或可替代主键
- 标题
- 正文
- 作者名或作者标识

### 最好还能拿到

- 点赞数
- 评论数
- 收藏/转发等互动信息
- 发布时间
- 标签
- 图片/视频资源链接

### 失败判定

以下任一情况出现，就不能算通过：

- 只能拿到空壳 metadata，没有正文
- 标题、正文、作者三者缺失其二
- 返回结构极不稳定，同一类链接字段名频繁变化

---

## 4.2 `creator`

### 必须成功拿到

- 主页链接
- 作者名或作者唯一标识
- 至少一批帖子列表

### 最好还能拿到

- 粉丝/关注/获赞等主页指标
- 头像
- 简介
- 每条帖子标题
- 每条帖子的互动指标

### 失败判定

- 只能拿到主页基础信息，没有帖子列表
- 只能拿到少量残缺列表，无法形成内容池
- 返回的列表没有稳定的帖子 ID 或 URL

---

## 4.3 `comments`

### 必须成功拿到

- 帖子链接或帖子唯一标识
- 评论正文
- 评论作者信息

### 最好还能拿到

- 回复结构
- 点赞数
- 评论时间
- IP 属地

### 失败判定

- 只能拿到评论总数，拿不到评论内容
- 只能拿到第一页极少量评论，而且无法稳定复现
- 评论内容没有稳定结构，无法落表

---

## 5. 和我们当前数据模型的映射要求

当前最关键的是能不能稳定写入这 3 张表：

1. `import_jobs`
2. `source_items`
3. `imported_comments`

参考当前 schema：

- [V0.1-Postgres-Schema-草案.md](/Users/wy/Desktop/静境/静境4.0/小红书抖音矩阵获客平台/docs/架构规范/V0.1-Postgres-Schema-草案.md)

## 5.1 写入 `import_jobs` 所需

服务商至少要让我们记录：

- `platform`
- `import_type`
- 原始输入参数
- 本次导入任务状态
- 成功条数 / 错误信息

如果服务商只给纯内容，不给任务状态，我们也还能自己包一层任务记录。  
这一项不是硬伤。

## 5.2 写入 `source_items` 所需

最低映射字段建议：

- `platform`
- `source_type`
- `external_item_id`
- `source_url`
- `creator_id`
- `creator_name`
- `title`
- `body_text`
- `engagement_snapshot`
- `trace_payload`

如果供应商返回结构不统一，也可以先把原始包放进：

- `trace_payload`

但下面 4 项尽量要稳定：

- `external_item_id`
- `source_url`
- `creator_name`
- `body_text`

## 5.3 写入 `imported_comments` 所需

最低映射字段建议：

- `source_item_id`
- `external_comment_id`
- `parent_external_comment_id`
- `author_name`
- `content`
- `like_count`
- `reply_count`
- `published_at`

这里最关键的是：

- 评论正文能不能稳定取到
- 主评论和回复能不能区分

---

## 6. 真正要看的是“稳定性”，不是“单次能跑通”

一个服务商即使单次能跑通，也不等于可选型。

最低建议用这 4 条来打分：

1. `success_rate`
   同一批样本连续 3 次成功率
2. `field_completeness`
   必要字段齐全程度
3. `schema_stability`
   返回字段结构是否稳定
4. `ops_friction`
   是否强依赖 cookie、人工干预、奇怪调参

建议最低判断线：

- `detail` 成功率至少达到 `80%`
- `creator` 成功率至少达到 `70%`
- `comments` 成功率至少达到 `60%`

这不是最终 SLA，只是 `V0.1-A` 试点是否能开的最小线。

---

## 7. 是否依赖 cookie，要单独验收

这个点对我们很关键，因为它直接影响产品形态。

要分别测试两组：

1. 不带 cookie
2. 带 cookie / session

如果结论是：

- `detail` 不带 cookie 可以
- `creator` 勉强可以
- `comments` 强依赖 cookie

那产品侧就要尽早做取舍：

- 先接受“评论能力偏弱”
- 还是转向本地浏览器桥接
- 还是保留云端 API 做 detail/creator，评论后置

---

## 8. 当前建议的验收流程

### 第一轮

- 先测单条同步接口
- 目的：确认它能不能直接传链接拿结果

### 第二轮

- 再测批量异步接口
- 目的：确认它适不适合导入任务

### 第三轮

- 做字段映射入库演练
- 目的：确认能否稳定落到 `source_items` / `imported_comments`

### 第四轮

- 做成本估算
- 目的：确认真实单商户使用是否划算

---

## 9. 当前可直接套用到 Apify 的判断

基于 `2026-04-19` 查到的 Apify 文档和 actor 页面，我当前判断是：

- `detail`：很有希望先跑通
- `creator`：可跑通概率也不低
- `comments`：最值得重点盯，可能最受 cookie / 站点策略影响

这是一条**值得试**的 API 路线，  
但还不能直接升级成“稳定主方案已确认”。

---

## 10. 当前可执行结论

如果某个供应商满足下面这 3 条，就可以进入主线方案候选：

1. `detail` 稳定
2. `creator` 可用
3. `comments` 至少不是完全不可用

如果它再同时满足：

- 不需要我们自建浏览器集群
- 不需要我们长期维护代理池
- 接入方式就是标准 API / webhook

那它就已经足够强，可以优先于自建 `Worker` 进入 `V0.1-A` 主方案。
