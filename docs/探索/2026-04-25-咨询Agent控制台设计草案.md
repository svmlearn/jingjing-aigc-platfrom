# 2026-04-25 咨询 Agent 控制台设计草案

## 1. 文档定位

这份文档记录当前已经明确的 `咨询 Agent` 后台配置方向，重点覆盖：

- System Prompt 的可编辑与生效方式
- Skill 的创建、启用、禁用与绑定 Agent
- Knowledge 的平台知识启用方式
- Agent 测试台的必要性
- 仍需要继续讨论的流程空白

本稿属于探索文档，不是最终 PRD，也不代表代码已经实现。

## 2. 当前已明确的结论

### 2.1 Agent 容器是主体

后台配置不应只围绕一份 prompt 或一组 skill 展开，而应以 `Agent 容器` 为主体。

当前第一版只落地：

```text
+----------------------+
| consultation_agent   |
| 咨询 Agent           |
+----------------------+
```

后续可扩展：

```text
consultation_agent  咨询 Agent
article_agent       图文 Agent
video_agent         视频制作 Agent
```

第一版设计需要预留多 Agent，但页面和实现可以先只开放咨询 Agent。

### 2.2 Tool 与 Skill 必须区分

`Tool` 是代码层封装的受控后端能力，例如：

- 读取商家资料
- 检索平台知识库
- 更新策略快照
- 更新内容日历
- 生成图文 brief
- 生成视频 brief
- 读取历史内容

这些能力由代码控制，不自由开放给管理员配置。

`Skill` 是管理员可配置的能力说明、行为策略、场景方法论，本质是受控 prompt 片段。它可以影响 Agent 如何判断和表达，但不等于让 Agent 获得新的底层执行权限。

一句话边界：

```text
Tool 决定 Agent 能做什么。
Skill 决定 Agent 在某类场景下应该怎么想、怎么问、怎么答。
```

### 2.3 当前后台里的 Enabled Skills / Tools 需要重新命名

现有代码中 `platform_settings.consultation_agent.enabledTools` 对应的是内部 tools。

但产品概念上不应继续把这组配置叫 `Skills / Tools` 混在一起。

后续后台建议拆成：

- Agent 服务配置
- System Prompt
- Skills
- Knowledge
- 内部工具状态摘要

内部工具最多展示为只读运行能力摘要，不作为第一版管理员自由开关。

### 2.4 System Prompt 是 Agent 级配置

System Prompt 归属 Agent 容器。

当前咨询 Agent 已经支持后台编辑 `consultationAgent.systemPrompt` 并在下一轮咨询生效。

后续需要补强：

- 当前生效版本
- 草稿版本
- 发布动作
- 回滚动作
- 修改记录
- 测试预览

最低要求是管理员改 prompt 后知道：

- 现在是否已生效
- 生效在哪个 Agent
- 能否回到上一个稳定版本

### 2.5 Skill 是可绑定到 Agent 的 prompt 片段

Skill 第一版不做文件扫描，不动态加载 `SKILL.md`，不开放代码执行。

Skill 应由管理员在后台创建，并绑定到一个或多个 Agent。

当前讨论确认的最小字段：

```text
skill_id        系统内部 ID，不在普通界面暴露
name            Skill 名称
description     Skill 描述，用于管理员理解它解决什么问题
when_to_use     何时使用，用于 Agent 判断是否应加载该 Skill
body            Skill 正文，也就是按需加载的 prompt 片段
agent_ids       绑定的 Agent，第一版主要是 consultation_agent
dependencies    可选依赖，例如 knowledge_retrieval
status          draft | enabled | disabled
created_at
updated_at
```

`description` 和 `when_to_use` 不完全一样：

```text
description: 给人看的资产说明，回答“这个 Skill 是什么、解决什么问题”。
when_to_use: 给模型看的触发说明，回答“什么情况下应该调用这个 Skill”。
```

例如：

```text
description:
用于处理本地生活商家的门店定位、客群拆解和内容方向判断。

when_to_use:
当用户询问门店定位、目标客群、差异化卖点、成交异议、内容方向或不知道账号该怎么做时使用。
```

不进入第一版的字段：

- 风险等级
- 优先级
- 行业范围
- 商家范围
- 复杂触发条件
- 动态读取外部文件

### 2.6 Skill 的启用是 Agent 级启用

Skill 创建后不应自动全局生效。

推荐流程：

```text
创建 Skill
-> 保存为 draft
-> 在 Agent 配置里选择这个 Skill
-> 该 Agent 的候选 Skill 列表里出现它
-> 模型按需加载完整 Skill 正文
```

如果 Skill 状态是 `disabled`，即使某个 Agent 曾经绑定过它，也不进入该 Agent 的候选 Skill 列表。

Skill 冲突不作为系统层能力处理。创建和挂载 Skill 的人需要自己判断一个 Agent 下应该挂哪些 Skill，系统不做“表达风格冲突”“策略冲突”这类复杂判断。

### 2.7 Knowledge 当前指平台知识

本轮讨论中的 Knowledge 先指：

```text
平台管理员维护的平台知识库
```

它包括：

- 行业方法论
- 内容 SOP
- 禁忌话术
- 平台规则
- 案例拆解
- 运营模板

商家自己的资料库另外记录为后续功能：

```text
商家端在「商家设置」中增加「商家资料库」
```

该能力优先级后置，不进入当前 Agent 控制台第一版主范围。

### 2.8 Knowledge 以 Agent 服务开关接入

咨询 Agent 应有一个 Knowledge 服务开关：

```text
Knowledge 服务：启用 / 关闭
```

第一版建议：

- 先有知识集，再由 Agent 挂载知识集
- 启用后，咨询 Agent 只检索当前 Agent 已挂载知识集里的 `indexed` 平台知识
- 关闭后，咨询 Agent 不检索平台知识
- 不让新上传知识直接影响所有线上 Agent
- 不先做“按 Skill 绑定知识文档”

如果某个 Skill 声明依赖 `knowledge_retrieval`，但当前 Agent 关闭 Knowledge 服务，后台应提示管理员。

### 2.9 线上咨询 Agent 绑定

当前只需要一个线上咨询入口。

后台应有一个明确配置：

```text
当前线上咨询 Agent: agent-A
```

商家端 `/dashboard` 默认使用这个线上咨询 Agent。

后续可以扩展为：

```text
房地产商家 -> 咨询 Agent A
教培商家   -> 咨询 Agent B
IT 商家    -> 咨询 Agent C
```

但第一版不做按商家或行业自动路由，只保留“当前线上咨询 Agent”这一个绑定。

### 2.10 Agent 复制

后台应支持复制 Agent。

复制 Agent 时：

- 复制 System Prompt
- 复制已挂载的 Skill 列表
- 复制已挂载的 Knowledge Set 绑定
- 弹窗要求填写新 Agent 名称
- 生成新的 Agent ID
- 不复制线上绑定状态
- 不复制服务启动状态

也就是说，复制出来的 Agent-B 默认是测试/草稿容器，不会因为 Agent-A 在线上而自动上线。

### 2.11 会员与积分是横切底座

商家会有会员身份：

```text
free | plus | pro | max
```

其中：

- `free` 可以有一笔初始赠送积分。
- `plus / pro / max` 付费后获得对应积分或权益。
- 具体权益后续再定义。

但底层现在要先预留，因为它会影响：

- 咨询 Agent 对话
- Knowledge / Memory 检索
- 图文生成
- 视频生成
- 发布链路
- 后续不同 Agent 的使用权限

设计原则：

```text
Agent 配置决定“能力怎么工作”。
会员 / 积分层决定“某个商家能不能用、用一次扣不扣、扣多少”。
```

不要把会员权益写死到某个 Agent 配置里。所有真实商家侧的 AI 消耗，都应先经过统一的 entitlement / credits gate。

当前代码里已有 `free / plus / pro` 和 `dailyCredits` 的早期配置，但这是早期“每日改写额度”模型。后续需要升级为更通用的：

```text
membership_tier: free | plus | pro | max
credit_balance / credit_ledger
entitlement_rules
usage_events
```

管理员测试台不扣商家积分，也不要求测试商家账户有可用积分。

## 3. 第一版后台信息架构草案

建议在平台管理台增加或重组为：

```text
平台管理台
├── 总览
├── 邀请码
├── 商户
├── Agent 配置
│   ├── Agent 列表
│   ├── Agent 基础信息
│   ├── System Prompt
│   ├── 挂载 Skills
│   ├── 挂载 Knowledge Sets
│   └── 当前线上咨询 Agent
├── 技能管理
│   ├── 单体技能
│   └── 技能集（后置）
├── 知识管理
│   ├── 知识文档
│   └── 知识集
├── Agent 调试
│   └── 选择任意 Agent 做测试
└── 系统配置
```

这里的边界是：

- `Agent 配置`：一个 Agent 作为容器，编辑它的 System Prompt，并选择挂哪些 Skill / Knowledge Set。
- `技能管理`：创建和维护可复用 Skill 资产。
- `知识管理`：上传知识文档，并组织成可挂载的知识集。
- `Agent 调试`：选择任意 Agent 容器，验证它当前挂载的 prompt、skills、knowledge 是否符合预期。

## 4. Agent 容器配置草案

### 4.1 Agent 基础信息

```text
agent_id: 系统生成，不可修改
display_name: 咨询 Agent A
role: 本地生活商家内容咨询顾问
summary: 帮助商家沉淀定位、客群、卖点、内容策略和内容日历
service_status: draft | enabled | disabled
```

第一版可以内置一个初始咨询 Agent，但不要把 `agent_id` 固定死为唯一咨询 Agent。后台需要允许复制出 Agent-B，用于测试新 prompt、skill 或 knowledge set。

`service_status` 只表达 Agent 自身生命周期，不表达是否线上：

```text
draft    草稿 / 测试中，只能在 Agent 调试里使用，不服务商家端。
enabled  已启用，可被设置为当前线上咨询 Agent，也可只作为备用 Agent。
disabled 已禁用，不服务商家端；如果仍被线上绑定引用，商家端显示服务维护中。
```

是否正在服务商家端，由 `agent_route_bindings` 决定：

```text
consultation_default -> agent_id
```

### 4.2 服务开关

Agent 下至少需要三个服务开关：

```text
Agent 服务：启用 / 关闭
System Prompt：启用 / 关闭
Knowledge 服务：启用 / 关闭
```

其中：

- Agent 服务关闭：商家端咨询入口应提示该服务暂不可用。
- System Prompt 关闭：不建议真实关闭，可理解为使用默认系统 prompt。
- Knowledge 服务关闭：不执行平台知识检索，但不影响商家资料、会话上下文和工具链。

Skill 不建议作为一个总服务开关，而是每个 Skill 自己启用或禁用。

### 4.3 复制 Agent

复制入口建议放在 Agent 详情页。

流程：

```text
管理员点击「复制 Agent」
-> 弹窗输入新 Agent 名称
-> 系统复制当前 Agent 的 System Prompt、Skill 绑定、Knowledge Set 绑定
-> 生成新的 agent_id
-> 新 Agent 默认不设为线上咨询 Agent
-> 新 Agent 默认 service_status = draft
```

复制不携带：

- 当前线上咨询 Agent 绑定
- 服务启动状态
- 历史测试记录
- 历史咨询记录

这个能力用于测试新配置：

```text
线上 Agent-A 保持稳定
-> 复制出 Agent-B
-> Agent-B 挂载新 Skill / 新 Knowledge Set
-> 在 Agent 调试里测试 Agent-B
-> 测试满意后，再把配置挂回 Agent-A 或切换线上咨询 Agent
```

### 4.4 当前线上咨询 Agent

第一版后台只需要一个线上绑定：

```text
consultation_default -> agent_id
```

商家端咨询页读取这个绑定。

如果该 Agent 的 `service_status` 为 disabled，商家端展示：

```text
服务维护中
```

不要把测试中的 Agent 自动暴露给商家端。

## 5. System Prompt 管理流程草案

### 5.1 编辑与发布

推荐流程：

```text
管理员进入咨询 Agent
-> 打开 System Prompt
-> 编辑草稿
-> 保存草稿
-> 可选：在 Agent 调试里验证草稿效果
-> 发布为当前生效版本
```

### 5.2 版本与回滚

最低需要保留：

- 当前生效版本
- 最近一次草稿
- 最近若干历史版本

历史版本建议记录：

```text
version_id
agent_id
body
status: draft | active | archived
change_note
created_by
created_at
activated_at
```

### 5.3 需要避免的行为

- 管理员输入后立即影响线上咨询，无法测试。
- 没有回滚记录。
- 不知道当前商家端实际用的是哪一版 prompt。
- system prompt 与 skill 混在同一个大文本框里。

## 6. Skill 管理流程草案

### 6.1 创建 Skill

推荐流程：

```text
管理员进入技能管理
-> 新建 Skill
-> 填写名称、描述、when_to_use、正文
-> 选择可选依赖：如 knowledge_retrieval
-> 保存为草稿
-> 如要用于某个 Agent，到 Agent 配置中勾选挂载
```

### 6.2 启用 Skill

推荐流程：

```text
管理员打开 Skill 详情
-> 可选：先挂到测试 Agent-B 后，在 Agent 调试里验证
-> 将 Skill 状态改为 enabled
-> 在目标 Agent 配置中勾选挂载
-> 下一轮 Agent 调用时进入该 Agent 的候选 Skill 列表
```

### 6.3 禁用 Skill

推荐流程：

```text
管理员点击禁用
-> 系统提示禁用后不再进入任何 Agent 的候选 Skill 列表
-> 保存状态
-> 历史咨询记录不回写改变
```

禁用 Skill 不应删除历史记录。

### 6.4 删除 Skill

删除流程暂不建议第一版开放。

更稳的第一版是：

```text
只允许禁用，不允许硬删除。
```

如果确实需要删除，应只允许删除从未启用过的 draft。

## 7. Knowledge 管理流程草案

### 7.1 平台知识上传

当前已有平台知识上传、切块、embedding、检索能力。

第一版继续沿用：

```text
上传文本类知识
-> 必须选择至少一个知识集
-> 入库
-> indexed 后成为可加入知识集的知识文档
```

### 7.2 知识集

第一版需要先有知识集。

原因：

```text
如果新知识上传后直接进入所有 Agent 检索，会影响线上咨询稳定性。
知识集可以让管理员先把新知识挂到测试 Agent-B，验证后再挂到线上 Agent-A。
```

知识集最小字段：

```text
knowledge_set_id
name
description
status: draft | enabled | disabled
document_ids
created_at
updated_at
```

知识文档与知识集是多对多关系：

```text
一篇知识文档可以进入多个知识集
一个知识集可以包含多篇知识文档
```

新上传知识必须选择知识集，不做“上传后自动全局生效”。

### 7.2.1 初始平台知识集

第一版可以预置一个初始平台知识集，例如：

```text
name: 基础平台知识集
status: enabled
```

这个知识集的作用是承接当前已有的平台知识，方便从旧知识库平滑迁移到“Agent 挂载知识集”的新模型。

“初始”不是一种特殊状态，也不是说以后所有新知识都自动进入它。新上传知识仍然必须由管理员选择要加入哪个知识集。

### 7.3 Agent 使用 Knowledge

推荐运行逻辑：

```text
咨询 Agent 的 Knowledge 服务启用
-> 读取该 Agent 挂载的知识集
-> 用户发送咨询消息
-> 后端构造检索 query
-> 在所有已挂载知识集包含的 indexed 文档中合并检索
-> 将命中片段作为 knowledge context 注入
```

第一版不做知识集优先级，也不做知识冲突判断。命中排序交给向量相似度和后端检索策略。

### 7.4 商家资料库

商家资料库记录为后续功能。

推荐后续入口：

```text
商家端
-> 商家设置
-> 商家资料库
```

资料类型候选：

- 门店介绍
- 项目介绍
- 老板 / 主理人经历
- 活动说明
- 常见问答
- 成交异议
- 真实案例

本轮不展开实现。

## 8. 运行时上下文组装草案

咨询 Agent 每轮调用模型时，第一段上下文建议只放稳定配置和可用能力清单：

```text
1. 平台安全规则
2. Agent 当前生效 System Prompt
3. Runtime Policy：输出约束、工具边界、服务状态
4. 当前 Agent 可用 Skill 候选列表：name / description / when_to_use
5. 当前 Agent 可用工具 / 可调用资源清单
6. 商家基础资料摘要
7. 当前会话短期上下文
8. 当前用户消息
```

Skill 候选列表建议使用明显边界：

```text
<available-skills>
Skill: ...
Description: ...
When to use: ...
</available-skills>
```

完整 Skill 正文不需要每轮全部注入。模型判断需要某个 Skill 时，再按 Skill 名称加载正文。

Knowledge 和 Memory 也不需要每轮全部预注入。模型需要时，通过受控工具调用检索：

```text
retrieve_platform_knowledge
retrieve_merchant_memory
read_merchant_profile
```

工具返回的 Knowledge 注入建议使用明显边界：

```text
<knowledge-context>
Source: platform knowledge set
Knowledge Set: ...
Title: ...
Content: ...
</knowledge-context>
```

工具返回的商家长期记忆也建议使用明显边界：

```text
<merchant-memory-context>
Source: merchant memory
Title: ...
Content: ...
</merchant-memory-context>
```

这样做是为了避免模型把 skill、knowledge、memory、用户消息混成同一类指令。

### 8.1 统一工具调用层

运行时建议采用类似 Claude Code 的工具调用思路：

```text
模型看到可用能力清单
-> 模型输出结构化 tool call / JSON
-> 后端校验该 Agent 是否允许使用这个能力
-> 后端校验商家会员权益 / 积分是否允许本次调用
-> 后端执行对应函数
-> 如需扣积分，记录 usage event / credit ledger
-> 工具结果回填给模型
-> 模型继续生成最终回复
```

在抽象意义上，`Skill / Knowledge / Memory` 都可以被看作 Agent 可调用的上下文能力，但产品后台仍要区分它们：

```text
Skill    = 加载一段行为策略 / 场景方法论 prompt
Knowledge = 检索平台知识集里的内容片段
Memory   = 读取商家资料、长期记忆、会话沉淀
Tool     = 代码层真正执行这些动作的后端函数
```

第一版可先把这些后端函数收敛成少量受控能力：

```text
load_skill(skill_id)
retrieve_platform_knowledge(query, knowledge_set_ids)
retrieve_merchant_memory(query, merchant_id)
read_merchant_profile(merchant_id)
```

管理员配置 Skill 时不能直接新增底层工具权限。它只能声明依赖某类能力，例如 `knowledge_retrieval`，真正能不能调用由 Agent 配置和后端校验决定。

商家侧真实调用还要再经过权益与积分校验：

```text
check_entitlement(merchant_id, action_type)
reserve_or_consume_credits(merchant_id, action_type, estimated_cost)
record_usage_event(merchant_id, action_type, actual_cost)
```

第一版可以先只埋点或只做轻量拦截，但调用链位置要先留出来，避免后续会员权益上线时改动所有业务入口。

### 12.1 Claude Code 的核心模式

Claude Code 的 Skill 机制不是把所有 Skill 全文一次性塞进 system prompt。

更准确的模式是：

```text
1. 启动或配置变化时加载 Skill 元信息
2. 把 Skill 名称、description、when_to_use 等摘要列给模型
3. 模型判断某个 Skill 匹配任务
4. 模型调用 Skill 工具
5. Skill 工具按名称加载完整 Skill 正文
6. 完整正文作为 meta user message 注入当前对话
7. 后续模型按 Skill 正文继续执行
```

这对静境后台的启发是：

```text
启用 Skill 后，不一定每轮都注入完整正文。
更稳的第一版可以是：候选列表常驻，正文按需加载。
```

### 12.2 Skill 发现与加载来源

Claude Code 支持多种 Skill 来源：

- 内置 bundled skills
- 用户目录 skills
- 项目目录 `.claude/skills`
- 额外目录
- plugin skills
- MCP skills
- 动态发现的嵌套目录 skills

其中普通磁盘 Skill 的稳定格式是：

```text
skill-name/
└── SKILL.md
```

静境第一版不需要照搬本地文件扫描，也不需要支持 plugin / MCP / 远程 skill。

但可以借鉴“统一元信息 + 统一加载入口”的抽象：

```text
agent_skills 表存正文
agent_skill_bindings 表决定哪些 Agent 可用
运行时先列候选，再加载正文
```

### 12.3 Frontmatter 字段对静境的映射

Claude Code 支持的 Skill 元信息比静境第一版需要的更多。

可借鉴字段：

```text
name
description
when_to_use
argument-hint
arguments
model
context: inline | fork
agent
paths
user-invocable
disable-model-invocation
allowed-tools
hooks
```

静境第一版建议采用：

```text
name
description
when_to_use
body
agent_ids
dependencies / required_services
status
```

暂不采用：

- `allowed-tools`：Claude Code 用它给 Skill 临时增加工具权限；静境不把底层 tools 开放给管理员。
- `hooks`：属于运行时扩展点，当前不需要。
- `context: fork`：对应 forked sub-agent，当前咨询 Agent 不需要。
- `paths`：适合代码仓库文件路径触发，静境业务后台暂无必要。
- `argument-hint / arguments`：可后置，等 Skill 需要参数化再引入。

其中 `when_to_use` 值得第一版加入。它不是给管理员看的普通描述，而是给 Agent 判断是否加载该 Skill 的触发说明。

### 12.4 权限与安全启发

Claude Code 对 Skill 执行有几个安全边界：

- Skill 工具只接受 Skill 名称和可选参数，不直接接受任意正文。
- 调用前验证 Skill 是否存在、是否允许模型调用、是否是 prompt 类型。
- 如果 Skill 只包含安全属性，可自动允许；否则进入权限判断。
- `allowed-tools` 会影响后续工具权限，因此需要权限检查。
- 调用过的 Skill 会记录下来，用于上下文压缩后恢复，且按 agentId 隔离。

静境对应建议：

```text
1. 管理员只能编辑 Skill 正文，不能通过 Skill 开启底层 tool 权限。
2. Skill 依赖项只表达 required_services，不直接授予工具。
3. Agent 测试台必须展示本次到底加载了哪些 Skill。
4. 每次真实咨询应记录 skill_ids 快照，避免后续配置变更后无法追溯。
```

### 12.5 对当前方案的修正

基于 Claude Code 的参考，当前草案需要做一个产品判断修正：

旧问题：

```text
Skill 第一版是“启用即全部注入”，还是“按场景选择注入”？
```

更准确的新问题：

```text
Skill 第一版是否采用“候选列表常驻 + 正文按需加载”？
```

推荐第一版采用：

```text
启用且绑定 Agent 的 Skill，其 name / description / when_to_use 进入候选列表。
模型自己识别是否需要某个 Skill。
需要时按 Skill 名称加载完整正文。
测试台展示候选 Skill、实际加载的 Skill 和最终回复。
```

如果为了实现更快，也可以先简化为：

```text
所有已挂载 Skill 都进入候选列表。
不做系统层冲突检测。
不强制 Skill 启用前跑测试台。
```

## 13. 仍需要一起讨论的流程

### 13.1 Skill 运行方式

已定：

```text
候选列表常驻，完整正文按需加载。
```

系统不额外做复杂选择规则，也不做 Skill 冲突判断。模型根据候选 Skill 的 name / description / when_to_use 自行判断是否加载完整正文。

### 13.2 Skill 触发说明怎么写？

Claude Code 把 `when_to_use` 看得很重要。

已明确：

```text
when_to_use 不是 description。
```

区别是：

```text
description: 给管理员看的说明，描述这个 Skill 是什么。
when_to_use: 给模型看的触发条件，描述什么情况下应该加载这个 Skill。
```

第一版建议 `when_to_use` 作为必填字段，但不需要设计复杂规则。后台只需要给出简单示例，帮助管理员写清楚触发场景。

示例：

```text
description:
本地生活商家定位与客群拆解方法。

when_to_use:
当用户询问门店定位、目标客群、差异化卖点、成交异议、账号内容方向或不知道从哪里开始做内容时使用。
```

测试台可以展示本轮实际加载了哪些 Skill，但不强制解释“为什么命中”。如果模型输出了工具调用理由，可以展示；没有则不额外做复杂归因。

### 13.3 Skill 冲突怎么处理？

已定：

```text
不做系统层 Skill 冲突处理。
```

原因是 Skill 冲突属于创建者和配置者的判断。例如表达风格类 Skill，管理员本来就不应该在同一个 Agent 下挂多个互相冲突的版本。系统只负责让 Agent 挂载哪些 Skill 清晰可见，不负责替管理员判断表达策略是否冲突。

### 13.4 System Prompt 和 Skill 谁优先？

已定：

```text
System Prompt 高于 Skill。
Skill 不得覆盖安全规则和输出边界。
```

第一版不做额外提示，也不做 Skill 正文校验。

### 13.5 Agent 服务关闭后商家端怎么展示？

已定：

```text
商家端显示“服务维护中”。
```

测试台仍可选择测试 Agent，但不要自动影响线上咨询入口。

### 13.6 Prompt 发布是否必须经过测试台？

已定：

```text
不强制经过测试台。
```

System Prompt 是 Agent 配置的一部分。管理员如果要测试，应复制 Agent-A 为 Agent-B，在 Agent-B 中修改和测试；测试满意后，再把配置应用回线上 Agent-A，或切换线上咨询 Agent。

### 13.7 Skill 启用是否必须经过测试台？

已定：

```text
不强制经过测试台。
```

系统无法客观判断“测试通过”。正确流程是：新 Skill 先挂到测试 Agent-B，用测试台验证；满意后再在 Agent-A 中勾选该 Skill。

### 13.8 Knowledge 关闭时依赖它的 Skill 怎么办？

已定：

```text
允许启用，但在后台和测试台明显提示依赖未满足。
```

### 13.9 测试台是否写入真实咨询历史？

已定：

```text
不写入商家端真实 consultation_sessions。
```

管理员测试也不消耗商家的 LLM 配额。

说明：

```text
商家 LLM 配额属于商家侧真实使用额度。
管理员测试属于平台后台调试行为，不应要求测试商家账户本身有可扣减配额。
```

如果后续要控制成本，可以单独做平台后台测试额度或内部成本记录，但不要扣商家配额。

测试台结果第一版保存到 `agent_test_runs`，用于后台调试复盘。

### 13.10 是否需要 Agent 配置快照？

已定：

```text
需要。
```

这里的“配置快照”不是一个新功能入口，而是追溯用的日志。

意思是：当一次真实咨询发生时，系统顺手记录当时 Agent 用的是哪一套配置。以后即使管理员改了 Prompt、Skill、Knowledge Set，也能知道历史上某次回答是在什么配置下生成的。

可以记录轻量引用：

```text
agent_id
prompt_version_id
候选 skill_ids
实际加载 skill_ids
knowledge_set_ids
memory/tool call summary
model
created_at
```

不一定要复制完整 prompt 正文，也不需要在用户界面展示。它主要用于排查问题：

```text
为什么这个商家那天拿到的是这个回答？
当时是不是用了新 Skill？
当时有没有检索某个知识集？
后来改了 Prompt，历史回答还能不能解释清楚？
```

第一版按建议执行，至少记录 `agent_id / prompt_version_id / actual_skill_ids / knowledge_set_ids / tool_call_summary`。这属于后端审计与排查，不是商家侧显性功能。

### 13.11 商家资料库什么时候进入主线？

已确认商家资料库优先级后置，入口倾向在商家设置。

已明确：

```text
商家资料库属于长期记忆的一部分。
咨询 Agent 默认可以检索商家资料库。
是否实际检索，由 Agent 根据当前任务判断，并通过受控工具调用完成。
```

它和平台 Knowledge 的关系：

```text
平台 Knowledge：平台管理员维护，偏行业方法论、平台规则、SOP、案例。
商家资料库 / Memory：商家自己维护或平台代维护，偏门店事实、产品、案例、FAQ、历史沉淀。
```

从运行时看，它们都可以是 Agent 可调用的上下文工具，但后台产品入口要分开，避免平台知识和商家私有资料混在一起。

## 14. 剩余需要决策的点

目前大方向已经收口，剩下主要是第一版实现口径。

### 14.1 测试台记录是否长期保存？

已定：

```text
第一版保存到 agent_test_runs，但不作为商家真实咨询历史。
默认保留最近 30 天，或每个 Agent 最近 200 条。
```

原因是测试台后续要排查 prompt、skill、knowledge 为什么表现不好，没有记录会很难复盘。

### 14.2 线上 Agent 的配置修改是否需要“草稿 / 发布”？

已定：

```text
线上 Agent：保存草稿 -> 发布后生效。
测试 Agent：保存后立即用于测试台。
```

这样既允许管理员快速调试 Agent-B，又避免误改当前线上 Agent-A。

这里要分三层，不要混在一个状态里：

```text
Agent 生命周期状态：draft | enabled | disabled
配置版本状态：draft | active | archived
线上入口绑定：consultation_default -> agent_id
```

Agent 自身生命周期状态是：

```text
draft | enabled | disabled
```

其中 `enabled` 只表示这个 Agent 可用，不等于它正在服务商家端。真正线上服务由 `consultation_default -> agent_id` 这条绑定决定。

### 14.3 新上传知识是否必须选择知识集？

已定：

```text
上传知识时必须选择至少一个知识集。
```

这样可以避免新知识上传后无意影响线上咨询。

### 14.4 Agent 挂载多个知识集时怎么检索？

已定：

```text
第一版按所有已挂载知识集做合并检索。
不做知识集优先级。
不做冲突判断。
```

命中排序交给向量相似度和后端检索策略。

### 14.5 第一版是否内置初始知识集和初始线上 Agent？

这里的“初始”不是一种状态，而是系统初始化时预置的一组起步配置。

建议改名，不再叫“默认”，避免误解成“以后自动套用”。

推荐：

```text
预置一个“基础平台知识集”。
预置一个“初始咨询 Agent”。
设置线上绑定：consultation_default -> 初始咨询 Agent。
初始咨询 Agent 挂载“基础平台知识集”。
```

这样第一版上线时后台不是空的，也方便从现有平台知识平滑迁移。

### 14.6 会员与积分底座

已补充为必须预留的横切能力。

当前不需要先想完整权益，但需要先定底座：

```text
会员档位：free | plus | pro | max
积分账户：记录商家当前可用积分
积分流水：记录赠送、购买、消耗、退款、调整、过期
用量事件：记录每次 AI / Agent / 生成 / 发布相关消耗
调用前校验：真实商家侧消耗先过 entitlement / credits gate
```

建议：

