# 内容日历生成图文与视频脚本 Dify 工作流说明

状态：`POC 草案`  
日期：`2026-05-11`

更新记录：

- `v1.1`：根据首轮 Dify 输出收紧质量门禁。
  - End 节点只输出 `final_result_json`，避免 Dify 页面把多个 JSON 串在一起。
  - 质量评审改为 0-10 分，并规定六项全部 >= 7 才能通过。
  - 明确禁止“投资回报率高 / 租金回报高 / 收益稳定 / 保值增值”等高风险表达。
  - 视频脚本新增 `uploadReason` 和 `assetSourceHint`，区分成员必须上传与团队视频素材可补。

## 1. 文件

- Dify DSL：`docs/探索/2026-05-11-内容日历生成图文视频脚本-Dify工作流.yml`

## 2. 目标

验证第一段链路质量：

```text
内容日历 + txt 知识库 + 爆款内容 + 图片素材
-> 图文内容包 / 视频镜头脚本
```

这版不是最终工程实现，而是质量验证用 POC。核心是让每次生成都能看见：

- 用了哪些项目知识。
- 借鉴了哪些爆款结构。
- 匹配了哪些图片素材。
- 视频脚本需要哪些镜头。
- 哪里因为素材不足发生降级。
- 质量评审为什么通过或不通过。

## 3. 导入后必须手动配置

### 3.1 绑定 txt 知识库

YAML 里的 `txt 知识库检索` 节点保留了：

```yaml
dataset_ids: []
```

这是故意的。Dify 的知识库 ID 是环境相关的，写死后换环境容易导入失败。

导入后进入 Dify 画布：

1. 打开 `txt 知识库检索` 节点。
2. 选择你上传 txt/md 后形成的项目知识库。
3. 检索模式建议先用 `multiple`。
4. `top_k` 建议 6。

### 3.2 替换模型

YAML 默认使用：

```text
provider: langgenius/openai/openai
model: gpt-4o-mini
```

如果你的 Dify 没有 OpenAI provider，导入后把所有 LLM 节点统一换成你可用的模型，例如 DeepSeek、Qwen、SiliconFlow 上的 Qwen/DeepSeek。

建议：

- 任务理解 / 策略规划 / 质量评审：温度低。
- 图文 / 视频脚本生成：温度中等。

## 3.3 API 回归测试

本目录新增内容日历专用 Dify 测试脚本：

```bash
export DIFY_BASE_URL="https://你的-dify-domain/v1"
export DIFY_API_KEY="app-你的应用APIKey"

python3 docs/探索/2026-05-11-用dify来测试链路/run_content_calendar_dify_cases.py \
  --runs 1 \
  --save-nodes
```

也可以不用环境变量，直接传：

```bash
python3 docs/探索/2026-05-11-用dify来测试链路/run_content_calendar_dify_cases.py \
  --base-url "https://你的-dify-domain/v1" \
  --api-key "app-你的应用APIKey" \
  --case-path docs/探索/2026-05-11-用dify来测试链路/testcases \
  --output-dir docs/探索/2026-05-11-用dify来测试链路/results \
  --runs 1 \
  --save-nodes
```

输出：

- 单次运行结果：`results/*.json`
- 节点输出：`results/node_outputs/*_nodes.json`
- 汇总：`results/测试汇总_*.json`

脚本会自动检查：

- final JSON 是否可解析。
- 是否残留高风险词。
- `copyReadyText` 是否为空。
- 每个视频镜头 `assetQuery` 是否为空。
- `requiredUploads` / `optionalTeamVideoAssets` 是否和 scene 对齐。
- `qualityReview.pass` 是否符合测试用例预期。

## 4. 输入字段

### 4.1 `calendar_task_json`

建议输入：

```json
{
  "taskId": "task_20260511_article_video_001",
  "theme": "小户型回归",
  "contentType": "article_and_video",
  "platforms": ["xiaohongshu", "douyin"],
  "contentGoal": "种草",
  "targetAudience": "刚需客户",
  "summary": "低总价上车、成熟配套、租金回报",
  "teamCalendarSource": "团队本周内容日历",
  "date": "2026-05-11"
}
```

### 4.2 `viral_references_json`

爆款内容不作为事实，只作为结构参考。

```json
[
  {
    "id": "viral_001",
    "platform": "xiaohongshu",
    "title": "很多人以为小户型没人看了，其实刚需又开始回头看",
    "structure": ["反常识开头", "解释变化", "落到真实选择", "轻CTA"],
    "hook": "很多人以为小户型过时了",
    "ctaStyle": "想看户型和总价，可以私信"
  }
]
```

### 4.3 `image_assets_json`

只放图片素材，不放视频素材。

```json
[
  {
    "assetId": "img_001",
    "title": "项目外立面",
    "url": "https://example.com/project-facade.jpg",
    "tags": ["项目外立面", "小区入口", "封面"],
    "description": "适合承接项目可信度和封面展示"
  },
  {
    "assetId": "img_002",
    "title": "样板间客厅",
    "url": "https://example.com/living-room.jpg",
    "tags": ["样板间", "客厅", "空间感"],
    "description": "适合讲居住体验"
  }
]
```

### 4.4 `fallback_knowledge_text`

如果你还没配置 Dify 知识库，可以先把 txt 里的核心信息粘到这里兜底。

### 4.5 `extra_requirement`

例如：

```text
口吻更像本地中介，CTA 轻一点，不要制造焦虑。
```

## 5. 节点说明

| 节点 | 作用 | 关键输出 |
| --- | --- | --- |
| 开始 | 接收结构化任务、爆款、图片、兜底知识 | 输入变量 |
| 任务理解 | 把内容日历转成检索 query 和生成约束 | `copySearchQuery`、`scriptSearchQuery`、`imageSearchQuery` |
| txt 知识库检索 | 调用 Dify KB | `result` |
| 创作策略规划 | 决定怎么写、用什么事实、借鉴什么结构 | `articlePlan`、`videoPlan`、`trace` |
| 图文内容包生成 | 生成标题、正文、标签、CTA、封面字、配图建议 | `articlePackage` |
| 视频镜头脚本生成 | 生成故事大纲、分镜、口播、字幕、拍摄要求 | `videoScript` |
| 质量评审 | 打分、指出风险和缺失输入 | `qualityReview` |
| 最终结果编译 | 汇总成可保存 JSON | `final_result_json` |

## 6. 第一轮测试用例

### Case A：资料完整

输入有：

- 内容日历任务。
- txt 知识库。
- 2-3 条爆款结构。
- 2-4 张图片。

预期：

- 图文能具体到项目卖点，不泛泛写房地产。
- 视频脚本每个 scene 都有 `assetQuery`。
- 质量评审大部分分数 >= 7。

### Case B：没有图片素材

输入：

- `image_assets_json` 传 `[]`。

预期：

- 图文仍生成。
- `imageBriefIfMissing` 有内容。
- `degradationNotices` 或质量评审里提示缺图。

### Case C：没有爆款内容

输入：

- `viral_references_json` 传 `[]`。

预期：

- 内容仍生成。
- 结构不应照抄任何样例。
- 质量评审提示“缺少爆款结构参考”，但不阻塞。

### Case D：知识库弱

输入：

- 知识库没绑定，`fallback_knowledge_text` 只给很少信息。

预期：

- 不编造具体项目事实。
- 质量评审的 `factAccuracy` 不应虚高。
- `missingInputs` 应提示需要补项目资料。

## 7. 通过标准

先不要看“文案漂不漂亮”，先看四个硬标准：

1. 输出 JSON 可解析。
2. 不编造输入里没有的具体项目事实。
3. 图文里的图片只来自 `image_assets_json`。
4. 视频脚本每个镜头都有 `assetQuery` 和 `uploadRequired`。

这四个过了，再看标题、正文、脚本的内容质量。

## 8. 首轮输出暴露的问题

首轮输出已经证明 workflow 能跑通，但还没达到可验收质量：

1. 质量评审输出 `1 分` 却 `pass=true`，说明评分规则没有钉死。
2. 图文里出现“投资回报率高”，这是房地产内容的高风险表达，必须拦截。
3. 文案偏泛化，有“近年来、市场背景、优势明显”等空话，说明项目事实不足时没有降级。
4. 视频脚本把所有镜头都标成 `uploadRequired=true`，没有区分“成员自拍口播”和“团队素材可补画面”。
5. End 节点输出了多个 JSON，测试时不方便直接拿最终结果。

`v1.1` 已针对这些点收紧提示词。下一轮测试重点看：

- `qualityReview.pass` 是否会因为风险词变成 `false`。
- 图文是否避开“收益/回报/升值”承诺。
- 视频脚本是否只有真人口播/CTA 镜头要求成员上传。
- 最终输出是否只剩一个 `final_result_json`。
