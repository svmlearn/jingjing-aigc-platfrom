# 2026-05-13 Dify V3.1 数据流与最终 JSON 收敛规划

## 背景结论

最新测试中，LLM 节点的 `text` 已不再包含 `<think>`，但 `text` 仍然是“JSON 字符串文本”，不是稳定对象。

同一节点同时输出：

- `text`：适合人看或兜底解析，不适合继续作为下游 LLM 的主输入。
- `reasoning_content`：模型思考过程，不应进入下游业务链路。
- `structured_output`：Dify 按 schema 解析出的结构化对象，应作为后续节点主输入。

因此 V3.1 的核心方向不是继续扩大 `text` 传递，而是：

**LLM -> LLM 优先传 `structured_output` 的必要字段；Code 节点也优先吃 `structured_output`，`text` 只作为兜底。**

## 当前 V3.0 数据流

当前最新 YAML：

- `docs/探索/2026-05-11-用dify来测试链路/内容日历生成图文与视频脚本 POC V3.0.yml`

当前节点流：

```mermaid
flowchart TD
  start["开始"] --> task["任务理解"]
  task --> kb["TXT 知识库检索"]
  kb --> strategy["创作策略规划"]

  strategy --> title["标题与封面策略"]
  title --> body["正文与配图编排"]
  body --> articleCode["图文包编译"]

  strategy --> narrative["视频叙事结构"]
  narrative --> scene["分镜与素材策略"]
  scene --> videoCode["视频交付物编译"]

  articleCode --> quality["质量评审"]
  videoCode --> quality
  quality --> rewriteGate["是否需要违规改写"]
  rewriteGate --> rewrite["违规内容改写 LLM"]
  rewriteGate --> articleAgg["图文候选聚合"]
  rewrite --> articleAgg
  articleAgg --> videoAgg["视频候选聚合"]
  videoAgg --> final["最终结果编译"]
  final --> end["输出"]
```

## 当前不稳点

### 1. 下游 LLM 仍在吃 `text`

当前下游引用包括：

- `title_cover`：读取 `creative_strategy.text`
- `article_body`：读取 `title_cover.text`、`creative_strategy.text`
- `video_narrative`：读取 `creative_strategy.text`
- `scene_breakdown`：读取 `video_narrative.text`、`creative_strategy.text`
- `article_compiler`：读取 `title_cover.text`、`article_body.text`
- `delivery_compiler`：读取 `video_narrative.text`、`scene_breakdown.text`
- `final_compiler`：读取 `task_understanding.text`、`creative_strategy.text`

这会带来两个风险：

1. `text` 是字符串，不是对象；下游 LLM 容易把它当作普通上下文而不是字段约束。
2. `text` 即使没有 `<think>`，也可能包含格式化 JSON 字符串、换行、额外解释或供应商差异，稳定性低于 `structured_output`。

### 2. 知识库检索 query 暂时使用完整 `task_understanding.text`

这是为了解决 `task_understanding.structured_output.copySearchQuery` 缺失时 Dify 节点启动失败。

但长远看，完整 `text` 作为检索 query 太长，且包含无关字段。

更稳做法：

- 加一个 `retrieval_query_builder` Code 节点。
- 输入：`task_understanding.structured_output`。
- 输出：短字符串 `query`。
- 知识库检索只吃 `retrieval_query_builder.query`。

### 3. 最终 JSON 偏大

当前最终 JSON 同时包含：

- 发布成稿：`articlePackage`
- 标题策略：`titleStrategy`
- 视频脚本：`videoScript`
- 成员拍摄任务：`memberDelivery`
- worker 剪辑任务：`workerDelivery`
- 质量评审：`qualityReview`
- 全量 trace：`trace.taskUnderstanding`、`trace.creativeStrategy`、引用记录
- 保存提示：`saveHints`

这对调试很友好，但对代码主链路/前端直接消费偏重。

## V3.1 推荐数据流

### 任务理解 -> 知识库

当前：

- `task_understanding.text` -> `kb_project_knowledge.query`

建议：

- `task_understanding.structured_output` -> `retrieval_query_builder` Code
- `retrieval_query_builder.query` -> `kb_project_knowledge.query`

query 生成逻辑：

- 优先用 `copySearchQuery`
- 拼接 `scriptSearchQuery`、`coreTopic`、`sellingPointsNeeded`
- 限制长度，例如 200-300 字以内
- 如果结构化字段缺失，再兜底用 `task_understanding.text`

### 创作策略 -> 标题/正文/视频

当前：

- `creative_strategy.text` -> `title_cover`
- `creative_strategy.text` -> `article_body`
- `creative_strategy.text` -> `video_narrative`
- `creative_strategy.text` -> `scene_breakdown`

建议：

- `creative_strategy.structured_output.articlePlan` -> `title_cover`
- `creative_strategy.structured_output.chosenAngle` -> `title_cover`
- `creative_strategy.structured_output.mustUseFacts` -> `title_cover`
- `creative_strategy.structured_output.mustAvoidClaims` -> `title_cover`
- `creative_strategy.structured_output.viralPatternUsed` -> `title_cover`

- `creative_strategy.structured_output.articlePlan` -> `article_body`
- `creative_strategy.structured_output.mustUseFacts` -> `article_body`
- `creative_strategy.structured_output.mustAvoidClaims` -> `article_body`
- `creative_strategy.structured_output.tone` -> `article_body`

- `creative_strategy.structured_output.videoPlan` -> `video_narrative`
- `creative_strategy.structured_output.chosenAngle` -> `video_narrative`
- `creative_strategy.structured_output.narrativeArc` -> `video_narrative`
- `creative_strategy.structured_output.tone` -> `video_narrative`
- `creative_strategy.structured_output.mustUseFacts` -> `video_narrative`
- `creative_strategy.structured_output.mustAvoidClaims` -> `video_narrative`

- `creative_strategy.structured_output.mustUseFacts` -> `scene_breakdown`
- `creative_strategy.structured_output.mustAvoidClaims` -> `scene_breakdown`

如果担心 nested 子路径再次缺失，建议加一个 `strategy_compiler` Code 节点：

- 输入：`creative_strategy.structured_output`
- 输出：
  - `article_context_json`
  - `video_context_json`
  - `quality_context_json`

后续 LLM 吃 Code 节点输出的短 JSON 字符串，而不是直接吃 `creative_strategy.text`。

### 标题 -> 正文

当前：

- `title_cover.text` -> `article_body`

建议：

- `title_cover.structured_output` -> `article_body`

至少传：

- `selectedTitle`
- `selectedCoverCopy`
- `hookAngle`
- `titles`

### 视频叙事 -> 分镜

当前：

- `video_narrative.text` -> `scene_breakdown`

建议：

- `video_narrative.structured_output` -> `scene_breakdown`

至少传：

- `hook`
- `narrativeArc`
- `storyOutline`
- `estimatedDuration`
- `bgmDirection`
- `toneOfVoice`
- `voiceoverDraft`

### 编译 Code 节点

当前：

- `article_compiler` 解析 `title_cover.text`、`article_body.text`
- `delivery_compiler` 解析 `video_narrative.text`、`scene_breakdown.text`

建议：

- 优先输入 structured_output。
- 如果 Dify Code 节点不能直接选择完整 `structured_output` 对象，则选择具体子字段，或使用上一步 `*_compiler_context` Code 节点聚合。
- `text` 只保留为兜底输入。

## 最终 JSON 是否需要这么多

答案：不需要都作为主输出给业务代码消费。

建议拆成三层：

### A. 主业务输出：给前端/代码消费

只保留真正要展示、落库、进入下一条链路的字段。

```json
{
  "workflowVersion": "content_calendar_generation_poc_v3_1",
  "status": "passed | needs_review | blocked",
  "articlePackage": {},
  "videoScript": {},
  "memberDelivery": {},
  "workerDelivery": {},
  "qualityReview": {}
}
```

说明：

- `articlePackage`：给图文工作台。
- `videoScript`：给视频脚本工作台。
- `memberDelivery`：给中介/成员拍摄口播任务。
- `workerDelivery`：给 AI 剪辑 worker。
- `qualityReview`：给前端提示“是否可发布 / 为什么不可发布”。

### B. 调试输出：给研发和 Dify 回归用

建议不放进主输出，或放在可选 `debug` 里。

```json
{
  "debug": {
    "taskUnderstanding": {},
    "creativeStrategy": {},
    "usedKnowledgeRefs": [],
    "usedViralRefs": [],
    "usedImageAssets": [],
    "degradationNotices": []
  }
}
```

### C. 保存快照提示

`saveHints` 不建议作为 Dify 最终业务 JSON 的固定字段。

它是代码实现时的保存策略，应该由代码侧决定，或写入架构文档，不必每次 Dify 输出都带。

## 字段收敛建议

### `articlePackage`

建议保留：

- `titles`
- `selectedTitle`
- `coverCopy`
- `body`
- `contentBlocks`
- `hashtags`
- `cta`
- `imageMatches`
- `imageBriefIfMissing`
- `riskNotes`
- `copyReadyText`

可以不放在主业务输出：

- `titleStrategy` 的完整推理理由，可放 debug 或工作台“展开详情”。

### `videoScript`

建议保留：

- `narrative`
- `scenes`
- `riskNotes`

注意：

- `videoScript.scenes` 是创作脚本视角。
- `workerDelivery.scenes` 是 worker 执行视角。
- 如果两者完全一样，可考虑只保留一份，另一个只保留 worker 额外字段。

### `memberDelivery`

建议保留：

- `tasks`

这是成员端执行任务，非常有价值。

### `workerDelivery`

建议保留：

- `storyOutline`
- `bgm`
- `toneOfVoice`
- `estimatedDuration`
- `scenes`
- `teamAssetQueries`

这是下一段“AI 剪辑成片”链路的核心输入。

### `qualityReview`

建议保留：

- `scores`
- `pass`
- `needsRewrite`
- `riskTerms`
- `problems`
- `redFlags`
- `missingInputs`

可选：

- `revisionSuggestions`

### `trace`

建议默认不进入主业务输出，改为：

- Dify 测试阶段：保留，方便回归。
- 代码接入阶段：可存入数据库 debug 字段，不给前端主视图。
- 生产阶段：只保留 `traceId` 或轻量 `sourceRefs`。

## 前端渲染导向的最终 JSON 契约草案

最终输出应直接对应两个前端页面：

1. 图文任务详情：展示图片、文案、复制按钮。
2. 视频任务详情：展示故事大纲、镜头脚本、拍摄要求、按镜头上传槽位、AI 剪辑入口。

因此主输出可以收敛为：

```json
{
  "workflowVersion": "content_calendar_generation_poc_v3_1",
  "status": "needs_review",
  "article": {},
  "video": {},
  "quality": {},
  "debug": {}
}
```

其中 `debug` 可选，生产主链路可不返回给前端。

### 图文输出：`article`

图文前端真正需要的是：

- 标题
- 封面文案
- 图片槽位或已匹配图片路径
- 可直接复制到小红书/抖音的正文
- 轻量素材缺失提示

- `hashtags` 不必单独作为前端主字段，直接拼进 `copyText` 即可。若后台要做分析，可在 debug 或内部字段保留。
- `imageMatches` 与 `imageBriefIfMissing` 可以合并为 `imageSlots`：有图就填 `assetPath/assetId`，没图就填 `brief`。
- `copyReadyText` 可改名为更直观的 `copyText`。
- `titles`、`titleStrategy`、`selectedTitleReason` 不建议进入主输出。它们是调试/策略信息，不是成员端发布必需字段。

### 视频输出：`video`

视频前端不是普通文案页，而是“镜头任务 + 上传槽位 + worker 输入”。

截图中的卡片至少需要：

- 镜头编号
- 时长或时间范围
- 是否必传
- 镜头标题
- 镜头任务说明
- 字幕/口播
- 拍法
- 提示
- 上传槽位

但专业镜头脚本还应该保留：

- 镜头类型：口播 / 素材 / 文字卡
- 情绪节拍 / 叙事作用
- 画面描述 / 镜头语言
- 景别或构图
- 运镜建议
- 转场
- 节奏
- 素材检索词或兜底画面

### 质量输出：`quality`

前端不需要完整评分细节，但需要知道是否可用、为什么不可用。

```json
{
  "quality": {
    "status": "needs_review",
    "pass": false,
    "blockingReasons": [
      "项目知识不足，成稿仅适合内部预览",
      "缺少可用图片素材"
    ],
    "missingInputs": [
      "更完整的项目事实",
      "图文图片素材"
    ],
    "riskTerms": []
  }
}
```

说明：

- `scores` 可以放 debug，不必在成员端主 UI 展示。
- `problems` 可以映射成 `blockingReasons`。
- `redFlags` 只在有风险时展示。

### 可删除或移入 debug 的字段

建议不进入最终主业务 JSON：

- `titleStrategy`
- `trace.taskUnderstanding`
- `trace.creativeStrategy`
- `usedKnowledgeRefs`
- `usedViralRefs`
- `usedImageAssets`
- `saveHints`
- `memberDelivery` 独立副本
- `workerDelivery` 独立副本

保留方式：

- Dify 回归测试阶段：可以放在 `debug`。
- 代码接入阶段：写入数据库 `debug_payload` 或日志。
- 前端主渲染：不展示这些字段。

## V3.1 优先级

1. 下游 LLM 输入改用 `structured_output` 或 Code 聚合后的短 JSON。
2. 知识库 query 加 `retrieval_query_builder`，不再直接用完整 `task_understanding.text`。
3. 编译 Code 节点优先读取 structured 数据，`text` 只兜底。
4. 最终 JSON 拆出主业务输出和 debug 输出。
5. 保留 pro 节点：`创作策略规划`、`违规内容改写 LLM` 可继续用 pro，因为它们属于高价值判断节点。

### 两个修正建议

1. `video.scenes[].requiresUserUpload` 不展示成文字是对的，但它会控制前端是否显示上传框。因此它应归类为“运行时字段”，前端渲染逻辑必须能读到它。

### 接入说明

- 图文前端直接渲染 `article.images[].cosPath`，不需要上传槽位。
- 图文复制内容使用 `article.copyText`，标签直接拼在文案里，不再单独输出 `hashtags`。
- 视频上传槽位由 `video.scenes[].requiresUserUpload` 控制：`true` 显示上传，`false` 不显示上传或走团队素材匹配。
- 成员 UI 只展示拍摄执行信息，不展示 `sceneType`、`purpose`、`subtitle`、`shotLanguage`、`editGuide`、`assetQuery` 等专业字段。
- worker 可使用 `video.storyOutline`、`bgm`、`toneOfVoice`、`sceneType`、`subtitle`、`shotLanguage`、`editGuide`、`assetQuery` 等字段完成剪辑。
