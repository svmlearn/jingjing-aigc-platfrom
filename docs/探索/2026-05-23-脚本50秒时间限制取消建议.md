# 脚本 50 秒时间限制取消建议

日期：2026-05-23
状态：探索记录 / 待确认实现点
提出原因：当前脚本执行时间较长时会撞上约 50 秒限制，随后被重启，导致任务无法持续跑完，也无法稳定产出结果。

## 结论

需要取消当前脚本执行链路中的 50 秒级硬限制。

这类限制只适合健康检查、短请求或快速探活，不适合当前项目的内容生成、视频脚本生成、Dify workflow、OpenStoryline / FireRed、数据修复脚本和批量处理任务。当前项目里的重型脚本天然容易超过 50 秒，如果执行器按 50 秒杀进程或重启服务，结果会变成：

1. 脚本还没完成就被中断。
2. 进程被重启后上下文丢失。
3. 中间产物、数据库状态、日志状态可能不一致。
4. 用户看到的是“任务一直重启 / 没结果”，但真实原因是运行窗口太短。

推荐改成：任务级异步执行 + 持久化状态 + heartbeat + 阶段超时 + 人工取消 / 重跑，而不是用 50 秒作为全局强制上限。

## 背景判断

当前项目已经存在多处长任务事实：

- `DIFY_WORKFLOW_TIMEOUT_SECONDS=900`：Dify 主链路默认允许 900 秒。
- `CONTENT_GENERATION_WORKER_REQUEST_TIMEOUT_MS=960000`：内容生成 worker 请求默认约 16 分钟。
- 视频链路曾出现 OpenStoryline 外层等待 `2700s` 后才超时失败。
- FireRed / OpenStoryline / 视频合成 / 口型同步 / BGM 选择等步骤本身可能进入分钟级耗时。

所以 50 秒不是合理的业务任务上限。它最多可以作为单次短 HTTP 请求、健康检查、连接建立或无进展探测的限制，不能作为脚本整体运行时间限制。

## 当前问题

用户反馈的现象是：

> 脚本时间过长时会撞上 50 秒限制，然后重启，做不出结果。

这说明当前链路里可能存在某个外层 watchdog、runner、平台函数、HTTP client、systemd / supervisor 配置或脚本包装器在 50 秒附近强制中断执行。

需要先定位限制来源，再决定具体改法。不要只在业务脚本里补重试，因为如果外层仍然 50 秒杀进程，业务层重试也会继续被打断。

## 可能来源

后续排查时优先查这些位置：

1. 脚本 runner 或封装命令中是否有 `timeout 50`、`--timeout 50`、`50000`、`50_000`。
2. Node 代码中是否有 `AbortSignal.timeout(50 * 1000)` 或等价写法。
3. API route、fetch client、worker client 是否配置了 50 秒请求超时。
4. systemd unit 是否存在 `RuntimeMaxSec=50`、`TimeoutStartSec=50`、`TimeoutStopSec=50` 或 watchdog 配置。
5. Docker / Compose / process manager 是否有健康检查失败后自动重启。
6. 部署平台是否有不可取消的函数执行上限。如果平台本身强制限制同步请求，则必须改为异步 job，不应继续在同步请求里跑完整脚本。

## 改造原则

### 1. 取消 50 秒全局硬上限

脚本执行器不应因为总运行时长超过 50 秒就重启。

如果业务任务需要 3 分钟、15 分钟甚至更久，worker 应该持续执行，并通过任务状态表记录进度。真正需要超时的是“某个阶段长时间没有进展”，而不是“总时长超过 50 秒”。

### 2. 同步入口只负责派发任务

前端或 API 入口应该尽快返回：

- `jobId`
- 当前状态
- 查询进度的接口

重型逻辑交给后台 worker 执行。这样即使浏览器、网关、平台函数或 HTTP 连接有短限制，也不会影响后台任务继续运行。

### 3. 用 heartbeat 判断是否卡死

worker 执行时需要定期写入：

- `heartbeat_at`
- `current_stage`
- `stage_started_at`
- `elapsed_ms`
- 最近一条关键日志或失败原因

清理逻辑根据 heartbeat 和阶段耗时判断任务是否 stale，而不是直接按 50 秒重启进程。

### 4. 阶段级超时要可配置

不同阶段耗时差异很大，建议按阶段配置：

| 阶段 | 建议策略 |
| --- | --- |
| 健康检查 / 探活 | 保留短超时，例如 5-15 秒 |
| 普通 API 请求 | 保留中短超时，例如 30-120 秒 |
| Dify workflow | 使用分钟级超时，例如 900 秒 |
| 内容生成 worker | 使用分钟级超时，例如 10-30 分钟 |
| OpenStoryline / FireRed / 视频合成 | 使用阶段级分钟超时，并记录具体卡点 |
| 数据修复 / 批量脚本 | 不用 50 秒总上限，改用日志、dry-run、进度和人工取消 |

### 5. 重启只能处理异常退出

进程管理器可以在 worker crash 后重启服务，但不能把“脚本正常运行超过 50 秒”当成异常。

如果确实需要防止进程永久卡死，应由任务层控制：

- 超过阶段最大时长后标记失败或降级。
- 保留 failure reason。
- 支持人工重跑。
- 支持从最近稳定阶段恢复。

## 建议实现方案

### P0：先解除 50 秒中断

目标：先让脚本能跑完。

动作：

1. 定位 50 秒限制的具体配置或代码来源。
2. 对业务脚本取消总时长 50 秒限制。
3. 如必须保留总上限，至少提升到与业务现实匹配的分钟级，并通过环境变量配置。
4. 保留短健康检查，不把健康检查超时等同于业务脚本失败。

验收：

- 构造一个 70-120 秒的测试脚本，确认不会被重启。
- 真实长脚本超过 50 秒后仍能继续运行。
- 日志能看到同一个 job / process 持续推进，而不是反复启动。

### P1：补任务状态和 heartbeat

目标：脚本跑得久也能看见进度。

动作：

1. 每个长任务写入 `current_stage`。
2. 每 10-30 秒写入 heartbeat。
3. 关键阶段开始、结束、失败都写结构化日志。
4. 前端或管理端展示当前阶段、已耗时、最近更新时间。

验收：

- 用户能区分“还在跑”“卡住了”“失败了”“已完成”。
- worker 重启后，不会留下永久 running 的任务。

### P2：补取消、重跑和阶段降级

目标：长任务不是只能等到底。

动作：

1. 支持人工取消。
2. 支持失败后重跑。
3. 对可降级步骤提供明确策略，例如 BGM 选择超时后跳过或使用默认音乐。
4. 对不可降级步骤明确失败原因，避免静默重启。

验收：

- 任务卡住时可以人工取消。
- 失败后可以从任务详情页或运维命令重跑。
- 重跑不会重复写入不可控的脏数据。

## 需要避免的做法

1. 不要只把 50 秒改成另一个很短的固定值。
2. 不要在同步 HTTP 请求里跑完整视频生成或复杂 Dify 链路。
3. 不要靠进程重启当作业务重试。
4. 不要让重启清掉唯一的错误现场。
5. 不要把所有阶段共用一个统一超时值。

## 待确认问题

1. 当前 50 秒限制来自哪里：脚本 runner、API route、worker fetch、systemd、Docker、平台函数，还是其他外层工具？
2. 被影响的是哪类脚本：内容生成、Dify、OpenStoryline、视频 worker、数据修复，还是全部长脚本？
3. 当前重启后任务状态是否会持久化：会恢复、会失败、还是一直 pending / running？
4. 产品上能接受的最长等待时间是多少：单条内容、单个视频、批量任务是否需要不同上限？
5. 哪些阶段允许降级，哪些阶段必须失败并等待人工处理？

## 推荐验收标准

完成改造后至少验证：

1. 70-120 秒测试脚本不会触发重启。
2. 一个真实内容生成脚本超过 50 秒后能完成并写回结果。
3. 一个真实失败任务能记录准确失败原因，而不是只显示重启。
4. worker 进程异常退出后可以重启，但任务不会丢失。
5. 前端或日志能看到任务当前阶段和耗时。
6. 人工取消 / 重跑路径可用。

## 当前建议

先把“取消 50 秒硬限制”作为 P0 运维 / 架构修复项处理。

后续如果继续推进内容生成、图文工作台、视频工作台和 OpenStoryline 链路，长任务会越来越常见。这个问题不先解决，后面的生成质量、脚本复杂度和视频链路都会被执行时间窗口卡住，最终表现为任务反复重启、结果不稳定、用户以为功能不可用。
