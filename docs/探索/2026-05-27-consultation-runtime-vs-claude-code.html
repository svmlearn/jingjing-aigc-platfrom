咨询 Agent Runtime 与 Claude Code 对照

结论先放前面：runtime 不应该识别“你有什么工具”这种自然语言意图。 它应该只接收模型输出，判断是否是结构化 tool call，然后执行、回填 tool result。 工具目录问题应由 LLM 基于可见工具 schema 和系统上下文自然回答。

置信度：高

刚才那个修法是错的

在 runtime 层加 isToolInventoryQuestion 这类硬识别， 本质是把自然语言意图分类塞进执行器。它会继续扩大规则表，也会制造新的边界问题。 这个提交已在本地 main 上用 revert 撤掉，服务器没有发布它。

这次异常更像上下文污染

同一个老会话里，前序 assistant 回复和 expertTurnNotes 已经带入“园区工友、独家腌料、15分钟夜宵战、408厂”等内容。 新开会话能正常回答，说明不是账号串库的主问题，而是旧会话上下文和工具结果边界失真。

Claude Code 的设计骨架

1

用户输入

普通文本、slash command、附件、上下文提示都先进入统一消息处理。

2

QueryEngine

持有会话状态，拼装 system prompt、user context、tools、权限上下文和历史消息。

3

LLM

模型看到工具 schema 后自行决定输出自然语言，还是输出 tool_use block。

4

Tool Registry

runtime 只按 tool 名称找到工具，做 input schema、权限和可用性检查。

5

Tool Result

工具结果以 tool_result block 回到消息流，和用户文本严格分开。

6

下一轮模型

模型基于结构化工具结果继续回答或再次调用工具。runtime 不替模型解释语义。

Claude Code 谁负责什么

LLM
理解自然语言意图 决定 answer 或 tool_use 填写工具参数 读取 tool_result 后组织回复
Runtime
拼 prompt 和消息 提交模型请求 识别结构化 tool_use 权限和 schema 校验 执行工具 回填 tool_result 记录 transcript 压缩上下文边界
Tools
声明 name 声明 description 声明 inputSchema 执行 call 映射 tool_result 渲染工具使用和结果
Context
CLAUDE.md / memory system context user context message selection compact boundary tool_result 不混成用户话

我们现在的咨询 Runtime

1

Consultation Service

加载商家、策略资产、会话历史、专家容器、知识库设置和工具设置。

2

Slim Context Pack

拼 merchantIdentity、策略快照、日历、检索命中、工具结果、专家白板。

3

Runtime Loop

优先 native tool calling；失败或未启用时走 JSON tool loop；最后可能回到 bounded planner。

4

Business Tools

模型可见工具包含知识库检索、视频素材检索、保存爆款检索、策略编辑、日历更新。

5

Tool Cards

工具执行后写事件、payload、summary，并用于可见工具卡和后续上下文。

6

Expert Turn Notes

每轮生成短期专家白板，供下一轮或下一个专家接续。

这次异常链路

前序轮次
会话里已经出现“园区工友、独家腌料、15分钟夜宵战、408厂”等表达。 其中 408厂 不是已确认用户事实，更像模型生成的示例被后续上下文重新吸收。
用户问工具
老会话里用户问“你现在能用什么工具了”。模型没有直接回答工具目录，而是错误调用 search_saved_viral_materials，runtime 按模型 tool call 执行。
工具检索
检索仍然 scoped 到 shaokao@163.com 对应商家，不是账号串库。 但查询词被旧上下文和商家行业扩展成烧烤/餐饮方向，命中了夜宵类保存内容。
下一次追问
用户追问“我是问，你能用什么工具”。这一轮没有工具调用，但模型继续借用了旧 expertTurnNotes 和上一轮素材检索语境，于是输出了过度具体的“园区场景/产品操作类视频”和“夜宵/工友模板”。
新会话正常
新开会话没有污染的专家白板、错误示例和前序工具上下文，所以模型能自然列出工具。 这支持“上下文工程问题”而不是“runtime 缺一个元问题硬门禁”。

差距对照

维度 Claude Code 倾向 我们现在的问题 应改方向
工具目录 工具 schema 和 prompt 自然暴露给模型。模型可直接用自然语言回答“我有什么工具”。 工具目录、工具结果、业务建议混在同一咨询语境里，模型容易把“能用工具”说成“刚检索到什么”。 把 capability catalog 作为稳定上下文提供给 LLM，不在 runtime 做用户意图分流。
tool_use 只有模型输出结构化 tool_use block 才执行工具。 JSON loop 和 native loop 已有这个形态，但 fallback planner 仍保留历史痕迹，容易让人误以为 runtime 会主动规划。 默认只走 native/model JSON 工具循环；planner 作为兼容降级单独记录，后续再删。
tool_result tool_result 是结构化 user block，和用户原话、assistant 自由文本分开。 我们的 summary、visibleSummary、expertTurnNotes 会把工具结果和 assistant 表述揉在一起。 区分当前轮工具结果、历史工具结果、assistant 推断。没有当前轮 tool_result 就不能说“我检索到”。
上下文压缩 有 compact boundary、message selector、tool result 专门处理。 短期专家白板把“下一位专家继续围绕定位推进”这类接续语放进后续上下文，错误示例会被强化。 白板只能保留 fact、decision、open question、actual tool result，不保留营销文案式示例。
失败处理 工具失败以 tool_result error 进入下一轮，模型据此恢复或说明。 错误修法想在 runtime 根据用户文本短路。这会绕开模型，也绕开工具协议。 失败只按结构化调用处理：schema 不合格、权限不够、结果为空、query 过泛，都由工具结果表达。

正确改法，不是硬门禁

1. 给 LLM 一个清楚的能力目录

从 getConsultationBusinessToolCatalog() 派生一段稳定 toolCapabilityCatalog，放进 system/context。 规则是：用户问“你能做什么/有什么工具”时，模型直接基于目录回答； 只有用户要求“检索、更新、写入、参考素材”时才调用工具。

2. 清理 expertTurnNotes 的值域

whatIUnderstood 只能来自用户原话、策略资产、真实工具结果。 whatIChanged 只能来自 completed tool result。 handoffForNextExpert 不应把 assistant 自由发挥的例子变成下轮事实。

3. 当前轮证据和历史语境分层

Claude Code 的关键不是“证据门禁”，而是消息角色清楚。 我们也应把 current-turn tool results、history tool results、strategy snapshot、 assistant conversation 分开标注。模型可以参考历史，但不能把历史推断说成当前检索。

4. 工具只做参数质量校验

runtime 不判断“这是不是元问题”。但工具可以拒绝不合格参数，比如 query 为空、过泛、 与素材检索无关，返回 skipped/failed tool_result 和修正建议。这是工具契约，不是语义门禁。

5. 给老会话一个污染隔离策略

对已经出现“408厂”等错误示例的会话，下一轮应通过 context preflight 标注 assistant_generated_example 或从 expert 白板移除，而不是让它继续进入事实上下文。

6. 测试应该覆盖上下文，而不是硬触发词

测试目标不是“问工具时 runtime 返回固定文案”，而是验证： 模型消息里有工具目录、没有旧工具结果冒充当前结果、expertTurnNotes 不携带 assistant 编造事实。
