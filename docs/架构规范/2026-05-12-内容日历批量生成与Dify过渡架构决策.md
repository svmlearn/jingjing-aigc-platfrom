# 2026-05-12 内容日历批量生成与 Dify 过渡架构决策

## 1. 决策状态

- 状态：`MVP 执行依据 / 待实现落地`
- 适用范围：选题中心、咨询聊天、内容日历、团队成员批量生成、图文内容包、视频镜头脚本、后续 LangGraph.js 迁移
- 关联文档：
  - `docs/产品文档/V2.1-内容日历到图文视频工作台协作PRD.md`
  - `docs/架构规范/2026-04-25-AI视频图文数据与系统架构补充决策.md`
  - `docs/探索/2026-05-11-用dify来测试链路/2026-05-12-Dify质量门禁分支与改写节点修改说明.md`
  - `docs/探索/2026-05-11-用dify来测试链路/内容日历生成图文与视频脚本 POC.yml`

这份文档记录一个关键决策：

> Dify / 后续 LangGraph.js workflow 只负责“单条内容生成”；批量展开、队列、限流、重试、入库、进度展示由本系统负责。

## 2. 一句话结论

当前 MVP 不把 Dify 做成一个一次性生成 700 条内容的大 workflow。

正确结构是：

```text
选题中心聊天
-> 生成 7 天内容日历
-> 系统按 内容日历条目 × 团队成员 展开 generation_jobs
-> content-generation-worker 从队列领取单个 job
-> 每个 job 调一次 Dify workflow
-> 保存图文内容包 / 视频镜头脚本 / 质量评审 / 输入快照
-> 前台按 batch 展示进度和结果
```

例如：

```text
7 天内容日历 × 100 个中介 = 700 个 generation_jobs
每个 generation_job = 1 次 Dify workflow 调用
```

Dify 当前只是单条内容生成 worker。后续迁移到 LangGraph.js 后，这个边界不变，只是把单条生成 worker 的内部实现从 Dify API 替换为本地 workflow 代码。

## 3. 为什么现在用 Dify

当前阶段目标不是先把所有 workflow 工程化，而是验证：

1. 内容日历 + 爆款结构 + txt 知识库 + 图片素材能否生成可用图文内容包。
2. 同一输入能否生成可执行的视频镜头脚本。
3. 合规质量门禁和违规改写能否跑通。
4. 缺图片、弱知识库、风险词输入时能否可控降级。
5. 输出 JSON schema 是否稳定，是否适合落库。

Dify 适合当前阶段，因为：

- 节点可视化，方便快速调整 prompt、结构化输出、分支和聚合。
- 用户可以直接在 Dify UI 里改模型、参数、structured output 和节点连接。
- 可以快速通过 API 和测试脚本跑回归。
- 便于在真正写 LangGraph.js 前验证“流程是否值得工程化”。

但 Dify 不适合作为长期调度中心：

- 不负责 700 条任务展开。
- 不负责队列并发、抢占、重试、幂等。
- 不负责前台批次进度。
- 不负责生成结果与业务表关系。
- 不负责团队成员权限和商家账号边界。

## 4. 分阶段方案

### 4.1 阶段 0：Dify 单条 POC 调试

当前阶段。

目标：

```text
一条内容日历任务
+ 爆款参考
+ txt 知识库
+ 图片素材
+ 额外要求
-> 一份图文内容包
+ 一份视频镜头脚本
+ 质量评审
+ trace
```

当前已验证：

- Dify workflow 能通过 API 调用。
- 最终输出 `final_result_json` 可解析。
- 质量门禁 + 违规改写分支可跑通。
- 最终公开 JSON 可清理 `<think>` 和风险词。
- 弱知识库 / 缺图片可以保留 `qualityReview.pass=false`，但 workflow 仍成功返回可解释结果。

本阶段不追求：

- 批量性能。
- 队列吞吐。
- 低成本。
- 完整前端进度 UI。
- LangGraph.js 代码化。

### 4.2 阶段 1：MVP 接入 Dify API

目标是把主链路跑通：

```text
选题中心聊天
-> 生成 7 天内容日历
-> 用户确认或选择要批量生成的日历条目
-> 系统展开团队成员任务
-> 创建 generation_batch
-> 创建 generation_jobs
-> worker 调 Dify API
-> 保存 content_drafts / content_variants
-> 前台查看批量结果
```

MVP 的重点是“链路打通”，不是先追求最优生成效率。

阶段 1 仍然使用 Dify 的原因：

- 保持工作流可视化，方便继续调质量。
- 避免同时承担“产品链路 + workflow 工程化”两类风险。
- 可以先用真实用户/真实素材评估输出质量。

### 4.3 阶段 2：批量生产稳定化

当 MVP 链路跑通后，再补稳定性：

- 批次进度页。
- 队列并发控制。
- 失败自动重试。
- 手动重跑单条。
- 任务取消。
- 成本和耗时统计。
- Dify API 超时 / SSL EOF / 5xx 的重试策略。
- 每个 job 的输入快照、输出快照、workflow 版本、prompt 版本。

这一阶段仍可继续使用 Dify，但需要把 Dify 当成外部不稳定依赖来处理。

### 4.4 阶段 3：迁移到 LangGraph.js

当以下条件满足时，再把 Dify workflow 迁移为 LangGraph.js：

1. 单条生成质量已经通过足够多真实样本验证。
2. 输出 schema 稳定。
3. 节点职责稳定。
4. 合规词库和质量门禁稳定。
5. 批量生产的任务模型、数据落点、前台状态已经跑通。

迁移方式：

```text
Dify task_understanding        -> LangGraph.js LLM node + Zod/JSON Schema
Dify knowledge retrieval       -> Supabase pgvector / 自建 retriever
Dify creative_strategy         -> LangGraph.js LLM node
Dify article_generator         -> LangGraph.js LLM node
Dify video_script_generator    -> LangGraph.js LLM node
Dify quality_reviewer          -> TypeScript deterministic function
Dify if_else                   -> LangGraph conditional edge
Dify content_risk_rewriter     -> LangGraph.js LLM node
Dify final_compiler            -> TypeScript deterministic function
```

这里建议优先使用 `LangGraph.js`，并复用 `LangChain.js` 生态里的模型、retriever、structured output 能力。换句话说，LangChain.js 是组件库，LangGraph.js 更适合表达这个多节点 workflow。

## 5. 批量生成运行方式

### 5.1 概念对象

建议新增或等价实现以下概念：

```text
content_generation_batches
- id
- merchant_id
- created_by
- source: consultation_calendar / manual_calendar / campaign
- calendar_snapshot
- member_scope_snapshot
- total_jobs
- succeeded_jobs
- failed_jobs
- running_jobs
- status: pending / running / completed / completed_with_errors / canceled
- workflow_provider: dify / langgraph
- workflow_version
- created_at
- started_at
- finished_at

content_generation_jobs
- id
- batch_id
- merchant_id
- member_id
- calendar_item_id
- idempotency_key
- status: pending / running / succeeded / failed_retryable / failed_manual / canceled
- current_stage
- attempt_count
- max_attempts
- input_snapshot
- output_json
- quality_review
- error_message
- workflow_provider
- workflow_version
- dify_workflow_run_id
- started_at
- finished_at
- created_at
```

可以先不急着定最终表名，但系统里必须有“batch”和“job”两层概念。

### 5.2 任务展开规则

输入：

```text
calendar_items = 7 条内容日历
members = 团队下 100 个中介 / 账号
```

展开：

```text
for calendar_item in calendar_items:
  for member in members:
    create generation_job(calendar_item_id, member_id)
```

生成幂等键：

```text
merchant_id
+ calendar_item_id
+ member_id
+ workflow_provider
+ workflow_version
+ calendar_version
```

同一个幂等键不应重复创建多个有效 job。用户手动“重跑”时应创建新 attempt 或新版本，而不是悄悄覆盖旧结果。

### 5.3 Worker 执行规则

`content-generation-worker` 负责：

1. 从 Supabase 领取 `pending` job。
2. 将 job 标记为 `running`。
3. 组装 Dify inputs。
4. 调用 Dify workflow API。
5. 解析 `final_result_json`。
6. 写入 `content_drafts` / `content_variants`。
7. 回写 job 状态、耗时、错误、质量评审、输出摘要。

前端和 Vercel API 不应该同步等待单条生成完成，原因是当前 Dify 单条可能 7-9 分钟，已经超过正常交互等待体验，也容易碰到 serverless 超时。

### 5.4 Dify API 调用方式

当前测试脚本已验证的调用方式：

```http
POST https://api.dify.ai/v1/workflows/run
Authorization: Bearer <DIFY_API_KEY>
Content-Type: application/json
```

请求体：

```json
{
  "inputs": {
    "calendar_task_json": "...",
    "viral_references_json": "...",
    "image_assets_json": "...",
    "fallback_knowledge_text": "...",
    "extra_requirement": "..."
  },
  "response_mode": "streaming",
  "user": "batch_<batch_id>_job_<job_id>"
}
```

注意：

- `DIFY_API_KEY` 只能放在环境变量，不写入数据库、代码、文档、日志。
- 当前脚本使用 `streaming`，可以保存节点输出用于调试。
- 生产环境可以继续用 streaming 采集节点状态，也可以先用 blocking 简化，但需要考虑超时。
- 每次调用结果以 `outputs.final_result_json` 为准。

### 5.5 Dify inputs 需要扩展成员画像

当前 POC inputs 只覆盖内容日历、爆款、知识库和图片素材。

批量给 100 个中介生成时，建议新增：

```json
{
  "member_profile_json": "{...}",
  "account_profile_json": "{...}"
}
```

最低字段：

```text
memberId
displayName
storeName
city
serviceArea
role
tonePreference
ctaPreference
doNotMention
contactPolicy
```

用途：

- 让同一条内容日历在不同中介账号下有轻微差异。
- 控制 CTA 口吻。
- 避免不同账号发出完全一样的内容。
- 记录当时生成使用的是哪一个成员画像快照。

如果 MVP 暂时没有完整成员画像，也应该传一个最小空对象，保持接口稳定。

## 6. 结果落库规则

每个成功 job 至少保存：

```text
content_drafts
- merchant_id
- source = content_calendar_batch
- input_snapshot
- quality_review
- selected_variant_id

content_variants
- draft_id
- variant_type = note
- title
- body / copy_ready_text
- payload.articlePackage

content_variants
- draft_id
- variant_type = video_script
- script_text
- payload.videoScript
```

如果一次 Dify 同时产出图文和视频脚本，可以选择：

1. 一个 `content_draft` 下挂两个 variant：`note` 和 `video_script`。
2. 或两个 draft，通过 `generation_job_id` 关联。

MVP 建议先选第 1 种：一个 job 对应一个 draft，draft 下挂图文和视频脚本两个 variant，便于从「我的内容」按同一条内容日历追踪。

`input_snapshot` 必须包含：

```text
source
batchId
jobId
calendarItemId
selectedCalendarItem
memberProfileSnapshot
strategySnapshot
viralRefs
knowledgeRefs
imageAssetRefs
workflowProvider
workflowVersion
extraRequirement
```

这样后续即使知识库、成员信息、日历内容变化，也能解释“当时为什么生成成这样”。

## 7. 批量进度与失败处理

前台不展示“正在生成，请等待 9 分钟”的单点等待，而展示批次进度：

```text
本批次共 700 条
已完成 143
生成中 10
排队中 541
失败 6
```

job 状态建议：

```text
pending
running
succeeded
failed_retryable
failed_manual
canceled
```

失败分类：

```text
failed_retryable:
- Dify API SSL EOF
- timeout
- 429 rate limit
- 5xx
- 临时网络错误

failed_manual:
- final_result_json 无法解析
- schema 缺关键字段
- 多次重试后仍失败
- 输入缺必要上下文
- Dify app key 无效
```

重试策略：

```text
max_attempts: 3
retry delay: 递增退避，例如 1min -> 5min -> 15min
```

注意区分：

- `workflow API 调用成功 / 失败`
- `qualityReview.pass=true / false`

例如缺图片素材或弱知识库时，workflow 可以成功，job 也可以 `succeeded`，但 `qualityReview.pass=false`，前台展示为“已生成，但需要补素材/补资料后再发布”。

## 8. 并发与吞吐

当前 Dify POC 单条耗时约 7-9 分钟，主要慢在：

```text
article_generator
video_script_generator
content_risk_rewriter
```

因此 700 条不能单并发跑。

MVP 建议：

```text
初始并发：2-5
稳定后压测：10
不要一上来 100 并发打 Dify
```

需要记录：

```text
每个节点耗时
总耗时
token 使用
失败率
重试次数
每批完成时间
```

后续如果成本和耗时压力太大，再考虑“母版 + 个性化改写”：

```text
7 条内容日历先生成 7 个母版
再按 100 个中介做轻量个性化改写
```

但这不是当前 MVP 的默认方案。当前 MVP 先按“一个 job 调一次 Dify”跑通真实链路，避免提前优化影响质量判断。

## 9. 图片来源策略

房地产内容对真实性要求高，图片策略必须保守。

### 9.1 默认优先级

```text
P0：团队真实素材 / 项目素材 / 实拍图片
P1：素材中心中已审核的项目图、样板间图、周边配套图、户型图
P2：缺图时输出 imageBriefIfMissing / requiredUploads，提示团队补拍或上传
P3：AI 生图仅用于非事实性辅助视觉，不默认用于项目实景表达
```

### 9.2 允许 AI 生图的场景

可以考虑 AI 生图：

- 信息图。
- 封面文字背景。
- 抽象概念图。
- 非具体项目的生活方式氛围图。
- 内容结构海报。
- 平台风格化配图。

必须满足：

- 不伪装成真实项目照片。
- 不表达具体楼盘、真实户型、真实周边、真实人流。
- 入库时标记 `asset_source = ai_generated`。
- 保存 prompt、model、生成时间、使用场景。
- 前台或审核侧能看到“AI 生成 / 示意图”标记。

### 9.3 禁止 AI 生图的场景

默认禁止 AI 生图用于：

- 项目外立面“实拍”。
- 样板间“真实照片”。
- 楼下商业“已开业实景”。
- 地铁、学校、公园等周边配套“真实距离证明”。
- 销售现场、人流、客户到访等事实性画面。
- 任何可能让用户误以为这是项目真实状态的图片。

如果后续要引入 AI 生图，应作为独立生成节点或独立 job，不直接混进当前 Dify 主 workflow。图文 workflow 只输出 `imageBriefIfMissing` 或 `imageGenerationBrief`，由素材审核/生成模块决定是否真的生成。

## 10. 当前 MVP Completion Gate

当前阶段真正要跑通的是：

```text
选题中心聊天
-> 生成 7 天内容日历
-> 用户确认内容日历
-> 展开团队成员 × 日历条目生成任务
-> job 队列调用 Dify API
-> 保存图文内容包和视频镜头脚本
-> 前台能看到批次进度
-> 我的内容能看到生成结果
-> 缺素材 / 弱知识库 / 合规风险有明确提示
```

不要求：

```text
1. 立即替换成 LangGraph.js。
2. 立即做 AI 生图。
3. 立即做视频成片渲染。
4. 立即做到 700 条在几分钟内全部完成。
5. 立即做到每个中介高度个性化。
```

## 11. 后续工程化迁移原则

当从 Dify 迁移到 LangGraph.js 时，只替换“单条生成 worker 内部实现”，不要推翻批量调度层。

保持不变：

```text
generation_batches
generation_jobs
input_snapshot
output_json
quality_review
content_drafts
content_variants
前台批次进度
失败重试策略
```

替换内容：

```text
Dify API call
-> LangGraph.js workflow invocation
```

这样可以保证：

- MVP 先跑通。
- Dify 调试成果不会浪费。
- 后续工程化只是替换 worker provider。
- 生产数据结构和前台体验不反复推倒。

## 12. 当前冻结决策

1. Dify 只做单条内容生成，不做批量调度。
2. 7 天 × 100 个中介的 700 条内容，由系统展开为 700 个 generation_jobs。
3. 前端不等待 Dify 生成完成，只创建 batch 并查看进度。
4. 后台 worker 负责调用 Dify API、重试、落库和状态回写。
5. 当前阶段用 Dify 是为了调试质量和流程；MVP 跑通后再迁移 LangGraph.js。
6. 图片默认优先用真实素材；AI 生图只作为非事实性辅助视觉，且必须明确标记。
7. 缺图片时优先输出补拍/上传需求，不默认生成假实景图。
8. `qualityReview.pass=false` 不等于 job 失败；它可能表示需要补素材或补知识库后再发布。
9. 所有生成结果必须能回到「我的内容」或后续内容工作台，不只停留在 Dify 响应里。
10. Dify API key 只放环境变量，不写入仓库、文档、日志或数据库。
