# 2026-05-13 国内化部署与 ba-ba-ke 域名备案决策

## 1. 决策状态

- 状态：`部署架构决策 / 待执行落地`
- 适用范围：中介端 / 商家端 PWA、素材上传、视频 worker、对象存储成片下载、国内生产部署、后续从 Supabase/Vercel 迁移

  - 现有 `Supabase + Vercel + 新加坡服务器 + COS` 链路已经证明核心视频链路可跑通。
  - 后续国内生产版不建议继续把 Vercel / Supabase Cloud / 新加坡 COS 作为主链路。
  - 不自建 Supabase；目标是迁到 `国内 PostgreSQL + 自己的 Node API + 国内服务器 + 国内对象存储`。
  - 2026-05-15 已确认：`ba-ba-ke.com` 是国内公司主体，当前只是挂在 / 解析到新加坡服务器；域名主体不再阻塞大陆路线。
  - `ba-ba-ke.com` 可作为长期品牌主域名；正式国内生产前建议完成 ICP 备案。
  - 2026-05-15 晚间已收敛：正式资源统一走阿里云，因为公司已有阿里云企业账号，采购、发票、实名、备案主体更容易统一。
  - 第一阶段国内验证建议先用 `1 台阿里云 8 核 16G ECS + 阿里云 RDS PostgreSQL 基础系列 + 阿里云 OSS`，worker 先保持单并发。
  - 国内化代码改造分支已推进到 `codex/domestic-infra-migration` / `cdc5ca1`，离线可做项和部署 readiness kit 已完成；当前仍等待真实国内资源验证，恢复入口见 `架构规范/2026-05-13-国内化改造分支冻结与恢复断点.md`。

## 2. 背景

当前已知链路：

```text
商家端 / 中介端
-> 上传素材到 COS
-> 创建 video_edit_jobs
-> 新加坡服务器 video-worker / FireRed 执行剪辑
-> 成片上传回 COS
-> app 展示预览 / 下载链接
```

最近一次问题中，COS 返回：

```text
AccessDenied
Request has expired
```

这说明成片对象已经存在于 COS，失败点不是剪辑未完成，而是下载 / 预览使用了过期的临时签名 URL。

该问题应由另一条技术修复处理：

```text
数据库长期保存 bucket + storage_key
不要长期保存临时签名 URL
用户每次预览 / 下载时，由后端重新签名或通过下载接口动态跳转
```

本决策文档不修改该代码，只记录国内生产部署方向。

## 3. 域名决策

### 3.1 ba-ba-ke.com 可以继续用

`ba-ba-ke.com` 当前已经存在，并可通过 HTTPS 访问。2026-05-15 用户确认该域名是国内公司主体，当前只是解析到新加坡服务器，页面承载“芭芭客”品牌介绍。

该域名适合作为长期品牌域名，不需要另起新域名。

推荐子域名规划：

```text
ba-ba-ke.com          官网 / 品牌介绍页
app.ba-ba-ke.com      中介端 / 商家端 PWA
admin.ba-ba-ke.com    平台管理端，可选
api.ba-ba-ke.com      Node API
cdn.ba-ba-ke.com      OSS/CDN 素材和成片访问域名
```

不要直接把根域名完全覆盖成应用入口。根域名更适合保持品牌官网，应用入口使用 `app.ba-ba-ke.com`。

### 3.2 不备案也能做 PWA，但不适合长期国内生产

如果 `ba-ba-ke.com` 继续指向香港 / 新加坡等境外服务器，技术上可以：

- 手机浏览器打开。
- 添加到手机桌面，作为 PWA / 类应用使用。
- 上传素材。
- 下载剪辑成片。

但风险是：

- 国内不同运营商访问速度不稳定。
- 大素材上传和大视频下载容易慢、断、卡。
- 无法稳定使用中国大陆 CDN 加速。
- PWA 只是更像 App 的浏览器入口，不能解决跨境网络不稳定。

因此，不备案方案只适合：

```text
老板演示
小范围内测
验证中介是否愿意使用
```

不建议作为正式生产长期方案。

### 3.3 国内生产版需要 ICP 备案

如果后续将 Web/API、PostgreSQL、OSS、video-worker 放到中国大陆服务器或大陆 CDN，则应对 `ba-ba-ke.com` 做 ICP 备案。

由于 `ba-ba-ke.com` 已确认是国内公司主体，当前优先判断是：不需要新买域名绕开主体问题，而是继续确认云账号实名、备案材料、域名注册商控制权和 DNS 解析权限是否齐全。

备案通过后，再将以下子域名解析到国内资源：

```text
app.ba-ba-ke.com -> 国内 Web/API 服务器
api.ba-ba-ke.com -> 国内 Node API
cdn.ba-ba-ke.com -> 国内 OSS/CDN
```

## 4. ICP 备案准备

### 4.1 备案前需要确认

需要先确认：

1. `ba-ba-ke.com` 的域名注册商控制权。
2. DNSPod 解析权限。
3. 域名实名认证主体。
4. 备案主体是否与公司 / 老板业务主体一致。
5. 计划购买哪家云厂商的中国大陆服务器。
6. 是否需要使用云厂商备案服务码。

如果域名当前实名是个人，但生产服务要以公司主体运营，建议先将域名实名过户到公司主体，避免备案被驳回或后续主体不一致。

### 4.2 常见材料

企业备案一般需要准备：

```text
企业营业执照
法人或网站负责人身份证
网站负责人手机号、邮箱
域名实名认证信息
中国大陆云服务器或备案服务码
网站名称
网站服务内容说明
真实性核验材料
必要时的授权书或补充说明
```

### 4.3 时间预期

备案不是特别复杂，但不要按“当天完成”规划。

建议排期：

```text
资料齐全、主体一致：预留 1-3 周
主体不一致、资料被驳回、实名信息未同步：预留 3-4 周
```

通常流程包括：

```text
云厂商初审
-> 短信核验 / 真实性核验
-> 提交管局
-> 管局审核
-> 备案通过
-> 域名解析到大陆服务器
```

网站正式开通后，还应按要求补公安联网备案。

### 4.4 公安联网备案

ICP 备案通过、网站正式开通后，应补公安联网备案。

入口：

```text
https://beian.mps.gov.cn
```

通常需要准备：

```text
ICP备案号
网站域名
主体信息
网站负责人信息
服务器 / 接入信息
安全管理制度或安全责任信息
```

公安联网备案不是替代 ICP，而是 ICP 之后的补充动作。

### 4.5 算法 / 深度合成备案

本项目涉及：

```text
用户上传自拍视频
用户上传声音音频
声音克隆 / 音色复用
AI 口播音频生成
AI 视频 / 图文内容生成
```

因此需要按深度合成、生成式 AI、算法备案相关要求提前准备材料。入口：

```text
https://beian.cac.gov.cn
```

当前判断：

- 声音克隆和 AI 视频合成属于需要严肃对待的深度合成能力。
- 是否立即提交算法 / 深度合成备案，需结合服务开放范围、是否面向公众、是否具有舆论属性或社会动员能力等口径确认。
- 但正式对外收集真实用户自拍视频、声音音频并提供声音克隆前，材料应先准备好，不要等上线后再补。

建议先准备：

```text
算法 / 深度合成服务说明
模型或第三方服务说明，例如 RunningHub
输入数据类型：自拍视频、图片、声音音频、文本脚本
输出内容类型：口播音频、合成视频、图文内容
内容安全策略
用户授权和撤回机制
AI 生成合成内容标识方案
投诉举报和处置机制
日志留存和审计说明
```

### 4.6 用户协议和个人信息合规材料

本项目处理的自拍视频、人脸、声音、声纹、声音克隆音色，均应按敏感个人信息高标准处理。

正式收集真实用户素材前，至少要准备：

```text
《隐私政策》
《用户服务协议》
《声音克隆授权协议》
《AI合成内容使用规则》
《用户素材授权与肖像/声音承诺》
个人信息处理清单
第三方共享清单
个人信息保护影响评估记录
```

产品内需要同步落地：

- 上传声音前，用户单独勾选声音克隆授权。
- 上传自拍视频 / 图片素材前，用户确认素材是本人或已取得合法授权。
- 明确禁止冒用他人肖像、声音制作虚假内容。
- 提供素材删除、音色删除或停用入口。
- 后台记录授权版本、授权时间、授权用户、撤回记录。
- AI 生成内容在页面或导出物上提供显式标识；需要下载 / 导出时，后续按要求补隐式标识或元数据方案。
- RunningHub、阿里云 OSS、阿里云 RDS 等第三方处理方写入隐私政策和第三方共享清单。

## 5. 目标国内生产架构

### 5.1 总体结构

目标结构：

```text
国内备案域名
-> Nginx / HTTPS
-> Next.js app + 自己的 Node API
-> 阿里云 RDS PostgreSQL
-> 阿里云 OSS
-> 国内 video-worker / FireRed
-> PWA 添加到手机桌面
```

当前 Vercel / Supabase Cloud / 新加坡服务器可继续作为：

```text
开发环境
staging
海外演示
回滚参考
```

不再作为国内正式生产主链路。

### 5.2 不自建 Supabase

本项目不建议为了“迁走 Supabase Cloud”而自建完整 Supabase。

原因：

- 当前核心业务数据本质是 PostgreSQL 表结构和应用逻辑。
- 自建 Supabase 会引入额外运维面：Auth、Realtime、Storage、Gateway、备份、高可用、安全升级。
- 国内生产真正需要的是稳定数据库、稳定 API、稳定任务队列和稳定媒体链路。

目标是：

```text
Supabase Cloud
-> 国内 PostgreSQL
-> 自己的 Node API
```

而不是：

```text
Supabase Cloud
-> 自建 Supabase
```

## 6. 迁移需要补的技术项

### 6.1 数据库

需要将当前 `app/supabase/migrations/` 中已经生效的业务 schema 迁到国内 PostgreSQL。

重点：

- 保留 `merchant_profiles`、`content_drafts`、`content_variants`、`asset_objects`、`video_edit_jobs` 等核心表。
- 核对 Supabase 特有能力，例如 RLS、Auth user id、扩展、函数、策略。
- 明确哪些字段继续沿用，哪些要改成自有 API 层权限控制。
- 准备 staging 数据迁移脚本和回滚点。

### 6.2 Node API

迁移后，前端不应再直接依赖 Supabase client 读写业务数据。

需要补：

```text
登录 / 登出
当前用户信息
商家 / 门店 / 中介成员权限
内容草稿和变体读写
素材上传意图
素材上传完成回调
视频任务创建
视频任务查询
成片预览 / 下载重新签名
平台管理端接口
```

权限判断从 Supabase RLS 迁到 Node API 层统一处理。

### 6.3 登录和权限

如果不继续使用 Supabase Auth，需要实现自己的登录体系。

MVP 可先采用：

```text
手机号或邮箱 + 密码
HTTP-only session cookie
merchant_id / member_id / role 绑定
服务端权限校验
```

后续再扩展：

```text
短信验证码
微信扫码
企业微信
多门店 / 多账号权限
```

### 6.4 OSS 和媒体访问

国内生产版应新建中国大陆区域阿里云 OSS bucket。旧文档中出现的 `COS` 可以理解为“对象存储层”的历史表述；正式阿里云方案中，对应实现应改为 OSS。

需要补：

- 国内 OSS bucket 和 region。
- CORS 配置。
- STS 临时上传凭证。
- 分片 / 大文件上传稳定性。
- 成片下载签名接口。
- OSS object key 规范和生命周期策略。
- 可选 CDN 加速域名 `cdn.ba-ba-ke.com`。

重要规则：

```text
长期保存 OSS bucket + storage_key
临时 signed URL 只在用户打开预览 / 下载时生成
```

不要把临时 signed URL 当作永久成片地址保存。

### 6.5 video-worker / FireRed

国内生产版 worker 应与数据库和 OSS 尽量在同一区域。

需要补：

```text
从国内 PostgreSQL claim video_edit_jobs
running heartbeat
任务超时检测
失败分类
自动重试
手动重跑
成片上传回国内 OSS
result_payload / asset_objects 回写
worker 日志和关键耗时记录
```

服务器配置不是唯一关键。要同时记录：

```text
素材上传耗时
worker claim 等待时间
worker 下载素材耗时
AI / VLM / TTS 耗时
FireRed / FFmpeg 渲染耗时
成片上传耗时
数据库回写耗时
```

这样才能定位“卡住”到底发生在哪一段。

#### 6.5.1 当前资源判断

2026-05-13 根据 staging 服务器日志和监控，当前结论更新为：

```text
2 核 4G：可以跑通单个视频任务，但 CPU 和内存峰值已接近打满，不建议继续承载 Web/API + worker。
4 核 8G：可做低成本单并发验证，但视频任务期间可能影响前台访问。
8 核 16G：推荐作为第一阶段国内验证单机，混跑 Web/API + worker + FireRed，worker 先保持单并发。
16 核 32G：适合后续验证 2-3 个视频任务并发，或当 8 核 16G 压测数据贴边时升级。
```

需要注意：

- 当前 worker 代码默认并强制 `WORKER_MAX_CONCURRENCY = 1`，所以 8 核 16G 不能直接等同于支持 3 并发。
- OpenStoryline / FireRed 不跑本地大模型，不需要 GPU；但仍会消耗 FFmpeg、Docker、CPU torch、ASR/embedding、临时文件和对象存储 IO。
- 第一阶段不建议买四台服务器。先用 1 台阿里云 8 核 16G ECS + 阿里云 RDS PostgreSQL 基础系列 + 阿里云 OSS 跑通完整链路，再按监控数据决定是否拆 Web/API 和 worker。

### 6.6 PWA 类应用

中介端优先做 PWA，而不是先做原生 App。

需要补：

```text
manifest.json
service worker
应用图标
启动页 / theme color
移动端全屏适配
弱网 loading / retry
登录态持久化
视频下载入口
```

PWA 不需要 iOS App Store 上架。iPhone 用户通过 Safari 添加到主屏幕；安卓用户可通过浏览器安装 PWA。

安卓 APK 可以作为后续方案，但不是当前主路径。

## 7. 分阶段落地建议

### 7.1 阶段 0：现有链路继续验证

继续使用当前 staging 链路验证：

```text
Vercel
Supabase Cloud
新加坡服务器
COS
```

本阶段重点不是大迁移，而是确认：

- 成片链路稳定跑通。
- COS signed URL 过期问题修复。
- worker 失败原因可见。
- 中介端真实使用流程是否成立。

### 7.2 阶段 1：ba-ba-ke 境外 PWA 小范围试用

如果备案尚未完成，可先用：

```text
app.ba-ba-ke.com -> 新加坡 / 香港服务器
```

用于老板演示和小范围中介试用。

本阶段必须明确：

```text
这是境外链路验证，不是国内生产承诺。
```

### 7.3 阶段 2：备案和国内资源准备

并行准备：

```text
ba-ba-ke.com ICP 备案
国内服务器，第一阶段推荐 8 核 16G 单机混跑
国内 PostgreSQL
国内 OSS
国内 worker 服务器，第一阶段可不单独购买，后续按真实负载拆分
Nginx / HTTPS
DNS 子域名规划
ICP / 公安联网备案 / 算法备案材料
隐私政策和声音 / 肖像 / 素材授权协议
```

备案期间不阻塞产品继续验证。

### 7.4 阶段 3：国内 staging 环境

搭建国内 staging：

```text
staging-app.ba-ba-ke.com

```

验证：

- 登录。
- 上传素材。
- 创建视频任务。
- worker 领取任务。
- FireRed 生成成片。
- 成片上传 OSS。
- 预览和下载重新签名。
- 手机 PWA 添加到桌面。

### 7.5 阶段 4：国内生产切换

国内 staging 验证通过后，再切换生产：

```text
app.ba-ba-ke.com
api.ba-ba-ke.com
cdn.ba-ba-ke.com
```

切换前保留旧环境作为回滚参考。

## 8. 验收清单

国内生产链路至少要满足：

- 国内手机网络可稳定打开 `app.ba-ba-ke.com`。
- PWA 可添加到桌面并保持登录态。
- 中介可上传图片 / 视频素材。
- 大文件上传有进度、超时、失败重试提示。
- worker 能稳定生成视频。
- 成片能预览。
- 成片能下载。
- OSS 临时链接过期后，刷新页面仍能重新获取可用链接。
- 每个 video job 有明确状态、失败原因和耗时日志。
- 数据库、对象存储、worker 在同一区域或低延迟区域。
- 正式阿里云方案中，数据库、OSS、worker 尽量在同一区域或低延迟区域。
- 上线收集真实自拍视频 / 声音前，用户协议、隐私政策、声音克隆授权、素材授权和 AI 合成内容规则已上线。
- ICP 备案、公安联网备案、算法 / 深度合成备案材料有明确责任人和进度。
- 旧 Vercel / Supabase staging 不影响国内生产。

## 9. 当前非目标

当前不做：

- 自建 Supabase 全家桶。
- iOS 原生 App 上架。
- 安卓 APK 作为第一主路径。

## 10. 一句话结论

`ba-ba-ke.com` 可以作为未来正式域名。

### 11.3 担忧和注意事项

短期风险不大，但有几个运维注意点：

1. DNS 操作分散

   服务器、OSS、备案在企业账号，域名解析在个人账号。后续新增 `app.ba-ba-ke.com`、`api.ba-ba-ke.com`、`cdn.ba-ba-ke.com`、SSL 校验、CDN 校验或 TXT 记录时，需要登录个人账号操作。

2. 续费和资产归属风险

   域名续费、自动续费、联系人邮箱和付款方式仍在个人账号下。长期看不利于企业财务、权限、交接和审计。

3. 不要改变域名实名认证主体

   后续如果做账号间域名转移，只应转移管理权，不应把域名实名主体改成个人或其他公司。域名实名主体、备案主体、企业账号实名主体应保持一致。

4. 账号迁移后要复查 DNS

   将域名从个人账号转到企业账号管理后，需要立即检查解析记录、自动续费、联系人邮箱、SSL / CDN / 邮箱相关记录是否完整保留。

5. 以阿里云备案系统最终校验为准

   当前判断是基于阿里云域名实名截图和通用备案规则。正式提交时仍以阿里云 ICP 备案系统、管局校验和页面提示为准。
