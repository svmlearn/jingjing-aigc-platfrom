# 2026-05-14 COS 私有素材库与个人克隆声音工作方案

> 渐进式披露入口。不要把这份方案当成一篇从头读到尾的大文档；按当前任务只读对应板块。

## 0. 当前结论

本方案分成两条主线：

1. 商家团队素材库：商家端确认入库的图片 / 视频进入 COS 和数据库索引，切片打标签后通过 Pexels-compatible 接口供 OpenStoryline 检索。
2. 个人克隆声音：基础链路已由 `codex/voice-clone-user-flow` 合入，后续重点是“每人一个当前音色、重新录制覆盖旧音色、真实 provider 联调”。
3. Dify 脚本制作链路：当前真正的单条内容生成 / 脚本制作来源是 Dify。系统 worker 调 Dify 后解析 `outputs.final_result_json`，按字段确认器里的 `article.*`、`video.*`、`quality.*`、`debug.*` 落库。

硬边界：

- COS 只存对象，不承担数据库职责。
- 索引、权限、状态、标签、检查和纠错都落在 PostgreSQL / Supabase 与服务端逻辑。
- 团队素材按 `merchant_id` 隔离。
- 个人克隆声音按 `created_by_user_id` 私有。
- 用户端 / 成员端临时上传的制作素材不进入团队素材库，不切片打标签，不长期保存。
- 视频工作台和后续视频 worker 消费 Dify 生成并校验落库后的 `video_script` variant；不要再引入另一套“脚本制作 Agent 原生 JSON”作为主合同。

## 3. 外部依据

- Pexels API 文档：用于兼容 `photos/videos` 请求、分页字段、`next_page`、`src`、`video_files`。
  <https://www.pexels.com/api/documentation/>

  <https://intl.cloud.tencent.com/document/product/436/45242>
- Tencent COS 预签名 URL：下载 / 分享链接应有有效期；本项目对 OpenStoryline / 前端素材预览统一给 60 天有效下载 URL。
  <https://intl.cloud.tencent.com/document/product/436/45243>
- Supabase RLS：公开 schema 的表必须启用 RLS 并配置策略。
  <https://supabase.com/docs/guides/database/postgres/row-level-security>
- OWASP File Upload Cheat Sheet：上传前必须做认证、授权、文件类型和存储隔离检查。
  <https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html>
- GitHub REST API 分页文档：大结果集必须分页，客户端应能稳定追踪下一页。
  <https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api>
- Supabase GitHub Discussion：RLS 不应替代查询过滤；多租户列和 RLS 相关列需要显式索引和显式查询条件。
  <https://github.com/orgs/supabase/discussions/14576>
- GitHub Community Discussion：多租户 RLS 中 `auth.uid()` 是用户 ID，不是 tenant ID；tenant / merchant 隔离必须通过 membership 或 claim 映射。
  <https://github.com/orgs/community/discussions/149922>
- Stack Overflow 预签名上传讨论：客户端 `Content-Type` / `file.type` 不可信，真实类型应在服务端代理上传或对象落地后验证。
  <https://stackoverflow.com/questions/72477856/aws-s3-presigned-url-how-to-make-sure-that-the-file-type-is-correct>
- tus resumable upload protocol：大文件上传需要过期、校验和、可恢复 / 可清理机制作为工程参考。
  <https://tus.io/protocols/resumable-upload>
- Reddit / Supabase 多租户审计经验：上线前要做“用户 A 尝试访问用户 B / 商家 B 数据”的双租户 fixture 扫描。
  <https://www.reddit.com/r/Supabase/comments/1t80q7e/expert_for_a_paid_multitenant_security_audit/>
- addyosmani/agent-skills：参考其生命周期化工作方式，把 spec、plan、build、test、review、ship 拆成可验证 gate；同时采用 progressive disclosure、contract-first、incremental implementation 和 launch checklist。
  <https://github.com/addyosmani/agent-skills>

这些依据不是装饰性参考，已转成下面的硬规则：

| 专业社区 / 官方经验 | 在本方案里的落地方式 |
| --- | --- |
| GitHub / Supabase RLS 经验：RLS 是安全兜底，不应替代业务过滤；RLS 列要有索引。 | 所有 repository 查询显式带 `merchant_id` 或 `created_by_user_id`，migration 必须补索引，测试要查出“只靠 RLS”的实现。 |
| GitHub Community 多租户讨论：`auth.uid()` 是用户 ID，不是 tenant ID。 | 不能把 `auth.uid()` 直接当 `merchant_id`；必须通过 `merchant_profiles` / `merchant_team_members` 映射商家权限。 |
| GitHub REST API 分页实践：分页响应要让客户端知道下一页。 | Pexels-compatible 接口必须支持 `page/per_page/next_page`，结果稳定排序，必要时补 `Link` header 方便排查。 |
| Stack Overflow 预签名上传经验：客户端 MIME / 扩展名不可信。 | 上传完成后必须做真实文件探测，图片 / 视频 / 音频都要进入 `post_upload_validating`，失败进入 quarantine 或清理。 |
| OWASP 文件上传安全：上传前授权，上传后验证，存储隔离。 | 上传 intent 必须先校验登录、商家权限、owner、大小、类型；COS key 服务端生成；下载给 60 天有效 URL，但不开放 public bucket。 |
| COS STS / 签名 URL 官方机制：临时授权有有效期和权限范围。 | 前端上传只拿短期临时凭证；下载返回 60 天平台下载 URL 或可行时的 60 天 COS 签名 URL；STS policy 限定到单个 prefix / key，不能暴露永久密钥和永久公开 URL。 |
| tus 可恢复上传经验：长上传需要过期、校验和和孤儿清理。 | upload intent 必须记录 `expires_at`、checksum / ETag、幂等 key；doctor 要清理超时 pending 和 orphan 对象。 |
| agent-skills 工程流程：spec 先行、contract-first、薄切片、验证不可省、发布可回滚。 | 本方案分册就是渐进式入口；实现时按“合同 -> DB/RLS -> 服务端 -> worker -> UI -> staging”小步推进，每一步必须有验收证据。 |

## 4. 总硬门禁

任何实现分支必须同时满足：

- 不绕过 `merchant_id` 做素材检索。
- 不绕过 `created_by_user_id` 使用个人声音。
- 不把前端临时上传素材写入团队素材库索引。
- 不返回永久公开 COS URL；OpenStoryline / 前端素材预览返回 60 天有效下载 URL。
- 不在 OpenStoryline 内部大面积改搜索、下载、剪辑节点；优先用 Pexels-compatible 层适配。
- 不把“已设计”写成“已实现”；未落地能力必须标注为待实现。
- 不只依赖 RLS 做过滤；服务端查询也必须显式带 `merchant_id` / `created_by_user_id` 条件。
- 不信任前端声明的 MIME / 扩展名；对象落地后必须做真实文件探测。
- 不假设 DB 和 COS 是同一个事务；所有跨 DB / COS / provider 的流程必须有 pending 状态、幂等 confirm 和补偿清理。
- 不把外部依据只写在文档里；每条高风险依据必须落成 migration 约束、repository 过滤、契约测试、doctor 检查或上线门禁之一。
- 不做大爆炸式一次性合并；必须按可回滚薄切片推进，每个切片都有边界、测试和回滚点。
