# 01 依据与全局硬门禁

## 摘要

本分册定义 Dify 主链路进入国内自托管后的共同底线：

```text
Dify 生成图文内容包和视频脚本
-> 系统落库
-> 用户确认脚本
-> 用户点击 AI 剪辑
-> app 创建 video_edit_jobs
-> video-worker / OpenStoryline / FireRed 执行
```

这不是一条新视频执行链路，而是把“脚本来源”换成 Dify。视频后半段仍沿用既有 `video_edit_jobs.input_payload` 合同。

## 当前决策

- Dify 是当前内容生成 / 脚本生成主链路。
- Dify 不做批量调度，只做单条内容生成。
- 批量展开、队列、落库、状态展示由本系统负责。
- 当前阶段不做多并发，所有 Dify job 按单队列顺序消费。
- Dify job 成功后不自动启动视频服务器。
- 用户确认 `video_script` 并点击“AI 剪辑 / 生成视频”后，才创建 `video_edit_jobs`。
- 国内正式部署不再以 Vercel serverless 为目标运行环境。
- 国内自托管默认按腾讯云大陆路线规划；具体服务器拓扑等资源购买后再定。
- 所有真实 key、密码、provider secret 只允许进服务器环境变量或云平台 secret，不进仓库、文档、日志、截图。

## 依据

项目依据：

- `docs/架构规范/2026-04-28-current-architecture.md` 规定 `video_edit_jobs.input_payload` 是 app 和 video-worker 的稳定合同。
- `docs/架构规范/2026-05-12-内容日历批量生成与Dify过渡架构决策.md` 已明确 Dify 只做单条生成，系统负责 batch / job / 落库。
- `docs/产品文档/V2.1-内容日历到图文视频工作台协作PRD.md` 规定视频脚本必须落到 `content_variants.variant_type = video_script`，创建视频任务前必须有 `contentVariantId`。
- `docs/handoff/2026-05-15-dify-to-video-worker-integration-workdoc.md` 记录当前代码缺口：Dify `video.scenes[]` 在真实 Supabase 中尚未可靠持久化为 `productionScenes`。
- 国内化部署文档已明确后续不以 Vercel / Supabase Cloud / 新加坡服务器作为国内正式主链路，目标是国内服务器、国内 PostgreSQL、国内 COS/OSS、自托管 Node API。

外部依据：

- Dify 官方 workflow API 支持 `POST /v1/workflows/run`，`response_mode` 可选 `blocking` 或 `streaming`，并返回 `workflow_run_id`；长任务更适合 streaming 或轮询模式。
- Dify 官方文件上传 API `POST /v1/files/upload` 要求 API Key 服务端保存；上传文件返回 `id`，可作为 workflow 文件输入的 `upload_file_id`。
- Dify GitHub / 官方 Docker Compose 文档说明 Dify 是 workflow、RAG、模型接入和 LLMOps 平台；官方自托管最低资源为 2C/4G，并建议 Docker Compose。
- GitHub Dify discussion 中对长工作流的建议是使用 streaming 或 workflow_run_id 轮询，不依赖 webhook/callback。
- FireRed/OpenStoryline GitHub 定位是自然语言视频创作和剪辑 agent，本项目只把它作为视频制作执行引擎，不让它理解商家权限或 Dify 原始总包。
- Gitee 上的 Dify 仓库多为镜像或二次分发，国内可用性有参考价值，但版本、接口和安全策略不能替代官方文档和官方 GitHub。
- CSDN / 问答社区常见经验集中在 Docker Compose `.env` 位置、端口冲突、镜像拉取、升级后新环境变量未同步等问题，本项目只把这些吸收为部署检查项。
- OWASP 文件上传安全建议不要信任 `Content-Type`，文件落地后仍要做真实类型探测。
- Tencent COS 临时凭证实践要求前端直传使用临时 key，永久密钥保留在服务端。
- GitHub / Supabase 多租户经验说明 RLS 是安全兜底，不应替代业务查询过滤；`auth.uid()` 是用户 ID，不是租户 ID。

## 专业社区经验落地规则

| 经验 | 本项目规则 | 检查方式 |
| --- | --- | --- |
| 长 workflow 不适合前端同步等待。 | Dify job 进入队列，由服务端单队列消费。 | 前端只创建 batch，不等待 Dify 完成；`run-next` 可独立触发。 |
| Dify API key 应只在服务端。 | 不允许 key 出现在客户端、文档、commit、日志。 | `rg "app-"`、env bundle 检查、日志脱敏。 |
| 上游生成 JSON 不应污染执行层。 | Dify final JSON 只能先落库，再经 payload builder 生成 video job。 | `video_edit_jobs.input_payload` 快照不得包含 Dify 原始总包。 |
| RLS 不能替代业务过滤。 | repository 查询仍必须显式带 `merchant_id` / `created_by_user_id`。 | 双商家 fixture、代码审查、必要时 explain。 |
| 文件上传 MIME 可伪造。 | COS complete 后做真实文件探测或隔离。 | 伪造扩展名 / MIME 上传测试。 |
| 视频执行要可回放、可定位。 | worker 记录 stage log、engine request 摘要和 result payload。 | 失败能定位到 Dify、落库、payload、download、engine、upload。 |

## 工作边界

必须做：

- Dify final JSON 落 `content_generation_jobs.output_json` 或 `content_drafts.input_snapshot` 作为追溯。
- 图文结果落 `note` variant。
- 视频脚本落 `video_script` variant。
- Dify `video.scenes[]` 结构化持久化，供用户确认后创建视频任务。
- 用户点击 AI 剪辑前，不创建 `video_edit_jobs`。
- 自托管部署必须预留 Dify 队列消费入口。

不做：

- 不让 Dify 直接创建 `video_edit_jobs`。
- 不让 OpenStoryline / FireRed 直接吃 Dify JSON。
- 不在当前阶段做多并发 Dify 消费。
- 不把 Vercel 作为国内正式运行前提。
- 不把真实 Dify key、服务器密码、数据库连接串写进任何文档。
- 不自建 Supabase 全家桶作为迁移目标。

## 全局硬门禁

实现前：

- 必须确认当前改动属于 Dify 生成、落库、队列、视频触发、worker 执行、国内部署中的哪一层。
- 涉及新增表或字段时必须先写 migration 和验收 SQL。
- 涉及真实 Dify / COS / PostgreSQL / OpenStoryline 时必须确认密钥只存在环境变量。

合并前：

- Dify `outputs.final_result_json` 不得直接进入 `video_edit_jobs.input_payload`。
- Dify 成功后不得自动创建 `video_edit_jobs`。
- `video_edit_jobs` 只能由用户确认脚本并点击 AI 剪辑后创建。
- `content_variants.variant_type = video_script` 必须有非空 `script_text`。
- 真实 Supabase / PostgreSQL 中必须能持久化结构化分镜。
- `run-next` 或后续队列消费器必须一次只 claim 一个 job。
- 所有队列失败必须分 `failed_retryable` 和 `failed_manual`。
- 所有新增公开业务表必须有 RLS，或明确只允许 service role / 后端访问。
- 国内部署文档必须以自托管 Node/API 为目标，不再要求 Vercel `maxDuration`。

上线前：

- Dify 真实 smoke 至少跑通 1 个 job。
- Dify job 成功后成员端能看到图文和视频脚本。
- 用户确认脚本前创建视频任务必须被拒绝。
- 用户点击 AI 剪辑后能创建 `video_edit_jobs`。
- video-worker 能消费该 job 并进入 OpenStoryline/FireRed。
- 结果能回写 COS / `asset_objects` / `video_edit_jobs`。
- 有 progress / handoff 记录命令、环境、job id、失败或成功证据。

## 检查功能

建议增加 `dify_mainline_doctor` 或等价检查，至少检查：

- 是否存在 Dify 成功 job 但没有 `content_draft_id`。
- 是否存在 Dify 成功 job 但没有 `video_variant_id`。
- 是否存在 `video_script` 缺 `script_text`。
- 是否存在 Dify 来源的 `video_script` 缺结构化 `production_scenes`。
- 是否存在 Dify job 成功后自动创建的 `video_edit_jobs`。
- 是否存在 `video_edit_jobs.input_payload` 含 `article`、`video`、`quality`、`outputs` 等 Dify 原始总包字段。
- 是否存在未脱敏的 Dify key / provider key 字符串进入仓库。
- 队列是否有长时间 `running` 且无进展的 job。
- 服务器环境变量是否缺 `DIFY_API_KEY`、`DIFY_BASE_URL`、`CONTENT_GENERATION_WORKER_SECRET`。

## 纠错功能

- Dify API 失败：标记 `failed_retryable`，记录 HTTP status / timeout 类型，不记录 key。
- Dify final JSON schema 失败：标记 `failed_manual` 或 `schema_failed`，保留原始输出用于排查。
- 落库失败：job 保留错误，允许重新消费或人工修复。
- 结构化分镜缺失：阻断 AI 剪辑，提示回到 Dify adapter / migration 修复。
- 用户误点 AI 剪辑但脚本未确认：API 返回可解释错误，不创建 job。
- video-worker 失败：按既有 `failed_retryable` / `failed_manual` 规则处理，不回滚 Dify 生成结果。

## 板块验收

通过标准：

- 每个子分册都写清工作流程、工作边界、硬门禁、检查、纠错。
- 文档明确“不使用 Vercel 作为目标服务器”。
- 文档明确“当前不做多并发，只做队列顺序消费”。
- 文档明确“Dify 完成后不自动剪辑，用户点击后视频服务器才动”。
- 所有外部资料只转化为工程规则，不把论坛内容当作架构真相源。
