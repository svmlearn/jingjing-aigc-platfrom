# 07 门禁解释与把关清单

## 摘要

本文件给产品负责人、技术负责人和验收人使用。它解释每个硬门禁为什么存在、没过会造成什么后果、通过时应该有什么证据。

## G1 Dify 不得直塞 worker payload

门禁：

```text
outputs.final_result_json 不得直接作为 video_edit_jobs.input_payload
```

为什么：

- Dify JSON 是内容总包，不是视频执行合同。
- worker 稳定合同是 `script + productionDirective + productionConfig + materialContext + input_assets`。

没过的后果：

- worker 被迫理解 Dify schema。
- Dify 字段一改，视频执行就坏。
- 旧脚本链路和 Dify 链路分裂成两套 worker input。

过关证据：

- Dify 来源和非 Dify 来源都通过同一个 payload builder。
- payload 快照没有 `article/video/quality/outputs/final_result_json`。

## G2 Dify 成功后不自动剪辑

门禁：

```text
Dify job succeeded 后不得自动创建 video_edit_jobs
```

为什么：

- 用户必须先看脚本、确认脚本。
- 视频服务器开始工作是用户点击 AI 剪辑后的动作。
- 这和以前的视频工作台链路一致。

没过的后果：

- 用户还没确认内容，视频服务器就消耗算力。
- 错脚本会直接出片。
- 用户无法区分“内容生成完成”和“视频剪辑开始”。

过关证据：

- Dify job succeeded 后查不到对应 `video_edit_jobs`。
- 点击 AI 剪辑后才出现 pending video job。

## G3 当前只做单队列，不做多并发

门禁：

```text
当前阶段 Dify job 一次只消费一个
```

为什么：

- 先验证链路正确，不先优化吞吐。
- Dify 单条耗时较长，复杂并发会增加排障难度。
- 国内服务器资源尚未最终确定。

没过的后果：

- 多个 job 同时 running，失败归因困难。
- Dify rate limit 或 timeout 放大。
- 用户误以为已进入生产吞吐规划。

过关证据：

- `run-next` 一次只 claim 一个 job。
- 消费器只有一个实例。
- 文档和部署脚本没有批量并发参数。

## G4 国内正式链路不依赖 Vercel

门禁：

```text
国内自托管是目标运行环境
```

为什么：

- 用户已确认后续不用 Vercel 服务器。
- Dify 长 workflow 不适合受 serverless 时长限制。
- 国内用户访问、上传、下载需要国内服务器和对象存储稳定链路。

没过的后果：

- 方案继续围绕 Vercel timeout 打补丁。
- 国内部署时还要重写一遍。

过关证据：

- 文档使用自托管 Node/API、国内 PostgreSQL、国内 COS。
- Vercel 只作为旧 staging / 过渡参考。

## G5 video_script 必须持久化结构化分镜

门禁：

```text
Dify video.scenes[] 必须落 content_variants.production_scenes
```

为什么：

- `script_text` 适合人看，不适合稳定素材匹配。
- AI 剪辑需要分镜查询、素材槽位、拍摄要求。

没过的后果：

- 创建视频任务时只能从文本中猜分镜。
- Dify 的结构化成果丢失。
- 素材匹配和 ProductionDirective 质量下降。

过关证据：

- 真实 DB 读取 `video_script.productionScenes` 非空。
- payload 中 `sceneAssetQueries` 来自 structured scenes。

## G6 用户确认脚本是进入视频任务的门禁

门禁：

```text
reviewStatus 必须为 approved
```

为什么：

- app 是业务语义进入执行层的唯一门禁。
- worker 只执行锁定脚本，不改写语义。

没过的后果：

- 未审核内容进入出片。
- 后续修订责任不清。

过关证据：

- 未 approved 创建 video job 返回错误。
- approved 后同一 variant 可创建 job。

## G7 真实密钥不得进文档和仓库

门禁：

```text
key / password / connection string 不写入 repo-tracked 文件
```

为什么：

- Dify key、COS key、DB 连接串泄漏会直接造成成本和数据风险。

没过的后果：

- 需要轮换密钥。
- 可能导致素材、成片、数据库暴露。

过关证据：

- 文档只写变量名。
- `rg` 搜不到真实 key pattern。
- 服务器检查只输出 present / missing。

## G8 content-generation 和 video-worker 不混职责

门禁：

```text
content-generation 消费 Dify jobs
video-worker 消费 video_edit_jobs
```

为什么：

- 内容生成和视频渲染是两类长任务。
- 混在一个 worker 里会导致排障、扩容、暂停互相影响。

没过的后果：

- Dify 堵塞影响视频出片。
- 视频渲染故障影响内容生成。

过关证据：

- 两类 job 表不同。
- 两类消费器入口不同。
- 日志能分开看。

## G9 国内资源未验收前不声明完成

门禁：

```text
没有真实国内服务器 / DB / COS / Dify / video-worker 证据，不写完成
```

为什么：

- API smoke 不能替代真实手机访问、上传、出片、下载。

没过的后果：

- 产品误以为可交付。
- 后续接手人找不到真实阻塞点。

过关证据：

- progress 文档有环境、命令、job id、COS key 摘要、状态截图或日志摘要。
- Completion Gate 全部满足。

## 最终把关顺序

1. 看 Dify final JSON 是否能稳定落库。
2. 看 `video_script` 是否有结构化分镜。
3. 看 Dify 成功后是否没有自动 video job。
4. 看用户确认脚本门禁是否有效。
5. 看点击 AI 剪辑后是否创建标准 `video_edit_jobs.input_payload`。
6. 看 video-worker 是否不关心脚本来源。
7. 看国内自托管环境是否能跑真实 Dify 和真实出片。
8. 看 progress / handoff 是否有证据。

只要 G1、G2、G3、G5、G6 任一失败，就不要进入视频真实出片验收。
