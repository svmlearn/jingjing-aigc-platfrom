# 2026-05-15 选题到内容生成全链路产品总纲

## 1. 文档定位

本文是当前产品主链路的总纲文档，用来统一说明：

- 用户端从选题对话到一周内容日历的产品流程。
- 图片素材、视频素材、用户知识库、爆款内容、Agent 方法论知识库之间的分工。
- 内容日历进入 Dify / 后续 LangGraph 单条生成器前，系统如何组织上下文和候选输入。
- Dify 输出 JSON 后，前端、content-worker、video-worker 如何继续消费和落库。

本文描述的是目标主链路和协作边界，不表示所有能力都已经完整上线。实际实现状态仍以代码、migration、progress 和 smoke test 记录为准。

## 2. 一句话主链路

```text
用户维护资料和素材
-> 用户与选题 AI 对话
-> 选题 AI 读取方法论知识库、用户知识库和内容资产
-> 生成一周内容日历
-> content-worker 按日历条目组装 Dify 候选输入
-> Dify 基于单条任务再次理解和检索文本知识库
-> Dify 输出图文 JSON 和视频脚本 JSON
-> 前端渲染图文、图片和视频脚本
-> 用户补充声纹、口播和拍摄视频素材
-> video-worker 根据脚本和素材生成成片
-> COS / asset_objects / content_drafts / video_edit_jobs 回写沉淀
```

## 3. 当前产品入口取舍

### 3.1 主入口：选题

用户端主入口应从早期“咨询诊断”收敛为“选题”。

选题不是普通聊天，也不是简单 prompt 输入框。它的产品职责是：

- 理解用户这一周要做什么内容。
- 读取项目资料、销售话术、爆款参考和方法论知识。
- 形成可确认、可编辑、可追溯的一周内容日历。
- 为后续批量生成图文和视频脚本提供稳定任务。

本文默认描述用户端主链路。团队成员 / 多账号批量生成可以作为后续扩展，但不应干扰当前用户端主流程理解。

### 3.2 图文工作台和视频工作台

图文工作台、视频工作台当前暂时保留，但后续不再作为用户端主链路入口。

建议定位为：

- 调试入口。
- 高级编辑入口。
- 单条内容详情页。
- 生成结果的人工修订入口。

当“选题 -> 内容日历 -> 批量生成 -> 结果查看”主链路稳定后，可以在 UI 上隐藏普通用户的工作台入口，或通过权限 / feature flag 控制展示。

## 4. 核心对象分工

### 4.1 用户知识库

用户知识库保存用户自己的业务事实和表达边界。

典型内容：

- 产品内容。
- 项目资料。
- 楼盘 / 门店 / 服务介绍。
- 销售话术。
- 客户异议。
- 常见问答。
- 禁用词和合规边界。

主要服务：

- 选题 Agent 判断本周选题方向时检索。
- Dify 单条生成时补充项目事实。
- 后续 LangGraph 单条生成器复用同一输入合同。

一句话：用户知识库回答“这件事是不是真的，能不能这么说”。

### 4.2 Agent 方法论知识库

Agent 方法论知识库属于选题 Agent 自身能力，不等同于用户知识库。

典型内容：

- 小红书选题方法。
- 短视频脚本方法。
- 九宫格选题法。
- 评论区需求提炼方法。
- 爆款拆解方法。
- 本地生活 / 房地产内容打法。
- 拍摄和复盘方法论。

主要服务：

- 选题 Agent 在对话中规划内容日历。
- 让 Agent 有“怎么问、怎么判断、怎么排一周内容”的方法。

一句话：方法论知识库回答“这一周应该怎么规划内容”。

### 4.3 爆款内容库

爆款内容库保存外部抓取或用户导入的高互动内容。

典型内容：

- 小红书爆款笔记。
- 抖音爆款视频脚本或摘要。
- 标题、hook、正文结构、互动数据。
- 评论区需求和用户痛点。

主要服务：

- 给选题 Agent 参考内容方向。
- 给 Dify / LangGraph 单条生成器参考表达结构。

限制：

- 不能作为用户项目事实。
- 不能直接复制正文。
- 不能当作视频 worker 的项目视频素材。

一句话：爆款内容库回答“这件事怎么说更像平台内容”。

### 4.4 图片素材库

图片素材库保存用户上传或团队沉淀的真实图片素材。

典型内容：

- 项目外立面。
- 样板间。
- 户型图。
- 周边配套。
- 门店 / 服务现场。
- 可作为图文封面和正文配图的图片。

主要服务：

- 图文封面图。
- 图文内容图。
- 图文内容中每个信息块的配图。

限制：

- 图片素材不作为视频 worker 主输入。
- 房地产项目类内容优先使用真实图片。
- AI 生图只适合非事实性视觉，如信息图、封面背景、抽象概念图，并且需要标记来源。

一句话：图片素材库回答“图文用什么画面表达”。

### 4.5 视频素材库

视频素材库保存可供剪辑的视频资产。视频文件本体在 COS，数据库保存 `asset_objects`、素材归属、解析状态和后续可检索元数据。

典型内容：

- 项目实拍。
- 样板间 B-roll。
- 周边配套视频。
- 销售口播片段。
- 用户后续按脚本补拍的视频。

主要服务：

- video-worker 生成成片时，从 COS / 视频素材索引中检索、下载并使用素材。
- 按视频脚本中的 `assetQuery` 或 app 合同化后的素材匹配计划，匹配可剪辑片段。

限制：

- 视频素材不直接进入图文配图。
- 未完成解析 / 索引的视频素材不应被当作可精准匹配片段。

一句话：视频素材库回答“剪辑时间线用什么片段表达”。

## 5. 分阶段数据流

### 5.1 阶段一：资料与素材入库

用户或团队先沉淀可复用资产。

输入来源：

- 用户上传文本资料。
- 用户录入销售话术。
- 用户上传图片。
- 用户上传视频。
- 用户导入爆款链接。
- 平台或运营侧维护 Agent 方法论知识。

系统落点：

- 文本资料进入用户知识库。
- 爆款内容进入爆款内容库或 source_items。
- 图片进入 asset_objects / 素材中心，并标记可用于图文配图。
- 视频进入 asset_objects / 素材中心，并标记可用于视频剪辑。
- 方法论进入 Agent 挂载的知识集。

输出要求：

- 每个素材需要知道 `sourceKind`、`usageType`、`retrievalTargets`。
- 图片和视频不能只保存文件地址，还需要后续可检索摘要、标签或解析状态。

### 5.2 阶段二：用户与选题 AI 对话

用户在“选题”入口和 AI 对话。

选题 Agent 可读取：

- 当前用户资料。
- 用户知识库。
- Agent 方法论知识库。
- 已导入爆款内容。
- 历史内容日历。
- 已生成图文 / 视频脚本。
- 用户本轮新增目标和限制。

选题 Agent 负责输出：

- `strategySnapshot`：定位、卖点、目标客群、内容目标、风险边界。
- `contentCalendar`：一周内容日历。
- 每条日历的业务意图和生成目标。

建议每条内容日历至少包含：

```text
calendarItemId
dayLabel
calendarDate
title
summary
targetPlatform
contentType
contentGoal
strategyTag
ctaHint
```

内容日历阶段不预生成 `copySearchQuery`、`scriptSearchQuery`、`imageSearchQuery`、`videoAssetQueryHints`。

这些 query 已经由 Dify 的“任务理解”节点负责生成。内容日历只保存业务意图，不保存检索实现字段，避免同一判断在选题 Agent 和 Dify 内部重复生成两份。

这一阶段的结果是“生成任务计划”，不是最终图文或最终视频脚本。

### 5.3 阶段三：确认内容日历

内容日历进入批量生成前，用户应能确认或调整。

用户可做：

- 确认一周内容日历。
- 删除某条。
- 修改某条标题 / 摘要 / 目标平台。
- 增加额外要求。
- 选择生成范围，当前默认是当前用户自己；团队成员批量生成是后续可选扩展。

系统写入：

- 日历快照。
- 用户确认状态。
- 生成范围。
- 后续 batch 的 `calendar_snapshot`。

### 5.4 阶段四：content-worker 组装 Dify 候选输入

content-worker 不负责创作文案，它负责把每条内容日历转成稳定的单条生成任务。

输入：

- 已确认内容日历条目。
- 当前用户画像。
- 成员画像，仅在启用团队批量生成时使用。
- 用户知识库兜底文本或候选摘要。
- 爆款内容候选。
- 图片素材候选。
- 额外要求。

输出给 Dify 的最小输入包：

```text
calendar_task_json
viral_references_json
image_assets_json
fallback_knowledge_text
extra_requirement
```

可选扩展输入，不作为当前最小合同：

```text
user_profile_json
member_profile_json
account_profile_json
```

其中 `image_assets_json` 只放图片素材候选，建议结构：

```json
{
  "assetId": "img_001",
  "title": "项目外立面",
  "description": "小区正门与两侧绿化",
  "cosPath": "cos://bucket/path/to/image.jpg",
  "previewUrl": "/api/media/cos-preview?path=...",
  "tags": ["外立面", "封面", "项目实景"],
  "usageHint": "cover"
}
```

content-worker 可以基于日历标题、摘要、内容目标、用户手动选择和素材已有标签做候选召回，但不应新增一套 LLM query 生成逻辑。

content-worker 同时负责：

- 创建 `content_generation_batches`。
- 创建 `content_generation_jobs`。
- 记录 `input_snapshot`。
- 控制队列、并发、重试和状态。

### 5.5 阶段五：Dify 单条生成

Dify 当前是单条内容生成器，不负责批量调度。

当前 Dify V3.1 核心节点：

```text
开始
-> 任务理解
-> TXT 知识库检索
-> 创作策略规划
-> 标题与封面策略
-> 正文与配图编排
-> 图文包编译
-> 视频叙事结构
-> 分镜与素材策略
-> 视频交付物编译
-> 质量评审
-> 是否需要违规改写
-> 违规内容改写
-> 最终结果编译
-> 输出 final_result_json
```

Dify 内部 TXT 知识库检索可以保留。它是单条生成阶段的二次精确检索，也是 `copySearchQuery`、`scriptSearchQuery`、`imageSearchQuery` 等字段的主要生成位置。

检索分层关系：

- 选题 Agent 检索：为了规划一周做什么。
- content-worker 候选召回：为了给 Dify 候选上下文和候选素材，不重复生成 Dify 内部 query。
- Dify 内部检索：为了让单条内容基于任务理解再补充文本事实。

Dify 输出应以 `final_result_json` 为准。

当前建议业务输出结构：

```json
{
  "status": "passed",
  "article": {
    "title": "标题",
    "coverCopy": "封面字",
    "images": [
      {
        "cosPath": "cos://bucket/path/to/image.jpg",
        "role": "cover"
      }
    ],
    "copyText": "可复制图文正文"
  },
  "video": {
    "storyOutline": "故事线",
    "estimatedDuration": "60s",
    "bgm": "BGM方向",
    "toneOfVoice": "口吻",
    "scenes": [
      {
        "sceneNo": 1,
        "sceneType": "口播",
        "requiresUserUpload": true,
        "taskDescription": "用户需要拍什么",
        "visualDescription": "画面描述",
        "voiceover": "口播台词",
        "assetQuery": ""
      },
      {
        "sceneNo": 2,
        "sceneType": "素材",
        "requiresUserUpload": false,
        "taskDescription": "需要素材库匹配什么画面",
        "visualDescription": "项目外立面远景",
        "assetQuery": "项目外立面 远景 小区入口"
      }
    ]
  },
  "quality": {
    "riskTerms": []
  }
}
```

### 5.6 阶段六：生成结果落库与前端渲染

content-worker 拿到 Dify 输出后负责落库。

建议落点：

- `content_generation_jobs.output_json`
- `content_generation_jobs.quality_review`
- `content_drafts.input_snapshot`
- `content_variants.variant_type = note`
- `content_variants.variant_type = video_script`
- 关联到日历条目、当前用户、batch、job；若启用团队批量生成，再关联到成员。

前端负责：

- 渲染图文标题、正文、封面字。
- 通过 `article.images[].cosPath` 调 COS preview API 展示真实图片。
- 渲染视频脚本分镜。
- 标注哪些镜头需要用户上传。
- 标注哪些镜头从视频素材库匹配。
- 展示生成状态、失败原因和可重试入口。

注意：

- 前端不应把 Dify 原始 trace 当作用户主内容展示。
- Dify 输出里的图片应是图片素材引用，不是视频素材。
- 没有图片时应展示补图提示或图片需求 brief，而不是技术错误。

### 5.7 阶段七：用户补充声纹、口播和拍摄视频

视频脚本生成后，用户可能继续补充：

- 自己的声纹。
- 口播视频。
- 按分镜拍摄的视频素材。
- 额外素材说明。

这些补充资产进入：

- asset_objects。
- draft input assets。
- video job input payload。

视频脚本中的 `requiresUserUpload = true` 表示该镜头需要用户补拍或上传。

视频脚本中的 `sceneType = 素材` 和 `assetQuery` 表示该镜头优先从 COS 中已有的视频素材库或视频素材索引检索。

### 5.8 阶段八：video-worker 生成成片

video-worker 不负责理解选题，也不负责重写脚本。

video-worker 负责：

- 读取已确认视频脚本。
- 基于 `video_edit_jobs.input_payload`、分镜 `assetQuery` 和素材索引，从 COS 检索 / 下载用户上传或团队已有的视频素材。
- 校验 `video_edit_jobs.input_payload`。
- 调用 FireRed / OpenStoryline。
- 上传 final.mp4、封面、字幕到 COS。
- 回写 `video_edit_jobs`。
- 写入结果资产到 `asset_objects`。

video-worker 的输入必须来自 app 合同化后的 payload，不能直接消费 Dify 自由文本。

## 6. Dify 与 LangGraph 的迁移边界

后续迁移 LangGraph 时，不推翻主链路。

保持不变：

- 选题对话。
- 内容日历。
- content_generation_batches。
- content_generation_jobs。
- input_snapshot。
- 输出 JSON 合同。
- content_drafts / content_variants。
- 前端渲染。
- video-worker 输入合同。

替换部分：

```text
runDifyWorkflow(inputs)
-> runLangGraphWorkflow(inputs)
```

LangGraph 应承接的是“单条生成器内部节点”，例如：

- 任务理解。
- 文本知识检索。
- 创作策略。
- 图文生成。
- 视频脚本生成。
- 质量评审。
- 风险改写。
- 最终 JSON 编译。

不建议让 LangGraph 接管：

- 批量展开。
- 队列。
- 并发。
- 重试。
- 前端进度。
- 数据落库。
- 团队成员权限和多账号批量范围。

## 7. 关键边界规则

### 7.1 不要混用素材类型

```text
文本知识库 -> 图文文案 / 视频脚本事实依据
爆款内容 -> 标题 / hook / 结构 / 节奏参考
图片素材 -> 图文封面和正文配图
视频素材 -> video-worker 剪辑输入
```

任何一个生成环节都不能把所有资料混进一个大 prompt。

### 7.2 不要把 Dify 变成调度中心

Dify 只处理单条内容生成。

批量生成必须由系统负责：

- batch。
- job。
- claim。
- retry。
- cancel。
- progress。
- idempotency。
- 落库。

### 7.3 不要把产品事实交给模型编造

项目名、区域、户型、价格、配套、销售承诺等事实只能来自：

- 用户知识库。
- 用户明确输入。
- 已确认项目资料。

如果缺失，应降级表达或提示补资料。

### 7.4 图文工作台 / 视频工作台不是主链路前提

后续用户端主体验可以是：

```text
选题
-> 一周内容日历
-> 批量生成
-> 内容结果列表
-> 单条详情 / 修订 / 补素材 / 生成视频
```

工作台入口可以保留，但不应成为普通用户必须理解的核心概念。

## 8. 最小验收门禁

主链路跑通的最低标准：

1. 用户能在选题入口与 AI 对话，并得到一周内容日历。
2. 内容日历每条有稳定 `calendarItemId` 和生成所需字段。
3. 用户确认内容日历后，系统能创建 batch / jobs。
4. 每个 job 能组装 Dify 输入包。
5. Dify 能返回可解析 `final_result_json`。
6. 图文结果能落库并渲染真实 COS 图片。
7. 视频脚本能落库并展示每个分镜。
8. 分镜能区分用户上传、视频素材库匹配和文字卡。
9. 用户上传视频素材后，video-worker 能生成成片并回写。
10. 缺知识、缺图片、缺视频素材时，用户看到的是可操作提示，不是技术错误。

## 9. 后续待定问题

1. 选题 Agent 生成内容日历时，是否允许同时创建 draft，还是只创建 calendar item。
2. 用户知识库与 Dify TXT 知识库是否保持同步，还是由 content-worker 把检索结果写入 `fallback_knowledge_text`。
3. Dify 内部 TXT 知识库在迁移 LangGraph 后由哪个 retriever 替代。
4. 图片素材是否需要单独的 image analyzer 生成场景标签、OCR 和封面适配标签。
5. 视频素材是否由独立 asset analyzer 做 ASR / OCR / 画面描述 / 时间码切片。
6. 图文工作台和视频工作台隐藏后，历史 URL 与高级编辑入口如何保留。

## 10. 当前推荐下一步

建议下一步先补一份更细的接口合同，主题是：

```text
内容日历条目
-> Dify 输入包
-> final_result_json
-> 前端渲染与 video-worker 输入
```

只要这四段合同稳定，Dify 可以继续调质量，LangGraph 也可以在后续替换，不会反复推翻产品主链路。
