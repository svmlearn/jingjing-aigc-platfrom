# Docker 部署方案

日期：2026-05-18  
状态：OpenStoryline / FireRed 单机部署规范，已按当前服务器链路沉淀为可复用方案。  
适用范围：`video-worker`、`openstoryline-engine`、`firered-openstoryline`、OpenStoryline 小代码包发布、服务器 Docker Compose 重建、模型和媒体资源挂载。

## 1. 文档定位

本文用于规范当前 AI 视频链路中 OpenStoryline / FireRed 的 Docker 部署方式。

它不是通用 Docker 教程，也不是完整迁移 Web 应用的方案。当前目标是把本地已经改过的 OpenStoryline 能力稳定接入现有生产链路：

```text
video-worker
-> openstoryline-engine
-> firered-openstoryline
-> final.mp4
```

当前结论：

- OpenStoryline / FireRed 以 headless 执行服务存在，不作为用户 Web 入口。
- `video-worker` 和 `openstoryline-engine` 继续作为外层编排和适配层。
- 快速迭代阶段优先上传小代码包，并在服务器本地 `docker compose build`。
- 模型、资源、缓存和输出产物通过服务器本地 volume 挂载，不随代码包和镜像反复分发。
- 版本冻结、多机分发或服务器无法 build 时，再考虑镜像仓库或 Docker 镜像归档。

## 2. 服务边界

当前服务边界保持为：

```text
前端 / 业务系统
-> video-worker
-> openstoryline-engine
-> firered-openstoryline
```

各层职责如下：

- `video-worker`：接收和 claim 任务，下载输入素材，调用 engine，上传结果到 COS / OSS，回写数据库状态。
- `openstoryline-engine`：内部适配层，把 worker 的 `ProductionDirective` 转换为 OpenStoryline / FireRed worker API 请求。
- `firered-openstoryline`：真实视频执行服务，只负责读取本地素材、脚本和制作指令，生成 `final.mp4` 及元数据。

OpenStoryline / FireRed 不承担：

- 用户 Web 页面入口。
- 浏览器聊天入口。
- 浏览器素材上传流程。
- 业务任务状态管理。
- COS / OSS 上传。
- 数据库状态回写。

OpenStoryline / FireRed 必须承担：

- 读取本地素材路径。
- 读取锁定脚本和剪辑指令。
- 执行剪辑、配音、时间线、字幕和渲染。
- 输出成片和可诊断元数据。

## 3. 当前推荐部署策略

当前推荐采用：

```text
小代码包上传
+ 服务器本地 docker compose build
+ 服务器挂载已有 resource / .storyline / outputs
+ 固定 config.toml 随私有部署包上传
```

当前不优先采用：

```text
本地打 1GB+ Docker 镜像
+ 上传 COS / OSS
+ 服务器 curl 下载
+ docker load
```

推荐小代码包方案的原因：

- 上传体积小，失败重试成本低。
- OpenStoryline / FireRed 仍在快速迭代，代码包比镜像包更适合高频替换。
- 服务器已有模型、资源、缓存和输出目录，不应随代码重复分发。
- `video-worker` 和 `openstoryline-engine` 已经稳定运行，单次替换 OpenStoryline 不需要全量重启。
- 大镜像通过 COS / OSS 中转会引入上传速度、签名 URL 过期、断点续传、对象清理和镜像加载时间等额外变量。

经验规则：

```text
快速迭代阶段：优先传小代码包。
稳定发布 / 多机分发阶段：再沉淀镜像制品或推私有镜像仓库。
```

## 4. Docker 的角色

Docker 在当前方案中的角色是运行环境封装，不是全部资产搬运箱。

镜像内应包含：

- Python 运行环境。
- 系统依赖，例如 `ffmpeg`。
- OpenStoryline / FireRed 代码。
- Python 依赖。
- 启动脚本。

镜像外应挂载：

- `config.toml`
- `resource/`
- `.storyline/`
- `outputs/`
- server cache
- 其他大模型、大素材和渲染中间产物目录。

禁止把以下内容烘焙进公开镜像：

- API key。
- 服务器私有 `config.toml`。
- 用户素材。
- 模型权重。
- 成片输出。
- 运行日志和临时包。

核心原则：

```text
镜像放稳定运行环境。
volume 放会变化的大资产、配置、缓存和产物。
```

## 5. 打包边界

小代码包应该包含：

```text
agent_fastapi.py
src/
prompts/
scripts/
requirements.txt
run.sh
Dockerfile
.dockerignore
config.toml
```

小代码包不应该包含：

```text
outputs/
resource/
.storyline/models/
.storyline/.server_cache/
.venv/
.tmp_wheels/
dist/
.git/
*.log
*.tar
*.zst
*.part
```

正常代码包大小应是 MB 级。如果包体变成几百 MB 或 GB 级，优先判断是否误打入资源、输出、虚拟环境、模型或历史压缩包。

发布前必须检查：

1. 包体大小是否符合预期。
2. 包内文件列表是否符合边界。
3. 是否包含 `.git`、`.venv`、`outputs`、`resource`、模型目录或历史包。
4. 是否包含不应公开的 key、token、credential。
5. 是否生成并记录 sha256，方便服务器侧校验。

## 6. 配置文件边界

当前 `config.toml` 按服务器私有运行配置处理。

允许：

- 随私有部署包上传到服务器运行目录。
- 通过 SSH 修改服务器上的运行配置。
- 用于固定模型名、`base_url`、TTS 参数和其他 provider 配置。

不允许：

- 提交到 Git。
- 写入公开镜像。
- 在文档、日志、CI 输出中打印 API key。
- 混入前端公开配置。

配置文件需要区分三种位置：

```text
本地工作区
服务器运行目录
代码仓库
```

能上传到服务器，不代表能进入代码仓库。能进入私有部署包，不代表能进入公开镜像。

## 7. 服务器目录处理

服务器旧 OpenStoryline / FireRed 不作为当前生产基线保留。

替换时应执行：

1. 备份旧代码目录。
2. 清理旧上传残留和无效临时包。
3. 替换 `openstoryline/firered` 代码。
4. 保留 `/srv/jingjing-video-worker/firered` 下的运行资源、模型、缓存和输出目录。
5. 只重建并重启 `firered-openstoryline`。

必须保留：

```text
video-worker
openstoryline-engine
/srv/jingjing-video-worker/firered/resource
/srv/jingjing-video-worker/firered/.storyline
/srv/jingjing-video-worker/firered/outputs
```

可以清理：

```text
旧 openstoryline/firered 代码
tmp 里的无效 .part
tmp 里的旧 openstoryline tar / zst
旧的误打大包
```

替换规则：

```text
替换代码，不删除运行资源。
备份旧代码，不把服务器旧代码合回本地。
以本地当前工作区或指定 release 包作为部署基线。
```

## 8. Compose 更新方式

只替换 OpenStoryline / FireRed 时，禁止使用会影响整条链路的全量停机命令。

推荐命令：

```bash
docker compose build firered-openstoryline
docker compose up -d --no-deps firered-openstoryline
```

不推荐：

```bash
docker compose down
docker compose up -d
```

除非明确要重建整条链路，否则不要让 OpenStoryline 单服务替换影响 `video-worker`、`openstoryline-engine`、数据库连接或其他已运行服务。

## 9. COS / OSS 与 CORS 判断

CORS 只影响浏览器跨域访问，例如：

```text
browser -> COS / OSS PUT/GET object
```

本部署链路通常是：

```text
本机 CLI 上传部署包
服务器 curl 下载部署包
```

这两类请求不走浏览器 CORS 机制。

因此：

- 浏览器直传 COS / OSS 需要 CORS。
- `coscli cp`、`ossutil cp` 不依赖 CORS。
- `curl signed-url` 不依赖 CORS。
- CORS 配正确也不能解决大包上传慢、签名过期、服务器下载中断或对象清理问题。

排查上传 / 下载问题时，应先判断请求是谁发出的：浏览器才有 CORS；CLI 和服务器之间通常不是 CORS 问题。

## 10. 分层验证顺序

部署后不要直接跑完整视频任务。必须先分层验证。

1. 容器是否启动：

```bash
docker compose ps
```

2. OpenStoryline / FireRed 是否健康：

```bash
curl http://127.0.0.1:7860/health
```

3. Engine 是否能探测 OpenStoryline：

```bash
curl http://127.0.0.1:8000/ready
```

4. 挂载是否存在：

```bash
docker compose exec firered-openstoryline bash -lc "test -f /app/config.toml && ls -la /app/resource /app/.storyline /app/outputs"
```

5. 再跑全链路任务：

```text
video-worker 下载素材
-> engine 调 OpenStoryline
-> OpenStoryline 生成 final.mp4
-> worker 上传 COS / OSS
-> worker 回写状态
-> 前端预览成片
```

全链路失败时，不要先猜模型问题。优先按以下顺序排查：

```text
容器
-> health
-> engine ready
-> volume 挂载
-> config.toml
-> provider key / base_url / model
-> 任务 payload
-> 渲染日志
```

`401 Unauthorized`、`403 Forbidden` 优先检查：

- key 是否有效。
- `base_url` 是否对应供应商。
- model 是否被该 key 授权。
- 配置是否被环境变量覆盖。

不要先改业务逻辑。

## 11. 大镜像方案的适用条件

大 Docker 镜像归档链路通常是：

```text
本地 build 镜像
-> docker save
-> zstd 压缩
-> 上传 COS / OSS
-> 生成签名 URL
-> 服务器下载
-> sha256 校验
-> docker load
-> docker tag
-> compose up
```

该方案适合：

- 多台服务器分发。
- 版本已经冻结。
- 镜像仓库不可用但需要制品归档。
- 依赖安装极慢，服务器不能 build。
- 发布流程已经标准化，制品需要长期留档。

该方案不适合当前快速迭代阶段，尤其当：

- 本地功能仍在频繁修改。
- 镜像体积达到 GB 级。
- 上传速度和重传成本不可控。
- 服务器已经具备模型、资源和运行缓存。
- 只是替换单个 OpenStoryline / FireRed 服务。

后续版本稳定后，可以演进为：

- 推私有镜像仓库。
- 拆分 base image 和 app image。
- COS / OSS 仅保存镜像归档制品。
- 用 release tag 管理可回滚版本。

## 12. 当前项目部署流程

当前项目推荐流程：

```text
本地当前 OpenStoryline / FireRed
-> 生成小代码包，包含服务器私有 config.toml
-> 上传到 /srv/jingjing-video-worker/tmp
-> 备份并替换 /srv/jingjing-video-worker/openstoryline/firered
-> 复用 /srv/jingjing-video-worker/firered/resource 和 .storyline
-> docker compose build firered-openstoryline
-> docker compose up -d --no-deps firered-openstoryline
-> 分层验证 health / ready / volume / 全链路
```

这套方案的核心不是省略部署步骤，而是把代码、配置、模型、资源、输出和编排层拆开管理。

拆清楚以后：

- 部署包更小。
- 重试成本更低。
- 回滚边界更清楚。
- provider 配置问题更容易定位。
- 单服务替换不影响整条 worker 链路。

## 13. 发布门禁

每次执行 OpenStoryline / FireRed Docker 部署前，至少确认：

1. 当前部署基线来自本地当前工作区、指定 commit 或明确的 release 包。
2. 服务器旧代码已备份，不作为合并来源。
3. 小代码包未包含模型、输出、资源、虚拟环境和历史压缩包。
4. `config.toml` 未进入 Git，日志中未打印 secret。
5. volume 挂载路径和服务器目录保留清单已确认。
6. 只替换 `firered-openstoryline` 时使用 `up -d --no-deps firered-openstoryline`。
7. 已按容器、health、engine ready、挂载、全链路顺序验证。

## 14. 可复用判断框架

后续部署类似 AI 视频服务时，先问五个问题：

1. 当前是快速迭代还是稳定发布？
2. 模型和资源是否已经在服务器存在？
3. 运行产物是否应该进入镜像？
4. 配置是公开配置、服务器私有配置，还是环境变量？
5. 要替换的是单个服务，还是整条链路？

对应决策：

- 快速迭代：传小代码包。
- 稳定多机分发：传镜像或推镜像仓库。
- 大模型 / 大资源：优先服务器挂载，不跟代码一起发。
- 输出产物：只放 volume，不进镜像。
- 敏感配置：不进 Git，不打印日志。
- 单服务替换：`up -d --no-deps <service>`，不要全量 `down`。
