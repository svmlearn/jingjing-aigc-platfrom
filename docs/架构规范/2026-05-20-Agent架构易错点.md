# Agent 架构易错点：不要把模型判断写死在代码里

状态：经验沉淀
日期：2026-05-20
适用范围：咨询台 Agent、RAG、工具调用 loop、内容日历、Dify/后续工作流输入组装

## 1. 本次踩到的问题

在团队选题 Agentic RAG 优化中，曾经把视频脚本素材边界写成了代码默认文案，例如由 helper 自动生成“不要写某些素材无法支撑的镜头”之类的固定约束。

这类写法表面上是在保护生成质量，实际容易变成 Agent 架构里的硬编码业务判断。

问题不在于“限制素材边界”这个目标，而在于边界来源错了：

- 正确来源：真实素材库、用户确认的可补拍能力、知识库中的项目事实、prompt 中的生成原则。
- 错误来源：代码 helper 凭经验生成一段固定业务文案，然后塞进每条日历隐藏上下文。

## 2. 为什么这是 Agent 架构易错点

Agent 系统里经常会出现这种冲动：为了让输出更稳，把模型容易犯错的地方直接写进代码默认值里。

但如果写死的是业务判断、内容判断、创意判断，就会产生几个问题：

1. **把假设伪装成事实**
   代码生成的固定约束看起来像系统掌握的真实素材边界，但其实只是开发时的经验判断。

2. **污染下游上下文**
   一旦进入 `calendar_task_json`、`fallback_knowledge_text` 或隐藏 guidance，下游 Dify/LLM 会把它当作高优先级事实使用。

3. **难以适配真实变化**
   如果某个团队后来上传了对应素材，硬编码约束仍可能继续压制模型输出。

4. **测试会固化错误**
   如果测试断言某个固定文案存在，就会把临时经验变成长期架构规则。

5. **职责边界变模糊**
   工具层本应负责检索、编排、校验和传递事实，却开始替模型做内容策略判断。

## 3. 正确分层

### 3.1 代码层负责什么

代码层应该负责稳定、可验证、可回放的事情：

1. 调用工具。
2. 控制 tool loop 轮数和预算。
3. 校验工具参数 schema。
4. 检索知识库和素材库。
5. 保留来源、引用、分数和 trace。
6. 把真实事实打包进上下文。
7. 对写入类操作做权限、状态和幂等保护。

代码层可以传递字段，例如：

```text
assetCapabilityHints
shotConstraints
retrievalTrace
videoAssetCapabilities
knowledgeRefs
```

但这些字段应来自真实数据或上游明确输入，不应由 helper 凭空生成固定业务禁令。

### 3.2 Prompt 层负责什么

Prompt 层负责表达生成原则和判断方式，例如：

```text
生成视频选题、脚本方向或日历隐藏上下文时，画面描述必须根据已返回的素材能力、用户确认的场景或可补拍方式来写；没有素材依据的镜头不要写成确定方案。
```

这里可以讲原则，也可以给少量例子，但例子不应变成每条业务数据里的固定字段。

### 3.3 LLM 层负责什么

LLM 负责把真实素材能力、知识库事实、用户目标和平台表达方式综合起来，生成具体选题、日历摘要、图文文案或视频脚本。

如果素材能力里有某类镜头，模型可以使用。

如果素材能力里没有某类镜头，模型应避免把它写成确定可执行方案。

### 3.4 Guardrail 层负责什么

Guardrail 可以用于：

1. 权限与数据安全。
2. 结构化 schema。
3. 状态机合法性。
4. 合规高风险内容。
5. 写操作防重复、防越权、防覆盖。

Guardrail 不适合用来替代模型的业务策划判断，除非该规则是确定、长期、可验证的产品契约。

## 4. 可接受与不可接受

### 可接受

```text
从素材库检索到：
- 标题：样板间 walk-through
- 描述：室内客厅、卧室、阳台窗外视角
- shotTypes：室内走动、定点口播、窗外景
```

然后把这些事实放入 `videoAssetCapabilities`。

### 不可接受

```text
代码默认给所有视频日历 item 加：
“不得写高空航拍、大规模人群、跨城街景……”
```

除非这些约束来自真实素材解析、用户明确要求或长期产品契约。

## 5. 写 Agent 架构前的检查清单

做 Agent runtime、RAG、tool contract 或 workflow 输入组装时，先检查：

1. 这段逻辑是在传事实，还是在替模型做业务判断？
2. 这个默认文案是否来自真实数据？
3. 如果真实业务情况变化，这个规则会不会误伤？
4. 测试是在验证结构和流转，还是在固化某段临时文案？
5. 这条规则更适合放在 prompt、tool output、guardrail，还是代码默认值？
6. 如果它是 guardrail，是否具备确定性、长期性和可验证性？

## 6. 更好的 Agentic 做法

这次经验背后的准则不是“完全不要约束模型”，而是约束要放在正确层级。

### 6.1 Agent loop 要能查

模型要知道自己可以查知识库、素材库、历史上下文，并且在第一次检索没有覆盖完整问题时，可以换 query 继续查。

例如团队选题场景里，一次生成营销日历可能需要分别查：

1. 项目事实。
2. 干货方法论。
3. 销售或种草话术。
4. 视频素材能力。
5. 用户确认过的可补拍场景。

如果 loop 只允许一次 RAG，模型就容易在信息不足时猜。

如果 loop 允许无限写入，系统又容易重复覆盖资产。

所以原则是：读类工具允许多轮深挖，写类工具保持严格幂等和状态保护。

### 6.2 上下文要给足，而不是给结论

代码不要直接告诉模型“你不能写什么固定内容”，而应该把真实上下文给够。

视频素材上下文至少应让模型知道：

1. 当前有哪些视频素材。
2. 每条素材大概拍了什么。
3. 适合承接什么画面或镜头。
4. 哪些只是图文素材，不适合视频剪辑。
5. 哪些素材能力不确定，需要标注为待补拍或先追问。

这类上下文可以进入：

```text
videoAssetCapabilities
assetCapabilityHints
materialHints
knowledgeRefs
retrievalTrace
```

但不要把开发者自己的经验判断伪造成素材事实。

### 6.3 Prompt 要说清判断原则

Prompt 应明确告诉模型如何使用这些上下文。

推荐原则：

```text
撰写营销日历和视频脚本时，画面描述必须基于检索到的视频素材能力、用户确认可补拍的场景，或明确标注为需补拍；不要把未检索到、未确认、无法执行的画面写成已有素材可完成。
```

这个原则比在代码里列一串固定禁止项更稳，因为它允许模型根据真实素材变化做判断。

### 6.4 让 AI 判断，但要让判断可追溯

“让 AI 自己决定”不等于放任模型自由发挥。

更好的形态是：

1. 模型可以判断是否继续检索。
2. 模型可以判断素材是否足够支撑某个画面。
3. 模型可以判断某个镜头是已有素材、可补拍，还是应避免。
4. 系统保存支撑判断的 `knowledgeRefs`、`videoAssetCapabilities`、`retrievalTrace`。
5. 后续出错时能回放：模型当时看到了什么，为什么这样生成。

也就是：少写业务判断型 helper，多做可追溯上下文和清晰 prompt 约束。

### 6.5 硬门禁只用于确定性契约

代码硬门禁适合：

1. 账号权限。
2. 数据越权。
3. JSON schema。
4. 状态机非法迁移。
5. 重复写入。
6. 明确违法、违规、高风险内容。

代码硬门禁不适合：

1. 内容创意。
2. 选题角度。
3. 镜头表达。
4. 风格判断。
5. 需要结合知识库和素材上下文动态判断的业务策略。

这些应由 prompt、工具结果和 LLM 共同完成。

## 7. 本项目当前约定

1. `shotConstraints` 保留为隐藏上下文字段，但不由咨询台代码默认生成固定镜头禁令。
2. `assetCapabilityHints` 用来传递已确认内容场景、卖点线索或素材能力摘要，不表达代码假设。
3. `videoAssetCapabilities` 从素材库 `video_edit_asset` 检索生成，不携带 OSS/COS 具体链接。
4. 视频脚本画面边界主要通过 prompt 原则和真实素材能力共同约束。
5. 测试优先验证字段存在、可归一化、可汇总、可进入 Dify 输入；不要断言某段固定业务禁令文案。
