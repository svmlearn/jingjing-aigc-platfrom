# 2026-05-22 咨询 Agent 上下文与工具边界反思

状态：问题记录 / 暂不改造

本文件记录 2026-05-22 对咨询 Agent native tool calling、Skills 注入、用户资料上下文和历史消息处理方式的复盘。当前只沉淀问题和方向，不直接进入实现。

## 1. 背景

用户在咨询台里看到工具执行过程出现失败卡：

- `编辑策略资产` 参数校验失败。
- `更新内容日历` 参数校验失败。

初步修复过程中曾尝试过把写入类工具参数校验改为 strip 多余字段。该方向被否定：工具契约严格是正确的，不能为了聊天体验放宽 runtime 校验。

随后形成的新原则是：

1. 工具参数契约继续严格。
2. 工具描述只说允许字段，不列“不要输出某些字段”的反向提示。
3. 内部参数错误保留 trace / event / snapshot，但不作为商家可见执行事实卡展示。
4. 更深层的问题不只是工具 schema，而是上下文、工具边界和 message 结构混在一起。

## 2. Skill 注入问题

### 2.1 当前实现

当前 `selectActiveConsultationSkills()` 每一轮都会根据：

- 当前用户输入 `userContent`
- 最近若干用户消息 `userMessages.slice(-3)`

重新给 skill 打分。命中的 skill 会进入 `activeSkills`，随后 `buildActiveSkillPrompt()` 把 skill 正文放入 system message。

这意味着：

1. skill 正文不是“发现后下一轮只塞一次”。
2. 由于打分使用 recent messages，同一个 skill 可能连续多轮重复进入 system prompt。
3. 最多 3 个 skill，每个正文 clip 到 3600 字符，最坏情况下每轮会额外注入约 10800 字符。

### 2.2 与 Claude Code 参考方向的差异

参考 `references/open-source/claude-code项目/claude-code-main` 的文档和代码：

- Claude Code 的 session 由 `QueryEngine` 管理完整 `mutableMessages`。
- 每次 `submitMessage()` 会重新构建 system prompt，但 skill 更像可调用能力，而不是每轮 heuristics 直接塞正文。
- Skill 列表倾向轻量目录；真正使用 skill 时，通过 SkillTool / command 进入主对话或 fork 子 agent。
- `discoveredSkillNames` 是 turn 级状态，用于控制当前 turn 的发现与注入，不是长期把正文反复塞进 system prompt。

### 2.3 反思

当前咨询 Agent 的 active skill 机制偏重。它把“可能相关的方法论正文”提前塞进主模型 system prompt，容易导致：

1. 模型被 skill 正文带偏。
2. 普通聊天也变得僵硬。
3. Prompt 体积持续偏大。
4. 测试和 prompt 文案容易固化临时经验。

后续更合理的方向：

1. system prompt 常驻轻量 skill 目录。
2. skill 正文按需注入，最好作为一次明确的上下文事件或 tool result。
3. 对长任务类 skill，考虑 fork / 子 agent，避免污染主咨询上下文。
4. 同一 turn 内控制重复发现；跨 turn 是否复用，应由压缩摘要或明确状态管理，而不是重复塞正文。

## 3. 用户资料不应是 LLM 可见工具

### 3.1 当前问题

当前工具目录里有 `read_merchant_profile`，展示为“读取用户信息”。它被作为 LLM 可见工具参与 planning / native tool calling。

用户指出：这类信息天然应该每轮都带上，不应该让模型决定要不要调用。

这个判断成立。

### 3.2 原因

用户资料包括：

- 用户 / 商家名称
- 行业
- 服务项目
- 能力项
- 背景摘要
- 表达风格
- 默认 CTA

这些不是外部动作，而是当前咨询身份和业务事实。它们不应该被包装成工具调用，也不应该在商家 UI 里显示成“执行事实”。

如果做成工具，会产生几个问题：

1. 模型误以为这是一个可选动作。
2. tool dependencies 变复杂。
3. 聊天过程里会出现没有业务意义的工具卡。
4. 用户资料与系统级规则、agent prompt、soul.md 的层级关系变模糊。

### 3.3 后续方向

后续可考虑：

1. 从 LLM visible tools 移除 `read_merchant_profile`。
2. 每轮自动注入 `merchantProfileContext` 或 `userProfileContext`。
3. 该上下文语义上高优先级，但不一定要放进真正 system role；可以作为独立 context message / user context message。
4. 只在 runtime debug 中记录“已加载用户资料”，不作为商家可见 tool card。

## 4. 历史内容不应是普通工具

### 4.1 当前问题

当前工具目录里有 `read_history`，展示为“读取历史内容”。它返回当前会话历史消息数和摘要。

用户指出：当前咨询会话历史、本轮 user message、模型回答，本来就应该在模型上下文中，而不是变成一个工具。

这个判断基本成立。

### 4.2 当前实现缺口

当前 native path 并不像 Claude Code 那样直接把完整 `messages` 流交给 query loop。

现在主模型 native loop 大致是：

1. 一个 system message。
2. 一个 user JSON，包含 `merchant`、`userMessage`、`round`、`expertRouting`、`strategySnapshot`、`currentKnowledgeMatches`。
3. 后续工具结果以 native tool role 或 JSON tool_result 返回。

虽然 service 层构造了 `conversationMessages`，但它主要用于策略资产 Editor 的 `recentConversation`，不是主模型 native loop 的真实多轮 message history。

所以 `read_history` 目前更像是为了弥补主模型缺少真实历史消息而加的补丁，但它只返回 count 和 summary，价值有限。

### 4.3 后续方向

后续可考虑：

1. 从 LLM visible tools 移除 `read_history`。
2. 主模型上下文显式携带 `conversationContext`。
3. `conversationContext` 至少包含最近 N 条真实 user / assistant 消息，或 session summary + 最近 N 条。
4. 长历史通过 compact / summary 处理，而不是让模型调用“读取历史工具”。
5. 历史上下文的来源和新鲜度要可追溯，但不应变成商家可见工具执行卡。

## 5. User JSON 结构需要重新审视

### 5.1 当前结构

当前 native path 的 user message 是一个 JSON object，典型结构：

```json
{
  "merchant": {},
  "userMessage": "...",
  "round": 1,
  "expertRouting": {},
  "strategySnapshot": {},
  "currentKnowledgeMatches": []
}
```

这把用户原始输入和系统提供的上下文打包在同一个 user message 中。

### 5.2 风险

这种结构有几个风险：

1. 模型可能把上下文 JSON 当成用户在说的话的一部分。
2. `userMessage` 字段本身让“用户消息”变成 JSON 属性，而不是 message 流中的真实 user content。
3. 策略资产、知识片段、专家路由、用户输入都混在一个层级里，后续裁剪和缓存不清晰。
4. 与 Claude Code 的 message 流思路差异较大。Claude Code 更强调 `messages` 作为跨 turn 累积的主状态，工具结果、附件、记忆或上下文作为可区分的 message / section 注入。

### 5.3 后续方向

后续可考虑改成更分层的消息结构：

1. system：平台规则、agent prompt、工具协议。
2. context message：`merchantProfileContext`、`strategySnapshotContext`、`conversationContext`、`selectedKnowledgeContext`。
3. user：用户原始输入。
4. tool result：真实工具执行结果。

这样可以让模型更清楚地区分：

- 用户说了什么。
- 平台提供了什么上下文。
- 工具真实返回了什么。
- 哪些字段只是 debug / snapshot。

## 6. 工具边界初步建议

后续咨询 Agent 的 LLM visible tools 建议收敛为真正需要模型选择的动作：

### 应保留为工具

1. `retrieve_knowledge_base`
   - 检索平台方法论、用户知识库、材料片段。
   - 这是动态、按需、可能多轮深挖的动作。

2. `search_benchmark_materials`
   - 检索小红书 / 抖音爆款内容。
   - 这是外部数据获取和沉淀动作。

3. `update_strategy_snapshot`
   - 写右侧策略资产。
   - 这是受控写入动作。

4. `update_content_calendar`
   - 写内容日历。
   - 这是受控写入动作。

### 不应作为 LLM 可见工具

1. `read_merchant_profile`
   - 应自动注入上下文。

2. `read_history`
   - 应由 message history / conversationContext / compact 提供。

3. `generate_article_brief` / `generate_video_brief`
   - 当前已经不对 LLM visible，继续保持。

## 7. 暂不改造的原因

本轮先不直接改造，原因：

1. 这涉及 tool dependencies、planner、native path、JSON path、UI tool card、runtime snapshot 多处边界。
2. 改动会影响咨询台主链路，需要单独任务设计和回归验证。
3. 当前先记录问题，避免下一轮 Agent 只修局部提示词，忽略更底层的上下文结构问题。

## 8. 后续推荐任务顺序

建议后续单独开任务按以下顺序推进：

1. 调整工具目录和 dependencies：
   - 移除 LLM visible `read_merchant_profile`。
   - 移除 LLM visible `read_history`。
   - 让写入类工具不再依赖这两个伪工具。

2. 新增上下文分层：
   - `merchantProfileContext`
   - `conversationContext`
   - `strategySnapshotContext`
   - `selectedKnowledgeContext`

3. 重构 native path message 结构：
   - 减少大 user JSON。
   - 让用户原始输入成为清晰的 user message。
   - 把系统上下文作为独立 context message。

4. 重构 Skills 注入：
   - 轻量 skill catalog 常驻。
   - 正文按需注入。
   - 控制同一 turn 重复发现。
   - 必要时引入 fork / 子 agent 执行。

5. 更新可视化评审页：
   - 对比改造前后 message / tools / context 层级。
   - 支持继续人工删减上下文块。
