Snapshot

当前结论

这不是把错误参数“吞掉”的方案，而是把严格契约和用户界面解耦。

当前架构状态

主模型仍通过原生 tools 返回结构化 tool_calls。 工具的参数范围由 parameters 和 runtime Zod schema 共同约束； schema 外字段会被拒绝，不会被 strip。

新增变化只发生在两个地方：工具描述变成正向 allowed fields；商家可见 tool card 过滤内部参数校验失败。

一句话判断

当前修复方向符合“工具契约严格、提示不反向灌字段、内部错误不要展示给商家”的原则。

契约：严格 提示：正向字段 展示：过滤内部错误 调试：保留 trace

Next Review

建议下一步看三件事

如果要继续减少“僵硬感”，下一步不该再往工具描述里加规则，而应该缩小上下文和路由动作空间。

1. 工具目录继续瘦身

保留工具名、用途和影响范围即可。业务工具目录里不要暴露内部字段，也不要塞参数禁令。

2. 日历 intent 单独门控

把日历写入规则从长 system message 中进一步挪到“本轮明确是日历任务”时才出现。

3. Debug 与商家 UI 分层

继续保留 trace 给平台管理端；商家侧只展示真正执行过或业务上有意义的工具动作。

当前验收点

  • 工具参数错误不再显示为商家顶部失败卡。
  • 写入类工具 schema 仍严格拒绝 schema 外字段。
  • 主模型工具描述只列允许字段，不列不允许字段。
  • 调试链路仍能从 runtime snapshot / event 看到 native_tool_call_rejected。
