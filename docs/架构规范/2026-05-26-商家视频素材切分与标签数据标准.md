# 2026-05-26 商家视频素材切分与标签数据标准

## 1. 结论

本标准定义商家团队视频素材从“原始上传文件”到“可被 video-worker 检索和剪辑的片段”的数据合同。

核心结论：

- 系统必须区分 `asset` 和 `clip`。`asset` 是原始上传文件；`clip` 是可检索、可剪辑、可签名下载的最小素材单元。
- 一条短视频可以只生成一个 `full_video` clip；一条长视频应该先生成逻辑片段 `segment`，必要时再物理切出 mp4。
- 标签必须打在 `clip` 上。`asset` 只保存文件事实、来源、校验和处理状态。
- 人工打标、AI 辅助打标、未来自动打标都必须输出同一套 clip JSON 结构。
- 当前主线使用 provider-neutral 命名：`sourceStorageKey / storageKey / thumbStorageKey`。旧参考包里的 `sourceCosKey / cosKey / thumbCosKey` 只能作为历史兼容字段。
- `tagSource` 入库只用当前数据库允许的值：`manual`、`vision_model`、`fixture`、`mock`。更细的打标方法写入 `metadata.taggingRevision.method` 或审核 CSV，不要塞进 `tagSource` 破坏约束。

置信度：高。依据是本地参考包 `/Users/wy/Downloads/metadata/metadata`、导入模板 `/Users/wy/Downloads/sql/sql/merchant_media_import.template.sql`、当前 PostgreSQL migration 和 repository contract。

## 3. 两层模型

### 3.1 `merchant_media_assets`

`asset` 表示商家团队素材库里的原始文件。

它回答的问题是：

- 这个文件属于哪个商家？
- 谁上传的？
- 原始文件在对象存储哪里？
- 文件类型、大小、mime、处理状态是什么？
- 这条原始资产是否已经产出可用 clip？

`asset` 不负责回答：

- 这段画面是什么内容？
- 适合当开场、转场、细节还是主展示？
- worker 应该把它匹配到哪条脚本分镜？

这些问题都交给 `clip`。

### 3.2 `merchant_media_clips`

`clip` 表示 video-worker 可以检索、签名下载、放进剪辑流程的素材单元。

它回答的问题是：

- 这条素材片段属于哪个原始 asset？
- 它是完整视频，还是从长视频里切出的片段？
- 片段起止时间是什么？
- 存储对象和缩略图在哪里？
- 画面可见内容是什么？
- 角色标签 `role:` 和剪辑用途标签 `lens:` 是什么？
- 置信度、审核状态和质量状态如何？

当前检索链路按 ready clip 工作，不应该直接把未打标的原始 asset 交给 video-worker。

## 4. 生命周期

视频素材进入团队素材库时按这个状态机处理：

```text
uploaded
  -> validating
  -> processing
  -> tagging
  -> ready
```

失败或人工处理状态：

```text
validation_failed
processing_failed
tagging_failed
needs_reclip
needs_retag
quarantined
archived
```

规则：

- `asset.status=ready` 时，必须至少有一条 `clip.status=ready` 的 clip。
- `asset.status=uploaded / validating / processing / tagging` 时，不能进入 `video_edit_asset` 检索池。
- `clip.status=ready` 才能被 video-worker 检索。
- `quarantined / archived / missing_object` 的 clip 必须从检索结果中排除。

## 5. 存储字段命名

当前主线统一使用 storage 命名，不再把 COS 写进通用字段。

| 含义 | 标准 JSON 字段 | 当前 DB 字段 | 旧包兼容字段 |
| --- | --- | --- | --- |
| 原始文件对象 key | `sourceStorageKey` | `source_storage_key` | `sourceCosKey` |
| clip 视频对象 key | `storageKey` | `storage_key` | `cosKey` |
| clip 缩略图对象 key | `thumbStorageKey` | `thumb_storage_key` | `thumbCosKey` |
| bucket | `bucketName` | `bucket_name` | `bucketName` |

对象 key 目录约定：

```text
merchant-media/{merchant_id}/originals/{asset_id}/source.mp4
merchant-media/{merchant_id}/clips/{asset_id}/{clip_id}.mp4
merchant-media/{merchant_id}/thumbs/{asset_id}/{clip_id}.jpg
```

对于 `full_video`：

- 如果不物理复制原视频，`clip.storageKey` 可以直接等于 `asset.sourceStorageKey`。
- 如果为了统一签名、转码或水印生成了派生文件，也可以放到 `clips/{asset_id}/{clip_id}.mp4`。

对于 `segment`：

- `clip.storageKey` 应该指向实际切出的片段文件。
- 如果当前阶段只做逻辑切分，还没有物理切片，包内 JSON 可以先生成 `segmentPlan`，但不得把未存在的 `storageKey` 标成 `ready` 入库。

## 8. Clip 类型

当前允许三种：

| `clipType` | 用途 | 时间字段 |
| --- | --- | --- |
| `full_video` | 短视频或完整文件就是可用素材 | `startTimeSeconds=0`，`endTimeSeconds=durationSeconds` |
| `segment` | 从长视频切出的可用片段 | `startTimeSeconds>=0`，`endTimeSeconds>startTimeSeconds` |
| `image` | 图片素材作为 Pexels-like photo 结果 | 不写视频时间 |

视频素材标准：

- `mediaType=video` 时，只能产出 `full_video` 或 `segment`。
- `segment.durationSeconds = endTimeSeconds - startTimeSeconds`。
- `clipIndex` 必须在同一 asset 内从 0 开始递增。
- 同一 asset 下 `(assetId, clipIndex)` 必须幂等。

## 9. 切分策略

当前阶段先定标准，不要求立刻物理切分全部素材。

推荐策略：

| 原视频时长 | 处理方式 | 推荐 clip 数 | 单 clip 时长 |
| --- | --- | --- | --- |
| `<= 15s` | 不切，生成 `full_video` | 1 | 原时长 |
| `15s - 45s` | 可逻辑切 1-2 段 | 1-2 | 8-15s |
| `45s - 120s` | 建议切成多个 `segment` | 3-5 | 8-15s |
| `> 120s` | 抽样切重点片段，不全量切碎 | 最多 6 | 8-15s |

切分原则：

- 不追求把每个镜头都切到极细。video-worker 需要的是“可稳定召回的素材块”，不是帧级镜头库。
- 一个 clip 内最好只有一个主要语义：烤串特写、炭火翻烤、顾客聚餐、门头外景、后厨制作。
- 如果 1 分钟视频有明显三段内容，就切 3 段；如果全程都是同一种烤串近景，切 1-2 段即可。
- 长视频超过 2 分钟时，只抽取有代表性的片段，不做全量物理拆分。
- 物理切分前可以先生成 `segmentPlan` 做人工审核；审核通过后再批量 ffmpeg 生成真实 `segment` 文件。

逻辑切分计划的 JSON 可以长这样：

```json
{
  "assetId": "uuid",
  "strategy": "logical_first_physical_later",
  "sourceDurationSeconds": 63.4,
  "segments": [
    {
      "clipIndex": 0,
      "startTimeSeconds": 0,
      "endTimeSeconds": 12,
      "plannedClipType": "segment",
      "plannedRole": "bbq_storefront_context",
      "plannedLens": "opening_context",
      "physicalClipCreated": false,
      "reviewStatus": "pending"
    }
  ]
}
```

这种 `segmentPlan` 不能作为 `ready clip` 入库；它只是切分任务书。

## 10. 尺寸与质量标准

当前视频素材测试的推荐范围：

```text
min(width, height) >= 640
max(width, height) <= 2048
mimeType = video/mp4
```

推荐处理：

- 原始素材不合规但可转码：`asset.status=processing`，转码后生成合规 clip。
- 不合规且不可修复：`asset.status=validation_failed`。
- clip 已可用但需要人工确认：`qualityTags` 增加 `待人工最终确认`，不要提高到 1.0 置信度。
- 预览帧判断的标签：`tagConfidence` 通常在 `0.72 - 0.88`。
- 完整模型识别 + 人工复核通过：`tagConfidence` 可以到 `0.9+`。

当前 DB 只硬约束 `width > 0 and height > 0`。`640-2048` 属于 video-worker 输入质量门禁，应在上传校验、转码或入库前校验中执行。

## 11. 标签字段分工

| 字段 | 标准用途 |
| --- | --- |
| `title` | 人看的短标题，导出包和审核表使用 |
| `description` | 一句话描述画面可见内容，DB 必填 |
| `tags` | 综合检索标签，必须包含中文主题词，建议包含 `role:` 和 `lens:` |
| `industryTags` | 行业/业务大类，例如餐饮、烧烤店、本地生活 |
| `sceneTags` | 场景/空间，例如门头、后厨、炭火烤炉、堂食区 |
| `shotTags` | 镜头语言/剪辑用途，例如食物特写、外景建立、转场、过程细节 |
| `peopleTags` | 人物情况，例如无明显人物、仅手部入镜、顾客聚餐 |
| `qualityTags` | 质量、审核、合规状态 |
| `queryHints` | 自然语言召回短语，当前可先存在导出包 |
| `tagConfidence` | 标签置信度，范围 `0-1` |
| `tagSource` | 入库枚举：`manual`、`vision_model`、`fixture`、`mock` |
| `metadata.reviewNotes` | 为什么这样打标签、有哪些不确定性 |

硬规则：

- 每条 ready clip 的 `tags` 至少 3 个。
- `tags` 里不要只放英文机器标签，必须保留中文可读标签。
- `role:` 负责素材角色，`lens:` 负责剪辑用途。
- `description/tags/queryHints` 只能写画面可见或来源已明确的信息。
- 商家卖点、价格、地理优势、口味好坏、排队火爆等不能凭想象塞进 clip 标签。

## 12. `role:` 标准

`role:` 是稳定素材角色，不是一次性描述。

烧烤店测试素材建议先用这些角色：

```text
role:bbq_storefront_context
role:bbq_grill_fire
role:bbq_skewer_closeup
role:bbq_food_closeup
role:bbq_seafood_grill
role:bbq_whole_meat_roast
role:bbq_staff_preparation
role:bbq_customer_eating
role:bbq_night_market
role:bbq_dining_table
```

使用原则：

- 一个 clip 原则上只选一个主 `role:`。
- 如果确实跨场景，可以加一个次级中文标签，不要堆多个 `role:`。
- `role:bbq_customer_eating` 必须看见或明确指向顾客吃饭/聚餐/聊天，不得因为标题有“美食”就误打。
- `role:bbq_night_market` 用于夜市、街边、摊位、人流环境，不等于所有烧烤。
- 不符合烧烤店主题但可做氛围补镜的素材，要加 `qualityTags:弱相关素材`。

## 13. `lens:` 标准

`lens:` 是剪辑用途，帮助 worker 按脚本分镜选画面。

烧烤店测试素材建议先用这些用途：

```text
lens:opening_context
lens:menu_showcase
lens:detail_proof
lens:process_detail
lens:social_proof
lens:transition_detail
lens:atmosphere_context
```

含义：

| `lens` | 适用画面 |
| --- | --- |
| `lens:opening_context` | 店面、招牌、街边环境、夜市环境 |
| `lens:menu_showcase` | 菜品展示、烤串成品、桌面食物 |
| `lens:detail_proof` | 油脂、炭火、滋滋冒油、食物质感细节 |
| `lens:process_detail` | 员工翻烤、撒料、切配、穿串、制作过程 |
| `lens:social_proof` | 顾客吃、聊天、碰杯、聚餐、人气氛围 |
| `lens:transition_detail` | 火焰、烟气、翻面、上菜、手部动作转场 |
| `lens:atmosphere_context` | 夜色、街边烟火气、环境氛围 |

剪辑召回优先级：

- 开头：优先 `opening_context / atmosphere_context`。
- 菜品卖点：优先 `menu_showcase / detail_proof`。
- 制作过程：优先 `process_detail / transition_detail`。
- 人气证明：优先 `social_proof`。

## 14. 人工与 AI 打标流程

人工 + AI 初版流程：

```text
1. ffprobe 读取时长、尺寸、codec、帧率。
2. 抽 3-5 张预览帧，长视频增加中段和尾段抽样。
3. 生成 contact sheet 给人快速复核。
4. AI 先按可见内容生成候选 title/description/tags/role/lens。
5. 人工修正明显误判，特别是人物、门头、店型、非烧烤弱相关素材。
6. 通过审核后生成 ready clip JSON / JSONL / CSV / SQL 模板。
```

未来自动打标流程：

```text
1. 上传后自动进入 validating。
2. 校验 mime、尺寸、时长、文件大小。
3. 自动抽帧和镜头边界检测。
4. 视觉模型生成候选 segmentPlan 和候选标签。
5. 对高置信短视频可自动 ready；对低置信、长视频、多场景视频标记 needs_review。
6. 人工审核只改 segmentPlan 和标签，不改底层资产事实。
7. 审核通过后生成真实 segment 文件、缩略图和 ready clip。
```

## 15. 导入 SQL 标准

导入 SQL 必须分两段：

```text
begin;

insert into public.merchant_media_assets (...)
on conflict (merchant_id, idempotency_key) do update set ...;

insert into public.merchant_media_clips (...)
on conflict (asset_id, clip_index) do update set ...;

commit;
```

当前主线 SQL 字段应使用：

```text
merchant_media_assets.source_storage_key
merchant_media_clips.storage_key
merchant_media_clips.thumb_storage_key
```

不要再生成新 `source_cos_key / cos_key / thumb_cos_key` 导入模板。旧模板只能作为历史包兼容输入，导入前必须转换。

导入前校验：

- `merchant_id / uploaded_by_user_id / bucketName` 已替换真实值。
- `asset.sourceStorageKey` 符合 `merchant-media/{merchant_id}/originals/{asset_id}/...`。
- `segment.storageKey` 对应对象真实存在。
- `thumbStorageKey` 对应缩略图真实存在。
- `tagSource` 是 DB 允许枚举。
- 每个 ready asset 至少一条 ready clip。
- 每条 ready clip 至少 3 个 tag。
- `(assetId, clipIndex)` 无重复。

## 16. 审核 CSV 标准

`tag_review.csv` 面向人工快速复核，应包含这些列：

```text
asset_scope
```

## 18. 与 video-worker 的关系

video-worker 不应该自己猜“原始长视频哪一段能用”。它应该拿到已经 ready 的 clip。

检索时优先使用：

- `merchantId`
- `mediaType=video`
- `status=ready`
- `orientation`
- `durationSeconds`
- `tags`
- `industryTags`
- `sceneTags`
- `shotTags`
- `peopleTags`
- `qualityTags`

脚本分镜匹配建议：

```text
脚本需要“店门口/开场” -> role:bbq_storefront_context + lens:opening_context
脚本需要“烤串细节” -> role:bbq_skewer_closeup + lens:detail_proof
脚本需要“制作过程” -> role:bbq_staff_preparation + lens:process_detail
脚本需要“人气氛围” -> role:bbq_customer_eating / role:bbq_night_market + lens:social_proof
脚本需要“转场烟火气” -> role:bbq_grill_fire + lens:transition_detail
```

当同一个 asset 既有 `segment` 又有 `full_video`：

- 默认优先检索 `segment`。
- `full_video` 可作为 fallback 或人工预览入口。
- 不要在同一支成片里重复使用同一 asset 的多个高度相似片段，除非脚本明确需要。

## 19. 烧烤店素材初始标准

烧烤测试主题先按以下业务边界打标：

高相关素材：

- 烤肉、烤串、烤鱿鱼、生蚝、炭火、烤炉、撒料、翻烤。
- 顾客吃烧烤、聚餐、聊天、碰杯。
- 烧烤店门头、夜市摊位、街边烟火气。

中相关素材：

- 夜市小吃街、餐饮街、人流、桌面菜品，但没有明确烧烤元素。
- 泛餐饮后厨制作，但可作为过程氛围。

弱相关素材：

- 火锅、茶餐厅、高端餐厅桌布、非烧烤海鲜、鸭货、早餐、普通街景。
- 弱相关素材不一定删除，但必须加 `qualityTags:弱相关素材`，避免 worker 当作烧烤强素材优先使用。

不允许标签：

- “生意火爆”“本地第一”“必吃榜”“回头客多”等画面不能证明的营销结论。
- “高端餐厅”“街边小店”等风格判断，除非画面强证据明显。
- 从素材下载标题猜出来但画面看不见的菜品细节。

## 20. 后续实现建议

短期：

- 先用这个标准生成本地 `assets.json / clips.json / tag_review.csv / validation.json`。
- 对烧烤素材先做人工 + AI 标签审核，不急着全量物理切片。
- 对 45 秒以上、多场景明显的视频，先生成 `segmentPlan` 给人看。

中期：

- 补自动打标任务：上传后自动抽帧、生成候选 role/lens/tags。
- 补 segmentPlan 审核 UI：人只改起止点和标签。
- 通过审核后由 worker 批量切片和生成缩略图。

长期：

- clip 检索从简单 token 命中升级到结构化过滤 + 向量召回。
- `title/queryHints/metadata` 如果要线上使用，应补正式 DB 字段或统一落到 trace/metadata JSONB。
- `role` 和 `lens` 应形成跨行业词表，烧烤只是第一批测试词表。
