# 小红书抖音矩阵获客平台 V0.1 Postgres Schema 草案

## 1. 文档目的

这份文档把前面的 `V0.1 数据表草案` 再往前推进半步，收敛成一版适合落到 `Supabase Postgres` 的 SQL 结构草案。

本稿定位不是最终迁移文件，而是为了回答 3 个问题：

1. 核心表到底怎么命名
2. 主外键关系到底怎么落
3. 哪些字段已经足够稳定，可以直接进入第一版 schema

---

## 2. 当前约定

### 2.1 命名风格

- 表名统一用 `snake_case` 复数
- 主键统一用 `uuid`
- 时间字段统一用 `created_at` / `updated_at`

### 2.2 字段策略

- 枚举先尽量用 `text + check`，避免第一版改状态值时迁移太重
- 不稳定结构先保留 `jsonb`
- 账号敏感凭据只存 `credential_ref`，不存明文 cookie

### 2.3 当前不做

- 不在这一版 schema 里提前引入多租户组织表
- 不在 `V0.1-A` 提前引入 `store_profiles` 门店表
- 不提前引入复杂审批流表
- 不提前引入分析看板表

补充说明：

- 长期方向已经明确会走多租户 SaaS
- 但 `V0.1` 第一版 schema 仍先聚焦内容主链路
- 注册侧可以先通过 `邀请码` 控流，再在后续版本补齐完整租户表
- 当前默认按“一个商户一个 owner 账号”实现
- 后续如果要扩成员与角色，不建议改动业务主表，只新增成员关系层即可

## 4. 这版 schema 的几个关键选择

### 4.1 为什么状态字段先不用 PostgreSQL enum

因为 `V0.1` 仍在快速收敛阶段。

如果现在就把：

- `draft status`
- `publish status`
- `login status`

全部做成数据库 enum，后面每次调整状态值都要额外迁移。

当前更合适的做法是：

- 先用 `text + check`
- 等状态真正稳定后，再看是否收成 enum

### 4.2 为什么 `selected_variant_id` 放在 `content_drafts`

因为 `V0.1` 的草稿中心需要快速知道“当前主选版本是哪一个”。

不然每次都要从多个 `content_variants` 里额外推断，会让：

- 草稿列表
- 发布准备
- 发布任务创建

都更绕。

### 4.3 为什么 `asset_objects` 先做成轻量多态结构

第一版最重要的是把资源挂载点统一起来：

- 来源素材
- 草稿输出素材

先用：

- `owner_type`
- `owner_id`

就足够了。

如果后续资源体系更复杂，再改成更强约束的独立关联表也来得及。

## 5. 对 Supabase 的直接影响

这份 schema 草案落到 `Supabase` 时，意味着：

- `Postgres` 可以直接承接绝大多数核心表
- `Storage` 建议至少准备 3 类 bucket

建议 bucket：

1. `source-assets`
2. `draft-assets`
3. `publish-logs`

---

## 6. 当前先不写进 SQL 的内容

下面这些虽然以后可能会需要，但本稿先不下沉：

- RLS 详细策略
- 后台管理员用户表
- `tenants / memberships / invitations` 这类完整多租户用户表
- Worker 内部凭据明文表
- 审批流相关表
- 内容日历与排期视图表

原因不是不重要，而是它们都依赖后续两个决策：

1. 内部登录方案怎么选
2. Worker 部署在哪里

不过关于“后续多成员是否好扩展”，当前答案是：

- **好扩展**

前提是保持一个原则：

- 业务数据始终挂在 `merchant_id` 上
- 不把草稿、账号、任务直接绑死到单个用户上

这样后面只需要追加：

- `merchant_memberships`
- `role`
- `member_invite_codes`

而不需要重写内容主链路表。

## 8. 本稿的关键收敛结论

这份 schema 草案最关键的价值是：

1. 把前面的“对象名”翻成了真正可建表的结构
2. 把主外键、唯一约束和索引关系基本定住了
3. 说明了 `Supabase` 确实能承接数据库这一层
4. `V0.1-A` 先按一个商户一个 owner 实现，同时保留后续多成员扩展空间
5. 也进一步证明 `Worker` 不能省
