# 01 依据与全局硬门禁

## 摘要

本板块只回答三件事：

1. 为什么要这样做。
2. 哪些边界不能破。
3. 每个子系统失败时如何检查和纠错。

## 依据

外部依据：

- Pexels API 返回分页字段、照片数组、视频数组和 `next_page`，因此私有素材服务必须保持 Pexels-like 外壳。
- Tencent COS 官方建议前端直传使用临时密钥，永久密钥留在服务端；预签名 URL 可控制访问有效期。本项目对 OpenStoryline / Pexels-compatible / 素材库外部预览要求 60 天有效下载入口；平台内登录态成片预览可走稳定 app route 并由服务端短期重签 COS。
- Supabase 官方要求对公开 schema 中暴露给 API 的表启用 RLS，未配置 policy 前不应可访问。
- OWASP 上传安全建议在访问上传能力前同时校验认证和授权，并把文件存储与应用执行环境隔离。
- GitHub REST API 用分页降低大结果集处理压力；本方案采用 Pexels 的 `page/per_page/next_page` 形式，但保留同样的分页硬门禁。
- Supabase GitHub Discussion 中的经验是：RLS 用于安全兜底，不应替代业务查询过滤；本方案要求所有列表 / 检索服务端查询也显式携带 `merchant_id` 或 `created_by_user_id`。
- GitHub Community 多租户 RLS 讨论指出 `auth.uid()` 是用户 ID，不是 tenant ID；本方案不把 `auth.uid()` 直接等同 `merchant_id`，必须通过 `merchant_profiles` / `merchant_team_members` 做映射。
- Stack Overflow 预签名上传讨论里的核心风险是：客户端可以拿“好文件”骗过校验，再用同一个预签名 URL 上传“坏文件”；本方案要求对象落地后做真实文件探测。
- tus 协议把上传过期和 checksum 作为可恢复上传的重要机制；本方案把大视频上传的 `expires_at`、checksum、orphan cleanup 当作硬要求。
- Reddit / Supabase 多租户审计经验强调真实双租户扫描；本方案把“登录 A、枚举 B 的 ID”列为上线前硬门禁。
- addyosmani/agent-skills 强调 spec-driven、incremental implementation、API/interface design、shipping checklist；本方案把它转成“分册渐进披露、接口合同先行、小切片实现、每步有硬门禁和验收证据”。

项目依据：

- 当前工程真实边界是 `merchant_id`，不是独立 `team_id`。
- 声音克隆基础链路已合入：`voice_profiles`、`asset_objects(owner_type=voice_profile, asset_type=audio)`、`productionConfig.voiceover.mode = "voice_profile"`。
- worker 已把 `voice_profile` 映射到 `pixelle_clone`，并把 `voiceover_artifacts` 回写到 result payload。这里的 `pixelle_clone` 是当前代码里的 RunningHub clone 适配名 / 历史命名，不代表另接一个 Pixelle 服务。
- Dify 内容生成链路是后续新生成主链路；现有视频脚本、测试草稿、`video_edit_jobs.input_payload` 和 video worker 合同保留为兼容辅路，不因 Dify 接入被破坏。

## 专业社区经验落地规则

这部分把 GitHub / Stack Overflow / OWASP 里的工程经验翻译成项目门禁：

| 经验 | 本项目规则 | 检查方式 |
| --- | --- | --- |
| RLS 可能很慢，也不应替代业务过滤。 | RLS 负责兜底，repository 仍必须 `.eq("merchant_id", merchantId)` 或 `.eq("created_by_user_id", userId)`。 | code review 搜索 repository 查询；单测构造跨商家 ID；必要时在非生产跑 explain。 |
| `auth.uid()` 不是 tenant。 | `merchant_id` 必须来自 membership 映射，不能由 user id 猜。 | 双商家 fixture：同一用户不同商家、不同用户同商家、无 membership 三类都测。 |
| 预签名上传只约束请求形态，不证明文件真实类型。 | 前端 MIME 只作为预检，落地后必须 sniff / ffprobe。 | 伪造扩展名和 `Content-Type` 上传，complete 必须失败或 quarantine。 |
| 大结果集必须分页且排序稳定。 | Pexels-compatible 查询必须有 `per_page` 上限和稳定排序键。 | 同一 query 连续翻页无重复、无漏项；空 query 不跨商家兜底。 |
| 对象存储、数据库、provider 不共享事务。 | 任何跨系统流程都必须 pending、confirm 幂等、cleanup 可重试。 | 故障注入：上传成功但 DB 写失败、provider 成功但 cleanup 失败、retry 重复提交。 |
| agent-skills 的 spec / plan / build / test / ship 生命周期。 | 每个分册都必须写清工作边界、接口合同、检查、纠错和上线 gate。 | code review 不只看实现，还检查是否有分册、测试证据、回滚点和 handoff。 |

## 渐进实施切片

参考 agent-skills 的 incremental implementation，本方案按可验收薄切片推进：

1. Dify 融合切片：新生成以 Dify `article/video/quality/debug` 为主，先落兼容 variant，再由现有 payload builder 生成 worker 合同。
2. 声音覆盖切片：在现有 `voice_profiles` 基础上补“一个当前音色、覆盖失败保旧、cleanup job”。
3. COS 安全切片：收紧 upload intent、complete、post-upload validation、60 天下载 URL 和 orphan cleanup。
4. 素材库数据切片：新增 `merchant_media_assets` / `merchant_media_clips`、RLS、索引、双租户测试。
5. 入库处理切片：商家端入库、切片、缩略图、标签、低置信度复核。
6. Pexels-compatible 切片：先用 fixture 契约跑通图片 / 视频 JSON，再接 OpenStoryline。
7. Worker 集成切片：私有素材下载、voice profile ref audio、engine request 回放、结果回写。
8. Staging 发布切片：端到端、故障注入、doctor 无阻断项后再考虑生产。

## 工作边界

必须做：

- 商家端确认入库素材，才进入团队素材库。
- 用户端 / 成员端临时上传素材，只服务当前任务，不进入团队素材索引。
- 个人声音默认仅本人可用。
- Pexels-compatible 接口只返回当前 `merchant_id` 可见素材。

不做：

- 不做全平台公共素材池。
- 不用 COS list 当检索数据库。
- 不把 voice profile 作为团队共享资产。
- 不让 worker 负责业务侧素材选择策略。

## 全局硬门禁

实现前：

- 必须能指出当前改动属于哪个板块。
- 必须确认是否涉及真实账号、真实 COS、真实 voice clone provider。
- 必须确认是否需要新增 migration。

合并前：

- 所有新增公开表必须有 RLS 或明确只由 service role 访问。
- OpenStoryline / Pexels-compatible / 素材库外部预览下载入口必须 60 天有效；可用服务端下载 token URL，在请求时校验状态后 302 到 COS 或流式转发。平台内成片预览不暴露 60 天裸 COS URL，使用登录态 app route 重签即可。
- 所有素材检索必须在业务查询和 RLS 两层都检查 `merchant_id`。
- 所有 voice profile 使用必须在业务查询和 RLS 两层都检查 `created_by_user_id`。
- 所有多租户 RLS policy 不得直接把 `auth.uid()` 等同 `merchant_id`。
- 所有新接口必须有失败码和可观测日志。
- 所有跨 COS / DB / provider 的动作必须有状态机，不允许“先删旧资源，再赌新资源一定成功”。
- Dify 主链路只能通过融合 adapter 输出到现有 `video_script` / `video_edit_jobs.input_payload` 合同；feature flag 关闭时现有链路必须无感可用。

上线前：

- staging 跑通端到端。
- 有跨商家越权测试。
- 有旧声音覆盖失败保护测试。
- 有 COS 孤儿对象清理策略。

## 检查功能

建议做一个 `private_media_doctor` 检查任务，至少检查：

- `merchant_media_assets` 是否存在没有 clips 的 ready 记录。
- `merchant_media_clips` 是否存在 COS 对象不存在的记录。
- `voice_profiles.ref_audio_asset_id` 是否指向不存在或非 audio 的 asset。
- `asset_objects.owner_type = voice_profile` 的对象是否不属于对应 voice profile。
- 是否存在同一 `merchant_id + created_by_user_id` 多个 ready voice profile。
- 是否存在用户端 / 成员端临时素材被写入 `merchant_media_*`。
- RLS 相关列是否有索引，例如 `merchant_id`、`created_by_user_id`、`owner_type + owner_id`。
- 服务端 repository 查询是否显式带了 `merchant_id` 或 `created_by_user_id`，而不是只靠 RLS。
- migration 是否给 `merchant_id`、`created_by_user_id`、`asset_id`、`owner_type + owner_id`、状态字段建了必要索引。
- API 测试是否包含“双租户枚举 ID”场景，而不只是 UI 正常路径。
- 上传 intent 是否有未 complete 且超过 TTL 的对象。
- provider cleanup 任务是否积压。

## 纠错功能

纠错分四类：

- 自动重试：切片失败、标签生成失败、COS 短暂下载失败。
- 自动隔离：检测到跨商家数据、无 owner 的素材、无法读取的 COS 对象时标记 `quarantined`。
- 自动清理：覆盖声音成功后清理旧 audio asset、旧 COS 对象和旧 provider voice。
- 人工复核：标签明显不符、素材归属不明、声音授权不清时进入人工处理队列。
- 安全阻断：doctor 发现跨商家可读、public bucket、service role 泄漏到客户端 bundle 时，直接阻断上线。
- 数据修复：多 ready voice profile 时保留当前项，其余归档，并创建审计记录。

## 板块验收

通过标准：

- 每个子板块都有“依据 / 工作边界 / 硬门禁 / 检查 / 纠错”。
- 文档中的表名、字段名、合同名与当前代码一致。
- 未实现能力标注为“待实现”，不写成已完成。
