# 03 商家团队素材库与标签

## 摘要

商家团队素材库只接收商家端确认入库的素材。用户端 / 成员端临时上传素材不入库、不切片、不标签化、不长期保存。

## 依据

外部依据：

- OWASP 文件上传建议必须做认证、授权、类型校验和存储隔离。
- Pexels API 本身不要求我们返回内部标签；标签是私有检索层能力，外部只需要 Pexels-like 响应。
- GitHub / Supabase 多租户讨论中的共同经验是：tenant / merchant 字段应在业务查询中显式出现，不能只寄托于 RLS；因此素材表必须直接带 `merchant_id` 并建索引。
- 预签名上传社区经验表明，上传完成不等于内容可信；素材入库前必须通过媒体解析和安全检查。

项目依据：

- 当前视频工作台临时制作素材已通过 `content_draft` / `asset_objects` 支撑当前任务。
- 当前素材库逻辑已有 `material_workbench_references` 和 `merchant_id` 边界。
- 新增私有素材库应避免污染当前 `content_draft` 临时素材链路。

## 专业社区经验落地规则

这里的“参考 Pexels”只参考请求 / 响应外壳，不照搬 Pexels 的公共素材池模式。GitHub / Supabase 多租户讨论、上传安全经验和 agent-skills 的渐进式实现方法在本板块落成以下规则：

- 素材表直接保存 `merchant_id` 并建索引；不要通过 join 临时推导商家归属后再过滤。
- 标签是内部召回字段，不是 Pexels response 的必需字段；OpenStoryline 不需要知道我们的标签体系。
- 入库前先做确定性媒体解析，再做 LLM / VLM 标签；宽高、时长、方向不能由模型猜。
- 标签生成必须有置信度和人工纠错入口；低置信度素材不能自动进入高优先级召回。
- 用户端 / 成员端临时素材即使在 COS 中存在，也不能被 `merchant_media_*` 引用。
- 按 agent-skills 的 incremental implementation，先用少量 fixture 跑通入库和标签合同，再扩大到批量处理。

新增表建议：

```text

- uploaded_by_user_id
- media_type
- source_cos_key
- original_filename
- mime_type
- file_size_bytes
- status
- failure_reason
- created_at
- updated_at
```

```text
merchant_media_clips
- id
- asset_id
- merchant_id
- media_type
- cos_key
- thumb_cos_key
- description
- tags
- industry_tags
- scene_tags
- shot_tags
- people_tags
- quality_tags
- tag_confidence
- tag_source
- orientation
- duration_seconds
- width
- height
- status
- failure_reason
- created_at
- updated_at
```

入库来源：

- 允许：商家端素材库上传、商家端明确“加入团队素材库”。
- 禁止：成员端任务临时素材、视频工作台当前草稿素材、voice profile audio、worker 输出成片。

入库状态机：

```text
uploaded
-> validating
-> processing
-> tagging
-> ready
```

失败 / 纠错状态：

```text
validation_failed
processing_failed
tagging_failed
needs_reclip
needs_retag
quarantined
archived
```

## 切片策略决策

### 决策状态

- 决策编号：`ADR-MEDIA-SLICE-001`
- 状态：V1 采纳，V2 复审。
- 一句话结论：当前 V1 采用“确定性整段 clip”策略，不做自动分镜，不做固定时间窗口切片，不让 LLM / VLM 决定切点。

目标是先把商家端原始上传稳定加工成可检索、可回滚、可追踪的 ready clip。复杂多段切片放到后续 V2，不阻塞私有素材库和 OpenStoryline Pexels-compatible 链路先跑通。

### 参考做法怎么落地

| 参考来源 | 观察到的做法 | 本方案落地 |
| --- | --- | --- |
| Pexels API | 照片检索返回 `photos[]`，每个 photo 通过 `src` 给多尺寸地址；视频检索返回 `videos[]`，每个 video 通过 `video_files[]` 给可播放文件；分页使用 `page/per_page/total_results/next_page`，`per_page` 最大 80。 | 私有素材库先产出 Pexels-like 的“素材对象 / clip 对象”，而不是先做镜头级复杂分片；检索响应保留 Pexels 外壳和分页上限。 |
| GitHub REST API | 大结果集分页返回，客户端通过下一页链接继续读取，避免一次返回过大结果。 | Pexels-compatible 检索必须分页、稳定排序；同一 query 翻页不能重复、不能漏。 |
| GitHub / Supabase RLS 讨论 | RLS 是安全兜底，不应替代业务过滤；多租户列需要索引和显式查询条件。 | `merchant_media_assets` 和 `merchant_media_clips` 必须直接保存 `merchant_id`，repository 查询必须显式带 `merchant_id`。 |
| Stack Overflow / OWASP 上传安全经验 | 预签名上传和 `Content-Type` 不能证明文件真实类型，落地后仍要做真实探测和签名校验。 | 切片前必须先完成 post-upload validation、ffprobe / 文件签名检查；失败不得进入切片和标签。 |
| FFmpeg filters | `thumbnail` 可以从连续帧中选代表帧，官方也给了生成缩略图示例。 | V1 把“真实缩略图必须生成”作为 ready 门禁，但不把代表帧选择升级成自动分镜算法。 |
| addyosmani/agent-skills | 强调 spec-driven、incremental implementation、thin vertical slice、verification evidence、progressive disclosure。 | 本轮只交付“整段 clip + 缩略图 + 标签 + Pexels-compatible 检索”这个薄切片；每一步必须有测试证据和回滚状态。 |

### 候选方案与取舍

| 方案 | 描述 | 当前结论 | 原因 |
| --- | --- | --- | --- |
| A. 确定性整段 clip | 图片 1 条 image clip；视频 1 条 full_video clip。 | V1 采用 | 最容易验证，和 Pexels 的“可检索媒体对象”外壳对齐；不引入不可解释切点。 |
| B. 固定时间窗口切片 | 视频按 5s / 10s / 15s 固定窗口切成多段。 | V1 不采用 | 会产生大量弱语义片段，标签容易重复或失真，检索噪声高。 |
| C. 镜头变化切片 | 用 scene detection 根据画面变化切段。 | V2 评估 | 更接近视频素材库，但需要阈值、误切纠错、回放验收和更多算力。 |
| D. LLM / VLM 决定切点 | 让模型判断哪里该切、每段是什么。 | V1 禁止 | 切点不可稳定复现，失败难回滚；模型可以参与标签，不参与 V1 切点决策。 |
| E. 全人工切片 | 上传后由运营手动标记每段。 | 保留纠错入口 | 可用于 `needs_reclip` 个案，但不能作为主链路，否则无法规模化。 |

### V1 规则

- 图片素材：生成 1 条 image clip。
- 视频素材：生成 1 条 full_video clip。
- `clip_index = 0`。
- `clip_type = full_video` 或 `image`。
- `start_time_seconds = 0`。
- `end_time_seconds = duration_seconds`。
- V1 不重编码、不裁剪视频；`clip_cos_key` 默认引用原始视频 COS key。
- 缩略图必须单独生成并上传 COS，写入 `thumb_cos_key`。
- 视频缩略图优先取中点帧；中点帧失败时取第 1 秒；时长不足 1 秒时取第 0 秒。
- 超过配置时长上限的视频不得自动 ready，进入 `needs_reclip`，等待人工处理或后续 V2 多段切片 worker。
- `D:\Desktop\测试素材` 下的 MP4 只能当作商家端原始上传输入；不是已切片、已打标、可检索的 ready 素材。
- `D:\Desktop\测试素材` 下的 M4A 只能当作个人声音录音输入；不能进入 `merchant_media_assets` / `merchant_media_clips`。

### V1 标签范围

- 标签针对整段视频 / 整张图片生成，不做片段级语义拆分。
- 标签字段服务内部召回和排序，不照搬到 Pexels response；OpenStoryline 只消费 Pexels-like 外壳。
- `description` 必须解释画面主体和可用场景，不能只复述文件名。
- `tags` 至少覆盖主体、场景、镜头 / 画面类型三类信息。
- 无真实 VLM / LLM 时允许使用 fixture / mock 标签，但 `tag_source` 必须明确写为 `fixture` 或 `mock`。
- mock / fixture 标签只用于本轮合同验证；progress / handoff 必须写清楚不是已完成真实视觉识别。

### 决策后果

正向后果：

- 可先跑通商家端上传、COS 入库、媒体解析、缩略图、标签、Pexels-compatible 检索和 OpenStoryline 接入。
- 每个原始素材最多 1 条 ready clip，幂等和回滚简单。
- 失败定位清楚：是上传校验、媒体解析、缩略图、标签还是检索映射失败。
- 不会因为自动分镜误切，把素材库提前变成难纠错的数据垃圾场。

代价：

- 长视频的召回粒度较粗，可能只能召回整段素材。
- 同一视频里多个场景无法在 V1 里分别排序。
- Dify `video.scenes[].assetQuery` 如果需要更精准镜头，只能先召回整段，再由人工或后续 V2 处理。
- 超长视频会进入 `needs_reclip`，不能自动 ready。

### V2 复审条件

满足以下条件后，才能重新评估多段切片：

- V1 已在 staging 跑通至少一批商家真实上传素材。
- Pexels-compatible 检索已证明不会跨 `merchant_id` 召回。
- 标签抽检通过，低置信度纠错流程可用。
- OpenStoryline 能稳定使用私有 Pexels base URL。
- 已有 `needs_reclip` 样本证明整段 clip 不能满足业务。
- 有可回放的切片 worker 测试集，包括误切、漏切、黑屏、静帧、字幕画面、多人画面。

V2 可选方向：

- 固定时间窗口切片。
- 镜头变化切片。
- 按人物、场景、镜头类型做多段切片。
- 根据 Dify `video.scenes[].assetQuery` 做按需召回和二次裁剪。

### 切片策略硬门禁

- LLM / VLM 不能在 V1 决定 `start_time_seconds` / `end_time_seconds`。
- `duration_seconds`、`width`、`height`、`orientation` 必须来自真实媒体解析。
- `clip_index = 0` 的幂等键必须稳定；同一 `asset_id + clip_index` 重试不得生成重复 ready clip。
- 图片不得写入视频专属字段；视频不得缺少 duration。
- 缩略图缺失、COS 对象缺失、媒体解析失败、标签失败时不得进入 ready。
- 超过时长上限不得静默裁掉后半段，必须进入 `needs_reclip`。
- mock 标签不得伪装成真实模型标签。
- 用户端 / 成员端临时素材不得切片入库。

### 测试项目和标准

- MP4 原始上传合同测试：给定商家端 MP4，完成后必须生成 1 条 asset 和 1 条 clip，`clip_type = full_video`，`clip_index = 0`，起止时间覆盖完整时长。
- 图片原始上传合同测试：给定图片，完成后必须生成 1 条 image clip，且无视频 duration 误写。
- 声音隔离测试：给定 M4A 录音，只能进入 voice profile 链路，不得写入 `merchant_media_*`。
- 超长视频测试：超过配置上限时进入 `needs_reclip`，不得 ready。
- 缩略图失败测试：缩略图生成失败时 clip 不得 ready。
- mock 标签测试：没有真实 VLM / LLM key 时允许 fixture 跑通，但 `tag_source` 必须是 `fixture` 或 `mock`。
- Pexels-compatible 回放测试：ready clip 能映射成 `photos[]` 或 `videos[]`，分页字段符合 Pexels-like 合同。
- 双租户测试：商家 A 的 query 不能召回商家 B 的 clips。

### 检查和纠错

- doctor 检查到 V1 下同一 asset 生成多条 ready clip 时，标记 `slice_policy_violation`。
- doctor 检查到 `start_time_seconds != 0` 或 `end_time_seconds != duration_seconds` 时，标记 `slice_boundary_violation`。
- doctor 检查到 long video 仍 ready 时，标记 `duration_gate_violation`。
- 标签明显不准时标记 `needs_retag`，不重新切片。
- 切点策略不满足业务时标记 `needs_reclip`，进入人工或 V2 worker 队列。
- 缩略图丢失时标记 `missing_thumbnail` 并从检索池下架。
- COS 原对象丢失时标记 `missing_object`，从 Pexels-compatible 响应中剔除。
- 发现用户端临时素材进入团队素材库时标记 `wrong_source`，从 `merchant_media_*` 移除并记录审计。

## 硬门禁

入库门禁：

- 必须有 `merchant_id`。
- 必须来自商家端素材库入口或显式入库动作。
- 必须记录上传操作者 `uploaded_by_user_id`。
- 必须完成 COS 对象存在检查。
- 必须通过文件类型、大小、时长上限检查。
- 必须使用幂等 key，避免同一对象重复入库。
- 必须记录 `source = merchant_upload` 或等价字段，禁止来源不明素材入库。
- 必须记录 `processing_trace_id` 或等价字段，能追踪一次上传、切片、标签、入库全链路。

切片门禁：

- 视频宽高、时长、方向必须来自真实媒体解析，不允许由 LLM 猜。
- clip 生成失败不得写 `ready`。
- 缩略图缺失时不得进入 Pexels-compatible ready 池。
- LLM 标签失败时允许 `tagging_failed`，但不得参与自动召回。
- 切片 worker 必须可重试；同一 `asset_id + clip_index` 重试不得生成重复 ready clip。

标签门禁：

- `description` 必须非空。
- `tags` 至少 3 个。
- `tag_confidence` 低于阈值时不得自动 ready，进入 `needs_review` 或 `needs_retag`。
- `orientation` 必须是 `portrait` 或 `landscape`。
- `duration_seconds`、`width`、`height` 必须非空。
- 标签必须来自已验证的媒体内容，不能只根据文件名或商家输入生成。

## 检查功能

自动检查：

- ready asset 是否至少有一个 ready clip。
- ready clip 的 COS 对象和缩略图是否存在。
- 标签是否为空、重复、过长。
- `tag_confidence` 是否缺失，低置信度标签是否误入 ready。
- LLM 标签和文件类型是否冲突，例如图片 clip 却有 duration。
- 是否有 `content_draft` 临时素材进入 `merchant_media_*`。
- 同一 COS key 是否重复入库。
- ready clip 是否缺少 `merchant_id` 索引条件。
- 是否存在 `tagging_failed` 仍参与检索。

抽检：

- 每批至少抽查 5 条标签。
- 标签必须能解释画面主体、场景和镜头类型。
- 不确定内容不得写成确定事实。

## 纠错功能

- 标签不准：标记 `needs_retag`，重新跑 VLM / LLM。
- 切片不准：标记 `needs_reclip`，重跑切片。
- COS 缺失：标记 `missing_object`，从检索池下架。
- 误入库：标记 `wrong_source`，从 `merchant_media_*` 移除，必要时删除 COS 对象。
- 内容敏感或授权不明：标记 `quarantined`，不参与召回。
- 重复入库：保留一条 canonical 记录，其余标记 `duplicate`。
- worker 半途失败：保留原 asset，删除半成品 clip，重试从 `processing` 开始。

## 板块验收

- 商家端上传 3-10 个视频 / 图片后能生成 `merchant_media_assets` 和 `merchant_media_clips`。
- 每个 ready clip 都有真实宽高、方向、时长、缩略图、description、tags。
- 标签抽检能解释“为什么这个素材会被某个 query 召回”。
- 用户端 / 成员端临时素材不会产生 `merchant_media_assets` 或 `merchant_media_clips`。
- 错误素材可下架、重切、重打标。
