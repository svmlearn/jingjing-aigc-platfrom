# 05 个人克隆声音与覆盖

## 摘要

声音克隆基础链路已合入。下一步不是从零做音色库，而是把当前多 profile 能力收敛为“每人一个当前音色，重新录制覆盖旧音色”。

## 依据

外部依据：

- OWASP 文件上传建议上传前必须校验认证和授权。
- Tencent COS 临时密钥和预签名 URL 文档支持前端临时上传、服务端控制访问有效期；个人声音下载给 worker 时也按服务端权限签发，不暴露永久密钥。
- Stack Overflow 预签名上传讨论提醒：参考音频不能只相信前端 MIME，必须在落地后校验真实音频类型。
- 多租户审计社区经验要求“用户 A 尝试使用用户 B 的资源”作为固定测试；本方案把跨用户 voice profile 使用列为硬失败。
- 对象存储 / DB / provider 不具备共同事务，因此覆盖声音必须用 pending -> validate -> provider success -> swap -> cleanup 的补偿流程。

项目依据：

- `voice_profiles` 表已存在。
- `asset_objects` 已支持 `owner_type = voice_profile`、`asset_type = audio`。
- `GET /api/voice-profiles`、`POST /api/voice-profiles` 已存在。
- `productionConfig.voiceover.mode = "voice_profile"` 已进入视频任务合同。
- worker 当前把 `voice_profile` 映射为 `pixelle_clone` 形态的克隆 TTS 配置；这里的 `pixelle_clone` 是 RunningHub clone 的当前代码适配名 / 历史命名。RunningHub 同时支持普通 TTS 和声音克隆，因此检查重点是是否进入 clone 语义、是否携带 ref audio、是否回写 `voiceover_artifacts`，不是服务商名字。

## 专业社区经验落地规则

个人克隆声音比素材库更敏感：它是个人资产，不是团队共享素材。GitHub / Supabase 多租户经验、COS 对象存储经验和 agent-skills 的增量发布方法在这里落成五条规则：

- 所有 voice profile 查询都按 `created_by_user_id` 过滤；`merchant_id` 只用于当前商家上下文，不把团队成员变成可共享声音使用者。
- 覆盖声音走 pending 流程，不能先删旧声音；只有新音频校验通过且 provider 成功后才 swap。
- 覆盖请求必须有 operation id / idempotency key，防止刷新页面或重试创建多个当前音色。
- 旧 provider voice、旧 COS audio、旧 asset 删除失败不影响新声音使用，但必须进入 cleanup job。
- 按 agent-skills 的切片方式，先做“失败保旧”的本地合同测试，再接真实 provider。

## 当前合同

创建 voice profile：

```json
{
  "displayName": "我的克隆音色",
  "refAudioAssetId": "asset-id",
  "authorizationAccepted": true
}
```

视频任务 voiceover：

```json
{
  "voiceover": {
    "enabled": true,
    "mode": "voice_profile",
    "voiceProfileId": "voice-profile-id",
    "refAudioAssetId": "asset-id"
  }
}
```

worker 内部规范化后：

```json
{
  "mode": "voice_profile",
  "provider": "pixelle_clone",
  "clone_enabled": true,
  "voice_profile_id": "voice-profile-id",
  "ref_audio_asset_id": "asset-id",
  "ref_audio_asset": {
    "storageProvider": "tencent_cos",
    "storageKey": "voice-profiles/..."
  }
}
```

## 工作边界

必须保留：

- 用户明确授权确认。
- `ref_audio_asset_id` 指向 audio asset。
- app 创建 job 前做 voice profile 和 ref audio asset 归属校验。
- worker 下载参考音频后再调用 provider。

后续新增：

- 同一 `merchant_id + created_by_user_id` 只保留一个当前可用 voice profile。
- 重新录制成功后覆盖旧声音。
- 新录制失败时旧声音继续可用。

## 硬门禁

创建 / 覆盖门禁：

- 必须登录。
- 必须有 `authorizationAccepted = true`。
- ref audio 必须是 `asset_objects.owner_type = voice_profile`。
- ref audio 必须是 `asset_type = audio`。
- ref audio 的 `owner_id` 必须等于当前 `voice_profile.id`。
- ref audio storage provider 必须是 `tencent_cos`。

覆盖门禁：

- 新音频上传成功但 provider 创建失败时，不替换旧 profile。
- 新 provider voice 成功后，才更新 `ref_audio_asset_id / external_voice_id / external_model_id`。
- swap 必须在数据库事务内完成：新 profile 或新引用变为 current，旧引用进入 archived / cleanup_pending。
- 覆盖成功后，旧 audio asset、旧 COS 对象、旧 provider voice 必须进入清理流程。
- 同一用户不得出现多个 ready 当前音色。
- 覆盖操作必须幂等：重复提交同一个 pending audio 不得创建多个当前音色。
- 参考音频必须通过真实音频解析，不能只信 `Content-Type`。

视频任务门禁：

- 使用 voice profile 时必须同时提供 `voiceProfileId` 和 `refAudioAssetId`。
- `voice_profiles.created_by_user_id` 必须等于当前创建 job 的用户。
- `voice_profiles.merchant_id` 必须等于当前 job 的 `merchant_id`。
- 失败时标记为可解释的 manual failure，不进入模糊渲染失败。

## 检查功能

自动检查：

- 同一 `merchant_id + created_by_user_id` 是否有多个 `ready` profile。
- `voice_profiles.ref_audio_asset_id` 是否存在。
- ref audio asset 是否为 `voice_profile/audio`。
- ref audio COS 对象是否存在。
- worker result 是否包含 `voiceover_artifacts`。
- pending 覆盖任务是否超过 TTL。
- cleanup 任务是否连续失败。
- 覆盖操作是否有审计记录：旧 `ref_audio_asset_id`、新 `ref_audio_asset_id`、operator、结果、失败原因。

手动检查：

- 用户 A 不能选择用户 B 的 voice profile。
- team member 不能使用 owner 的声音，除非后续明确做授权功能。
- 新录制 provider 失败时旧声音仍可用于创建视频。

## 纠错功能

- 多个 ready profile：保留最新或用户选择的一个，其余 `archived`，同时记录修复日志。
- ref audio asset 缺失：禁用该 profile，提示重新录制。
- COS 对象缺失：标记 `disabled`，不允许创建 job。
- provider 旧 voice 删除失败：写入清理任务，不影响当前新 voice 使用。
- worker 下载参考音频失败：标记 `failed_retryable` 或 `failed_manual`，按错误类型区分。
- 重复 ready profile：自动归档非当前 profile，并触发一次权限回归测试。
- pending 超时：删除 pending audio asset 和 COS 对象，保留旧 profile。

## 板块验收

- 用户录制 / 上传一次音频后可创建 voice profile。
- 选择“我的克隆音色”创建视频任务时，payload 包含 `voiceProfileId`、`refAudioAssetId` 和 ref audio asset 摘要。
- 重新录制覆盖成功后，列表只显示一个当前音色。
- 覆盖失败时旧音色仍可用。
- staging 配置可用的 RunningHub clone provider 后完成一次真实克隆配音。当前代码默认变量名仍是 `TTS_PIXELLE_CLONE_BASE_URL`、`TTS_PIXELLE_CLONE_API_KEY`，但含义按 RunningHub clone 理解；必须用测试证明 `voice_profile` 模式能携带 ref audio 完成克隆配音。
