# 07 测试、验收、纠错与上线

## 摘要

这个板块是最终 gate。没有通过这里，不进入 staging 验收；没有 staging 真实链路，不进入生产。

## 依据

外部依据：

- Supabase RLS 文档：公开 schema 表要启用 RLS 并配置 policies。
- OWASP 文件上传安全：上传前必须校验认证和授权。
- COS 文档：前端使用临时凭证，下载使用有效期 URL。
- GitHub API 分页实践：大结果集必须分页，客户端要能追踪下一页。
- Supabase GitHub Discussion：RLS 不是查询过滤器，业务查询仍要显式 `.eq("merchant_id", merchantId)` / `.eq("created_by_user_id", userId)`。
- Reddit / Supabase 安全审计经验：多租户上线前必须做双租户 fixture，手工和自动都要验证“用户 A 不能读 B”。
- Stack Overflow 预签名上传讨论：对象落地后仍要校验真实文件类型。
- tus 协议：大文件 / 长上传需要过期和 checksum 思路，避免半成品长期滞留。

项目依据：

- 当前 `voice_profiles` migration 尚需确认是否已在 staging 执行。
- 当前 Pixelle clone 真实 provider 配置仍需 staging 联调。
- 团队素材库表和 Pexels-compatible 接口尚未实现。

## 专业社区经验转成测试项

上线测试不是只跑 happy path。结合 GitHub / Stack Overflow / OWASP / agent-skills 的常见工程门禁，本方案把以下场景列为阻断项：

| 经验来源 | 必测场景 | 失败标准 |
| --- | --- | --- |
| GitHub / Supabase RLS | 登录 A，枚举 B 的 `merchant_media_assets`、`merchant_media_clips`、`voice_profiles` ID。 | 任意接口返回 B 的数据即阻断。 |
| GitHub RLS 性能实践 | 大量素材下查询必须显式过滤并走索引。 | explain 出现全表扫描且无合理解释即阻断。 |
| GitHub REST 分页 | `per_page` 超上限、连续翻页、最后一页、空结果。 | 返回全部数据、翻页重复、`next_page` 错误即阻断。 |
| COS 60 天下载 | Pexels-like JSON 中 `link/src` 可在 60 天内访问，下架后可撤销。 | URL 很快失效，或下架后仍可下载即阻断。 |
| Stack Overflow 预签名上传 | 前端把非音频伪造成 `audio/wav`，或把非视频伪造成 `video/mp4`。 | complete 成功或进入 ready 即阻断。 |
| OWASP 文件上传 | 未登录、无商家权限、错 owner、错 bucket、错 prefix。 | 任一非法上传拿到可用 URL 或入库即阻断。 |
| agent-skills shipping gate | 每个切片必须有 spec、验收证据、回滚点和 handoff。 | 只有实现没有证据，或无法说明回滚方式即阻断。 |

## 测试矩阵

### A. 数据库 / RLS

硬门禁：

- 新增表必须 enable RLS，或明确只由 service role 访问。
- 跨 `merchant_id` 查询必须失败。
- 跨 `created_by_user_id` 使用 voice profile 必须失败。
- RLS 涉及列必须有索引。
- 服务端 repository 查询必须显式带 tenant / owner 条件，不得只靠 RLS。

检查：

- 两个商家、两个用户、至少一个 team member 测试账号。
- 测试 select / insert / update / delete。
- 登录 A，枚举 B 的已知 ID，逐个打 API。
- 检查客户端 bundle / env 中没有 service role key。
- 非生产 explain 检查核心列表查询是否使用 `merchant_id` / `created_by_user_id` 相关索引。

纠错：

- RLS 过宽：立即阻断合并。
- RLS 过窄：补 policy test，避免只在 UI 层兜底。

### B. COS 上传 / 下载

硬门禁：

- 前端不能拿永久密钥。
- upload key 只能由服务端生成。
- complete 必须验证 key 前缀。
- 下载 URL 必须 60 天有效，且不是永久公开 URL。

检查：

- 错 bucket 测试。
- 错 prefix 测试。
- 60 天 URL 过期测试。
- COS 对象存在性测试。
- 前端伪造 MIME，落地后真实类型检查必须拦截。
- intent 超时后 complete 必须失败或进入 quarantine。
- STS policy 越权测试：把 key 改到同商家其他 prefix 或其他商家 prefix，上传 / complete 必须失败。
- 60 天下载 URL 测试：生成后能访问，素材下架 / quarantine 后被服务端入口拦截。

纠错：

- orphan object 定期清理。
- missing object 下架。
- wrong prefix quarantine。

### C. 商家素材库

硬门禁：

- 只有商家端确认入库素材可进入 `merchant_media_*`。
- ready clip 必须有真实元数据和缩略图。
- 标签失败不得参与自动召回。

检查：

- 上传 3-10 个素材。
- 随机抽查 5 条标签。
- 用户端临时素材误入库检查。
- 标签召回解释检查：给定 query 能看到命中的 tags / description / scene_tags 来源。

纠错：

- `needs_reclip`。
- `needs_retag`。
- `missing_object`。
- `quarantined`。

### D. Pexels-compatible 接口

硬门禁：

- 返回字段满足 OpenStoryline 当前消费字段。
- 只返回当前 `merchant_id` 素材。
- `per_page` 有上限。

检查：

- 视频 fixture。
- 图片 fixture。
- 空结果。
- 下一页。
- 60 天下载 URL 下载。
- 同一 query 连续翻页无重复。
- `per_page` 超上限被截断或拒绝。
- 生产响应不包含内部 `merchant_id`、COS key、bucket、tags。

纠错：

- 字段缺失阻断合并。
- 下载 URL 签发失败跳过单条结果并记录。
- 下载失败 clip 降权。

### E. 个人克隆声音

硬门禁：

- 使用 voice profile 必须校验 `created_by_user_id`。
- 新声音成功前不删除旧声音。
- 覆盖成功后不能保留多个当前音色。

检查：

- 首次录音。
- 重新录制成功。
- 重新录制 provider 失败。
- 用户 A 尝试用用户 B 声音。
- 重复提交同一个覆盖请求。
- pending 超时清理。
- 覆盖成功后的旧 audio / provider voice 进入 cleanup job，cleanup 失败不影响当前新声音使用。

纠错：

- 多 ready profile 自动归档旧项。
- ref audio 缺失禁用 profile。
- provider cleanup 失败进入补偿队列。

### F. Worker / OpenStoryline

硬门禁：

- worker payload 校验失败不能进入渲染。
- ref audio 下载失败必须可观测。
- final video 缺失不能标记 succeeded。

检查：

- system voiceover job。
- voice_profile job。
- 私有素材检索 job。
- OpenStoryline request / response 留档。

纠错：

- failed_retryable 重试。
- failed_manual 提示用户修正。
- voiceover_artifact_missing 进入人工复核。
- retry 后重复 `asset_objects` 检查。
- engine request / response 可回放检查。

### G. Dify 脚本制作 JSON 落库

硬门禁：

- Dify 是当前脚本制作链路；字段以 `2026-05-13-Dify最终JSON字段确认器.html` 为准。
- Dify `outputs.final_result_json` 不得直接作为 `video_edit_jobs.input_payload`。
- 必须从 Dify 最终 JSON 中读取 `article.*`、`video.*`、`quality.*`、`debug.*`。
- `article.*` 落图文 variant。
- `video.*` 校验后落 `video_script` variant。
- `quality.*` 决定能否继续进入视频任务；`debug.*` 只做 trace / metadata。

检查：

- 固定 fixture 覆盖 `workflowVersion / status / article / video / quality / debug`。
- `article` 至少校验 `title`、`coverCopy`、`images[].cosPath`、`images[].role`、`copyText`。
- `video` 至少校验 `storyOutline`、`estimatedDuration`、`scenes[]`。
- `video.scenes[]` 至少校验 `sceneNo`、`timeRange`、`durationSec`、`sceneType`、`title`、`requiresUserUpload`、`taskDescription`、`visualDescription`、`voiceover`。
- worker-only 字段如 `video.bgm`、`video.toneOfVoice`、`subtitle`、`shotLanguage`、`editGuide`、`assetQuery`、`fallbackVisual` 必须保留给后台 / worker，即使不展示给成员。
- `quality.status = blocked` 或关键字段缺失时，不得直接创建视频任务。
- `debug.*` 保存在 metadata / trace 字段，不能污染成员 UI 主输出。
- 已映射 `video_script` variant 经成员端确认后，才能进入 `video_edit_jobs`。

纠错：

- 字段缺失：标记 `schema_failed` 或 `needs_review`，保留 Dify 原始包用于排查。
- 字段语义不一致：标记 `needs_review`，进入视频工作台人工修订。
- 重复落库：用 Dify workflow run id / content calendar item id 做幂等 key，避免重复创建 variant。
- 错把 `outputs.final_result_json` 原文传给视频 worker：合同测试阻断，回到 content-generation-worker 修复。

## 上线顺序

1. 先合并声音覆盖修正和 provider staging 联调。
2. 再实现商家素材库表和入库 worker。
3. 再实现 Pexels-compatible 私有检索接口。
4. 同步补齐 Dify `article/video/quality/debug` 到 content variants 的 schema gate。
5. 最后接入 OpenStoryline 私有 base URL 做真实出片。

## 最终验收

必须同时满足：

- 商家素材端到端：上传 -> 切片 -> 标签 -> 私有检索 -> OpenStoryline 下载 -> 成片。
- Dify 内容生成端到端：`final_result_json` -> `article.*` 图文 variant -> `video.*` 视频脚本 variant -> `quality.*` gate -> 成员端确认。
- 个人声音端到端：录音 -> voice profile -> 创建视频任务 -> worker 下载 ref audio -> 克隆配音 -> 成片。
- 跨商家、跨用户、错 key、错 bucket、60 天 URL 过期、provider 失败都有明确行为。
- 所有纠错任务有状态、有日志、有人工接管入口。
- doctor 检查无阻断项：无跨租户泄漏、无 public bucket、无 service key 泄漏、无过期 pending 积压、无多 ready voice profile。
