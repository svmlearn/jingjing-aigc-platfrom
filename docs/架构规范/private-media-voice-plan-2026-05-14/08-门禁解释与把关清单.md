# 08 门禁解释与把关清单

## 摘要

本文件给产品负责人、技术负责人和验收人使用。它不重复实现方案，只解释每个硬门禁为什么存在、通过代表什么、失败会造成什么后果，以及发现问题后怎么纠错。

核心原则：

- Dify 链路为新内容生成 / 脚本制作主链路。
- 现有视频脚本、测试草稿、手工脚本和 `video_edit_jobs.input_payload` 为兼容辅路和稳定传输合同。
- 两条链路必须通过融合 adapter 收敛，不能互相打断。
- COS 私有素材库服务商家团队，个人克隆声音服务个人本人。

## 依据来源

- `docs/架构规范/2026-05-12-内容日历批量生成与Dify过渡架构决策.md`：Dify 只做单条内容生成，批量调度和落库由本系统负责。
- `docs/探索/2026-05-11-用dify来测试链路/2026-05-13-Dify最终JSON字段确认器.html`：Dify 最终字段以 `workflowVersion/status/article/video/quality/debug` 为准。
- `docs/架构规范/2026-04-28-current-architecture.md`：`video_edit_jobs.input_payload` 是 app 和 video worker 的稳定连接点。
- Pexels API：私有素材接口只模仿请求 / 响应外壳，不照搬其公共素材权限模型。
- Tencent COS STS / pre-signed URL：上传用短期临时凭证，下载给 OpenStoryline / 前端预览按业务要求给 60 天有效 URL。
- Supabase RLS / GitHub 多租户经验：RLS 是兜底，业务查询仍必须显式带 `merchant_id` / `created_by_user_id`。
- OWASP File Upload：上传认证、授权、真实文件类型检查和隔离存储不能省。
- addyosmani/agent-skills：按 spec、plan、build、test、review、ship 分阶段推进，每一步都要有证据。

## G1 Dify 主链路不得直塞 worker payload

门禁：`outputs.final_result_json` 不得直接作为 `video_edit_jobs.input_payload`。

为什么：

- Dify 最终 JSON 是内容生成总包，里面包含图文、视频脚本、质量、debug，不是视频 worker 的原生执行合同。
- worker 的稳定输入是现有 `video_edit_jobs.input_payload`。如果让 worker 直接吃 Dify 总包，就会把上游实验格式扩散到执行层。

没过的后果：

- 旧视频脚本和测试草稿可能无法创建任务。
- worker 需要同时理解两套 schema，后续排查会分裂。
- Dify 字段调整会直接影响出片链路。

过关证据：

- 有 Dify fixture 落 `note` + `video_script` variant。
- 有合同测试证明 Dify 来源和非 Dify 来源都经过同一个 payload builder。
- `video_edit_jobs.input_payload` 快照中没有完整 `outputs.final_result_json` 原始总包。

纠错：

- 回滚绕过 payload builder 的代码。
- 在 fusion adapter 内补字段映射和 schema gate。
- 把失败样本保存为 fixture，防止再次直塞。

## G2 Dify 主链路和现有辅路必须同时可用

门禁：feature flag 打开时，新生成优先走 Dify；feature flag 关闭、Dify API 失败或 schema gate 失败时，现有视频脚本 / 测试草稿 / 非 Dify `video_script` 仍能正常工作。

为什么：

- 用户明确要求 Dify 为主，但不能影响现有功能和传输。
- Dify 当前仍可能受 API、schema、质量 gate 和线上导入状态影响，必须有回退通道。

没过的后果：

- Dify 异常会拖垮现有生成。
- 用户无法区分是 Dify 失败、adapter 失败还是 worker 失败。
- 后续合并时很难安全拆分问题。

过关证据：

- flag on：Dify fixture 能生成 `note` + `video_script`，确认后创建合法 `video_edit_jobs`。
- flag off：现有测试草稿 / 非 Dify `video_script` 能按原路径创建合法 `video_edit_jobs`。
- 现有 video worker 单测继续通过。

纠错：

- 先关闭 flag 保现有链路。
- 修复 Dify adapter 或 schema gate。
- 不通过修改 worker 主合同来迁就 Dify 原始字段。

## G3 Dify 字段必须按确认器落库

门禁：Dify 接入只接受字段确认器里的 `workflowVersion/status/article/video/quality/debug` 主结构；旧 POC 的 `articlePackage/videoScript/qualityReview/trace/saveHints` 只能作为兼容输入转换。

为什么：

- 字段确认器是当前最清晰的 Dify 合同。
- 保留旧 POC 字段作为主输出会让前端、worker 和数据表继续摇摆。

没过的后果：

- 同一内容可能以多套结构落库。
- 视频工作台需要不断判断旧字段和新字段。
- 质量 gate 和 debug trace 无法稳定复用。

过关证据：

- schema fixture 覆盖 `article.title`、`article.images[].cosPath`、`video.scenes[]`、`quality.status`、`debug.usedKnowledgeRefs`。
- 旧字段 fixture 能转换到新结构。
- 缺关键字段时进入 `schema_failed` 或 `needs_review`。

纠错：

- 在 adapter 增加别名转换。
- 不改 LLM prompt 去硬凑下游字段，优先在 deterministic compiler / adapter 收敛。

## G4 COS 下载必须给 60 天可用 URL，且不能 public bucket

门禁：OpenStoryline / Pexels-compatible / 素材库外部预览收到的 `src` / `link` 必须 60 天有效；bucket 不得公开；下架、quarantine、missing object 后必须能被平台入口拦截。平台内登录态成片预览可使用稳定 app route 重签短期 COS URL。

为什么：

- 短期签名 URL 会导致后续复查、重跑、人工验收时素材看不了。
- public bucket 虽然省事，但会破坏“团队私有素材”的边界。

没过的后果：

- 成片任务隔天或几周后无法重放。
- 商家团队素材可能被外部访问。
- 下架素材仍被旧链接下载，无法治理。

过关证据：

- URL 生成逻辑明确 `expiresIn = 60 days` 或平台 token 过期时间为 60 天；若使用登录态保护的 app route，则 app route 必须能在业务有效期内重新签短期 COS URL。
- 生成后下载成功。
- 素材 archived / quarantined 后，通过平台下载入口访问失败。
- 客户端代码没有 COS 永久密钥。
- 成片结果预览和下载分开：`signedPreviewUrl` 是 `inline`，`signedDownloadUrl` 是 `attachment`。

纠错：

- 下载侧改为服务端 60 天签名 URL，或平台 download token URL。
- 发现 public bucket 立即阻断上线，改回私有 bucket。
- 已发出的不可控 URL 通过下架对象、轮换 key 或平台拦截补救。
- 若只是平台内成片预览，不要为了“60 天”把 COS 裸签名 URL 暴露给前端；优先保留 app route，由服务端鉴权后重签。

## G5 商家素材库只收商家端确认入库素材

门禁：只有商家端确认入库的图片 / 视频进入 `merchant_media_assets` / `merchant_media_clips`；用户端 / 成员端临时上传素材不入库、不切片、不打标签、不长期保存。

为什么：

- 商家素材库是团队共享资产，不是用户临时素材缓存。
- 临时素材可能没有授权、质量不足或只服务单次任务。

没过的后果：

- 临时素材误变成团队可检索资产。
- OpenStoryline 可能召回不该共享的用户素材。
- 后续标签和版权治理不可控。

过关证据：

- 入库 API 只在商家端或具有商家素材管理权限的角色开放。
- 临时上传路径不会写 `merchant_media_*`。
- doctor 能查出误入库临时素材。

纠错：

- 误入库素材标记 `quarantined` 或删除索引。
- 清理对应 clips 和标签。
- 补权限测试和来源字段检查。

## G6 素材检索必须按 `merchant_id` 双层隔离

门禁：repository 查询显式带 `merchant_id`，RLS policy 也校验当前用户对该 merchant 的 membership。

为什么：

- RLS 是安全兜底，不是业务过滤器。
- `auth.uid()` 是用户 ID，不是商家 ID，不能直接等同 `merchant_id`。

没过的后果：

- 跨商家素材泄漏。
- 查询性能不可控。
- RLS policy 看似存在但实际 tenant 映射错误。

过关证据：

- 双商家 fixture：A 枚举 B 的 asset / clip ID 全部失败。
- repository code review 能看到 `.eq("merchant_id", merchantId)` 或 SQL where 条件。
- `merchant_id`、状态、排序字段有索引。

纠错：

- 立即阻断合并。
- 补 membership 映射和 RLS policy。
- 给泄漏查询补显式 where 和测试。

## G7 个人克隆声音只能本人使用，并支持覆盖失败保旧

门禁：voice profile 使用必须校验 `created_by_user_id`；每个 `merchant_id + created_by_user_id` 只有一个当前 ready 音色；重新录制必须新音频和 provider 成功后再 swap，失败保留旧音色。

为什么：

- 克隆声音是个人资产，不是团队素材。
- 覆盖流程跨 DB、COS、provider，不能先删旧资源再赌新资源成功。

没过的后果：

- 成员可能误用他人声音。
- provider 失败会让用户失去唯一可用音色。
- 多个 ready profile 会导致 worker 选错声音。

过关证据：

- 用户 A 调用户 B voice profile 被拒绝。
- 覆盖成功后只有一个 current ready。
- 覆盖失败后旧 profile 仍可创建视频任务。
- cleanup job 失败不影响新 profile 使用。

纠错：

- 多 ready 时保留最新 verified current，其他 archive，并写 audit。
- ref audio 缺失时禁用 profile，提示重新录制。
- provider cleanup 失败进入补偿队列。

## G8 上传后必须做真实文件探测

门禁：前端 MIME / 扩展名只做预检；对象落 COS 后必须 sniff / ffprobe / image probe，失败进入 quarantine 或清理。

为什么：

- 预签名上传不能证明文件真实类型。
- 后续切片、缩略图、声音 provider 都依赖真实媒体类型。

没过的后果：

- 恶意或错误文件进入处理队列。
- worker 报错位置滞后，排查困难。
- 标签、检索、OpenStoryline 下载都可能产生坏数据。

过关证据：

- 伪造 `audio/wav` 的非音频文件 complete 失败。
- 伪造 `video/mp4` 的非视频文件 complete 失败。
- 失败对象不会进入 ready 素材或 ready voice profile。

纠错：

- 标记 `quarantined`。
- 清理 COS orphan。
- 给 upload intent 增加 checksum / size / content probe 记录。

## G9 Pexels-compatible 只兼容外壳，不暴露内部标签

门禁：接口返回字段满足 OpenStoryline 当前消费的 Pexels-like JSON；生产响应不暴露 `merchant_id`、bucket、COS key、内部 tags、tag confidence。

为什么：

- OpenStoryline 需要的是可下载素材和基本媒体字段，不需要平台内部权限和标签体系。
- 内部标签可能包含商家隐私、素材来源或审核信息。

没过的后果：

- OpenStoryline 和内部数据结构耦合。
- 标签体系调整会影响剪辑引擎。
- 内部商家信息可能泄漏。

过关证据：

- photos / videos fixture 满足 `src`、`video_files[].link`、`page`、`per_page`、`total_results`、`next_page`。
- 响应脱敏测试不包含内部字段。
- 连续翻页无重复。

纠错：

- 在 response mapper 里做白名单输出。
- 内部标签只用于召回，不进入 Pexels response。

## G10 doctor 无阻断项才允许上线

门禁：上线前 doctor / 等价检查必须无阻断项。

为什么：

- 这条链路跨 Dify、DB、COS、worker、OpenStoryline、voice provider，单点 happy path 不能代表可上线。
- doctor 是把已知风险变成可重复检查的最低成本方式。

没过的后果：

- 已知跨租户、public bucket、service key 泄漏、pending 积压、多 ready voice profile 带病上线。

过关证据：

- doctor 报告无阻断项。
- progress 文档记录检查时间、环境、命令和结果。
- 仍有非阻断项时，写清 owner、风险和后续处理计划。

纠错：

- 阻断项必须先修再上线。
- 非阻断项可进入 backlog，但必须说明为什么不影响本次验收。

## 最终把关顺序

1. 先看 Dify 主链路和现有辅路是否都能产生合法 variant。
2. 再看两条链路是否都收敛到同一个 `video_edit_jobs.input_payload`。
3. 再看 COS 60 天 URL、商家隔离、个人声音隔离是否通过安全测试。
4. 再看 OpenStoryline 是否不依赖真实 Pexels 也能检索和下载私有素材。
5. 最后看 doctor / progress / handoff 是否齐全。

只要 G1、G2、G4、G6、G7 任一失败，就不建议进入 staging 验收。
