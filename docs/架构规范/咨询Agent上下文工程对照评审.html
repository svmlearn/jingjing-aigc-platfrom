Claude Code：它不是一个大 ContextInjector

Claude Code 的核心思路是把上下文分成多条管道，并在每次模型调用前做裁剪、压缩和预算判断。它不会把“项目记忆、工具结果、规则、当前任务、历史对话”全部揉成一个大 JSON 交给模型。

参考目录：references/open-source/claude-code项目/claude-code-main

输入分层

稳定规则、会话状态、项目记忆、工具执行状态和消息历史各走各的管道。

我们当前：system prompt 和 user JSON 双层注入

当前 native tool calling 路径中，system prompt 负责塞规则、身份、skill、工具和 ContextInjector；user JSON 又塞当前商家、用户消息、上下文对象、策略快照、知识命中、工具结果和 skillDisclosure。

核心文件：app/src/server/api/consultation-service.ts

System Prompt Stack

这些内容被 join 成一个 system message，强约束模型行为。

规则层
1
agent prompt
默认咨询 Agent 的身份、目标和硬规则。
2
soul
专家人格、语气、acknowledgement 和互动节奏。
3
专家容器
@ 切换专家时注入当前专家、agentKey、后台描述和知识边界。
4
skill catalog
全部候选 skill 的 name、description、whenToUse 简述。
5
active skills
当前轮命中的最多 3 个 skill 正文，每个 body 最多 3600 字符。
6
skill references
本轮 active skill 绑定参考资料标题，提示模型必要时调用知识库。
7
business tools
告诉模型有哪些受控工具、每个工具的目的和写入范围。
8
ContextInjector
告诉模型 sessionContext 是共享事实层，专家切换不能遗忘。
9
native tool loop 规则
规定 tool_calls、最终回复、失败处理、不要输出内部工具名等。
10
日历规则
何时写日历、何时改标题、已生成团队内容时如何提醒用户。
11
RAG 规则
何时先检索、如何拆 query、不要先写后查。
12
guardrail 规则
工具 skipped/guardrail 拒写时，最终回复不能声称已更新。

User JSON Payload

这些内容作为 user message 的 JSON 字符串传给模型，是“本轮数据层”。

数据层
A
merchant
商家名、行业、服务项目、默认 CTA。
B
userMessage / round
当前用户输入和轮次。
C
contextInjection
完整上下文对象：targetExpert、sessionContext、expertTraffic、budget 等。
D
strategySnapshot
策略快照摘要：定位、卖点、客群、场景、日历、生成状态等。
E
knowledgeMatches
知识库命中片段，当前每条传 title、score、content 前 600 字符。
F
toolResults
已完成或失败的工具结果摘要和 guardrail。
G
skillDisclosure
候选 skill 与本轮 active skill 的结构化披露。

不直观的问题：同一类信息出现了两次甚至三次

这不是说所有重复都错，而是重复会让模型不清楚哪个是权威来源，也会占掉上下文预算。

ContextInjector 说 sessionContext 是共享事实层；系统规则要求只能逐字使用 strategySnapshot 已有条目。

知识库命中
RAG 规则要求先检索、拆 query、不要说无法读取知识库。
contextInjection 里有 knowledgeMatchCount，顶层 knowledgeMatches 又放每条 content。
如果旧命中继续在上下文里，模型可能把旧依据当成本轮新依据。
工具结果
native loop 规则要求读取工具 skipped/guardrail，并据此回复。
contextInjection.sessionContext.toolResults 和顶层 toolResults 都放摘要。
结果摘要重复时，模型会更倾向围绕工具执行状态说话，聊天会像流程日志。
Skill
system prompt 有 skill catalog、active skill 正文、skill references。
user JSON 顶层还有 skillDisclosure。
模型既看到“能力说明”，又看到“能力披露结构”，容易把内部能力当成要对用户解释的对象。
日历规则
多条 system 规则强调何时生成、何时修改、已生成团队内容时要提醒。
strategySnapshot.contentCalendarDraft 和 contentCalendarGeneration 又作为数据给模型。
规则和状态都很强，模型可能过度谨慎，简单聊天也会先考虑日历副作用。

建议目标：从“大包注入”改成“按任务选包”

参考 Claude Code 的思想，我们不一定要照搬它的 CLI 机制，但可以把当前咨询 Agent 改成更清晰的 ContextPack。

ContextPack v2
1. Stable Rules 稳定身份、语气、工具调用协议。尽量短，少随业务状态变化。
2. Turn Intent 本轮用户到底要什么：轻问答、查依据、写日历、改某条标题、生成团队内容。
3. Selected State 只放本轮需要的策略资产子集。比如改周五标题，只放周五条目和生成标记。
4. Tool Evidence 只放最近、相关、已完成的工具结果。旧知识命中不默认继续当本轮依据。
5. Review/Debug 预算报告、完整 strategyMarkdown、全量 skillDisclosure 放调试面板，不默认进主模型。
一句话结论 当前问题更像“模型在很多重复规则和状态里找主线”，不是工具调用本身坏了。换更强模型会缓解，但更应该先把上下文变成可选择、可计量、可裁剪的 ContextPack。
