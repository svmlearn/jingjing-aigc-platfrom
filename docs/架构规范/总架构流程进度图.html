一张总图

业务事实从咨询台进入策略资产和内容日历；生产事实从 Dify 和 video-worker 回写任务、草稿、成片和资产对象。

1. 用户在咨询台讨论选题 围绕项目优势、客户异议、内容方向、图文/视频选题、素材边界提出问题。 输入：自然语言
2. Agentic RAG 与受控工具 runtime 注入 prompt、skill、context、knowledge matches，并让 LLM 自主选择工具。 输出：策略 / 日历
3. 内容日历资产 UI 展示轻量卡片，后台保留知识引用、素材提示、镜头边界和生成状态。 写入 strategySnapshot
4. 生成团队内容 点击按钮后展开成员任务，创建 batch/jobs，并把日历上下文压缩进 Dify inputs。 批量调度
5. Dify 单条生成 每个 job 调一次 workflow，返回图文包和视频脚本 final_result_json。 单条 worker
6. 成员执行与成片 成员端查看图文/视频脚本，上传素材或声音，video-worker 调 OpenStoryline/FireRed 输出成片。 输出：草稿 / 视频资产

选题侧：咨询 Agent Runtime

LLM 负责判断，runtime 负责边界。核心原则是“不硬编码替 LLM 决策，但把事实、工具和约束给够”。

Agent 提示词栈

一次 native tool calling 轮次会拼出以下 system prompt 片段，再把商家、策略资产、知识库命中、工具结果和 skillDisclosure 放进 user JSON。

Agent active prompt 默认角色是“静境商家平台里的 AI 商业顾问”，目标是沉淀定位、卖点、客群、关键场景、内容策略和一周内容日历。
soul.md 定义专家人格、语气、acknowledgement 和互动节奏，但不能覆盖平台硬规则。
专家容器 当前专家、agentKey、后台描述、知识边界。@ 只切换专家身份，不清空共享上下文。
Skill 渐进式披露 先给候选 skill 摘要，当前轮命中后才注入最多 3 个 active skill 正文。
受控业务工具 告诉 LLM 哪些工具能读资料、检索、找对标、写策略和写日历，以及每个工具影响范围。
ContextInjector 注入商家、会话摘要、策略快照、知识库命中、工具结果、专家共享白板，并记录 char budget。
Native tool loop 规则 工具必须通过 API tools 字段返回；是否检索、换 query、写日历由 LLM 判断；写日历前需要足够依据。

本轮核心硬规则

团队选题先查依据

i

营销日历、团队选题、图文/视频脚本会沉淀为生产任务，prior tool_result 没有依据时应先检索。

Prompt 片段

如果用户要求的是营销日历、团队选题、图文/视频脚本这类会沉淀为后续生产任务的内容，并且 prior tool_result 尚未提供知识库或素材能力依据，应先调用 retrieve_knowledge_base。

多轮 RAG 由 LLM 决定

i

项目事实、方法论、话术、素材边界可以拆成不同 query 深挖。

Runtime 事实
  • retrieve_knowledge_base 是 repeatable read tool。
  • native loop 最多 8 轮工具回合。
  • 每轮最多接受 2 个 tool_calls。
  • 工具结果会作为 tool message 回填给模型继续判断。

修改日历必须写工具

i

标题、摘要、日期、内容类型或选题角度的修改，不能只在自然语言里说“已调整”。

Prompt 片段

当用户要求修改某一条日历标题、摘要、日期、内容类型或选题角度时，也必须通过 update_content_calendar 写入修改后的日历。

已生成团队内容的日历

i

runtime 暴露 contentCalendarGeneration 标记，LLM 判断是否先提醒并确认，代码不硬拦截。

当前规则
  • 点击“生成团队内容”后记录 generatedFromRevisionId、batch、时间、任务数。
  • 日历修改后可变为 modified_after_generation。
  • update_content_calendar 不再从 available tools 移除。
  • 是否提醒“团队内容可能要整体重做”由 LLM 自行判断。

Skills：候选与激活

后台挂载的 enabled skills 先参与打分，当前用户消息或最近 3 条消息命中后，最多 3 个正文进入本轮 prompt。悬浮卡片可看内容摘要。

DBS 商业诊断

i

判断方向、变现结构、价值假设和问题本身是否成立。

dbs_diagnosis
Skill 内容

任务不是立刻做内容，而是判断方向、问题或商业模式是否成立。

  • 先消解问题，再回答问题。
  • 检查语言陷阱、假设错误、逻辑错误、事实缺口。
  • 输出核心判断、成立前提、最大风险、最小验证动作。
  • 如果已进入标题、开头、脚本、排期，交给营销 Agent。

依赖：retrieve_knowledge_base

DBS 概念拆解

i

把定位、人设、IP、差异化等模糊词拆成可判断概念。

dbs_deconstruct
Skill 内容
  • 不急着下定义，先看词在不同场景里怎么被使用。
  • 还原概念来源，检查挪用后是否保留关键属性。
  • 区分 Question 和 Problem，识别词语空转。
  • 用大白话重写概念，并说明对领域、价值或对标的影响。

触发：定位、人设、IP、爆款、价值、差异化等模糊词。

DBS 对标判断

i

判断对标对象是否值得学、能学什么、不能学什么。

dbs_benchmark
Skill 内容
  • 粉丝多不等于值得对标。
  • 五重过滤：他赚钱吗、看得懂吗、能模仿吗、能排除偏好吗、当前阶段是否该先模仿。
  • 输出可学部分、不可学部分、第一步模仿动作和风险提醒。
  • 不要直接生成标题或脚本。

DBS 目标清晰化

i

把“想做 IP、想变现、想涨影响力”改成可检查目标。

dbs_goal
Skill 内容
  • 先判断目标是否可指物、可否证、可验收。
  • 识别影响力、长期主义、变现、起号、定位等空转词。
  • 输出重写目标、验收 checklist 和下一步事实收集动作。
  • 目标未清楚前，不进入标题、脚本、日历或投放建议。

DBS 内容创作诊断

i

判断一个选题或内容是否值得做、适合什么形式。

dbs_content
Skill 内容

把已经确认的选题变成“该怎么做”的诊断，不默认替用户写完整内容。

  • 前提：用户应该已有明确选题；没有就先理清方向。
  • 判断图文、短视频、长视频、直播、文章等形式匹配。
  • 检查表达效率、标题封面、内容价值和 AI 辅助边界。
  • 适合团队选题进入图文/视频执行前的质量判断。

DBS 短视频开头优化

i

诊断短视频开头，判断 Hook、可信度和素材支撑。

dbs_hook
Skill 内容
  • 核心信念：写不出好开头，常常是内容本身有问题。
  • 开头公式：话题 + Hook + 可信度。
  • 只有选题/标题、没有正文时，先停止优化并要求补正文。
  • 适合口播稿、短视频开头、完播和悬念优化。

DBS 小红书标题公式

i

从小红书标题公式库中匹配触发器并生成标题。

dbs_xhs_title
Skill 内容
  • 不是万能标题生成器，而是公式匹配器。
  • 标题必须能追溯到公式编号。
  • 公式按认知冲突、好奇缺口、恐惧损失、身份代入、数字锚定、结果承诺等心理触发器分类。
  • 适合小红书标题起名、标题优化和公式解释。

DBS AI 写作特征识别

i

识别文案的 AI 味、模板味和过度完美感。

dbs_ai_check
Skill 内容
  • 默认只识别，不改写。
  • 反对简单“去 AI 味”，重点是帮用户看清文字里的生成痕迹。
  • 核心判断：AI 味常来自过度完美、过度均匀、缺少毛边。
  • 适合文案质检、模板味诊断和表达真实性判断。

Tools：LLM 能调用什么

工具注册在 consultation-runtime/tools.ts。runtime 做 schema 校验、权限校验和状态回写；LLM 决定是否调用。

读取用户信息

i

read_merchant_profile

读类，可重复
用途

读取用户基础信息、能力项、背景摘要、表达风格和希望引导的下一步。

影响范围：只读上下文。

检索平台与用户知识库

i

retrieve_knowledge_base

读类，可多轮
参数
  • query：明确问题或关键词。
  • knowledgeDocumentIds：只能来自当前专家绑定范围。
  • topK：受 agent 和 runtime 上限约束。
  • contextPolicy：固定为 controlled_context_chunks_only。

写入：knowledgeMatches / 受控上下文。

读取历史内容

i

read_history

读类，可重复
用途

读取当前咨询会话历史和摘要，避免“刚才、上次、前面”的上下文丢失。

参数：sessionId、previousMessageCount、previousSummary。

检索对标素材

i

search_benchmark_materials

写素材缓存
用途

按关键词或博主主页检索小红书/抖音对标内容，并写入素材中心缓存。

参数：platform、findMethod、keyword/profileUrl、count、cachePolicy。

编辑策略资产

i

update_strategy_snapshot

写 strategySnapshot
写入范围

把产品定位、核心卖点、目标客群、关键场景、当前建议作为一个整体资产编辑。

轻问答、寒暄、流程追问、信息不足时不应调用。

更新内容日历

i

update_content_calendar

写日历，可再次出现
参数
  • calendar：1 到 14 条。
  • 每条包含 dayLabel、contentType、title、summary、可选 strategyTag。
  • runtime 会补 merchantId、round、stage 和稳定 ID。

写入：strategySnapshot.contentCalendarDraft，并维护 contentCalendarGeneration 修订状态。

生成图文任务草案

i

generate_article_brief

对 LLM 隐藏
边界

仅在用户明确要求图文工作台 brief 时使用。团队内容日历直接生成链路不要把它作为前置。

生成视频任务草案

i

generate_video_brief

对 LLM 隐藏
边界

仅在用户明确要求视频工作台 brief 时使用。当前团队内容生成链路是内容日历 -> 生成团队内容 -> Dify。

Runtime 控制面

runtime 不替模型做业务判断，但控制上下文、工具可用性、执行边界、事件和失败处理。

工具循环

  • nativeMaxToolTurns = 8
  • nativeMaxToolCallsPerTurn = 2
  • toolChoice 为 auto。
  • 没有 tool_calls 时直接进入最终回复。

工具可用性

  • 读类工具可重复：profile、knowledge、history。
  • update_content_calendar 不因已调用而移除。
  • 其他写类工具默认避免同轮重复。
  • hidden tools 不暴露给 LLM。

安全校验

  • 校验工具名、enabledTools、JSON arguments 和 zod schema。
  • 检索文档 ID 只能来自当前专家绑定范围。
  • 工具失败或 skipped 时，最终回复不能声称已完成。

上下文预算

  • merchant 1600 chars。
  • strategySnapshot 2600 chars。
  • strategyMarkdown 8000 chars。
  • activeSkillBodies 4200 chars。
  • knowledgeMatches 4200 chars。

营销日历到 Dify

Dify 当前只负责“单条内容生成”。系统负责批量展开、队列、限流、重试、入库和成员端展示。

用户点击生成团队内容 输入 consultationSessionId、日期、天数、成员范围、extraRequirement。 前端动作
读取运营工作区 确认 merchant、owner/member 角色、活跃团队成员和当前日历草稿。 app server
展开 daily tasks consultationCalendar 存在时，按内容日历写入或更新成员的 daily_content_tasks。 任务生成
创建 batch/jobs 每个成员、日期、calendarItem 形成一个 content_generation_job。 队列
记录日历生成标记 标记 generatedFromRevisionId、batchId、generatedAt、generatedJobCount。 防误改
content-generation-worker 常驻轮询 /api/content-generation/jobs/run-next，claim pending job。 后台 worker
Dify workflow POST /workflows/run，response_mode 可 blocking 或 streaming，默认超时 900 秒。 单条生成
回写草稿与任务 解析 final_result_json，写 content_drafts、note/video_script variants、daily task 生成结果。 成员端可见

Dify 接收到的 inputs

实际由 readDifyWorkflowInputs 输出到 workflow。

{
  "calendar_task_json": "...",
  "viral_references_json": "...",
  "image_assets_json": "...",
  "fallback_knowledge_text": "...",
  "extra_requirement": "...",
  "member_profile_json": "...",
  "account_profile_json": "..."
}

每个输入承载什么

  • calendar_task_json：日历任务、UI 可见任务、隐藏 guidance、知识引用、视频素材能力。
  • viral_references_json：知识库片段、话术、方法论、对标素材摘要。
  • image_assets_json：图文可用图片素材和预览 URL。
  • fallback_knowledge_text：项目概况、任务摘要、事实、话术、素材限制的人类可读压缩版。
  • member/account profile：成员身份、项目名、项目摘要和默认 CTA。

Dify 必须输出什么

{
  "status": "passed | needs_review | blocked",
  "article": {
    "title": "",
    "coverCopy": "",
    "images": [{ "cosPath": "", "role": "" }],
    "copyText": ""
  },
  "video": {
    "storyOutline": "",
    "estimatedDuration": "",
    "bgm": "",
    "toneOfVoice": "",
    "scenes": []
  },
  "quality": { "riskTerms": [] }
}

Job 状态

  • pending：等待 worker claim。
  • running：Dify 调用或落库中。
  • succeeded：草稿和 daily task 已回写。
  • failed_retryable：可重试失败。
  • failed_manual：配置或合同错误，需要人工处理。

输出映射

  • article -> DailyArticleContentPackageDto。
  • video.scenes -> DailyVideoScriptPackageDto。
  • 创建 content draft，生成 note 与 video_script 两个 variant。
  • daily_content_tasks 回写 article/video 的 draftId、variantId 和 succeeded 状态。

删除的历史字段

  • 不再恢复 quality.missingInputs。
  • 不再恢复 quality.blockingReasons。
  • 不再把 imageBriefIfMissing 塞回成员端质量提示。
  • 缺素材应由素材池、任务进度或运营待办处理。

video-worker 成片链路

app 只创建合同化 video_edit_jobs；worker 是稳定执行器；OpenStoryline/FireRed 是内部引擎，不上浮到 app。

从成员任务到成片

成员端 读取 Dify 生成的视频脚本，上传口播视频、项目素材或 voice_profile，确认需要 AI 剪辑。
app 门禁 脚本必须锁定；素材必须有可下载对象；组装 video_edit_jobs.input_payload。
poller video-worker 轮询并 claim video_edit_jobs，进入 preparing/running。
directive 把 input_payload 校验并标准化为 ProductionDirective。
输入素材 下载用户上传素材、素材库匹配素材、voice_profile 参考音频到本地 workspace。
OpenStoryline 调用 /v1/runs/stream，把 ProductionDirective 映射到 FireRed worker API。
FireRed 执行 load/search/split/group/script/voiceover/timeline/lip_sync/render 等节点。
结果回写 校验 final video、cover、subtitles；上传 OSS/COS；写 result_payload、log_payload 和 asset_objects。

worker 进度模块

素材准备

i

material_preparation

映射

下载 input_assets、素材库资产、voice_profile 参考音频。失败归因到 upload。

素材匹配

i

material_match

映射

OpenStoryline 的 load_media、search_media、split_shots、understand_clips、group_clips、filter_clips 等事件。

配音生成

i

voiceover

映射

generate_voiceover、tts、clone voiceover。clone 模式必须产出可测量 voiceover segments。

lip_sync

i

aliyun_videoretalk

规则
  • 只处理 talking_head_segments。
  • 音频支持 wav/mp3/aac，2s 到 120s，30MB 内。
  • 视频支持 mp4/avi/mov，2s 到 120s，300MB 内。
  • render 必须消费 retalked timeline。

字幕与时间线

i

subtitles

字幕源

默认 script_audio_alignment 不触发 ASR；只有显式 asr_original_audio 才允许 ASR 回退。

合成渲染

i

render

规则

最终必须产生 render_video artifact，并包含 final_video；可选 cover 和 subtitles。

保存成片

i

output_delivery

落点

上传 final video、cover、subtitle 到对象存储，并写入 asset_objects。

video_edit_jobs.input_payload

  • script.text：已确认脚本文本。
  • script.locked = true：脚本已锁定。
  • productionDirective：执行指令。
  • input_assets：worker 可下载对象。
  • productionConfig：voiceover、BGM、subtitles、lip_sync、render 等配置。

OpenStoryline prompt

  • 这是 unattended background worker run。
  • 平台已授权执行，不要再问确认。
  • 不要改写锁定脚本，除非 ProductionDirective 明确允许。
  • lip_sync 开启时，先 plan_timeline，再 lip_sync，再 render_video。
  • ASR 只允许显式回退模式。

失败归因

  • upload：输入素材、下载、合同校验。
  • clone_tts：克隆配音参考和 voiceover artifact。
  • lip_sync：VideoRetalk 输入、执行或 render 消费校验。
  • timeline：素材匹配、字幕、时间线。
  • render：输出文件缺失。
  • oss：上传或 asset_objects 持久化。
