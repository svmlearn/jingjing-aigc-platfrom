## 可以做了

### V2.2 与 M 同学开发成果合并后跑通全链路

- 痛点：V2.2 后台能力和 M 同学开发内容需要先合并验收，否则后续优化咨询 Agent 时不知道真实链路哪里断。
- 方案：先拿到 M 同学当前分支 / patch / 提交范围，在干净集成工作区合并；按商家端主链路跑通“咨询 Agent -> 内容日历 / 图文工作台 / 视频工作台 -> 素材引用 / 生成记录 -> 后台配置可见”的最小闭环。
- 备注：全链路跑通前，不急着大改 Agent loop 或扩充复杂 tools。

### TikHub 等热点 / 内容抓取 API 验证

- 痛点：热点抓取、单帖导入、博主内容追踪、视频素材获取都依赖外部抓取 API，不能只看服务商说明。
- 方案：基于 TikHub SDK / Dashboard 做固定样本实测，验证平台覆盖、单帖详情字段、评论、博主主页 / 全量内容、视频资源、转写或字幕能力、稳定性、成本和落库映射。
- 备注：详细验证清单见 `docs/探索/2026-04-28-热点抓取与咨询Agent优化待验证事项.md`。

### TikHub 爆款内容媒体链接转存 OSS

- 痛点：社媒爆款内容库现在会保存 TikHub 返回的 `coverUrl`、`imageUrls`、`videoUrls` 和 raw payload，但这些仍是小红书/抖音等平台 CDN 链接，可能带签名和时效。若后续页面要稳定预览，或 Agent/工作流要长期复用媒体，需要在入库时尽快转存到我们自己的 OSS。
- 已验证事实：2026-05-21 在阿里云服务器上用真实 TikHub 小红书主页返回样本测试，图片链接可下载并返回 `206 image/webp`，视频链接可下载并返回 `206 video/mp4`。说明“下载后上传 OSS”技术上可行。
- 建议方案：
  1. TikHub 内容入库后，异步或同步创建媒体转存任务。
  2. 下载 `structureSummary.imageUrls`、`structureSummary.videoUrls`、`coverUrl` 中的资源，上传到 OSS。
  3. 以 `owner_type = source_item` / `owner_id = source_item.id` 写入 `asset_objects`，并把 OSS key、原始 CDN URL、媒体类型、文件大小、mime type、下载状态写入 trace 或资产表。
  4. 页面优先展示 OSS 链接；OSS 不存在时再 fallback 到 TikHub/CDN 原链接。
- 风险/待确认：爆款视频是否只做“预览存档”，仍不进入 video worker 可剪辑素材库；下载失败、CDN 过期、403、防盗链和大文件大小上限需要有明确失败状态。

## 需要想想

### 用户输入链接后沉淀为内容资产库

- 方向：用户每输入一个链接，抓取结果都应落到数据库，逐步形成可复用的爆款内容库、竞品内容库、评论洞察库和视频素材库。
- 依赖：需要先确认抓取 API 返回字段是否足够稳定；再确认 `source_items`、`imported_comments`、`material_workbench_references`、`asset_objects` 是否需要补字段或新增标签体系。
- 待展开：如何区分“用户导入素材”“平台热点抓取”“博主追踪同步”“Agent 推荐引用”；图文 / 视频工作台如何按行业、账号、选题、互动指标检索参考内容。

### 咨询 Agent RAG 方法论知识库建设

- 方向：抓取和整理短视频拍摄博主的方法论，沉淀为咨询 Agent 可检索知识，例如选题、日常素材积累、九宫格法、脚本结构、拍摄流程、复盘方法。
- 依赖：需要确认来源清单、版权 / 摘要规则、知识切块元数据、后台知识集挂载策略。
- 待展开：哪些内容进入平台全局知识库，哪些内容进入行业知识库，哪些内容只作为内部运营参考。

### 咨询 Agent runtime / loop / tools / skills 深度优化

- 方向：在全链路跑通后，增强咨询 Agent 的选题能力、方法论 skill、上下文工程、工具调用和自循环能力。
- 依赖：V2.2 Agent 控制台、线上 Agent 绑定、Agent assets API、工作台产物读取接口、内容资产库。
- 待展开：Agent 如何读取图文 / 视频工作台已制作内容；如何把历史产物、内容日历、爆款素材、评论洞察纳入下一轮咨询；loop 要做到多强，哪些工具只能后端受控调用。

### PostgreSQL 迁移后清理 Supabase 残留与 fallback 文案

- 方向：项目当前运行环境已经迁到自建 PostgreSQL，但代码里仍残留 Supabase auth / Supabase repository fallback / `supabase-not-configured` 错误文案。后续需要统一梳理并清理，避免本地或异常环境下出现“Supabase 未配置”这种与当前架构不一致的提示。
- 依赖：先确认正式环境是否彻底不再需要 Supabase fallback；再盘点登录、当前用户、平台管理、商家资料、素材库、知识库等模块里仍依赖 Supabase 的分支。
- 待展开：哪些 Supabase 分支可以直接删除，哪些还要作为历史兼容保留；登录页和 API 错误码如何改成 `APP_DATABASE_NOT_CONFIGURED` / “PostgreSQL 登录环境未配置”等当前架构口径。
